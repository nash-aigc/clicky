# 09 · 施工顺序与验收

> 动手的顺序：**先做不改变行为的（拆提示词），再做新增能力的（sub agent 分工），
> 最后做需要时间的（高速通道）**。
> 每一步都是独立可验证的——做完一步能单独回滚，不会牵连下一步。
> 定稿 2026-09-25。

---

## 一、总原则

| 原则 | 说明 |
|---|---|
| **先拆后加** | 先把今天的胖提示词拆开（行为不变），再加新东西——否则新旧问题混在一起，出了故障分不清是谁的 |
| **一步一验** | 每步做完立刻验收（下面每步都有判据），验完再动下一步 |
| **随时可回滚** | 每一步都是独立改动，不依赖下一步 |
| **先量后调** | 需要调参的地方（sub agent 目录粗细、场景加载方式）先测再定，不靠感觉 |

## 二、五步施工

### 第 1 步 · 拆提示词（行为不变）

**做什么**：把今天 22,954 字符的提示词按 [02-主agent](02-主agent.md) §二拆成
"主 agent 部分"与"三个 sub agent 技能文件"。

| 搬到哪 | 内容 |
|---|---|
| 留在主 agent | `rules:`、`examples:`、`format:`、用户补充指令、回答长度 |
| → 图形 agent 技能 | `element pointing:`、`drawing on screen:`、`kinds:`、用户自己圈选那一节 |
| → 执行 agent 技能 | `operating the computer:`（12,096 字符） |

**改动位置**：`CompanionManager.swift:1725`（字面量拆开）、`:1862`（组装函数按需拼接）。

**验收**：
- [ ] 主 agent 提示词字符数从 22,954 降到 ≤ 6,000
- [ ] **行为回归**：问屏幕、指位置、点按钮、画圈四类各试一次，结果与拆之前一致
- [ ] 日志能打出"这一次发出去多少字符"

---

### 第 2 步 · sub agent 目录 + 分工接线

**做什么**：在主 agent 提示词里加入 [02](02-主agent.md) §三 那段目录，
并让主 agent 能用 `[AGENT:名字]` 把活派出去；三个 sub agent 各自组装自己的提示词。

**验收**：
- [ ] 说「圈一下这个按钮」→ 主 agent 派给**图形 agent**（日志可验证）
- [ ] 说「帮我点登录」→ 派给**执行 agent**
- [ ] 说「写一篇关于 X 的文章」→ 派给**文本 agent**
- [ ] 说「屏幕上这句话什么意思」→ **主 agent 自己答**（不派活）
- [ ] 派错时（说不清的需求）→ 落回主 agent 自己答，**不是**乱派

**这一步要看的数据**：派对的次数 / 总数。**低于 90% 就先调目录粗细**（[02](02-主agent.md) §三 那条实测算在这里）。

---

### 第 3 步 · 权限分级落地

**做什么**：按 [06-权限模型](06-权限模型.md) 实施逐路径白名单（读/写分开），
再给三个 sub agent 各自套上不同的权限面。

**前置**：这一步依赖 [细节/02-文件访问授权.md](细节/02-文件访问授权.md) 的实现——**它是前置依赖**，
没做完之前，第 2 步只能做到"派活"，做不到"权限不同"。

**验收**：[06](06-权限模型.md) §六 的 P1–P7 全部通过，重点是：
- [ ] 文本 agent 写文件 → 被拒
- [ ] 图形 agent 写非图形文件 → 被拒
- [ ] 四条逃逸防线各构造一次，全部被拒

---

### 第 4 步 · 回传与通知接线

**做什么**：三个 sub agent 的结果走既有的数据块通道回主循环；
完成后在鼠标旁给一个对号 + 一句主 agent 生成的摘要，停 2–3 秒。

**验收**（[07](07-回传与通知.md)）：
- [ ] 多步任务完成后：鼠标旁出现对号 + "任务完成 · 关于…"，2–3 秒后消失
- [ ] 摘要文字是**按任务内容生成的**，不是固定文案（用一次 400 字任务验证）
- [ ] 失败时明确告知"这件事我没做成"
- [ ] 全程不出现"死循环"（三级兜底走完就停）

---

### 第 5 步 · 高速通道（最后做，因为它需要时间积累数据）

**做什么**：按 [08-复盘与高速通道](08-复盘与高速通道.md) 实现复盘的统计表与晋级，
以及提示词里那条 ≤20 行的路段。

**为什么最后做**：
1. 它依赖前四步（没有标准通道，就没有"落回"的地方）
2. 它需要**真实使用数据**才有意义——今天的历史里还没有统计基础
3. 它是最容易过度设计的一步，**先让它跑在纸上**（人工看统计表），确认判断对了再自动化

**验收**：[08](08-复盘与高速通道.md) §七 的 H1–H10。最小起步：
- [ ] 能生成两级统计表（人工看一眼，判断归类对不对）
- [ ] 一条高频需求走完"统计 → 候选 → 批准 → 写进提示词 → 命中直通"全链
- [ ] 超预算淘汰 + 60 天撤出 + 撤出后能重新晋级（三条防退化）

## 三、两件必须先做实测再定的事

| # | 待测 | 怎么测 | 测完决定什么 |
|---|---|---|---|
| E1 | **sub agent 目录写多细** | 用 20 条真实需求，看主 agent 派得对不对 | 目录的粒度（太粗选错、太细又长胖） |
| E2 | **文本 agent 的场景技能按需加载 vs 全量注入** | 同一批写作需求，两种做法各跑一遍，看质量与字符数 | 场景技能要不要拆、拆多细 |
| E3 | （可选）**主 agent 提示词长度对回答质量的影响** | 拆前/拆后各 10 个问题，人工比对 | 确认"拆"没有副作用 |
| E4 | （可选）**通知打扰度** | 2 秒 vs 3 秒，语音 vs 纯文字 | 用户的主观感受，只能自己看 |

## 四、施工完成的总验收

| # | 判据 |
|---|---|
| 总 1 | 主 agent 提示词里**看不到**任何坐标、动作、脚本细节（只有四样槽） |
| 总 2 | 三个 sub agent 的权限确实不同（文本写不了盘、图形碰不了别的文件） |
| 总 3 | 多步任务能跑完并把结果总结给用户，用户看得到对号 |
| 总 4 | 做不成的任务会一路升级到用户，**不会静默失败、不会死循环** |
| 总 5 | 高速通道只影响快慢：把它关掉，所有功能仍然正常（只是慢） |
| 总 6 | 仓库里 grep 不到任何密钥 |
| 总 7 | 每一处"设计已定尚未实施"的项，实施后回填一份验收记录 |
