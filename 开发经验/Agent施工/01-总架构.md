# 01 · 总架构

> 一条主线：**一个主 agent，三个各有权限的 sub agent，一个外援**。
> 两条通道：**标准通道**（完备，谁都走得了）与**高速通道**（快，只覆盖几个高频场景）。
> 定稿 2026-09-25。

---

## 一、为什么是这个形状

用户的设计原则（原话摘要）：

> 整个架构设计成一个**大的主 agent + 很多 sub agent**。主 agent 的提示词非常少——
> 屏幕、用户的话、历史对话、再加上「什么时候调用哪一个 sub agent」的一段描述。
> 大量"坐标怎么定位"这类东西**全部移走，但不是删掉**——放进 sub agent 自带的技能里。
>
> 先有一个**非常标准、正确的 agent 循环**，然后在它旁边加一条**并发/旁路**，专门处理更高频的问题。
> **不要把高频需求混进 agent 的分类里研究**——那样逻辑就错了，因为永远分不开。
>
> 整个循环可能比脚本慢，**但逻辑简单、容易理解——牺牲性能换简单性**。

## 二、两条通道

| | **标准通道** | **高速通道** |
|---|---|---|
| 是什么 | 主 agent → 判定 → 交给某个 sub agent → 执行 → 结果回主循环 | 提示词里的一行入口，命中即执行，**不进循环** |
| 覆盖 | **一切需求**（它是完备的） | 只覆盖几个高频场景 |
| 谁建 | 人（设计时写好） | **复盘 agent 从真实使用里统计出来**（[08](08-复盘与高速通道.md)） |
| 代价 | 慢一点（多一次模型判断 + 可能的循环） | 快、省 |
| 上限 | 无 | **20 行 / 约 800 字符**，超了按频率淘汰 |
| 兜底 | Claude Code → 通知用户 | 没命中或执行失败 → **落回标准通道** |

**唯一的铁律**：高速通道**只影响快慢，不影响对错**。它命不中、或者它挂了，标准通道必须能把同一件事做成。

## 三、主 agent

| 项 | 内容 |
|---|---|
| 它是谁 | 视觉模型（🧠 角色；百炼 `qwen3-vl-plus` 或 DeepSeek `deepseek-flash`——**同一个槽，换个服务商而已**） |
| 提示词 | **只有四样**：屏幕截图 · 用户的话 · 历史对话 · sub agent 目录（[02](02-主agent.md)） |
| 它决定什么 | 这件事归哪个 sub agent；或者自己直接回答；或者走高速通道 |
| 它的外环 | 每执行一步 → 新截图 → 结果回填 → 它判断是否完成（上限 15 步） |

**长期记忆已经存在**，不需要重新设计：对话历史就是记忆。会话列表与压缩摘要在
`ConversationSessionsStore`（对话窗口里用户能看到全部历史）。

## 四、三个 sub agent

| | **图形 agent** | **执行 agent** | **文本 agent** |
|---|---|---|---|
| 干什么 | 指位、圈/框/箭头、生成图形与图解 | 点击、打字、按键、开 App、调音量亮度、读写文件、跑脚本、调 MCP | 生成内容：问答、翻译、写作、讲解、总结；多场景方法论 |
| 工具 | 自己的工具链（几何编译器 + 模型） | **最多**（`MacosUseSDK` + 工具库 + MCP） | **零工具** |
| 文件权限 | **只碰图形相关文件** | 按授权路径（**建议第一期不给全盘**，见 [06](06-权限模型.md)） | **只读，不写** |
| 技能里放什么 | 怎么算坐标、怎么排版、怎么逐笔呈现 | 动作怎么写、什么动作能批量、各脚本怎么用 | 销售/营销/财务/法律/商务/建筑…各场景怎么写 |
| 兜底 | 画不出来 → 退化成一句文字说明 | **Claude Code**（10 轮未完成 → 升级） | 无（它自己就是生成者） |
| 结果 | 回主循环 | 回主循环 | 回主循环 |

三份说明：[03](03-图形agent.md) · [04](04-执行agent.md) · [05](05-文本agent.md)。
**权限分级是这个设计的核心特征**——它同时是安全边界和提示词瘦身的手段（[06](06-权限模型.md)）。

## 五、一次请求的完整走法

```
用户说话 / 打字
   │
   ├─ 转写（流式 ASR）
   │
   ▼
① 高速通道查询（本地，快）
   ├─ 命中 → 直接执行 → 一句收据 → 结束（不进循环）
   └─ 未命中 ↓
② 主 agent 一次调用：截图 + 用户的话 + 历史 + sub agent 目录
   ├─ 它自己答（低风险、纯问答）→ 说完就结束
   ├─ 它点名某个 sub agent → ③
   └─ 它输出动作标签 → ③（走执行 agent 的能力）
③ 执行 / 产出
   ├─ 一步做完 → 结果回主循环
   └─ 需要多步 → 一步一动作 → 新截图 → 回填 → 主 agent 再判断（≤15 步）
④ 结果回主循环 → 主 agent 总结 → 播报 + 鼠标旁给一个对号（2–3 秒）
⑤ 做不成：10 轮 → Claude Code → 再 10 轮 → 通知用户「做不到，请接管」
```

## 六、兜底链（三级，一环扣一环）

| 级别 | 谁 | 触发条件 | 结果去哪 |
|---|---|---|---|
| 1 | sub agent 自己重试 | 执行失败但可补救 | 继续循环（≤15 步） |
| 2 | **Claude Code** | 循环 10 轮未完成 | 面板切到 Agent 页，全程可见；完成后语音播报 |
| 3 | **通知用户** | Claude Code 也 10 轮未完成 | 明确告诉用户"这件事我没做成"，**不许死循环**（[07](07-回传与通知.md)） |

## 七、与旧架构的关系（一句话）

旧文档里那套"五出口 / 四类分流 / 薄层选类"的说法**全部作废**——它们描述的是"主 agent 不自己判断、
由外面一层代码或模型替它分类"的做法。本架构相反：**判断在主 agent 自己手里**，sub agent 是它的工具。
