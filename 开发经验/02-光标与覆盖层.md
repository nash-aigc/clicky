# 02 · 光标与覆盖层

蓝色光标是这个 App 最有辨识度的东西，也是**改动风险最高**的一块——它同时牵扯坐标换算、多显示器、动画、开机引导和「什么时候该出现」。

涉及的文件：`OverlayWindow.swift`（1064 行，全部渲染逻辑）、`CompanionManager.swift`（谁在什么时候让它出现）。

---

## 一、它到底是什么

不是系统光标，也不是 `NSCursor`。是**一块覆盖全屏的透明 `NSPanel`，里面用 SwiftUI 画了一个蓝色的东西**。

每个屏幕一个窗口（`OverlayWindow(screen:)`），窗口的属性是关键：

| 属性 | 值 | 为什么 |
|---|---|---|
| `isOpaque` | `false` | 要能看见底下的桌面 |
| `backgroundColor` | `.clear` | 同上 |
| `ignoresMouseEvents` | `true` | **绝对不能抢鼠标事件**，否则用户的点击全被吃掉 |
| `level` | 高 | 要浮在所有窗口上面 |
| `collectionBehavior` | 跨 Space | 切桌面时它也得在 |
| 是否能成为 key window | 否 | 不能抢焦点 |

截图时这些窗口**按 bundle id 排除**，所以模型看到的屏幕里不会出现光标自己。

## 二、坐标换算链（最容易出错的地方）

从模型的回答到屏幕上那个点，一共要走四步：

```
模型输出 [POINT:860,50:label]
        ↓  ① 归一化 → 截图像素
截图像素 (x/1000 × 图宽, y/1000 × 图高)
        ↓  ② 截图像素 → 屏幕点（除以 Retina 缩放比）
屏幕点
        ↓  ③ 屏幕点 → SwiftUI 坐标（AppKit 左下原点 → SwiftUI 左上原点）
SwiftUI 坐标
        ↓  ④ 找到属于哪个屏幕（:screenN），在那个屏幕的 overlay 上画
```

**第 ① 步是唯一容易漏的**，而且漏了**不会报错**。

Qwen 的视觉模型在内部会把图**缩放**之后再去看，所以它吐出来的 `[POINT:x,y]` 是 **0–1000 的归一化网格**，不是截图像素。`CompanionManager.screenshotPixelCoordinate(fromNormalizedPoint:...)` 做的就是这件事：

```swift
x: normalizedPoint.x / 1000.0 * CGFloat(screenshotWidthInPixels)
y: normalizedPoint.y / 1000.0 * CGFloat(screenshotHeightInPixels)
```

为什么会静默失败：**一个归一化值和一个合理的像素值长得一模一样**。`860` 当像素用也是合法的，光标就是落得偏一点，你不会觉得是 bug，只会觉得「不太准」。

**第 ③ 步**在 `convertScreenPointToSwiftUICoordinates`，注意 `y` 是 `(screenFrame.origin.y + screenFrame.height) - screenPoint.y`——屏幕原点在左下，SwiftUI 原点在左上。

**第 ④ 步**：模型会给 `:screenN` 后缀（N 是截图时给每张图的编号标签）。**没有这个后缀，光标就会指到错误的屏幕上去**。所以系统提示词里专门强调了一句：

> if the element is on a DIFFERENT screen, append `:screenN` … this is important — without the screen number, the cursor will point at the wrong place.

## 三、指路动画

`buddyNavigationMode` 有三个状态：

| 状态 | 行为 |
|---|---|
| `.followingCursor` | 跟着鼠标跑（每 16 ms 一次定时器） |
| `.navigatingToTarget` | 沿贝塞尔弧线飞向目标点 |
| （回程） | 飞回鼠标旁边 |

两个细节值得记：

**飞行途中的鼠标移动不会打断。** `startTrackingCursor` 里，只有**回程**时才允许鼠标移动取消动画，而且要求移动距离超过 100 点：

```swift
if self.buddyNavigationMode == .navigatingToTarget && self.isReturningToCursor {
    ...
    if distanceFromNavigationStart > 100 {
        cancelNavigationAndResumeFollowing()
    }
    return
}
```

去程时直接 `if self.buddyNavigationMode != .followingCursor { return }` 跳过跟踪。这是有意的——用户问「那个按钮在哪」，光标飞到一半被自己手抖打断，体验很差。

**指路的落点不是鼠标位置。** `startNavigatingToElement` 落点是元素坐标 `+8 / +12`，这是「停在元素旁边」的语义，**和「跟着鼠标」是两回事**。改跟随距离时不要顺手把这俩一起改了。

## 四、显示方式三档（第 5 波新增）

### 为什么以前关不掉

查清之后发现是个「三重叠加」的死结：

1. `CompanionManager.isClickyCursorEnabled` 是唯一的开关，存在 UserDefaults，**默认 `true`**；
2. 它唯一的 UI 在 `CompanionPanelView.swift:64-71`，而**那一段被注释掉了**；
3. `scheduleTransientHideIfNeeded()` 的第一行是 `guard !isClickyCursorEnabled && isOverlayVisible else { return }`。

第 1 和第 2 条让开关永远是 `true`，第 3 条让那段「按快捷键淡入、用完淡出」的调度**一次都不会跑**。设置页里那个「光标闲置后自动隐藏」滑块，描述里写「关闭『显示光标』时……」，而那个控件在界面上不存在。

**教训：一个能保存但什么都不做的设置，比没有这个设置更糟。** 项目里后来的规矩是——一个设置要么接到真实行为上，要么不要出现在界面上。

### 现在的做法：窗口常驻，只控制「画不画」

**没有**走「窗口显示/隐藏」那条路。原因是 `OverlayWindowManager.showOverlay` 每次隐藏之后再显示，都是**把 N 个全屏 `NSHostingView` 拆掉重建**：

- 会闪；
- `cursorPosition` 只在 `onAppear` 里初始化，重建会丢；
- 开机引导的视频播放器会被拆了重装。

所以改成：**窗口在 `hasCompletedOnboarding && allPermissionsGranted` 时建一次，之后一直在**；用一个 `@Published var isBuddyShown: Bool` 控制「画出来的东西可不可见」。

`OverlayWindow` 里三处 opacity 都乘上 `buddyPresenceFactor`（三角 / 波形 / 转圈），并挂一个 0.25 s 的淡入淡出：

```swift
.animation(.easeInOut(duration: 0.25), value: companionManager.isBuddyShown)
```

**动画刻意只绑定 `isBuddyShown` 一个值**，不绑导航模式。因为「只在指位置时出现」这一档要求光标在**飞行开始的那一刻**就出现，如果动画还盯着别的值，光标会在弧线飞到一半时才淡入，起点看着是错的。

### 三档的差别

| 档位 | buddy（三角 / 波形 / 转圈） | 回答文字气泡 |
|---|---|---|
| 一直显示 | 一直可见 | 照常 |
| 只在对话时出现 | 按快捷键淡入；朗读 + 指路 + 气泡 + 闲置延时都结束后淡出 | 照常 |
| 只在指位置时出现 | 同上，**外加**：跟随时不画 | 照常，仍显示在鼠标旁 |

第三档的文字气泡**是刻意保留的**：气泡的定位读的是 `cursorPosition`（即使 buddy 不可见它仍然在追鼠标），所以「没有光标但文字还在」是免费的。

### 两条不能误伤的路径

**波形和转圈不看「指位置时」那一档。** 如果把它们也按同一个条件藏起来，用户在**录音时看不到任何反馈**——不知道麦克风开没开。所以拆成两个条件：三角用 `buddyIdleAppearanceIsAllowed`，波形/转圈不用。

**开机引导强制可见。** 欢迎动画、引导视频、引导提示气泡本身不受三角 opacity 影响，但三角消失会让它们看着很怪。所以未完成引导、或 `showWelcome` / `showOnboardingVideo` / `showOnboardingPrompt` 任一为真时，系数强制为 `1`。

顺带确认过：引导演示的那次飞行发生在第 40 秒，而那时 `showOnboardingVideo` 还是 `true`（它在第 90 秒之后才变 false），而且引导视频期间按住说话是禁用的——所以没有任何按键能把 `isBuddyShown` 设成 `false`。这条路径是安全的。

### 面板状态行必须跟着改

`CompanionPanelView` 原来读 `isOverlayVisible` 判断「当前是 Ready 还是 Active」。**窗口一常驻，这个值恒为 `true`，面板就会永远显示成正在工作。** 改成读 `isBuddyShown` 之后语义正好对得上。

`isOverlayVisible` 保留原意（「窗口建好了没有」），只给 `CompanionManager` 自己用。

## 五、形状

`Triangle` 是改造前原有的。第 5 波新增 `ArrowCursorShape`，外形是 macOS 标准指针。

**关键约束：path 的尖端点画在 `rect` 的中心。**

```swift
let tip = CGPoint(x: rect.midX, y: rect.midY)
```

身体从中心向右下展开。这样两种形状「那个点」都在 frame 中心，`.position(cursorPosition)` 对两者语义一致，**不需要额外的锚点修正**。

如果改成「path 从 rect 左上角开始画」，箭头尖端就会落在鼠标的左上角，看起来永远偏一截。

尺寸：三角 16×16，箭头 20×20（箭头要更宽才画得下尾巴）。

**选标签的约束**：这一行的选项是并排的分段按钮，标签超过 4 个字会换行，然后撑破卡片。所以 `displayName` 是「三角箭头 / 标准指针」，含义交给行的描述文字去讲。

## 六、跟随距离

改造前把偏移写死在 **4 个地方**，一处都不能漏：

| 位置 | 作用 |
|---|---|
| `OverlayWindow.swift:134` | `init` 里 `_cursorPosition` 的初值 |
| `OverlayWindow.swift:413` | `onAppear` 里的初始定位 |
| `OverlayWindow.swift:504-505` | `startTrackingCursor` 里每帧的跟随 |
| `OverlayWindow.swift:703` | `startFlyingBackToCursor` 回程的落点 |

四个地方原来都是 `+35 / +25`。现在统一读 `companionManager.cursorFollowDistance.offsetFromMouse`：

| 选项 | 偏移 | 感觉 |
|---|---|---|
| 重叠 | (0, 0) | 完全压在鼠标上 |
| 紧贴 | (6, 6) | 只让开一点点 |
| 稍远 | (35, 25) | 改造前的行为 |

**漏掉第 4 处（回程落点）的后果**：指路之后光标飞回来，会停在旧的位置上，然后又突然跳到新的位置。

默认值选「稍远」是**故意的**：老用户升级之后看到的完全是原来的样子，不会有「怎么变了」的意外。

---

## 七、怎么验证这一块（不碰 TCC 的办法）

这一块的改动几乎全是视觉的，而**跑起来看**意味着要一遍遍重启 App、还要动 TCC 权限。用离屏渲染探针快得多，见 [`03-设置与配置.md`](03-设置与配置.md)。

但**光标本身的行为只能靠人眼看**——三档的淡入淡出时机、箭头尖对不对得准鼠标，没有别的办法。这一部分必须让用户在 Xcode 里 Run 之后手动过一遍。
