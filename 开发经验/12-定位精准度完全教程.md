# 十二、定位精准度完全教程（2026-09-22）

> 用户原话：「工作定位的准确性超过一切。」「这两个问题如果不修复，这两个功能都没有任何意义。」
>
> 这一篇是整个项目里最贵的经验：**定位精度曾经全面失效过一轮**——圈 2 答成 3 或 4、画圈稳定偏右——然后靠逐环节实测修回来的。这一篇把三条定位链路（光标、画圈、你圈我问）从头讲到尾：架构、方案、代码、每一个为什么、每一处实测数字、以及失败是怎么发生又怎么被抓住的。动这三条链路之前，先读完这一篇。

---

## 〇、一句话总纲

**这个项目的精度从来不靠坐标换算，靠的是「真数据优先，估算兜底」。**

视觉模型看截图估的坐标，实测误差可达 **±25% 屏宽，且方向随机**（2026-09-22 测，三次问同一句话得到三个不同方向偏移的答案）。任何一条「把模型估的坐标直接用」的路径都是不准的。三条链路全部遵循同一个模式：

```
模型给的 (坐标, 名字)
        │
        ▼
① 用「名字」去辅助功能树里查真实元素框        ← 精度的来源，命中即像素级准确
        │  查不到时
        ▼
② 用「坐标」做命中测试，吸附到落点上的小控件   ← 次级兜底，估算点大致对就能救回来
        │  也不行时
        ▼
③ 用模型裸估的坐标                            ← 最后的兜底，误差 ±25%，不能更好了
```

**凡是跳过 ①② 直接到 ③ 的路径，都是这次出过事故的路径。** 下面三条链路，全是这个模式在不同场景下的展开。

## 一、先懂坐标系：三个空间，一张换算表

这是整个定位体系的地基，也是历史上静默出错最多的一层（见 `10-踩过的坑.md` H3、第二节）。

| 空间 | 原点 | y 方向 | 谁在用 |
|---|---|---|---|
| **0–1000 归一化网格** | 截图左上角 | 向下 | 模型（`[POINT:]` `[CLICK:]` `[SHAPE:]` 全是它） |
| **Quartz 全局** | 主显示器左上角 | 向下 | AX 元素框、`CGEvent`（点击、滚动） |
| **AppKit 全局** | 主显示器**左下**角 | 向上 | `NSEvent`、`NSScreen.frame`（鼠标监听、光标覆盖层） |

关键事实：

1. **模型为什么说归一化网格**：Qwen 的视觉模型看图前会在内部缩放图片，所以它报的坐标天然落在 1000×1000 的网格上，而不是截图像素。把归一化值当像素用，不报错，光标就是「落短一截」——归一化值和像素值在这个量级上是无法区分的。
2. **AX 元素框和 CGEvent 用的是同一个空间**（Quartz 全局）。所以从辅助功能树查到的元素框，**中心点可以直接拿去点击，零换算**——这是「查名命中即像素级准确」能成立的原因。
3. **换算函数只有一处，谁也不许自己写第二份**：

| 换算 | 函数 | 说明 |
|---|---|---|
| 归一化 → 显示器局部（y 向下） | `MacosUseController.displayLocalPoint(fromNormalizedPoint:in:)` | 全项目唯一的归一化出口；`in:` 是那张截图（带 `displayID`） |
| 显示器局部 → Quartz 全局 | `MacosUseController.quartzGlobalPoint(fromNormalizedPoint:in:)` | 加 `CGDisplayBounds(displayID).origin` |
| 归一化 → AppKit 光标覆盖层 | 沿用旧路径：`appKitY = displayHeight − y` | 光标飞行用 AppKit 空间，与上面两条**并存不合并** |
| AppKit 全局 → 显示器局部（y 向下） | `localX = gx − frame.origin.x; localY = frame.height − (gy − frame.origin.y)` | 你圈我问的鼠标捕获用（`CircleToAskController.displayLocalPoints`） |

4. **每张截图都带 `displayID`**（`CompanionScreenCapture`）。多显示器下，Quartz 原点只能从 `CGDisplayBounds(displayID)` 拿——**用主屏高度去推 Quartz 原点，单屏碰巧对，其他每一块屏都静默错**。
5. **显示器局部 y 向下坐标 == SwiftUI 标注窗口的绘制坐标**（`NSHostingView` 内容），所以画圈路径换算一次就能直接画，不存在第二次会写反的映射。

> **改这里的铁律**：任何新换算都要写探针做**往返验证**（去程 + 回程必须回到原位），不能靠肉眼看效果。历史上最贵的 bug 全在这一层，而且全部静默。

## 二、光标定位怎么做到精准（`[POINT:]` 与 `[CLICK:]` 共用一套）

### 2.1 链路（`MacosUseController.resolvedClickPoint`，`MacosUseController.swift:721`）

光标飞行（指路）和真实点击**走同一个解析函数**——`resolvedPointerLocation`（`:791`）和 `execute(.clickText…)`（`:358`）都调它。这是刻意设计：**「指」和「点」若是两套逻辑，必然出现「指得准、点得偏」的分裂**，这个分裂在指路接入同一解析前真实存在过（同一条回复，点击落点 5/5 正确，光标却飞到 277pt 之外）。

```
模型标签 [CLICK:572,668:7]
   │
   ├─ ① screenCapture(for:among:)     确定在哪块屏（1-based screenN，否则光标所在屏）
   ├─ ② quartzGlobalPoint             估算点 → Quartz 全局
   ├─ ③ accessibilityElementFrame(    名字查找：
   │      matchingLabel:"7",            · 只查【前台应用】的树（名字只在知道是谁的名字时才有意义）
   │      nearestTo:估算点)             · 排序三键：名字完全相等 → 控件尺寸(≤400×120) → 离估算点最近
   │                                   · 命中 ⇒ 直接用元素真框中心，估算点**不再参与**
   ├─ ④ accessibilityElementFrame(    名字查不到 ⇒ 系统级命中测试（AXUIElementCopyElementAtPosition）
   │      near:估算点)                  落点是【小控件】(≤400×120) ⇒ 用它的中心；落点是窗口/容器 ⇒ 不吸附
   └─ ⑤ 都失败 ⇒ 用估算点              兜底，误差 ±25%
```

### 2.2 排序规则为什么是这三键（缺一不可）

- **名字完全相等优先**：叫「7」的按键，赢过只是文字里提到 7 的东西。
- **控件尺寸优先（≤400×120，`maximumSnappableElementWidth/Height`）**：命中测试和文字匹配都可能落到窗口、滚动区这种容器上——**窗口的中心不是任何人要点的**。实测曾把估算点吸到一个 1201×1436 的 `AXGroup` 上，点击落在按键旁边。
- **离估算点最近**：前两键打平时的裁决。注意它**只在打平时说话**——名字命中后估算点不参与定位，这是整条链最重要的一条：估算 ±25% 的误差不能污染已经查到的真框。

### 2.3 label 是承重墙

`[CLICK:x,y:发送]` 里的「发送」不是装饰——**名字查找完全靠它**。系统提示词要求模型**抄元素原文**（含标点），因为匹配是「包含」语义，不是语义匹配：「那个发送按钮」匹配不到任何东西。实测：写「7」解析到按键真框 `(964,722,48,48)`，到像素级精确，计算器读出 7。

### 2.4 实测数字（2026-09-22，计算器「7」键，真值 Quartz (988,746)）

| 路径 | 结果 |
|---|---|
| 模型裸估坐标（三问同一点） | (320,599)、(700,700)、(766,625) —— 误差 ±25% 屏宽，**方向相反** |
| AX 名字查找 | (964,722,48,48) —— 按键真框，**误差 0.0** |
| 修复后实际点击 | 5/5 落在键上，计算器读出 7 |
| 修复后光标飞行落点 | 4/4 落在 (988,371)（AppKit 空间同一按键），误差 0.0 |

### 2.5 工程细节

- AX 遍历是**同步跨进程 IPC**（实测 0.14–0.6 秒），全部走 `Task.detached`，绝不占主线程——光标动画正在飞。
- 每次解析都**现场遍历树**而不是缓存：界面随时在变，缓存就是过期数据。
- 只查**前台应用**：对一个用户根本没在看的窗口做名字匹配，就是在错误的 App 里点东西。

## 三、画圈定位怎么做到精准（`[SHAPE:circle/polygon]`）

### 3.1 画圈与点击的关系：借它的链，不进它的循环

`[SHAPE:]` 解析进 `ActionParseResult.shapeRequests`，**故意不进 `actions`**——圈碰不到任何东西，不该消耗一步一动作的循环节奏。但它**借用了点击的整套瞄准逻辑**：

```
[SHAPE:circle:x,y;x2,y2:发送]
   │
   ├─ anchor = 形状第一个点 → screenCapture(for:among:)   定屏幕；查不到这块屏 ⇒ 丢弃（丢比猜强）
   ├─ circle/polygon ⇒ MacosUseController.annotationEnclosingFrame(forLabel:estimate:)  ← 三级链（见 3.2）
   │     命中 ⇒ Quartz 真框 − CGDisplayBounds(displayID).origin = 显示器局部框
   │            加边距 (inset -8,-6)，circle 生成「圆心 + 圆上一点」（radius = max(w,h)/2），polygon 生成四角
   ├─ arrow/line/curve ⇒ 永远用模型给的点（见 3.3）
   └─ 交给 ScreenAnnotationManager 画（每屏一个透明窗口，描画动画 0.7s，10s 自动消失）
```

### 3.2 三级解析链（`MacosUseController.annotationEnclosingFrame`，这次修复的核心）

```swift
annotationEnclosingFrame(forLabel: elementLabel?, estimate: quartzEstimate) -> CGRect?
   ① accessibilityElementFrame(matchingLabel:)   名字查找（与点击同一函数，同一排序）
   ② accessibilityElementFrame(near:)            名字查不到 ⇒ 命中测试，小控件才吸附
   ③ 都失败 ⇒ nil（调用方用模型裸点画）
```

**这三级链是修出来的，不是设计出来的。** 最初版本只做了 ①：名字查不到就直接用裸点——等于点击路径里现成的 ② 兜底都没用上。用户实测「在数字 5 上画圈」**稳定偏右**，诊断后补上了 ②，并把 ① 升级成带词元重试的版本（见 3.4）。

### 3.3 为什么 arrow/line/curve 永不吸附

方向性笔画的两端各代表一个意思（「从这里到那里」）。把端点吸附到某个元素框上，等于**替模型改口**。这条界线要守住：不能因为查得到就到处查。圈和框不同——「圈住这个东西」的目标是唯一的、有名字的，吸附才是忠于模型的意思。

### 3.4 ASCII 词元重试：中文修饰标签的救生索（`MacosUseController.swift` 名字查找内）

**实测（2026-09-22，计算器）**：

| 标签 | 结果 |
|---|---|
| `"5"` | 按键真框 `(1018,776,48,48)`，**误差 0.0** |
| `"数字5"` | **零候选** → 走裸点 → 偏移（用户看到的故障） |
| `"数字5"` + 词元重试 | 词元 `"5"` → 按键真框，**误差 0.0** |

根因：模型会把用户的「在数字 5 的位置」回写成 `[SHAPE:…:数字 5]`，而界面元素叫「5」。修法：全标签查不到时，把标签按「非 ASCII 字母数字」切开（「数字 5」→ `["5"]`），取最长的词元重试，最多 3 个。

**安全边界**：纯中文标签（如「发送」）切不出 ASCII 词元，**不触发重试**——所以中文命名的元素永远不会被这条逻辑误配。它只在「本来一个候选都没有」时才介入，任何行为变化都严格是「原来返回 nil，现在可能返回一个真候选」。

### 3.5 圈住不等于点中：标注与点击的三条刻意差异

| 差异 | 原因 |
|---|---|
| 开关用 `pointsAtReferencedElements`（与指路共用） | 两者都是「在屏幕上告诉你我看的是什么」，关掉指路的人也不想看绿圈 |
| 丢弃时不询问 | 与 `[POINT:]` 同一先例 |
| 上限 4 个（`maximumAnnotationShapesPerReply`） | 提示词要求最多 2 个；代码兜底防失控回复刷屏 |

### 3.6 模型永远看不见自己的画

模型画的标注在**每次截图前清空**（还有打断时、新按键时）——否则模型会在下一张截图里看到自己画的绿圈，然后去描述它、重画它。**唯一例外见下一节。**

## 四、你圈我怎么做到精准（用户按住快捷键亲手画圈）

这是三条链路里**信息质量最高**的一条——圈是人画的，起点就是像素级准确的——也是这次栽得最狠的一条。分四层讲。

### 4.1 捕获层（`CircleToAskController.swift`，全部职责边界在这）

- **监听**：global + local `NSEvent` 鼠标监视器，只在录音期间装。**鼠标监听不走 TCC**（和键盘监听不一样），零新权限。
- **成圈条件**：拖动 ≥ 24pt（比这短的是点击不是圈）。
- **实时反馈**：拖动中的绿线 lasso 用 AppKit `NSView` 画（每秒几十个 dragged 事件，不需要 SwiftUI diffing）——样式与模型画的标注同款发光绿。
- **松手**：① 笔画交给 `ScreenAnnotationManager` 当普通 curve 标注显示（白得一套清屏纪律）；② 包围区加 12pt 边距，存成 `pendingMarkedRegion`（屏号、displayID、显示器局部框、归一化框）。

### 4.2 管线层（`CompanionManager.buildMarkedRegionContextIfPending`）

应答管线第一步消费区域，拼成三段数据，走 `[AX_TREE]` 同一条 `<screen_contents>`「数据不是指令」通道：

1. **区域本身**：归一化矩形 + 一句话「圈是问题的主语」。
2. **圈内 AX 元素清单**（`accessibilityElementsInRegion`）：完全在圈内的排最前（小到大），只擦到边缘的排后面；每行带角色、原文、归一化中心点、containment 标注；上限 12 个。
3. **系统提示词**「the user's own circle」一节：圈就是问题主语；「帮我把这个关掉」的「这个」指圈住的东西；回答和点击优先用清单里的精确字符串和坐标。

### 4.3 这次事故的两个根因（「圈 2 答 3 或 4」）

**根因一：截图前清标注的纪律误伤了用户的圈。**

管线的 `screenAnnotationManager.clear()` 原本在**每一步截图前无差别执行**——这是为「模型不能看见自己画的」设计的纪律。但用户画的圈**性质相反：它就是给模型看的**。清掉它，模型只剩文字描述可猜，这是「圈 2 答 3 或 4」的最大单一根因。

修法（`CompanionManager` 管线 step 1）：

```swift
if stepCount == 1, circleToAskController.pendingMarkedRegion != nil {
    // 用户的圈必须活着进这张截图 —— 它是模型判别「圈的是哪个」的最强信号
} else {
    screenAnnotationManager.clear()
}
// 截图完成后立刻补清：模型已经看过，后续步骤的截图依旧干净
```

**教训（通用）**：同一条「清屏纪律」服务两个目的——「不给模型看模型的痕迹」和「给模型看用户的痕迹」。**目的相反的两种标注，不能共用同一条无条件清理**。新的标注来源接入时，先问它属于哪一类。

**根因二：圈内元素清单没有判别力。**

实测（2026-09-22，计算器数字区）：按键 48×48、**间距只有 6pt**，12pt 内边距让区域碰到全部 9 个邻居，**10 个元素面积完全相同**——「按面积从小到大排」这种排序在等面积网格里等于随机。修法：**containment 分类**——完全在圈内的排最前、每行标注。实测圈住「2」时，完全在圈内的**只有「2」一个**。判别力从零变成唯一。

**教训（通用）**：给模型排序时要问「这批候选在我的场景里会不会全部同权」。等面积的网格、等宽的列表行，面积排序一概失效；**几何关系（在不在圈里）比大小关系硬**。

### 4.4 生命周期（每一处都有事故背景）

| 时机 | 动作 | 为什么 |
|---|---|---|
| 录音开始（`beginCaptureIfEnabled`） | **不清** pending 区域 | 确认模式下，发送已存问题的那一下**快按会先开启录音**——在这里清，圈先于问题死掉 |
| 新按键（press 路径） | 只在 `pendingConfirmationTranscript == nil` 时丢弃 | 同上：这一按可能是发送 tap |
| 打断（`interruptActiveResponse`） | 丢弃 | 被停掉的问题，圈没有下一问可搭 |
| 设置开关「圈选提问」（`allowsCircleToAsk`） | **管线时**才查，查完丢弃 | 开关不影响已开始的录音；关掉=丢弃而非冻结 |

### 4.5 完整时序（一遍走通的样子）

```
按下快捷键 → 录音开始，装上鼠标监视器
  ↓ 用户按住鼠标拖圈 → 实时绿线 lasso
  ↓ 松开鼠标 → 圈定格为 curve 标注；区域存入 pendingMarkedRegion
  ↓ 用户说话、松开快捷键 → 识别完成，进入应答管线
  ↓ step 1：不清标注 → 截图（圈在截图里！）→ 消费区域
      → 区域归一化框 + 圈内元素（containment 分类）→ <screen_contents> 随问题发出
      → 补清标注
  ↓ 模型：看到截图里的绿圈 + 清单里唯一的「fully inside」元素 + 用户的话
      → 回答点名「2」；要动手时直接用清单里的精确坐标 [CLICK:x,y:2]
```

## 五、完整复盘：失败是怎么发生的，成功是怎么来的

### 5.1 失败链条，逐环拆开

| 环节 | 失败形态 | 直接后果 |
|---|---|---|
| 模型回写标签 | 用户说「数字 5」，标签写成「数字5」 | 名字查找零候选 |
| 名字查找失败后的兜底 | 旧代码跳过 hit-test 直接用裸点 | 画圈稳定偏移（点击路径的兜底是现成的，圈没用上） |
| 截图前清标注 | 无差别执行，用户的圈也被清 | 模型看不到圈 |
| 圈内元素排序 | 等面积网格里面积排序失效 | 清单 10 个元素无判别力 |
| 模型决策 | 只剩截图 + 无判别力清单 | 猜：圈 2 答 3 或 4 |

**五个环节坏三个，任何一个单独修都不够。** 这就是为什么用户第一次实测前，代码自查抓到过一半问题（确认模式冲突），另一半（清圈、等面积、中文标签）全靠实测暴露。

### 5.2 为什么当时没发现

1. **渲染探针只验了「画得对不对」，没验「画在哪」**——探针给的是手工合成坐标，验证的是绘制管线，不是定位链路。「编译过 + 画出来好看」和「落在正确的元素上」之间隔着整整一条解析链。
2. **自查代码能抓「生命周期冲突」这类逻辑矛盾，抓不到「信息没有判别力」这类质量缺陷**——「面积排序」单看代码完全合理，要对真计算器跑一遍才知道 10 个元素面积全相等。
3. **多环节链路中，环节失败会向上伪装成「模型答错了」**——圈 2 答 3 或 4，看起来是模型问题，实际三环全是数据问题。

### 5.3 方法论（这次沉淀出的、以后必须执行的）

1. **多环节链路必须逐环节实测，不能整链黑盒测**。写一个 harness（这次在 `/tmp/wanna-ax-diagnosis`：只链 SDK 的 `AccessibilityTraversal.swift` + 逐字复制的解析函数，对真 App 跑），拿到每个环节的地面真值，再决定改哪。
2. **harness 里的复刻逻辑必须逐字复制 App 代码**。第一版照记忆重写，排序和 tie-break 写岔了都不自知。
3. **每个修复都要在 harness 里验证到数字**：词元重试修复后重跑，误差 0.0；containment 分类后重跑，fully-inside 唯一。「改了」不是验证，「误差从 ±25% 变 0.0」才是。
4. **真值从哪来**：辅助功能树本身就是地面真值（AX 框即真实框）。先遍历树找到目标元素的真框，再用它去检验各条解析路径。
5. harness 的 async 入口用 `dispatchMain()` 驱动主队列——**不要用信号量堵主线程**（MainActor 的 Task 永远排不上，整个诊断挂死，这次真的发生过）。
