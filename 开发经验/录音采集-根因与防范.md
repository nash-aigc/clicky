# 录音采集：为什么坏了十次，以及以后怎么不再坏

**写这份文档的原因**：2026-09-26 之前，「录音又坏了」连续发生过十次。每一次都是用户在真实使用
里撞出来的，每一次都要靠人回想「刚才是不是用过语音」。这份文档把**根因、排查方法、官方依据、
验证手段**沉淀下来，好让下一次（如果还有下一次）从正确的方向开始，而不是再从猜开始。

---

## 一、用户的需求（这是验收标准，不是背景）

> 启动之后无论用哪一个都能正常使用，随便切换都能正常使用，而且非常流畅、非常顺畅。

拆开就是三条，缺一条都不算解决：

1. **无条件**：不需要「先录音再对话」这种顺序要求。用户不会为了一个功能改变自己的使用顺序。
2. **可切换**：说了话之后录音、录着音说话、来回切 —— 都正常。
3. **不静默**：真出问题时，必须在**按下那一刻**就说话，而不是录完一整段零再报「录好了」。

第 3 条是这十次里最伤的一条：**静音是一种看不见的失败** —— 时长正确、文件写好了、没有报错、
没有崩溃。所有「看起来在正常运行」的信号它都有。

---

## 二、现象与它的误导性

用户报的是「录不了」，日志里长这样：

```
引擎声明的输入格式 采样率=48000.0 声道=1 · 设备=MacBook Pro麦克风 [id=88]   ← 好的那次
引擎声明的输入格式 采样率=48000.0 声道=3 · 设备=iShotAudioPlugin [id=50]    ← 坏的那次
第 200 块：1365 帧 峰值=0/32768 (0.000) 累计零块=200/200
服务端错误帧 code=45000081 [Timeout waiting next packet]                  ← 8 秒后才暴露
```

**误导点**：`设备=` 后面显示的是对的（`MacBook Pro麦克风 [id=88]`），声道数却是 3 ——
而**这台机器上根本没有任何 3 声道的设备**（麦克风 1、iShot 虚拟设备 2）。3 = 1 + 2，
是**聚合体**的形状。

## 三、我走过的三个错误方向（都会让下一次少走弯路）

### ❌ 方向一：以为「钉住设备」就够了

**做法**：在 `AVAudioEngine` 的 `inputNode.audioUnit` 上设 `kAudioOutputUnitProperty_CurrentDevice`。
**为什么看起来对**：日志里 `设备=` 确实显示绑到了正确的麦克风；`prepare()` 之后也还在。
**为什么没用**：**`start()` 会把它扔掉。** 见下面 §四的官方原文。

### ❌ 方向二：以为「放掉语音引擎」就够了

**做法**：起采之前调 `releaseAudioEngineNow()`，让共享语音引擎把硬件让出来。
**为什么看起来对**：机制是对的 —— 开语音处理（VPIO）确实会重配硬件 IO。
**为什么没用**：实测（独立探针）**放掉引擎并不能还原**，而且**问题根本不是污染**：

| 进程状态 | 钉到麦克风后引擎声明的格式 |
|---|---|
| 从没开过 VPIO | **1 声道 @48kHz** ✅ |
| 开过一次 VPIO，stop + 关语音处理 | **2 声道 @44.1kHz** ❌ |
| 紧接着再建一个引擎 | **2 声道 @44.1kHz** ❌ |

### ❌ 方向三：在"时好时坏"的状态上验证修法

这是**方法论上的错**，比前两条更值钱：同一个操作上午稳定复现 3 声道，下午却是 1 声道。
**抓不住"什么时候会坏"，任何修法都无法被证明有效。**

## 四、正确的做法：怎么查、查到了什么

### 4.1 搜索的路径（可复用）

1. **先搜现象，不要搜结论**：
   `AVAudioEngine inputNode returns CADefaultDeviceAggregate wrong channel count`
2. **再搜"别人怎么绕"**：
   `how to capture microphone from specific device on macOS while another engine uses voice processing`
3. **关键收获来自一个同样踩坑的项目的 `CLAUDE.md`**：
   `github.com/larshurrelb/quicktalk-app` —— 它把这条写成了禁止回退的规矩。
4. **顺着它追到官方**：Apple 技术文档 **TN2091《Device input using the HAL Output Audio Unit》**
   —— `developer.apple.com/library/archive/technotes/tn2091/`

**可复用的搜索习惯**：
- 别人的**项目文档/CLAUDE.md/踩坑记录**往往比问答站有用 —— 它们写的是"我量到了什么"。
- 找到线索后**一定要回到官方文档核对**，不要停在别人的结论上（TN2091 里就有我错了三次的那一行）。

### 4.2 官方原文（TN2091 + 别人的实测）

> **Capture is a raw AUHAL, not `AVAudioEngine`. Do not "simplify" it back.**
> `AVAudioEngine.start()` **silently** rebinds its input to a system `CADefaultDeviceAggregate`
> wrapping the *default* input device, discarding whatever was set on the input node.
> Setting `kAudioOutputUnitProperty_CurrentDevice` on `engine.inputNode` **succeeds, reads back
> correctly, survives `prepare()` — and is thrown away by `start()`.**
> Measured directly: after `start()` the unit's current device reads `CADefaultDeviceAggregate-…`,
> never the device that was set.

**这一句话解释了这个功能全部的怪现象：**

| 观测 | 真正的原因 |
|---|---|
| 日志 `设备=MacBook Pro麦克风 [id=88]` 是对的 | 那是在 `start()` **之前**读的 |
| 冷启动能用、说过话就不能用 | 聚合体的**组成**变了：只有麦克风 = 1 声道（能录）；麦克风 + 语音处理 = 3 声道（静音） |
| 放掉引擎、关语音处理都没用 | 问题不是污染，是 `start()` **每次**都重绑 |
| 时好时坏 | 聚合体由系统**动态**组，取决于当时还有谁在用音频 |
| iShot 装驱动之后更容易坏 | 多一个虚拟设备，聚合体更容易变成多声道 |

### 4.3 TN2091 里那行我错了三次的接线

```c
AudioUnitSetProperty(InputUnit,
    kAudioOutputUnitProperty_SetInputCallback,   // ← 输入侧是 SetInputCallback
    kAudioUnitScope_Global, 0, &input, sizeof(input));
```

**不是** `kAudioUnitProperty_SetRenderCallback` / `kAudioUnitScope_Input`。装错时的表现极具迷惑性：
**每一步 `AudioUnitSetProperty` 都返回 0（成功）、格式也读得到，但回调一次都不触发。**

完整的调用顺序（`LongFormAudioCapture.start()` 就是照这个写的）：

1. `AudioComponentFindNext` → `kAudioUnitSubType_HALOutput` → `AudioComponentInstanceNew`
2. `kAudioOutputUnitProperty_EnableIO`，`Input` scope，element **1**，值 1（开输入）
3. 同属性，`Output` scope，element **0**，值 0（关输出）
4. **`kAudioOutputUnitProperty_CurrentDevice`，`Global` scope，0** —— ★ 必须在 `AudioUnitInitialize` **之前**
5. 读设备格式：`kAudioUnitProperty_StreamFormat`，**`Input` scope，element 1**（硬件那一侧）
6. 设客户端格式：同属性，**`Output` scope，element 1**
7. **`kAudioOutputUnitProperty_SetInputCallback`，`Global` scope，0**
8. `AudioUnitInitialize` → `AudioOutputUnitStart`
9. 回调里 **`AudioUnitRender(unit, …, bus=1, …)`** 自己把数据拉进 buffer

## 五、修复

`LongFormAudioCapture` 的采集从 `AVAudioEngine` 换成 **AUHAL**：

- 新增 `halUnit` / `halRenderBuffer` / `captureTargetFormat`
- `start()` 按 §4.3 的九步建 AUHAL，回调里 `AudioUnitRender` 拉进 `AVAudioPCMBuffer`
- **`handleInputBuffer` 一行没改** —— 重采样、落盘、上行、电平四件事全部复用
- `stop()` 换成 `AudioOutputUnitStop` → `AudioUnitUninitialize` → `AudioComponentInstanceDispose`
- **`chosenInputDevice()` 一定落到一个具体的 `AudioDeviceID`**，绝不把「系统默认」原样交出去
  —— 那正是引擎去组聚合体的原因

### 验证（探针）

```bash
swift scripts/recording-capture-probe.swift
```

```
A. 干净状态：   回调 375 次 · 峰值 0.02362 · 48000Hz 1ch   ✅
B. 开一次 VPIO（污染进程）
C. VPIO 之后：  回调 375 次 · 峰值 0.02903 · 48000Hz 1ch   ✅
```

**A 和 C 完全一样** —— 这就是「不再随别人变」。

## 六、以后遇到这类问题，从哪个方向想

### 6.1 三条硬规矩

1. **先让故障稳定复现，再动代码。** 复现不了就不要改 —— 在"时好时坏"的状态上验证，
   等于把「碰巧好了」当成「修好了」。这个功能就是这么反复了十次。
2. **同一个问题两次没解决，停手查官方。** 不是换个写法再试。查的顺序：官方技术文档 →
   官方示例代码 → 别人的踩坑记录（往往比问答站有用）→ 回到官方核对。
3. **静默失败必须变成有声失败。** 只要一个失败模式是「看起来正常、实际什么都没有」，
   就先给它装判据（在最早能算出来的那一行算），再谈修。

### 6.2 遇到「设备/格式不对」时的思考顺序

```
现象：录到的全是零 / 采样率不对 / 声道数对不上
  │
  ├─ ① 先问：这台机器上**真的存在**这个格式的设备吗？
  │     （探针：枚举所有输入设备，打印名字/声道/传输类型）
  │     → 不存在 → 你拿到的是**聚合体**，不是设备
  │
  ├─ ② 聚合体是谁组的？
  │     AVAudioEngine 会用系统聚合体，而它的组成随"当时还有谁在用音频"变
  │     → 这就是"时好时坏"和"两个软件互相影响"的来源
  │
  ├─ ③ 我要的是"某个具体设备"还是"系统默认"？
  │     要具体设备 → **必须 AUHAL**，AVAudioEngine 做不到（TN2091）
  │
  └─ ④ 换了 AUHAL 还是没数据？
        检查回调是不是装饰在了 SetInputCallback / Global scope（见 §4.3）
        —— 装错时所有 API 都返回成功，只有回调不触发
```

### 6.3 这个仓库里已经就位的判据

| 判据 | 位置 | 作用 |
|---|---|---|
| 起采即自检 | `LongFormRecorderError.inputFormatMismatch` | 格式和设备对不上就**不开录**，并说明原因和办法 |
| 常驻复现探针 | `scripts/recording-capture-probe.swift` | 退出码非 0 = 故障已复现，**此时不要动 App 代码** |
| 每次变化的诊断行 | `LongFormAudioCapture` | `AUHAL 已启动 · 设备=… · …Hz …ch`，出问题第一眼就看它 |
| 规则 | `CLAUDE.md` | 改录音前先跑探针 |

## 七、和另一个子系统的边界（这条别忘）

Wanna 里有两条音频链路：**语音对话**（共享 `VoicePlaybackEngine` + 回声消除）和**长录音**
（自己的采集）。它们**必须是两条独立的路**：

- 语音那条约定的前提是「引擎保持开着，下一问才快」；
- 录音这条**绝不能再依赖那个引擎的状态** —— 这正是这次故障的本质。

用 AUHAL 之后，录音只认自己认下的那个设备，别人怎么折腾都影响不到它。
**以后任何"让录音蹭一下语音引擎"的想法，都是把这个 bug 装回去。**
