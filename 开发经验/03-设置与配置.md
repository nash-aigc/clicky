# 03 · 设置与配置

这个 App 有**两个配置文件**、**三个存储类**、**一个七页的设置窗口**。这一篇讲它们怎么拼在一起，以及**加一个新设置要动哪几个地方**。

---

## 一、文件存在哪（全部在仓库外）

| 文件 | 存什么 | 权限 |
|---|---|---|
| `~/Library/Application Support/Clicky/ModelConfiguration.json` | 三个模型角色、服务商、密钥 | `0600` |
| `~/Library/Application Support/Clicky/AppSettings.json` | 30 条设置 | `0600` |
| `~/Library/Application Support/Clicky/ConversationHistory.json` | 对话本身（可选） | `0600` |
| `~/Library/Application Support/Clicky/BailianSecrets.plist` | **只在第一次运行时**用来播种 | `0600` |

**为什么放仓库外**：这样一次干净的 `git clone`、甚至 `git clean -xfd` 都冲不掉用户的配置，而且这些文件里全是密钥和用户说过的话，本来也不该有机会被 `git add` 进去。

**而且这三个文件都不监听变化**：手工编辑 JSON，要重启才生效。这是有意的——设置窗口才是被支持的修改方式。三个文件里，只有 `AppSettings.json` 会通过通知机制让运行中的 App 立刻生效（见第四节）。

### `0600` 是怎么写上去的

```swift
try data.write(to: fileURL, options: .atomic)
try FileManager.default.setAttributes([.posixPermissions: 0o600], ofItemAtPath: fileURL.path)
```

**两步缺一不可**：`.atomic` 写入落地时是 `0644`（跟随 umask），所以必须在写完**之后**再改一次权限。三个存储类都是这个写法。

### 第一次运行怎么播种

`BailianSecrets.plist` 现在**只读一次**：第一次启动时如果 `ModelConfiguration.json` 不存在，就用它的 URL 和 Key 建一张「阿里云百炼」卡片，三个角色全指向它。之后设置窗口接管，plist 再也不读。

- 老用户升级：什么都不用改。
- 用户事后改 plist：**没有任何效果**，除非先删掉 JSON。

播种是**纯内存**的——用户不按「保存」，什么都不会写到磁盘。

## 二、七页设置窗口

| 页 | 存哪 | 条数 |
|---|---|---|
| 通用 | `AppSettings.json` | 9 |
| 模型 | `ModelConfiguration.json` | — |
| 对话与记忆 | `AppSettings.json` | 6 |
| 听（识别） | `AppSettings.json` | 4 |
| 说（播报） | `AppSettings.json` | 4 |
| 看与截图 | `AppSettings.json` | 5 |
| 快捷键 | `AppSettings.json` | 2 |

合计 30 条 `AppSettings` + 3 个模型角色。

**侧边栏那个数字是写死在 `SettingsPage.settingCount` 里的**，不是自动算的。这是有意的约束：**一个页面如果长出一行装饰性的假设置，它就得在侧边栏对自己撒谎**。加设置的时候记得同步改这个数字——第 5 波加三个光标设置时，「通用」就从 `6` 改成了 `9`。

### 加一个新设置要动的 6 个地方

照着 `answerBubbleLingerSeconds` 或第 5 波的 `cursorPresenceMode` 抄：

1. **`AppSettings.swift` — 声明属性**，带 `///` 注释说明它管什么。
2. **`AppSettings.swift` — `CodingKeys`**加一个 case。
3. **`AppSettings.swift` — `init(from:)`** 里加一行 `decodeIfPresent(...) ?? defaults.…`。
4. **`AppSettings.swift` — `clamped()`**（只有数值型需要，枚举不用）。
5. **`GeneralSettingsView.swift` — 对应的页面**里加一行 UI。
6. **`GeneralSettingsView.swift` — `SettingsPage.settingCount`** 加一。

第 3 步**绝对不能省**。合成的 `Codable` 遇到缺键会直接抛错，写成一个非可选的 `Bool` 会让**所有旧配置文件解码失败**。正确写法是 `Bool?`（或带默认值的 `decodeIfPresent`），并且默认值取「今天的行为」——老用户升级后应该看不到任何变化。

这个坑在第 4 波真的踩过：给 `ProviderProfile` 加 `visionReasoningEnabled` 时，写成 `Bool` 会让所有已有配置文件读不出来。

### 让它「保存就生效」

**`OverlayWindow` 从不直接读 `AppSettingsStore`**（已核实全文）。所有设置都由 `CompanionManager` 读进来、以 `@Published` 暴露，视图读 `companionManager.…`。

链路是：

```
用户在设置窗口按「保存」
  → GeneralSettingsViewModel 调 AppSettingsStore.save(...)
  → 存储类写完文件、改完权限、post .clickyAppSettingsChanged
  → CompanionManager 的观察者收到，把值抄进自己的 @Published 属性
  → SwiftUI 因为 @Published 变化重绘
```

**不需要重启，不需要重建任何客户端。** 第 5 波新增的三个光标设置走的就是这条路。

一个细节：`applyCursorSettings` 里，「一直显示」是**一个长期成立的答案**，所以保存的那一刻就生效；另外两档只会被「一次交互」打开，所以切过去的时候立刻隐藏，而不是留着等下一次提问。

## 三、为什么存储层全都标 `nonisolated`

这个 target 的构建设置是：

```
SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor
SWIFT_VERSION = 5.0
```

**未标注的类型默认是 MainActor 隔离的**，而 Swift 5 模式下编译器对隔离错误**不给任何诊断**。

配置这一条链上的所有类型——`ModelConfiguration` 的值类型、`BailianConfiguration`、`AppBundleConfiguration`、`ModelConfigurationStore`、`AppSettingsStore`、`ConversationHistoryStore`——全部显式标 `nonisolated`：

- 值类型没有共享可变状态，标了就能让读配置不必跳 actor；
- 存储类用一把 `NSLock` 守着自己那份缓存。

**注意**：只给存储类标 `nonisolated` 是不够的，它碰到的类型也得标，否则编译器会报错。

这是那种「隔离错了会**静默**出问题」的地方——所以宁可多标，也不要靠默认。

## 四、界面长什么样——怎么验证（离屏渲染探针）

改设置页面最烦的是**看一眼要重启一遍 App**。用离屏渲染探针可以完全不启动 App、不碰 TCC 权限就把页面画成 PNG。

思路是**直接把 App 自己的源文件编进一个独立可执行文件**，然后在里面构造真实的窗口再截图：

```bash
mkdir -p /tmp/clicky-probe && cd /tmp/clicky-probe
cp /Users/mjm/Desktop/clicky/leanring-buddy/*.swift .
rm -f leanring_buddyApp.swift     # 它带着 @main，会和探针的 @main 冲突
# 再写一个自己的 @main 探针文件
xcrun swiftc -O -sdk $(xcrun --show-sdk-path --sdk macosx) \
  -target arm64-apple-macos14.2 -swift-version 5 -default-isolation MainActor \
  -o probe *.swift
./probe general
```

探针主体：

```swift
let app = NSApplication.shared
app.setActivationPolicy(.accessory)          // 不抢焦点、不弹 Dock 图标

MainActor.assumeIsolated {
    let controller = SettingsWindowController()
    controller.presentWindow(initialPage: .general)
    guard let window = controller.window, let contentView = window.contentView else { return }

    window.layoutIfNeeded()
    contentView.layoutSubtreeIfNeeded()

    let bounds = contentView.bounds
    let rep = contentView.bitmapImageRepForCachingDisplay(in: bounds)!
    contentView.cacheDisplay(in: bounds, to: rep)
    try? rep.representation(using: .png, properties: [:])!.write(to: outputURL)
}
```

### 两个坑

**坑 1：窗口撑不大。** 想看到「在真实窗口里被折叠到下面」的卡片，第一反应是 `window.setContentSize(...)`——**没用**。SwiftUI 用约束把 hosting view 的 frame 钉死了，改窗口大小下一轮布局就被拉回去。

办法是把约束拆掉再改 frame：

```swift
NSLayoutConstraint.deactivate(hostingView.constraints)
NSLayoutConstraint.deactivate(hostingView.superview?.constraints ?? [])
hostingView.translatesAutoresizingMaskIntoConstraints = true
hostingView.frame = NSRect(x: 0, y: 0, width: 780, height: 1100)
```

**坑 2：页面里的 `ScrollView` 不是 `NSScrollView`。** 想靠 `firstScrollView(in:)` 找到它再滚到底，**找不到**（这个 SwiftUI 版本的 ScrollView 不是公开的 `NSScrollView` 子类）。所以「滚到底再看」这条路走不通，只能走坑 1 的办法把窗口撑高。

**坑 3（试过但不行）：`ImageRenderer`。** 用 `ImageRenderer(content: GeneralSettingsView(...))` 渲染出来是**一张纯黑图**——`ImageRenderer` 画不了 NSView 支撑的内容，而 `ScrollView` 正是。

### 这个探针真的抓到过东西

第 5 波第一次渲染「通用」页，一眼就看出两个问题：

- **分段选择器的标签换行了**（「只在对话时出现」太长），撑破卡片 → 把标签压到 4 个字以内（「一直显示 / 对话时 / 指位置时」），含义交给描述文字。
- **「跟随距离」那一行看起来挤出了卡片右边缘** → 把窗口撑到 1100 点再看，发现三行的右边缘其实**完全对齐**，之前的「溢出」是渲染图被窗口底边裁切造成的误判。

**第二条是重要的**：只看一张被裁切的图，很容易去修一个不存在的问题。验证布局的时候一定要看到完整的那张卡。

### 另外两个渲染探针的坑

- **`sips` 可以裁图**（`sips --cropOffset Y X -c H W in.png --out out.png`），放大局部看过界很方便；系统 Python **没有 PIL**，别指望 `from PIL import Image`。
- 探针文件在 SourceKit 里会报一堆 `Cannot find 'DS' in scope` 之类的红字——**那是单文件分析的假报错**，因为 SourceKit 看不到同目录的其他源文件。以 `swiftc -typecheck` 的结果为准。

## 五、两个必须记住的 AppKit 细节

**设置窗口必须先 `NSApp.activate()`。** 这是个 `LSUIElement` 应用，自己永远不会是活跃应用。不先激活，窗口**能出现但永远成不了 key window**，而**非 key 窗口的文本框会静默吞掉每一次按键**——看起来完全像是表单坏了。

**窗口控制器要同时持有强引用（`CompanionManager` 拿着）和 `isReleasedWhenClosed = false`。** 少任何一个：前者导致关窗即崩，后者导致窗口关掉就再也打不开。

## 六、加设置时容易犯的错（自检清单）

- [ ] 新属性在 `init(from:)` 里有默认值了吗？（不加的话旧配置文件读不出来）
- [ ] `SettingsPage.settingCount` 改了吗？
- [ ] 这个设置**真的接到行为了**吗？还是只是存下来了？
- [ ] 如果它是数值，`clamped()` 管到了吗？
- [ ] 如果界面要立刻反映，值是不是从 `CompanionManager` 的 `@Published` 走的？
- [ ] 如果某个选项会让另一行失效（比如「一直显示」让「闲置后自动隐藏」没用），那一行 `.disabled()` 了吗？
