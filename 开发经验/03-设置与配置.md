# 03 · 设置与配置

这个 App 有**两个配置文件**、**三个存储类**、**一个七页的设置窗口**。这一篇讲它们怎么拼在一起，以及**加一个新设置要动哪几个地方**。

---

## 一、文件存在哪（全部在仓库外）

| 文件 | 存什么 | 权限 |
|---|---|---|
| `~/Library/Application Support/Wanna/ModelConfiguration.json` | 三个模型角色、服务商、密钥 | `0600` |
| `~/Library/Application Support/Wanna/AppSettings.json` | 30 条设置 | `0600` |
| `~/Library/Application Support/Wanna/ConversationHistory.json` | 对话本身（可选） | `0600` |
| `~/Library/Application Support/Wanna/BailianSecrets.plist` | **只在第一次运行时**用来播种 | `0600` |

**为什么放仓库外**：这样一次干净的 `git clone`、甚至 `git clean -xfd` 都冲不掉用户的配置，而且这些文件里全是密钥和用户说过的话，本来也不该有机会被 `git add` 进去。

**而且这三个文件都不监听变化**：手工编辑 JSON，要重启才生效。这是有意的——设置窗口才是被支持的修改方式。三个文件里，只有 `AppSettings.json` 会通过通知机制让运行中的 App 立刻生效（见第四节）。

### `0600` 是怎么写上去的

```swift
try data.write(to: fileURL, options: .atomic)
try FileManager.default.setAttributes([.posixPermissions: 0o600], ofItemAtPath: fileURL.path)
```

**两步缺一不可**：`.atomic` 写入落地时是 `0644`（跟随 umask），所以必须在写完**之后**再改一次权限。三个存储类都是这个写法。

### 第一次运行怎么播种

`BailianSecrets.plist` 现在**只读一次**：第一次启动时如果 `ModelConfiguration.json` 不存在，就用它的 URL 和 Key 建一张「阿里云百炼」卡片，三个角色全指向它。之后设置窗口接管，plist 再也不读。

- 老用户升级：什么都不用改。
- 用户事后改 plist：**没有任何效果**，除非先删掉 JSON。

播种是**纯内存**的——用户不按「保存」，什么都不会写到磁盘。

## 二、八页设置窗口

| 页 | 存哪 | 条数 |
|---|---|---|
| 通用 | `AppSettings.json` | 9 |
| 模型 | `ModelConfiguration.json` | — |
| 对话与记忆 | `AppSettings.json` | 7 |
| 听（识别） | `AppSettings.json` | 4 |
| 说（播报） | `AppSettings.json` | 4 |
| 看与截图 | `AppSettings.json` | 5 |
| 操作 | `AppSettings.json` | 3 |
| 快捷键 | `AppSettings.json` | 3 |

合计 36 条 `AppSettings` + 3 个模型角色。

**「操作」页是第 9 波（2026-09-22）从「看与截图」里拆出来的。** 拆的理由是用户的话：听、说、看是**感官**，点击、打字、回车是**手**——「允许 Wanna 操作电脑」住在「看与截图」里，页面名和内容对不上。搬过去的是整张「操作电脑」卡（三个设置 + 辅助功能权限行 + 授权提示 note），另外补了一张**「它能做什么」**清单卡（点击/滚动/打字/选中文字/回车和快捷键/打开 App/读界面清单），每行对应 `MacosUseController.execute` 的一个真实分支。**能力行不是设置，不计侧边栏条数**（和「辅助功能权限」同一规矩），为此给 `SettingsRow` 加了一个无控件重载（`Control == EmptyView`）。「看与截图」从 8 掉回 5，「操作」从 0 起步记 3。

**「快捷键」页第 10 波（2026-09-22）从 2 涨到 3。** 原来的「按住说话快捷键」那一行裂成了两件事：

- **触发方式**（`pushToTalkTriggerModeRawValue` → `ShortcutTriggerMode`，存 raw string，未知值回退默认——枚举设置的通行写法）。「按住说话」是原有行为：按下开始、松开结束并发送。「点两下说话」是新加的：第一次按下开始录音+截图，**第二次按下**就停录+转文字+发送。语义要点：双击模式里**松开事件一律忽略**（一次点按必然松开，不能把松开当结束），开始时直接把 `sendsImmediately` 置真（确认模式是「松开时」的概念，双击模式没有松开这个时机）；第二次按下走的还是 `stopPushToTalkFromKeyboardShortcut`，草稿为空时它本来就会自动提交，所以不用新写提交逻辑。开关「松开立即发送」在双击模式下禁用（第二次按下就是发送），侧边栏条数仍然算它——它还是一条真设置，只是这一刻不可用。
- **说话快捷键的录制按钮**（`PushToTalkShortcutRecorder.swift` 的 `ShortcutRecorderButton`）。点一下进入录制态，下一个按键组合就是新快捷键（`customPushToTalkShortcut`，`nil` = 跟随预设）。三条硬规矩：**Esc 单按取消、点任意处取消**；**不带修饰键的裸键不收**（一颗字母键会被全局抢走）；**录制期间挂起真正的事件 tap**——靠 `.wannaShortcutRecorderStateChanged` 通知（object 布尔 = 是否在录制），`CompanionManager` 收到 true 就 `stop()` 全局快捷键监听、false 再按辅助功能权限门重启，否则「录制快捷键」这个动作本身就会触发一次真录音。预设和录制组合统一收敛到 `RecordedKeyboardShortcut { modifierFlagsRawValue, keyCode? }` 一个形状：修饰键-only 组合在 flagsChanged 上匹配（按下/松开即修饰键的按下/松开），带键的组合在该 key 的 keyDown/keyUp 上匹配——两条匹配路径汇成一条，显示（`displayText`）也从同一个形状出。

**这一波也留了一个 `RawRepresentable` 成例**：`AppSettings.json` 里存的 `"controlOption"` 这类 raw string 是**永不许改名的稳定标识符**，`BuddyDictationManager.ShortcutOption` 本体没有 raw value，在 `GeneralSettingsViewModel.swift` 尾部给了它一个 retroactive `RawRepresentable`（注释写明了为什么）。哪天动这个枚举，先看那段注释。

**侧边栏那个数字是写死在 `SettingsPage.settingCount` 里的**，不是自动算的。这是有意的约束：**一个页面如果长出一行装饰性的假设置，它就得在侧边栏对自己撒谎**。加设置的时候记得同步改这个数字——第 5 波加三个光标设置时，「通用」就从 `6` 改成了 `9`。

### 加一个新设置要动的 6 个地方

照着 `answerBubbleLingerSeconds` 或第 5 波的 `cursorPresenceMode` 抄：

1. **`AppSettings.swift` — 声明属性**，带 `///` 注释说明它管什么。
2. **`AppSettings.swift` — `CodingKeys`**加一个 case。
3. **`AppSettings.swift` — `init(from:)`** 里加一行 `decodeIfPresent(...) ?? defaults.…`。
4. **`AppSettings.swift` — `clamped()`**（只有数值型需要，枚举不用）。
5. **`GeneralSettingsView.swift` — 对应的页面**里加一行 UI。
6. **`GeneralSettingsView.swift` — `SettingsPage.settingCount`** 加一。

第 3 步**绝对不能省**。合成的 `Codable` 遇到缺键会直接抛错，写成一个非可选的 `Bool` 会让**所有旧配置文件解码失败**。正确写法是 `Bool?`（或带默认值的 `decodeIfPresent`），并且默认值取「今天的行为」——老用户升级后应该看不到任何变化。

这个坑在第 4 波真的踩过：给 `ProviderProfile` 加 `visionReasoningEnabled` 时，写成 `Bool` 会让所有已有配置文件读不出来。

### 让它「保存就生效」

**`OverlayWindow` 从不直接读 `AppSettingsStore`**（已核实全文）。所有设置都由 `CompanionManager` 读进来、以 `@Published` 暴露，视图读 `companionManager.…`。

链路是：

```
用户在设置窗口按「保存」
  → GeneralSettingsViewModel 调 AppSettingsStore.save(...)
  → 存储类写完文件、改完权限、post .wannaAppSettingsChanged
  → CompanionManager 的观察者收到，把值抄进自己的 @Published 属性
  → SwiftUI 因为 @Published 变化重绘
```

**不需要重启，不需要重建任何客户端。** 第 5 波新增的三个光标设置走的就是这条路。

一个细节：`applyCursorSettings` 里，「一直显示」是**一个长期成立的答案**，所以保存的那一刻就生效；另外两档只会被「一次交互」打开，所以切过去的时候立刻隐藏，而不是留着等下一次提问。

## 三、为什么存储层全都标 `nonisolated`

这个 target 的构建设置是：

```
SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor
SWIFT_VERSION = 5.0
```

**未标注的类型默认是 MainActor 隔离的**，而 Swift 5 模式下编译器对隔离错误**不给任何诊断**。

配置这一条链上的所有类型——`ModelConfiguration` 的值类型、`BailianConfiguration`、`AppBundleConfiguration`、`ModelConfigurationStore`、`AppSettingsStore`、`ConversationHistoryStore`——全部显式标 `nonisolated`：

- 值类型没有共享可变状态，标了就能让读配置不必跳 actor；
- 存储类用一把 `NSLock` 守着自己那份缓存。

**注意**：只给存储类标 `nonisolated` 是不够的，它碰到的类型也得标，否则编译器会报错。

这是那种「隔离错了会**静默**出问题」的地方——所以宁可多标，也不要靠默认。

## 四、界面长什么样——怎么验证（离屏渲染探针）

改设置页面最烦的是**看一眼要重启一遍 App**。用离屏渲染探针可以完全不启动 App、不碰 TCC 权限就把页面画成 PNG。

思路是**直接把 App 自己的源文件编进一个独立可执行文件**，然后在里面构造真实的窗口再截图：

```bash
mkdir -p /tmp/wanna-probe && cd /tmp/wanna-probe
cp /Users/mjm/Documents/SuperAgent/Wanna/Wanna/*.swift .
rm -f WannaApp.swift     # 它带着 @main，会和探针的 @main 冲突
# 再写一个自己的 @main 探针文件
xcrun swiftc -O -sdk $(xcrun --show-sdk-path --sdk macosx) \
  -target arm64-apple-macos14.2 -swift-version 5 -default-isolation MainActor \
  -o probe *.swift
./probe general
```

**从第 6 波（接 MacosUseSDK）开始，上面这条命令不够了。** `MacosUseController.swift` 真的 `import MacosUseSDK`，直接照抄会死在链接上。先在探针目录里把 SDK 编成自己的模块，再链过去：

```bash
APP_DIR=$(cd /Users/mjm/Documents/SuperAgent/Wanna && xcodebuild -project Wanna.xcodeproj \
  -scheme Wanna -configuration Debug -showBuildSettings 2>/dev/null \
  | awk -F' = ' '/ BUILT_PRODUCTS_DIR /{print $2}')
SDK_SRC=$(dirname "$APP_DIR")/../../SourcePackages/checkouts/MacosUseSDK/Sources/MacosUseSDK

# ① SDK 单独编成一个模块（少这一步，SDK 的声明会和 App 源文件里那份撞成 ambiguous use）
xcrun swiftc -emit-library -emit-module -module-name MacosUseSDK \
  -sdk $(xcrun --show-sdk-path --sdk macosx) -target arm64-apple-macos14.2 \
  -swift-version 5 -o libMacosUseSDK.dylib "$SDK_SRC"/*.swift

# ② 探针链上去
xcrun swiftc -sdk $(xcrun --show-sdk-path --sdk macosx) -I . -L . -lMacosUseSDK \
  -target arm64-apple-macos14.2 -swift-version 5 -default-isolation MainActor \
  -o probe *.swift
DYLD_LIBRARY_PATH=. ./probe
```

**别去链 `"$APP_DIR/MacosUseSDK.o"`**——那个目标文件带着覆盖率插桩，会报 `"___llvm_profile_runtime", referenced from: ___llvm_profile_runtime_user` 然后 `ld: symbol(s) not found`。这个报错完全不提覆盖率，看不出真正原因。

探针主体：

```swift
let app = NSApplication.shared
app.setActivationPolicy(.accessory)          // 不抢焦点、不弹 Dock 图标

MainActor.assumeIsolated {
    let controller = SettingsWindowController()
    controller.presentWindow(initialPage: .general)
    guard let window = controller.window, let contentView = window.contentView else { return }

    window.layoutIfNeeded()
    contentView.layoutSubtreeIfNeeded()

    let bounds = contentView.bounds
    let rep = contentView.bitmapImageRepForCachingDisplay(in: bounds)!
    contentView.cacheDisplay(in: bounds, to: rep)
    try? rep.representation(using: .png, properties: [:])!.write(to: outputURL)
}
```

### 两个坑

**坑 1：窗口撑不大。** 想看到「在真实窗口里被折叠到下面」的卡片，第一反应是 `window.setContentSize(...)`——**只改这个没用**。SwiftUI 用约束把 hosting view 的 frame 钉死了，改窗口大小下一轮布局就被拉回去。

办法是把约束拆掉再改 frame。**整棵子树都要拆**，只拆 hosting view 自己那层不够（里面有别的东西在撑）：

```swift
let targetSize = NSSize(width: 780, height: 1400)

func stretch(_ view: NSView) {
    NSLayoutConstraint.deactivate(view.constraints)
    view.translatesAutoresizingMaskIntoConstraints = true
    for subview in view.subviews { stretch(subview) }   // 递归，不能只拆一层
}

window.setContentSize(targetSize)
stretch(contentView)
contentView.frame = NSRect(origin: .zero, size: targetSize)
window.layoutIfNeeded()
contentView.layoutSubtreeIfNeeded()
```

**页面的高度是多少就设多少。** 设小了下面被裁掉（会误判成「卡片没渲染」），设大了底部留白。第 6 波的「看与截图」页要 **1400 点**才装得下三张卡。

**坑 2：页面里的 `ScrollView` 不是 `NSScrollView`。** 想靠 `firstScrollView(in:)` 找到它再滚到底，**找不到**（这个 SwiftUI 版本的 ScrollView 不是公开的 `NSScrollView` 子类）。所以「滚到底再看」这条路走不通，只能走坑 1 的办法把窗口撑高。

**坑 3（试过但不行）：`ImageRenderer`。** 用 `ImageRenderer(content: GeneralSettingsView(...))` 渲染出来是**一张纯黑图**——`ImageRenderer` 画不了 NSView 支撑的内容，而 `ScrollView` 正是。

**坑 4：开关的「开/关」画不准，别拿 PNG 判断设置的值。** 「看与截图」页上 `pointsAtReferencedElements` 在配置文件里明明是 `true`，离屏渲染出来**两个开关都画成关的**（灰色、圆点在左）。这是没有 key window / 没有真实 appearance 时的渲染问题，不是设置读错了。

**所以：想确认某个设置解析成了什么值，就打印，别截图。** 探针里加三行，一秒钟的事：

```swift
let liveSettings = AppSettingsStore.snapshot()
print("allowsComputerControl =", liveSettings.allowsComputerControl)
```

第 6 波就是靠这个确认了「旧配置文件升级后，新加的两个开关默认是开的」——`AppSettings.json` 里根本没有这两个键，`decodeIfPresent(...) ?? defaults.xxx` 落在 `true` 上。**看 PNG 会得出完全相反的结论。**

### 这个探针真的抓到过东西

第 5 波第一次渲染「通用」页，一眼就看出两个问题：

- **分段选择器的标签换行了**（「只在对话时出现」太长），撑破卡片 → 把标签压到 4 个字以内（「一直显示 / 对话时 / 指位置时」），含义交给描述文字。
- **「跟随距离」那一行看起来挤出了卡片右边缘** → 把窗口撑到 1100 点再看，发现三行的右边缘其实**完全对齐**，之前的「溢出」是渲染图被窗口底边裁切造成的误判。

**第二条是重要的**：只看一张被裁切的图，很容易去修一个不存在的问题。验证布局的时候一定要看到完整的那张卡。

### 另外两个渲染探针的坑

- **`sips` 可以裁图**（`sips --cropOffset Y X -c H W in.png --out out.png`），放大局部看过界很方便；系统 Python **没有 PIL**，别指望 `from PIL import Image`。
- 探针文件在 SourceKit 里会报一堆 `Cannot find 'DS' in scope` 之类的红字——**那是单文件分析的假报错**，因为 SourceKit 看不到同目录的其他源文件。以 `swiftc -typecheck` 的结果为准。

## 五、两个必须记住的 AppKit 细节

**设置窗口必须先 `NSApp.activate()`。** 这是个 `LSUIElement` 应用，自己永远不会是活跃应用。不先激活，窗口**能出现但永远成不了 key window**，而**非 key 窗口的文本框会静默吞掉每一次按键**——看起来完全像是表单坏了。

**窗口控制器要同时持有强引用（`CompanionManager` 拿着）和 `isReleasedWhenClosed = false`。** 少任何一个：前者导致关窗即崩，后者导致窗口关掉就再也打不开。

## 六、一个「什么都改」的设置：系统提示词编辑器

对话与记忆 → 「系统提示词」把 Wanna 每次提问都带着的那一整段原话摊开给用户看，可以直接改，旁边有「恢复默认」。加它的起因是用户的反馈：**模型废话多、光说不做**，但那段提示词用户一个字也看不到，只能描述症状。

它的存储形状和这个文件里其他所有设置都不一样，值得单独写一笔。

### `String?`，而且 **nil 本身就是有含义的值**

```swift
var customSystemPrompt: String?
```

nil 不是「还没设置」，是「**跟随内置版本**」。

换成别的写法就出问题：如果把内置提示词的正文当成这个属性的默认值存进去，那么每个**已经装好的用户在他第一次运行的那天，就被永久冻在了那天二进制里那段措辞上**——以后任何一次改进默认提示词的构建都到不了他那里，唯一的出路是让他自己把五千字重写一遍。所以内置版本必须留在代码里、由 `nil` 指过去。

### `init(from:)` 里唯一一个**不带 `?? defaults` 兜底**的属性

```swift
// 故意是可选的，而且没有 `?? defaults` 兜底：「没有这个键」和「键是 null」
// 都必须落到 nil 上，因为 nil 才是「用内置提示词」那个值。这里加兜底会把
// 每一个已有的配置文件变成一份当天提示词的冻结合同。
customSystemPrompt = try container.decodeIfPresent(String.self, forKey: .customSystemPrompt)
```

这正是 [`10-踩过的坑.md`](10-踩过的坑.md) E1 那条规矩（**每个新属性都要 `decodeIfPresent` + 兜底**）的**唯一例外**，而且是「兜底会主动造成伤害」的那种例外，不是偷懒。同时 `decodeIfPresent` 本身还是必须的——它保证缺键时不抛错。

### 读它的时候**不写入**

编辑器绑定的是 `String`，存的是 `String?`，中间这一层是 `GeneralSettingsView.systemPromptEditorBinding`：

```swift
get: { draftSettings.customSystemPrompt ?? CompanionManager.defaultVoiceResponseSystemPrompt }
set: { draftSettings.customSystemPrompt = $0 }
```

- **get 不写。** 所以打开这一页、什么都没碰就按「保存」，`customSystemPrompt` 仍然是 `nil`，用户还是在跟随内置版本。
- **「恢复默认」写的是 `nil`，不是当天那份文本的拷贝。** 存拷贝等于把「恢复默认」变成「冻结在今天」。
- 因为要给它读，`defaultVoiceResponseSystemPrompt`（原来叫 `companionVoiceResponseSystemPrompt`）从 `private` 改成了 `internal`。**这是它唯一的另一个读者。**

### 长度和补充指令仍然追加在**上面**

`companionSystemPrompt(for:)` 的结构没变，只是第一段从「永远用内置的」变成「有覆盖就用覆盖的」：

```
base（用户的覆盖 ?? 内置）
  + 回答长度那一句（显式声明「我覆盖上面的长度要求」）
  + 补充指令
```

**这一步不能省。** 编辑器管的是**基础提示词**，如果用户一碰编辑器就让「回答长度」和「补充指令」静默失效，那两个设置就变成了「保存了但什么都不做」——正是 A1 那条教训。

### 界面上的两个细节

- `SettingsTextEditorRow` 新增了 `minimumHeight` 参数（默认 62，够「补充指令」那种一行用）。**它是最小值，不是固定高度**：`TextEditor` 会撑到内容那么高。离屏渲染实测（780×2200，2026-09-22），4900 字的默认提示词把编辑器撑到约 1400 点，整页变成一条长滚动条——**这正是用户要的**（他说的原话是「完整地看到整个系统提示词」），所以没有去把它做成固定高度 + 内部滚动。
- 侧边栏 `.memory` 的计数从 6 改成 7。

## 七、加设置时容易犯的错（自检清单）

- [ ] 新属性在 `init(from:)` 里有默认值了吗？（不加的话旧配置文件读不出来）**唯一例外**是要能表达「跟随内置」的那种 `String?`——见第六节，那里的兜底会主动造成伤害
- [ ] `SettingsPage.settingCount` 改了吗？
- [ ] 这个设置**真的接到行为了**吗？还是只是存下来了？
- [ ] 如果它是数值，`clamped()` 管到了吗？
- [ ] 如果界面要立刻反映，值是不是从 `CompanionManager` 的 `@Published` 走的？
