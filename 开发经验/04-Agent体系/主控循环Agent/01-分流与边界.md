## 一、流水线：薄层一次调用（2026-09-25 定案，取代旧「四步两介入」）

> **2026-09-25 二次修订（用户判定，分流器换成模型）**：用户实测后的原话——
> 「用户的需求并不是运行某个代码，但他的触发词、语言里包含了一些代码运行的触发词，
> 这种情况下就会完全误触发。所以最好的方式是用模型来做分流……这个量化对照表就用 JEV
> 模型来做，然后做一个判断，它到底属于哪一种任务类型。**就分成这三类场景来做分流**：
> 纯视觉 / 纯文本 / 混合执行」。
> 三条防线（整句相等、哨兵词、引号数据区）**把 L0 的词面误触发压到了回归例零命中，但它们的本质是
> 往正则里继续堆意图边界意识——这是和词面匹配的形态在做无胜负的军备竞赛**（用户列出的
> 其他软件、英语、跨 App 叠加操作确实在任何有限词表的可预范围之外）。所以这一版把
> **类型判定整体交给 JEV 的 choice 原语**；关键词层不再是独立一级——它退成 JEV 脚本题
> 的候选池（固化脚本本身留着，**匹配改由 JEV 做**，见下面 2026-09-25 三次修订的薄层）。
>
> **实测依据**（同日，19 条难句含 5 条埋雷句 + 3 条对抗句，`../分流测速/bench_class3.py`、
> `../分流测速/三分类结果.json`）：
>
> | | JEV choice 三分类 | DeepSeek 同题面 |
> |---|---|---|
> | 准确率 | **19/19**（含「翻译成英文：把音量调到最大」这类执行词是被翻译对象的句子） | 17/19（两条误判都落在类边界上：翻译对象判成执行、读屏问答判成画圈） |
> | 中位耗时 | 702 ms | 532 ms |
> | P95 | 1332 ms（首调用冷启动 4.5 s，keep-alive 后即消失） | 903 ms |
> | 置信度 | 每题带 conf；**边界句 conf 0.19**（「帮我看看屏幕上有多少个图标」判对但明说在摇） | 无 |
>
> 所以选型：**分流用 JEV**——快中位让给 DeepSeek，但分流器要的是**错得少 + 知道自己什么时候不确定**。
> JEV 的 conf 天然就是第三条防线：低置信一律落纯文本（默认类，最安全），不赌。

| | 裸「脚本优先」 | **三级交叉仲裁** |

**回答「第一次用了几次 JEV」：一次。** 曾设计过两问版（脚本+分类）和更早的
「两层两次」版（词面代码一次、模型一次）；按手册计费口径与实测延迟，
一次调用三问严格优于两次调用——第二趟省下的不只是 $0.00005，还有整整一个
676ms 往返和一次"第一趟结果决定第二趟问什么"的状态机。

### 追问链：历史给 LLM，JEV 只拿最小上下文（2026-09-25 修，含一次自我更正）

用户的要求：「追问时一定要带两样东西——① 屏幕，必须带屏幕；② 之前的原话，
至少带 10 轮、10 句，但带太多也没有意义。同时**要标注哪一句是最近的、哪一句是上一句、
哪些是更早的话**，让 AI 能区分重点，而不是并列放在一起。」**这两样都成立，但都在 LLM 侧**——
本文下面给出载体与实测依据。

**为什么每轮仍要过 JEV**：实测同一串追问里用户会换类——「那把它关掉」→ 执行（conf 0.97）、
「圈一下」→ 图形（conf 0.94）。跳过 JEV 等于假设用户不改口，第一次改口就是误执行。

**一次自我更正（写下来，避免下次再犯）**：本文早先写过「JEV 的 state 必须带上上一句原话，
带上一句后 6/7→7/7」。**第二轮独立复测把这个结论推翻了**：同一批句子，仅本轮 7/7、
+上一句 6/7、+10句平铺 6/7、+10句标注 6/7——差异全部落在同一条本身无确定指代的句子上
（「再上面那句」）。两轮结论相反 ⇒ **该效果在噪声内，不能声称"带上下文提升准确率"**。
可复现的是另外两件事：

| 实测（两轮独立跑） | 数字 |
|---|---|
| 低置信时 JEV 的答案**跨轮翻转** | 「放大一点」首轮 图形(0.23) / 复测 执行(0.25)；「再上面那句」首轮 文字(0.64) / 复测 执行(0.78) |
| 上下文越多，JEV 平均置信越低（准确率不升） | 仅本轮 0.84 → +上一句 0.79 → +10句平铺 0.79 → **+10句标注 0.77** |
| 指代解析（10 对象池）谁都做不到高分 | JEV 1–2/3 · LLM 2/3——且该任务的 ground truth 本身靠假设，不足以给两者排名 |

**所以上下文这样分**：

| 谁 | 拿到什么 | 依据 |
|---|---|---|
| **LLM（外环）** | **屏幕截图** + **最近 10 轮用户原话，带远近标注** | 用户定案；只有它承接指代、且它的上下文本来就随对话增长 |
| **JEV（薄层）** | 本轮原话 + 前台 App 名 + （可选的）上一句用户原话 | 实测：塞 10 句只稀释它的注意力（平均置信 0.84→0.77），不提升准确率。它是选择器，不是对话解析器 |

**低置信的落点也定了**：JEV conf < 0.5 时不硬判，**转交 LLM 用历史决定**——
两轮实测都指向这条：低置信时 JEV 自己在翻转，而 LLM 带着历史给出的判断与它同水平、
且天然有指代能力。这正是用户"必须带历史"那条规则最该落的地方：
**JEV 的职责之一，是知道自己不知道。**

LLM 侧的历史格式（照用户要求把"重点"标出来，不并列）：

```
（本会话最近 10 轮用户原话，由早到晚，最后一条是上一句）
  1. 打开计算器
  …
  9. 打开 Safari
 10. 打开备忘录   ← 上一句
（「它 / 那个 / 刚才 / 再」优先指向最近提到的对象）
```

## 二、三类执行策略（2026-09-25 由用户定名为：纯文本 / 纯视觉 / 混合执行）

判据轴：**这个需求的完成，靠"呈现"、靠"执行"，还是旁路？** 技能引导不再是独立的类——它只是混合执行的一种输入（方法论注入），执行器相同。

| 类（用户的定名） | 是什么 | 产物 | 循环 |
|---|---|---|---|
| **⓪ 纯文本（默认类）** | 不碰机器不画图：翻译 / 写作 / 问答 / 讲解 / **读屏问答**（「屏幕上有多少个图标」——只看不指不画不动）。**分不动的、拿不准的、JEV 置信度低的，一律落这里**——纯文本最坏是一句不如意的回答，误执行的坏结果是在机器上做了没让做的事（风险不对称，默认类必须最安全） | 无标签回复，**不落盘**（用户的原话：「甚至不需要保存到本地，就是一个纯文本对话」） | 无 |
| **① 纯视觉**（旧名「纯显示」，同物改名） | 画圈、飞光标、画图讲解——对电脑无任何影响 | `[POINT]` `[SHAPE]` `[SVG_*]` | 无（内环照旧：画图工作流 ≤3 轮修复） |
| **② 混合执行**（旧名「纯执行」，同物改名） | 一切要动手/动状态的：预设脚本+参数、现写一行、自由组装、**技能引导组装**；用户明说这一类**可能同时生成文本、可能保存、可能点击按键**——所以一个回合里文本产物与动作可以并存 | `[RUN:]` `[CLICK]` `[TYPE]`… | **外环 ≤10 轮 → 10 轮未完成 = 打包升级给 Claude Code**（见 §六） |
| **③ 复盘** | 旁路，不接用户请求 | 技能/工具/参考条目 | 批处理内环 |

**改名不是文字游戏，是判据搬家**：旧的「纯执行」说的是"这一类只执行"，用户的新名「混合执行」说的是"这一类内部可以混着来"——判据从"它做什么动作"改成"机器状态是否变化"，一条需求既写文件又点开 App 不再需要拆成两类。**「纯视觉」同理**：判据是"屏幕上多了东西但机器没动"，于是「帮我看看屏幕上有多少图标」这类**读屏不画屏**的句子被正确地留在纯文本（JEV 在这个边界上 conf 0.19，它会明说自己不确定）。

**误触发回归例（2026-09-25，两类防线的共同依据）**：「在计算器里看一下数字然后搜索」/「请翻译’打开计算器’」/「打开某软件，然后翻译，请打开计算器」——无防线的子串匹配三个全误执行。**整句缓存**天然接不住它们（句子不等），**JEV 三分类**对同一批句子复测（conf 门槛 0.55 不变）：第一个→混合执行 ✓（conf 0.93，旧预期就是组装执行）；第二个→纯文本 ✓（conf 0.97）；**第三个→混合执行（conf 0.93），旧预期纯文本——这是判据搬家带来的合法改判**：用户的新分类明说「可能生成文本，可能保存，可能执行」多意图叠加归混合执行，而这一句里「打开某软件」本来就是真实的执行意图；落到混合执行后，执行器第一轮就看到全句与「翻译对象是数据」的规则，不会盲点计算器。三条句子**没有任何一条再触发盲执行**——这才是回归例真正要防的事。

**升级兜底是混合执行的出口，不是并列的第四类**：快循环轻量、高速、功能上有取舍，注定有完成不了的任务；10 轮未完成 = 打包交给 Claude Code（落在 Agent 窗口卡片里执行，全程可见），或用户点名 claude 直接进。

### 各类的细节判定

**① 纯视觉**（旧名纯显示）：判据 = 完成后**机器状态零变化**。旧「画图」整类并入这里——逐笔画出 + 逐步讲解只是它的呈现方式，不改变"无影响、无检查、无循环"的性质。

**② 纯代码**：三种形态，本质相同——

| 形态 | 例 |
|---|---|
| 预设脚本 + 模型生成参数 | `[RUN:保存到Notion:内容]` |
| 模型**现写的一行代码** | 一条 `osascript`、一条 `shortcuts run` |
| 预设脚本组合进一条命令 | 打开某标签页 = 预设脚本 + URL 参数 |

**「现写代码」的安全栏（必须有的补充，用户原话允许现写，这里补边界）**：现写代码过一道**静态危险词检查**（`rm -rf`、`sudo`、重定向覆盖、删目录等即拒），**破坏性动作仍然遵守既有规则**（用户本轮回合明确要求过才执行）。通过后直接运行——它属于 ②，不进观察循环。

**「不需要检查」的准确含义**：② 不进**观察循环**（无截图、无看一步做一步）。但**脚本级 verify 不因此取消**——那是用户自己定的三件套（创建 + 独立校验 + 兜底，见 [`06`](06-工具库与MCP.md) §六）：是否跑 verify 由**工具声明**决定；高频口令类（备忘录、Notion）建议声明，复盘会为常失败的补上。

**③ vs ④ 的唯一区别**：组装时**有没有方法论**。④ 先热加载技能描述（只暴露描述部分，模型知道该用哪个），选中后加载正文，按正文的步骤/规则组装；③ 没有正文可依，全凭模型对工具的理解现场研究。**两者的执行器相同**（主控循环），可组合（④ 的某一步内部也可以是自由组装）。

### 组装类的原料（AI 研究组合的对象）

| 原料 | 说明 |
|---|---|
| 鼠标 / 键盘动作 | `CLICK` `TYPE` `SCROLL` `DRAG` `PRESS`…（单点能力） |
| **模块化单步脚本** | 工具库里的脚本按"函数 = 工具"暴露——**它们不直接完成用户指令，但可以互相拼接**，本质与 MCP 的 tools 同类 |
| MCP 工具 | 按官方标准协议调用；被提炼过的（见 §四）以纯代码形态出现 |

AI 在这里研究的是**编排**：选哪个、先谁后谁、串行还是并行、中间要不要看结果。

## 三、循环上限：10 轮，到顶升级（2026-09-25 修订，取代 10–30）

用户的原话：

> 如果它循环 10 次以上，我建议直接切换到 Claude Code，把这个任务打包发给 Claude Code 来执行。

| 项 | 值 | 说明 |
|---|---|---|
| 混合执行的外环 | **≤10 轮** | 10 轮内不许向用户报「完成不了」 |
| **到顶 ≠ 失败报告，而是升级** | 打包交给 Claude Code | 打包内容：原始需求 + 已试步骤与失败原因（进度摘要）+ 当前屏幕状态 +「继续完成」 |
| 升级落点 | **Agent 窗口卡片**（现有 AgentSessionView） | 面板自动切到 Agent 页；HUD 芯片显示运行状态（现有 AgentHUDController）；完成语音播报（现有开关）——**解决"发给 Claude 之后不知道它在干嘛"** |
| 单条 C 类链 | 仍算 1 步（[`04-观察判据与批量.md`](04-观察判据与批量.md)） | 批量不绕过上限 |
| B/C 判据 | 继续用于混合执行内部 | 不变 |

## 四、提炼规则：高频 MCP 工具 → 纯代码

用户的原话：

> 如果 MCP 的某个脚本或某个工具经常被使用，但按照官方流程或使用方法需要传递很多次数据，比较麻烦，就把 MCP 里的工具和脚本直接提炼出来作为一个脚本，当作纯代码的方式来运行。
> 复盘时……直接把 MCP 里的某个工具提炼出来，单独做成一个脚本加参数的形式，用大模型生成参数、运行脚本，就可以减少很多中间 token 的消耗。

这条**已经在 06 / 复盘文档里**，此处确认它在 v2 框架里的位置：**提炼是 ④→② 的迁移通道**——经常以"组装"方式使用的东西，复盘把它固化成"纯代码"。三处落点：

| 场景 | 迁移 |
|---|---|
| MCP 某工具高频使用、传参繁琐 | 提炼成脚本 + 参数 → ② 纯代码 |
| 某需求反复靠"用户一步步引导"完成 | 梳理成**脚本组合**（→②）**或技能**（→④），看它是否有稳定的步骤序列 |
| 某类任务反复成功但没有沉淀 | 写成技能（方法论），让下次不用重新研究 |

## 五、复盘 agent 的三个新关注清单（第五个执行体的职责细化）

复盘要看的不只是"哪些能固化"，而是**三类高频模式**（用户的原话）：

| 清单 | 看什么 | 产出 |
|---|---|---|
| **A · 高频纯代码操作** | 哪些 `[RUN:]` / 现写代码反复出现 | 合并、参数化、进预设表（第 0/1 步命中率↑ → 更多请求零 AI） |
| **B · 高频组装需求** | 自由组装（③）的需求按类型聚类：哪几类任务总在拼同样的几步 | 沉淀成**技能**（→ 下次走 ④，有方法论）或**脚本组合**（→ ②） |
| **C · 反复失败 / 用户引导型** | 没有对应能力、AI 不知道调什么、或调用多次失败、最后靠用户一步步引导完成的任务 | **重点对象**：梳理成脚本（→②）或技能（→④，把"怎么被引导"写成方法论） |

清单 C 最有价值：**"用户教过 AI 一次"是最强的固化信号**——那次引导的每一步都是方法论的一部分。

## 六、Claude Code 的位置：两条入口 + 一条升级兜底（2026-09-25 修订）

用户的原话：

> 只有这两种情况下才需要调用，否则正常情况下永远都不要使用，因为它太复杂。我们现在设计的 agent 是正常情况下满足用户高频需求的 agent。

| 入口 | 触发 |
|---|---|
| **UI** | 面板侧栏的「对话 / Agent / 语音聊天」切换器（已存在，一行不改） |
| **转写关键词分流** | 用户的话明确提到 **claude / cloud（同音模糊）/ cc（词边界精确）**——转写之后、模型之前整体路由 |
| **升级兜底（新增）** | 混合执行循环 **10 轮未完成** → 打包（需求 + 已试步骤 + 失败原因 + 屏幕状态）交给 Agent 窗口卡片里的 Claude Code 会话；面板自动切到 Agent 页，全程可见 |

随之移除的：系统提示词的派发节（`:1688-1690`）、`[AGENT_SPAWN]/[AGENT_SEND]` 两个 pattern 与白名单、`dispatchAgentRequests`。**模型不再知道 Claude Code 的存在**；四类流水线永远到不了它。完整设计与验收见 [`../ClaudeCodeAgent/README.md`](../ClaudeCodeAgent/README.md)。
