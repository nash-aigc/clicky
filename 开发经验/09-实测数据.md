## 一、视觉模型的推理开销（2026-09-21）

**载荷**：App 自己的真实载荷——1280×827 的 JPEG 截图 + 4923 字的系统提示词。
**问题**：「屏幕右上角有什么？」
**模型**：`deepseek-flash`

### 推理开着（默认行为）

| 阶段 | 耗时 |
|---|---|
| 思考 | **3.4 s** |
| 上传 | 0.5 s |
| 回答 | 0.3 s |
| **合计** | **4.5 s** |

**第一个字之前的推理 token 数：664–868。**

**这一条是整次改造里最重要的一个数字**：Clicky 问的是**感知问题、念出来听的**，那 3.4 秒用户只能看着转圈，一个字都听不到。

### 关掉推理之后

| 指标 | 数值 |
|---|---|
| 首 token 时间 | **817 ms**（四轮中位数） |
| 对照（开着） | 4298 ms |
| `[POINT:x,y:label]` 标签正确率 | **4 / 4** |

### 四个候选开关哪个真的有用

| 字段 | 结果 |
|---|---|
| `thinking: {"type": "disabled"}` | ✅ 有用 |
| `reasoning_effort: "none"` | ✅ 有用 |
| `enable_thinking: false` | ❌ **仍有 629 个推理 token** |
| `chat_template_kwargs.thinking: false` | ❌ **仍有 378 个** |

后两个**会被接受**（HTTP 200），**静默地什么都不做**。

> **这张表就是「不要凭印象猜 API」的实物证据。** 四个字段里只有一个是从官方文档抄来的，其余三个都是「看起来合理」的猜测，两个是错的。

## 二、TTS 成本是线性的（2026-09-21）

**模型**：`qwen-audio-3.1-tts-flash` + 克隆音色
**测的是**：合成 + 下载（不含播放时间）

| 字数 | 耗时 |
|---|---|
| 10 | 0.72 s |
| 90 | 1.98 s |
| 250 | 5.85 s |
| 600 | 9.43 s |

**拟合出来**：

```
≈ 19 ms / 字  +  450 ms 固定开销
```

### 这个数字推论出什么

分块上限是 **500 字**（设置项 `maximumSpeechChunkCharacters`）。所以**一段正常的口头回答就是一块**，用户要**等整段合成完才能听到第一个字**。

**这里没有开关可以关**（不像推理那一段有 `thinking`）。能拉的两个杆：

1. 回答短一点（系统提示词里已经要求「一两句话」）；
2. 长回答时，第一句先合成、剩下的边流边合。

## 三、`max_tokens` 的天花板（2026-09-21）

**方法**：逐个服务商探测能接受的范围。

| 服务商 | 接受范围 | 越界的报错 |
|---|---|---|
| DeepSeek | `[1, 393216]` | — |
| 百炼 | `[1, 32768]` | `InternalError.Algo.InvalidParameter` |

**相差一个数量级。** 一个常量要同时服务两边，所以取**窄的那个：32768**。

**边界复测**：用真实的 **1.2 MB 截图** + App 自己的 4923 字提示词，在 32768 上两边各跑一次——都还能答，都还能吐 `[POINT:…]`。

**为什么不能把预算调小**：推理模型的思考**也算在这个预算里**。预算耗尽的返回是 **HTTP 200 + 空的 `content`**，不是错误。视觉客户端现在会把这种情况**抛成异常**，而不是当作「什么都没发生」。

## 四、DeepSeek 上的视觉模型（2026-09-21）

**方法**：列出端点暴露的模型，逐个试。

| 模型 | 结果 |
|---|---|
| `deepseek-v4-pro` | **拒绝截图**：`Unsupported Image` |
| `deepseek-flash` | 能看图、能回答，**而且会吐归一化的 `[POINT:…]` 标签** |

第二个结论**是不能假设的**——能看图不代表会用 0–1000 的归一化网格指位置。所以 DeepSeek 服务商预填的 🧠 模型是 `deepseek-flash`。

## 五、踩过的报错原文

留在这里是因为**它们全都不指向真正的原因**。

| 报错原文 | 真正的原因 |
|---|---|
| `InvalidParameter: url error, please check url` | **TTS 模型族和端点配错了**（见 [`04-模型接入.md`](04-模型接入.md)） |
| `[cosyvoice:]Engine error [411]` | **音色名不属于这个端点族**（Qwen-TTS 的 `Cherry` 给了 Qwen-Audio-TTS） |
| `InternalError.Algo.InvalidParameter` | `max_tokens` 超过 32768 |
| `Unsupported Image` | 用了 `deepseek-v4-pro` |
| `AllocationQuota.FreeTierOnly` | **账号问题**：免费额度用完了，但控制台里「仅使用免费额度」还开着 |

最后一条特别值得记：它让**视觉模型答得好好的，但用户听到的永远是一句道歉**（见 [`04-模型接入.md`](04-模型接入.md) 第七节）。**排查顺序：先查账号，再动管线。**

## 六、坐标系往返（2026-09-22）

给 Clicky 接上手（点击 / 滚动 / 打字）之前先验了一件事：**模型给的归一化坐标，能不能准确地变回 SDK 要的 Quartz 坐标**。这一条不验，点击会**上下镜像地偏**，而且不报错。

方法：一次性探针，取当前鼠标的真实位置，两条路各自往返一次，看能不能回到原位。屏幕 1728×1117，单显示器。

| 检查 | 结果 |
|---|---|
| 归一化网格往返（0–1000 → 屏内 → 回 0–1000） | 误差 `0.0000000000` |
| 真实鼠标位置：Quartz `(657.5, 1030.8)` → 归一化 `(380.50, 922.87)` → 回 Quartz | `(657.5, 1030.8)`，误差 0 |
| 主屏高度与 AppKit 的关系 | `1117 − 1030.8 = 86.2`，等于 `NSEvent.mouseLocation.y` 的实测值 |
| 光标处 AX 命中元素的矩形 `(506, 996) 929×43` | **包含 Quartz 点，不包含 AppKit 点** |

**最后一行是决定性的**：它把「AX 元素的矩形和 CGEvent 用同一个坐标空间」从文档里的一句话，变成了量出来的事实——而「点元素正中心」这个做法整个建立在这上面。

验完探针已删。多显示器没测（见下一节）。

## 七、截图分辨率**不影响**定位精度（2026-09-22）

**问题**：设置里「截图清晰度」有 960 / 1280 / 1600 / 原图 四档，默认 1280。往上调能不能让模型估坐标更准？

**答：不能，而且分辨率越高越散。**

**方法**：同一张屏幕截图（`screencapture` 的原生 3456×2234），用 `sips` 缩成四档，再按 App 的默认压缩质量（JPEG 0.8）编码。**同一个系统提示词**（App 自己的，10198 字）、**同一个问题**（「帮我点一下 7」）、**同一个服务商**（DeepSeek `deepseek-flash`，推理关闭，即 App 的真实载荷）。四档**交叉跑**（一轮里每档各跑一次，共四轮），这样时段漂移对四档的影响相同。共 16 次请求。

**地面真值**（跑之前现读的辅助功能树，不是推算的）：计算器 7 键 = `AXButton`，Quartz `(964, 722, 48, 48)`，中心 `(988, 746)` → 归一化 `(572, 668)`。

| 清晰度 | 实际像素 | 平均 x | 平均 y | x 误差 | y 误差 | **x 极差** |
|---|---|---|---|---|---|---|
| 960 | 960×620 | 570.5 | 416.2 | −1.5 | −251.8 | 164 |
| **1280（默认）** | 1280×827 | 379.2 | 688.8 | −192.8 | +20.8 | **87** |
| **原图** | 1728×1117 | 592.8 | 499.2 | +20.8 | −168.8 | **395** |
| 原生 2x | 3456×2234 | 460.8 | 682.0 | −111.2 | +14.0 | **640** |

（x 极差 = 同一档四次回答里最大减最小。归一化 1000 = 屏幕宽，所以 100 = 屏幕宽度的 10%。）

**三条读数**：

1. **误差不随分辨率单调下降。** 960 的 x 平均误差只有 −1.5，看起来最好；但那是因为它的四次样本是 `(677,814) (536,504) (513,93) (556,254)` —— y 方向散到 −251.8，平均出来的 x 恰好撞对，不是「准」。
2. **散开程度随分辨率变差**：1280 的 x 极差 87 → 原图 395 → 原生 2x 640。多给像素没有换来更细的定位，只换来更多种错法。
3. **这印证了第五节那个结论**：模型不是「看不清所以点不准」，是**它在缩略图上根本没有做精细定位**。这是它的能力边界，换像素换不掉。

**顺带确认的两件事**：

- **标签 16/16 全部写出来了**，四档都一样。所以「模型不写名字」这个风险，在 16 次里一次没出现。
- **「原图」这一档当时不是真正的原生像素**（2026-09-22 已修）。`CompanionScreenCaptureUtility` 的 `原图` 分支原来写 `configuration.width = display.width`，而 `SCDisplay.width` 是**点**不是像素——1728 点的屏，原图档出来是 1728×1117，真原生是 3456×2234，名不副实差一倍。**顺带排掉的一条死路**：`CGDisplayPixelsWide` 在这台机器上返回的也是 1728（点数），拿不到原生像素，倍数只能从匹配的 `NSScreen.backingScaleFactor` 拿。修复后实测：ScreenCaptureKit 配 3456×2234 就真出 3456×2234 的图（`screencapture` 同尺寸），payload 0.9 MB。**但第七节的主结论不变**——最后一行的 3456 就是真正的原生，定位精度照样没用，所以默认档仍然是 1280。

**成本对照**（同一张图）：960 = 154 KB，1280 = 249 KB，原图 = 412 KB，原生 2x = 1.13 MB。**所以往低调反而更划算**——除非为了「看清小字」（那是另一件事，没测过）。

## 八、指路落点：模型估计 vs 按名字解析（2026-09-22）

**问题**：点击改成「按名字找」之后准了，但**光标指路**还在用模型估的坐标——同一个元素，点击落对、光标落错。

**方法**：同一套端到端探针（真模型 / 真截图 / 真辅助功能遍历），问「计算器上的 7 在哪？」，四遍。每遍同时打印两条路的落点：旧公式（直接换算模型估计）和新公式（先按标签里的名字在辅助功能树里找，找不到才用估计）。

**地面真值**（独立探针现读的辅助功能树，不是推算）：`AXButton "7"`，Quartz `(964, 722, 48, 48)`，中心 `(988, 746)` → **AppKit `(988, 371)`**（`1117 − 746`）。屏幕 1728×1117，单显示器。

| 第几次 | 模型给的归一化坐标 | 标签 | 旧路径（估计）→ AppKit | **新路径（按名字）→ AppKit** |
|---|---|---|---|---|
| 1 | `(732, 561)` | `7` | `(1265, 490)` | **`(988, 371)`** |
| 2 | `(733, 557)` | `7` | `(1267, 495)` | **`(988, 371)`** |
| 3 | `(732, 557)` | `7` | `(1265, 495)` | **`(988, 371)`** |
| 4 | `(732, 557)` | `7` | `(1265, 495)` | **`(988, 371)`** |

**三条读数**：

1. **四次全部精确命中**，误差 0——落点是元素矩形的中心，和被检验的那段代码之外的独立读法完全一致。
2. **估计路径稳定偏 277 点**（屏幕宽度的 16%）。注意它**四次几乎不抖**（归一化 732/733）——这不是「随机误差取平均就没事」，是**一个稳定的错**，也正是用户看到的那个「总是偏一点」。
3. **降级路径逐位没变**：把同一个估计点分别喂给旧公式和新公式，两边都是 `(1266.624, 494.8309999999999)`。坐标翻转写反是静默错误，所以这一条是单独量过的，不是「看起来一样」。

**代价**：指路比原来晚 0.17–0.37 s 起飞（一次辅助功能遍历），付在起飞之前而不是飞到一半纠偏。

## 十、怎么复现这些测量

**载荷要一致。** 上面的视觉数据全部用同一份载荷测：1280×827 JPEG + 4923 字系统提示词。换一张图、换一次提示词，数字就不可比。

**多轮取中位数。** 首 token 那个 817 ms 是**四轮的中位数**，不是单次。单次测量在这类网络请求上没有意义。

**「有效」的判据要具体。** 判断一个推理开关有没有用，判据是**推理 token 数**（`delta.reasoning_content`），不是「感觉快了一点」。表里那两个没用的开关，如果只凭感觉是分辨不出来的。

**改模型的日期要记下来。** 这些数字都是 2026-09-21 的，服务商随时可能改行为。**过一段时间要重测。**
