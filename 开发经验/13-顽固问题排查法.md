# 13 · 顽固问题排查法——以「小人删不掉」为例

> 2026-09-22 的真实案件：展开面板的对话区顶部有一只 **约 256pt 的全身小人**，
> 用户要求删掉（「右侧的小人必须删除掉」）。删了两轮、重编译重启两次，它还在；
> 第三轮换掉思路，一次移除。这篇写的是：它到底是谁画的、前两轮为什么注定失败、
> 以及下次遇到同类顽固问题时按什么顺序取证。

---

## 一 · 案件本身

**现象**：面板展开后，会话胶囊下方偏左的位置站着一只全身像，尺寸 ≈ 256pt，
杀掉 Clicky 才消失。它不在任何代码注释过的位置上——当时的代码里，
对话区主页（`NotchHomeView.emptySessionHero`）只有问候语和提示行。

### 走错的两轮（先写错误，错误比正确更有信息量）

**第一轮：删错了组件。**
「对话区有个大吉祥物」→ 顺理成章地认为是主页 hero，于是把
`HomeHeroMascotPill` 从空会话主页里拿掉。重启，**小人还在**。

为什么错：这是从「大图 + 吉祥物 + 对话区」三个印象直接跳到结论，
没有先回答「**这只到底是哪个视图画的**」。主页 hero 是另一只（薄荷绿、坐胶囊、
带辉光），和用户看到的这只（跟随会话身份、无胶囊、无辉光）根本不是同一个东西。
删 hero 当然碰不到它。

**第二轮：改对了组件的「画法」，但没动它的「宿主」。**
第二轮的排查把范围收窄到了 `MascotAvatarDisc`（见下面证据链），于是重写它：
图片挪进 `overlay`（overlay 不参与布局）、`clipShape(Circle())`、
再 `.frame(width: 20, height: 20)` 三重保险。重启，**小人还在**。

为什么错：`MascotAvatarDisc` 在侧栏 38pt 渲染完全正常，坏的只是它在
`Menu` label 里的那一次使用。**在敌意宿主里给图加约束，约束不完整生效**
——机制是推测（Menu 的 label 走 AppKit 菜单渲染路径，SwiftUI 常规的
overlay/frame 布局手段在那里表现不同），但观测事实是确凿的：2026-09-22 实测，
`overlay + clipShape + frame(20)` 三重包裹后，图仍按素材原始 256pt 渲染，
整条顶栏仍被撑到 255pt 高。改了两次「图自己」，一次都没问「图被谁装着」。

### 破案的证据链（四条，缺一不可）

1. **窗口级取证：先证明它画在哪扇窗里。**
   `screencapture -x -o -l<窗口ID>` 只截一扇窗自己的像素
   （窗口列表来自 CGWindowList 脚本，全程不碰鼠标键盘）。截展开面板那扇窗
   → 小人在里面 → **排除覆盖层窗口**（蓝色光标那套）的所有嫌疑。

2. **身份跟随：让它自己暴露是哪个组件。**
   连续四次截图，小人的颜色分别跟随**当前活跃会话**的头像（薄荷 → 珊瑚 → 蓝）。
   全工程只在一处用 `MascotRoster.identity(forSessionID:)` 取「活跃会话」的身份：
   **顶栏会话胶囊**（`NotchSheetRootView.sessionChip`）`Menu` 的 label。
   「我改状态、它跟着变」是定位 UI 元素来源最便宜也最硬的证据。

3. **几何反推：量出撑大它的东西是 256pt。**
   胶囊文字「你好」垂直居中于面板 y≈157pt——恰好是「一行从 y=30 到 y=285」
   （255pt 高）的中点，而素材 PNG 的内在尺寸正是 256×256。
   侧栏行里同一个 `MascotAvatarDisc` 38pt 渲染正常，**唯一的环境差异就是
   Menu 这个宿主**。

4. **二进制新鲜度：排除「改了没编进去」。**
   `MascotAvatar.o` 22:07:19、`Clicky.debug.dylib` 22:07:21、
   进程 22:07:29 启动——三者递增，第二轮的失败是**真失败**，不是旧代码在跑。
   没有这一步，第二轮的「还在」就无法解释，下一步的方向就会更乱。

### 最终修法

不再跟 Menu 的布局较劲，直接按用户的要求把小人从胶囊里**整个移除**
（`NotchSheetRootView.swift` 的 `sessionChip`，label 只留会话名 + 小箭头），
并在原位留了注释禁止再放：

```swift
} label: {
    // 右侧不放小人（用户的要求：角色只在左侧会话列表出现）。
    // 这里也绝不能放 MascotAvatarDisc：macOS 的 Menu 对 label 提议
    // 不设上限，图会按素材原始 256pt 炸开、把整条顶栏撑高——
    // 实测 2026-09-22，任何 overlay/clipShape/frame 都压不住。
    Text(sessionsModel.activeSession?.title ?? "新对话")
    ...
```

状态：修改已通过 typecheck、构建（2026-09-22 22:12）、重启，并已于
2026-09-22 22:23 由用户的实机截图复核——展开面板顶栏只剩会话名胶囊，
小人确认消失，本篇闭环。

**教训**

> 元素删不掉时，先问「**谁画的**」，再问「**被谁装着**」，最后才是「怎么画」。
> 侧栏里正常、Menu 里炸开，说明问题从来不在图，在宿主。
> 而宿主的约束行为改不了的时候，**把东西从敌意环境里挪走**，
> 永远优于在原地继续加约束。

## 二 · 顺带查明的工具事实

排查期间另撞到两个「工具本身的坑」，记在这里避免下次重复浪费：

- **查符号要看对二进制。** 这个项目用 Xcode 的 debug-dylib 机制构建：
  主可执行 `Clicky` 只是 **59KB 的壳**，真正的代码全在旁边的
  `Clicky.debug.dylib`（**13.3MB**）。对着壳跑 `nm` / `strings`
  会得到「二进制里根本没有这个符号」的假结论，差点据此删错方向。
  要查符号：查 dylib，或更精确地查
  `DerivedData/…/Intermediates.noindex/…/Objects-normal/arm64/` 下的**单个 .o**
  （还能顺便用 `.o` 的 mtime 证明某个源文件有没有被重编）。
- **截图的时间戳不能当证据。** 粘贴文件（paste file）的 mtime 是**粘贴**的时刻，
  不是**截图**的时刻——二者可以差很远。时间线证据一律用
  进程 `lstart`、`.o` mtime、dylib mtime，不用文件粘贴时间。

## 三 · 方法论：下次遇到同类问题怎么办

这类问题的共同形状是：**「界面上有个东西，删了代码它还在」**。
按下面的顺序走，每一步都有对应的取证手段：

### 1. 先证明「看到的」和「以为的」是同一件事

- 用 `screencapture -l<窗口ID>` 逐窗取证，确定它画在哪扇窗。
  多窗口 App（本项目有覆盖层、注释层、面板三套窗）里，
  「在屏幕上看到」不等于「在面板里画」。
- 全程被动（CGWindowList + 窗口截图），不碰鼠标键盘——
  动作类取证会被拒绝，而且不需要。

### 2. 让元素自己暴露来源，而不是猜来源

- 找一个**会变的状态**（本项目里是活跃会话的身份），观察目标跟不跟着变。
- 跟着变 → 用「全工程谁读了这个状态」收窄到个位数候选
  （grep 身份函数的调用点，比猜快得多）。
- 不跟着变 → 换一个状态（比如某个开关、某条数据）再试。
  猜三次不如让元素招供一次。

### 3. 几何反推布局

- 量已知元素的位置（文字的垂直中心、基线），反推出它所在行的真实高度。
- 行高 ≈ 素材内在尺寸（256 ≈ 255）时，答案基本自己跳出来。
- 同一组件在别处正常、这里异常 → 差异在**宿主**，不在组件。

### 4. 两条失败红线（比全局规则更严的版本）

- **第一次失败**就应该触发质疑：「我在改正确的层吗？」——
  不是「换个写法再试」。换写法是把第一次的假设又提交了一遍。
- **第二次失败**必须停手，转入取证（本篇第一节的四步）。
  界面问题的取证成本极低（几次截图 + 几个 grep），
  而每多试一次错误修法，就多一次「重编译重启」的沉没成本。

### 5. 修法的选择顺序

1. **挪走**：把元素从敌意宿主里移除（本案的最终修法，
   也恰好符合用户「右侧不放小人」的需求本身）。
2. **换宿主**：必须留在这个位置时，换成约束可预期的宿主
   （例如 Menu 换成自绘按钮 + 弹层）。
3. **预渲染**：在 SwiftUI 之外把内容画成定尺寸 `NSImage` 再交给宿主，
   让宿主拿到的东西没有「内在尺寸」可炸。
4. ❌ **原地加约束**（overlay / clipShape / frame 三连）：
   本案已实测无效，别再走这条。

### 6. 验证闭环

- 改完 → 三对齐（`.o` mtime < dylib mtime < 进程 lstart）→ 无崩溃报告 →
  **再用第一条的同款取证流程截一次图**。
- 证据链要能证伪：修之前小人在这扇窗，修之后不在这扇窗——
  前后两次取证必须是同一种取证，结论才成立。
- 用户中途退出应用、复核没做，就**在文档里写「复核未完成」**
  （如本案第一节末尾），不留一个没有证据的「已修复」。

---

## 四 · 一句话版本

**删不掉的东西，先取证「谁画的」，再取证「被谁装着」；
组件在别处正常就别再改组件，改宿主；
宿主改不了就把东西挪走——两次原地修失败的每一分钟，
都够把整条证据链走一遍。**
