# 15 · 录音采集与设备自愈：为什么"录出来全是零"，以及怎么让它自己好

> 写于 2026-09-26。这一篇的主角是 `LongFormRecorderController.swift` 的采集那一半（`LongFormAudioCapture`），
> 以及它和 `AudioInputDeviceCatalog.swift` 的关系。想改这条路的人先读这一篇。

## 一、一页话

**症状从来不是"录音功能坏了"，而是"麦克风交出来的每一个样本都是零"。** 时长正确、文件写好了、
格式对、没有报错、没有崩溃 —— 只有内容是零，于是转写一个字都没有。这个仓库为它反复吃过亏，
而它最恶心的地方是：**所有"看起来在正常运行"的信号它都有**。

真正的根因有**两层，而且都不在我们代码里**：

| 层 | 事实 | 证据 |
|---|---|---|
| **交付层** | `AVAudioEngine.start()` 会**静默把输入重绑到系统默认聚合体**，你设的设备读回来是对的、`prepare()` 也活着，`start()` 之后就没了 | 官方 TN2091；探针实测格式在 VPIO 跑过之后从 `1ch@48k` 变成 `2ch@44.1k` |
| **设备层** | **别的软件**能把麦克风这个**设备**搞成"对谁都只给数字零"，之后连启动都失败；而且**跨进程**、**在肇事者退出之后仍然卡着** | 见第二节的三组对照 |

第一层是 AUHAL 能修的，第二层 AUHAL 修不了 —— **换设备才是解**。所以现在的设计是
「候选设备队列 + 看门狗自动换下一个」。

## 二、怎么知道"不是我们的代码"（这一步必须先做）

同一个现象，三个**互不相关**的实现拿到的东西完全一样，才敢说问题在下游：

| 实现 | 结果 |
|---|---|
| App 自己的 AUHAL 采集（`AUHAL 已启动 · 设备=MacBook Pro麦克风 [id=88] · 48000.0Hz 1ch`） | `峰值=0/32768`，500/500 块全零 |
| 全新进程的独立 AUHAL 探针（`scripts/recording-hal-amplitude-probe.swift`） | 187/187 块全零 |
| `ffmpeg` 的 AVFoundation 采集（第三个实现，跟上面两个没关系） | 27733 个样本全是零 |

**对照组是整件事的关键**：同一台机器、同一份代码、同一时刻，把默认输入换成
「"金｜14P"的麦克风」（iPhone 连续互通）——**立刻录到真实声音**（峰值 984/32768，188 块零 0 块）。
所以采集链路是好的，坏的是**那一个设备**。

再加上两条官方判据：

- 设备后来从"给零"变成"起不来"：`AudioOutputUnitStart` 返回 `1937010544` = `0x73746F70` = `'stop'`，
  查 SDK 头文件是 `AudioHardwareBase.h:155: kAudioHardwareNotRunningError = 'stop'`（"硬件没有在运行"）。
- **给零的是设备，不是某个 API**：`kAudioDevicePropertyDeviceIsRunning = 否`、
  `IsRunningSomewhere = 是`、输入**未静音**、主音量 0.275、没有 hog 独占 —— 属性全都正常，样本全是零。

**别忘了最后一条**：`AVCaptureDevice.authorizationStatus(for: .audio)` 说"已授权"，那是**权限**，
和"设备交得出样本"是两件事。没权限也会给零，所以它只能排除一半，不能当成"所以是设备坏了"。

## 三、判据为什么是"精确的零"，不是"安静"

这是整套自动化的地基，**不能凭直觉**：

- **健康设备永远有底噪**：安静房间里实测 188 块里只有 **0~3 块**全零，峰值 **246/32768**。
- **坏设备一个 bit 都不动**：187/187 块全零。那不是"安静"，是"没人往里写数据"。

所以「连续 N 块精确全零」只有一种解释，而**用户说话中间停一下绝不会触发**。

**块速率的换算必须记住（这里错过一次）：**

| | |
|---|---|
| 实测 | 850 块跨 **9.386 秒** → **90 块/秒**，一块 ≈ **11ms** |
| 为什么 | 一块是 16kHz 下的 171 帧，171 / 16000 = 10.7ms（和实测吻合） |
| 阈值 | `silentBufferAlarmThreshold = 90` 块 ≈ **1 秒** |
| ~~旧注释~~ | ~~"一块约 100ms，100 块 ≈ 10 秒"~~ —— **错了约 9 倍** |

而那个错数字**一路带进了给用户看的文案**：设置页里写「连续十秒没有任何声音」，其实只过了 1.1 秒。
**一个算错的常数不会自己待在注释里。**

## 四、自愈是怎么设计的

### 候选队列（`LongFormRecorderController.inputDeviceCandidates(for:)`）

**用户选定的 → 系统默认 → 其余真设备**，三个分寸都在这里：

- 用户**明确选了**就以他为准，队列**只有那一个**（换设备对他没有意义，见下）。
- 没选（"跟系统默认"，也就是绝大多数情况）→ 系统默认 + 其余非虚拟设备兜底。
- **虚拟设备不参与兜底**：环回声卡（录屏软件那种）天然不产出采样，没人往里送声音时它就是精确的零，
  会被看门狗当成坏设备换掉 —— 所以它不能当"备胎"。

聚合体（`kAudioDeviceTransportTypeAggregate`）在 `AudioInputDeviceCatalog` 里**一律不列**：
它不是设备是组合，声道数随成员变，变到某个形态就是纯静音。

### 看门狗与换设备（`LongFormAudioCapture`）

`handleInputBuffer` 本来就在数「连续零块」（那是为这个故障加的），现在**不只是报，而是修**：

1. 连续 90 块精确全零 → 诊断一行 + 请控制器换设备（计数器归零，换过去那个也可以再报一次）。
2. 控制器**不能在音频线程上换**（回调那头要求立刻返回），也不能占主线程（换设备实测慢起来是秒级），
   所以甩到 `Task.detached`。
3. `switchToNextCandidateDevice()` = `stop()` + `bindAndStartCapture(on:)` 顺着队列往后试。
   顺序有讲究：`AudioOutputUnitStop` 会等在途回调跑完，所以返回之后 dispose 是安全的
   —— `stop()` 一直是这个用法（`stopRecording` 也是在采集正跑着的时候调它）。
4. **拆函数是因为顺序错一步就是静默失败**：`SetRenderCallback` 装错时每一步都返回 0、
   格式也读得到，但回调一次都不触发。这个顺序只能有一份。

### 换不动的时候

| 情况 | 行为 | 为什么 |
|---|---|---|
| 用户**明确选了**设备（队列只有一个） | **只报，不换也不停** | 虚拟环回声卡"没人送声音时是零"是**正当用法**（录系统声音），替他停是帮倒忙 |
| 没选过、候选**全死** | **收尾**，并说明原因 | 这一场注定是空的，让他录 20 分钟静音再拿到一个"0 字"更糟 |
| 说不清"为什么" | **点名**：`processesCurrentlyCapturingInput()` 报出此刻正在开麦的 App | 「谁占着麦克风」是用户唯一能立刻行动的信息 |

### 第五个失败面：**起不来**（2026-09-26 补，客户端格式恒为单声道）

上面四条讲的是"起来了但给零"。还有**另一个面**：**根本起不来**，而且它跟"给零"是两套代码路径 ——
看门狗那条救不了它，因为采集压根没跑起来。用户撞到的就是这一种（「录音快捷键又无法使用了」）。

**现象与根因**（实测日志，2026-09-26 15:10）：

```
【1】系统此刻的默认输入设备：MacBook Pro麦克风 [id=91]，3 声道      ← 设备自己报 3 声道
AUHAL 失败④：客户端格式建不出来（48000.0Hz 3ch）
开始失败：拿不到麦克风输入（权限或设备问题）                        ← 连续 7 次，每次按键都被收到
```

原来客户端格式是**跟着设备的声道数建**的（`mChannelsPerFrame: hardwareFormat.mChannelsPerFrame`）。
而设备在系统进入语音处理 / 聚合体状态时会**自己从 1ch 变成 3ch / 9ch**（同一台机器当天两种都量到过）。
**3 声道的 `AVAudioFormat` 根本建不出来** —— 非交错格式要求一个合法的声道布局，1~2 声道能推断、
3 声道不能 —— 于是 `guard let clientAVFormat` 失败、抛错、整场结束。

**修法是两条，缺一条都不够：**

1. **客户端格式恒为 1 声道**（`mChannelsPerFrame: 1`），不再看设备报了几个声道。
   我们**本来只要一个声道** —— 目标是 16kHz 单声道，多声道到了下游那个 `AVAudioConverter` 里
   也一样要混成单声道。这样 1ch / 2ch / 3ch / 9ch 走的是**同一段代码**，这个失败面被整个去掉。
   实测（设备正处于 3 声道状态）：按 1 声道建格式 → `OSStatus=0`、起采成功、**188 块零块 0 个**、
   峰值 8/32768（真实样本，不是零）。
2. **`start()` 里也顺着候选队列往后试**：绑定抛错就换下一个设备，全部失败才抛。
   原来只有"起来了但给零"会换设备，起不来是直接结束 —— 两个失败面必须共用同一套"往后试"。

**已知代价**：`AudioOutputUnitStart` 在设备被系统卡死时会**阻塞约 10 秒**才返回错误
（实测 14:44:10 → 14:44:20），而 `start()` 跑在主线程上。三个候选都撞上就是半分钟。
但那是"设备整个死了"的极端情形；**本次这个格式故障是当秒返回的**（15:10:02 起七次都在同一秒）。

点名用的是 `kAudioHardwarePropertyProcessObjectList` + `kAudioProcessPropertyIsRunningInput`（macOS 14.2+）。
判据是**真的在开麦**，不是"在放音"——后者几乎所有软件都为真，报出来等于没说。
`cn.shandianshuo.desktop` 这种 bundle id 对用户没有意义，所以再用 `NSWorkspace` 换成显示名（`闪电说`）。

**唯一一处"告诉用户怎么做"**：换设备是我们能自己做的，而设备整个被系统卡死时只有两条路
——退出占用者，或者 `sudo killall coreaudiod`（约 2 秒，需要密码）。不说，用户就卡在那里了。

## 五、实测（2026-09-26，本机，都是真跑的）

### ① 正常路径：安静房间不该被误判

```
第 500 块：171 帧 峰值=57/32768 (0.002) 累计零块=0/500
录音结束：22 字，5.4 秒
自定义风格：重写完成，22 字（原文 21 字）
```
零块 **0/500**、**没有换设备**、转写成功 —— 地板的底噪足够让它不误判。

### ② 自愈路径：把默认输入设成一个哑巴设备

做法：`kAudioHardwarePropertyDefaultInputDevice` 指向 `iShotAudioPlugin`（录屏软件的虚拟声卡，
没人往里送声音，所以它的输入永远是零）—— 这同时也是一个**真实场景**（录屏软件抢默认设备）。

```
[06:54:17Z] AUHAL 已启动 · 设备=iShotAudioPlugin [id=53] · 48000.0Hz 2ch
[06:54:18Z] ⚠️ 连续 90 块（约 1.0 秒）没有任何声音 · 设备=iShotAudioPlugin [id=53] —— 这个设备不产出采样，换下一个试试。
[06:54:18Z] 🔁 输入设备已自动换到「MacBook Pro麦克风 [id=91]」（原来的「iShotAudioPlugin [id=53]」连续 90 块不产出采样）
   → 之后峰值非零（595 / 180 / 424 / …）
   → 新段 @连接后2.4s 音频位置1552ms 上行69KB 「你好」
   → 录音结束：25 字，9.3 秒
```

**1 秒内换完，同一场录音没断、没有重开一场、用户无感。**

## 六、AUHAL 到底修了什么、没修什么（更正一条旧结论）

早先（同一天早些时候）写在代码注释和 AGENTS.md 里的结论是：

> `AVAudioEngine` 的输入节点会被**进程级**的聚合体污染，所以让采集不走它、改用 AUHAL 就好了。

**前半句对，后半句错。** 实测把"换个 API 就没事"推翻了：

- AUHAL **一样**拿到全零、**一样**起不来（`kAudioHardwareNotRunningError`）。
- 坏的是**设备**，而且**跨进程**：全新进程、`ffmpeg`、App 自己都是零。
- 而 AUHAL 确实修好了它该修的那一类：**引擎重绑设备**（"冷启动第一场好、说过话之后就不行"）。
  这两类故障**症状一模一样**，这才是当初归错因的原因。

**教训（值得单独记）：一个改动"确实修好了一个真实存在的缺点"，和"它修好了眼前这个症状"是两件事。**
当时的 AUHAL 改动有探针、有对照、有数字，全都成立 —— 只是量的是另一类故障。

## 七、下次"录音又坏了"的排查顺序

**先跑探针，不要先改代码**（这条是拿十次真实损失换来的）：

```bash
cd /Users/mjm/Documents/SuperAgent/Wanna && swift scripts/recording-hal-amplitude-probe.swift
```

退出码 **0 = 采到了真实信号**；**非 0 = 复现出"全是零"**。它同时打印四件事：系统**此刻**的默认设备、
全部输入设备及声道数（3 声道那种东西只可能是聚合体）、设备的输入静音/音量、以及 2 秒采集的峰值与零块比例。

两条探针的分工别搞混：

| 探针 | 量什么 | 什么时候用 |
|---|---|---|
| `scripts/recording-capture-probe.swift` | 声明的**格式**和设备对不对得上 | AVAudioEngine 时代；**AUHAL 时代它永远绿**（AUHAL 读回来的格式总是对的，包括全零那几场），所以对"全是零"这类故障**已经失去意义** |
| `scripts/recording-hal-amplitude-probe.swift` | **振幅**（每块的峰值、零块比例） | 现在。判断"设备到底交没交出样本"必须用它 |

再往下查：

1. **先从探针的【1】看设备报几个声道。** 正常是 `1 声道`；**`3` 或 `9` 说明系统正处在
   语音处理 / 聚合体状态**，而设备一报多声道，历史上就有两个后果：客户端格式建不出来
   （起不来，2026-09-26 那次）、或者交出来的是纯静音（更早那几次）。
2. **谁在开麦**：`kAudioHardwarePropertyProcessObjectList` + `kAudioProcessPropertyIsRunningInput`
   （探针输出里没有，用 `/tmp` 那段脚本或直接看设置页报的名字）。
3. **设备是不是被自己人卡死**：App 自己的语音引擎开着语音处理（VPIO）时**也是**占着设备的那个。
   「引擎保持时间」和「释放引擎」快捷键就是为这件事存在的。
4. **最后手段**：`sudo killall coreaudiod`（要密码，约 2 秒），或重启。**这一步只能用户做**，
   所以 App 能做的只有"说清楚"。

## 八、还没做到的事（别把没验过的当验过了）

- **"所有设备同时死掉"那条分支没有端到端实测。** 自动收尾 + 点名 + 给最后手段那段逻辑写完了，
  取名那段单独跑通过（`cn.shandianshuo.desktop → 闪电说`），但在一台机器上把所有输入设备
  同时弄死做不到。**下次真撞上时，那是第一次真正执行它。**
- **没有"设备恢复后自动换回来"**：换了就是这一场一直用新的那个。中途换回原设备需要判断
  "它好了没有"，而现在没有可靠又便宜的判据。
- **不能用程序重启 coreaudiod**（要 root）。所以"全自动"的天花板就是"自己换设备"，
  再往下必须有人按一下。

## 九、重新转写（2026-09-26）

用户要它的理由：「网络问题或者其他的问题，他可能是断开了，然后用户可以通过这样的历史点击
重新进行一个重新撰写。」入口在**设置 → 录音 → 录音历史**每一行（音频还在才画那一颗）。

### 走的还是那条链

**同一个 `VolcengineRealtimeASRClient`、同一份设置解析出来的配置、同一个
`LongFormTranscriptWriter`**，只换了音频来源：`.wav` 的 44 字节头跳过去，剩下的就是当初
上行的那串字节（`RecordingAudioWriter` 落盘的就是上行缓冲的原样副本），所以不需要任何转码，
100ms 一块喂进去，最后发末包。

### 唯一一处实测逼出来的参数：喂多快

`retranscribeChunkPacingMilliseconds`，**20ms / 块 = 5 倍实时**。0（尽快喂完）**会坏**：

| 节奏 | 服务端自报的音频位置 | 结果 |
|---|---|---|
| 0（尽快） | **662ms**（而 `上行 1523KB` ≈ 47 秒的音频全发出去了） | 1 段、**15 字**，内容是录音的尾巴「这个。」 |
| 20ms / 块（5×） | 29.7s（跟着上行一起涨） | **5 段、114 字**，与录制当时那份 `.jsonl` **逐句一致** |

流式识别是按**到达速率**解码的：灌得比它解得快，中间那一段就被跳过，而且不报错
（HTTP 正常、连接正常、只有结果是短的）。所以这条的参数不能凭感觉调 —— 要改就先拿一条
长录音量「服务端自报位置 ≈ 音频总长」。

### 两条分寸

1. **旧的转写不删，改名留档**（`.txt` / `.jsonl` → `.superseded`）。重跑本身也可能半路失败，
   而"识别了一半就断"正是用户来点这个按钮的原因 —— 直接覆盖等于把上一份也弄丢。
   **两个 `.superseded` 都要先清掉**：`moveItem` 在目标已存在时失败，第二次重跑时那两个名字上
   还躺着上一次的留档，结果就是 `.txt` 换新了、`.jsonl` 悄悄留在旧的那份上（实测踩到，已修）。
2. **跑的时候写临时名**（`<id>-retranscribing`），整跑完了才顶替正式文件 —— 中途失败时磁盘上
   那两个文件还是完整的。
