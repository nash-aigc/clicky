# 00 · 问题根因排查法（本仓库最重要的方法文档）

> **这份文档排在所有文档之前，因为它是"怎么找答案"的方法，其余文档是"答案"。**
> 遇到任何一个说不清的问题——功能不对、偶发、时好时坏、改了没反应——**先读这篇**。
> 它的每一条都来自本仓库真实踩过的坑，不是通用建议。

---

## 一、唯一的铁律

> **遇到问题的第一件事是找根因，不是改代码。**
> 同一个问题，**自己动手两次没解决，立刻停手**——不再改、不再猜，转去做调查。

这条不是效率建议，是**正确性**建议。本仓库有一次连续四轮"找到了原因 → 改了 → 没有任何变化"的记录（见 §六）。四轮里每一轮都有一份看起来很合理的解释，每一轮都改了一个真实存在的缺点——**但症状一次都没有变化**。原因只有一句话：

> **真实存在的缺点，不等于本次症状的原因。**

---

## 二、四轮为什么全部失败：两个具体的读错方式

### 失败模式 1：把探针的输出读反了

当时用的探针在 run loop **回到空闲时**打印一段刚刚结束的忙碌：

```
⏱️ [hitch] main thread busy for 234ms
🔇 SystemSpeakerMuteCoordinator: system speakers MUTED for recording
```

推断是「停顿紧挨着静音 → 静音就是原因」。**这是倒因为果。**

`[hitch]` 报告的是一段**已经结束**的跨度；紧跟其后的那行日志是**接下来的工作**，不是原因。把静音挪出主线程之后，症状**毫无变化**——这一条本可以事先排除。

**规则：任何"时间跨度"型探针，先写清它报告的是跨度的起点、终点还是长度。报告"刚刚结束的一段"的探针，永远不能用它后面那行做归因。**

### 失败模式 2：仪器太窄，于是把真凶"排除"掉了

当时的计时只包住了两行：

```swift
let beganAt = Date()
audioEngine.prepare()
try audioEngine.start()          // ← 计时到这里结束
print("… took 77ms …")
```

而同一段主线程代码里，**在计时开始之前**还有：

```swift
let inputNode = audioEngine.inputNode                     // 首次触碰 → 实例化输入 AU
let inputFormat = inputNode.outputFormat(forBus: 0)       // 同步 HAL 查询
inputNode.removeTap(onBus: 0)
inputNode.installTap(onBus: 0, bufferSize: 1024, format: inputFormat) { … }
```

实测：那一整段主线程占用是 **102ms 和 166ms**，而计时器只报了 **77ms 和 69ms**。**停顿的 1/3 到 1/2 在计时之外**，于是得出了「只要 64~80ms，肉眼看不出来」的结论，把真凶排除，转去找别的原因。

**规则：一个计时器只覆盖它包住的那几行。用它去否定一个候选之前，先确认它包住的是这个候选的全部。**

## 三、正确的流程（六步，顺序不能换）

### ① 停手

同一问题第二次没解决 → 停止改代码。**继续改只会制造新的变量**，让下一次归因更难。

### ② 把用户的主观描述，翻译成一个"仪器能回答的问题"

用户说的是**感受**，仪器只能回答**量**。翻译是排查里最需要动脑的一步。

| 用户说的 | 仪器要回答的 |
|---|---|
| 「展开时卡一下」 | 主线程在动画的哪一段被占住、占多久？ |
| 「第一次特别慢」 | 从哪个事件到哪个事件、多少毫秒？拆成几步各多少？ |
| 「有时候没有声音」 | 是没被渲染，还是渲染了没送到设备？哪一步先断？ |
| 「一旦坏了就一直坏」 | 有没有一个标志位活得比它描述的对象更久？ |

**信号：如果你的"问题"里没有数字、没有时间点、没有状态量，那它还没被翻译完。**

### ③ 装仪器：加能测的东西，不是加日志

- **时间戳**：每个关键步骤一条 `⏱️` 打点，打印**距本轮起点**和**距上一条**两个数（只看总时长会漏掉"是哪一段"）。
- **跨度探针**：`CFRunLoopObserver` 挂在主 run loop 上，测「醒来 → 再次入睡」的忙碌长度，超过一帧预算就打印。**它回答"什么时候停了多久"**。
- **每条打点必须同时打印"它在哪个线程"**（`Thread.isMainThread`）。本次有两次误判都是因为不知道工作在哪个线程上。
- 打点要**成对或成链**：只有"开始"没有"结束"，量不出时长；只有"结束"没有参照，量不出位置。

**仪器的第一职责是让你能说"我量到了 N 毫秒"，而不是"我觉得大概是这里"。**

### ④ 并发派多个 agent，从不同角度看，其中至少一个是批判者

**这是本仓库验证过最有效的一步。** 本次最后破案，靠的是两个 agent 从**完全不同**的角度独立收敛：

- 一个查**动画的组成**：有几个动画、各驱动什么属性、是不是同一个事务、有没有中途重排窗口。
- 一个查**每帧的预算**：那段时间每一帧主线程欠多少活，谁在抢同一个线程。

两者独立得出的是**同一个结论**（同一段 106~167ms 的同步占用，落在动画 20%~70% 处）。

派 agent 时的硬性要求：

1. **每个 agent 一个互不重叠的角度**，并明确告诉它"别的角度已经有人在查"。
2. **必须给 `file:line` 证据**，结论要能顺藤摸瓜。
3. **至少一个是批判者**：要求它"假设最新的代码有罪"，并写出**"这条结论会被什么推翻"**。
4. **要求它们各自列出"哪些候选被排除了，凭什么"**——排除的过程和结论同等重要。
5. **明确禁止它们改代码**（read-only），否则它们会开始"顺手修一下"，污染证据。

**收敛才算数：只有一个 agent 说某处有问题 → 那是线索；两个互不相关的角度指向同一处 → 那才是根因。**

### ⑤ 与用户反馈对齐，做算术

用户给的往往是最好的约束条件。**把测到的数字放进用户描述的时间窗里算一遍。**

本次：测到主线程被占 **166ms**；用户说动画 380ms 且**卡在中间**；而 `easeInOut` 的**速度峰值恰好在 t=0.5**。三者一对：

> 166ms 的停顿落在 380ms 动画的中段，而那正是翅膀运动最快的时候 —— 所以观感不是"整体变慢"，而是**停在半路、然后跳完剩下的**，也就是用户说的「卡一半」。

**算术对上，才叫解释；对不上，就还是猜测。** 算术同时还能解释"为什么不是每次都卡"（那一段排在网络握手之后，握手慢的时候它被推出了动画窗口）。

### ⑥ 改一处，验证，再改下一处

一次只改一个原因。同时改三处，即使好了也不知道是哪一处、下次还会犯。

## 四、排查结束前必须回答的问题（缺一不可）

- 症状的**数字**是什么？（多少毫秒、第几次、哪个状态）
- 我**量到**了什么？还是我在**推理**？——**没量到的一律标注为"推测"**。
- 仪器的覆盖范围是什么？**它能不能否证我这个候选？**
- 探针报告的时间跨度，**起点和终点分别在哪一行代码**？
- 有几个独立的证据指向同一处？它们互相矛盾吗？
- 如果我的结论是错的，**什么现象会出现**？我去看过了吗？
- 用户的原话是什么？**我的结论能解释他描述的每一个字吗**（包括"位置"和"偶发性"）？

## 五、反模式（本仓库真实发生过的）

| 反模式 | 本次的代价 |
|---|---|
| 看到日志里两行挨着，就认定前者是后者的原因 | 修错了地方，症状无变化 |
| 用一个只包住部分代码的计时器去"排除"一个候选 | 把真凶排除了，多花三轮 |
| 不写"推测"和"实测"的区别 | 结论被当成事实往下传 |
| 一次改多处 | 就算修好了也说不清是哪一处 |
| 自己猜答案，不去派 agent 多角度看 | 四轮全部失败 |
| 探针打在不确定的线程上、不打印线程 | 两次误判工作发生在哪个线程 |
| 用"这段代码看起来慢"当理由 | 真正慢的是没被计时的那三行 |

## 六、本次案例的完整时间线（可作为模板）

**症状**：每次按住说话快捷键，刘海展开动画在**中间**卡一下。

| 轮次 | 做了什么 | 结果 |
|---|---|---|
| 1 | 猜是"推流引擎同步启动" | 加了计时 → 实测 64~80ms → **假设被自己的数据否定** |
| 2 | 猜是"相位中途从 Thinking 换成 Listening" | 改了，**症状不变** |
| 3 | 猜是"麦克风电平每秒 47 次重算全屏窗口" | 限流到 20Hz，**症状不变** |
| 4 | 加了新的 `[hitch]` 探针，看到停顿紧挨着"系统扬声器静音" | 把 CoreAudio 调用移出主线程，**症状不变** |
| 5 | **停手**。并发两个 agent（动画组成 / 每帧预算）+ 自己校准探针语义 | 两路**独立收敛**到同一处：录音启动收尾同步阻塞 106~167ms，落在动画 20%~70% 处 |
| 6 | 把整段收尾移出主线程（`Task.detached`） | **症状消失** |

**第 5 步之前的一切都是浪费。** 而第 5 步能成功，靠的是第 1~4 步留下的仪器和数据——**失败的尝试也有产出，前提是它们留下的是数据而不是新的猜测。**

## 七、可复用的探针

本次破案用的三个探针写在 `CompanionManager.swift` 里。**排查结束后，按事件触发的那两个已经删除**（`TurnTimingProbe` / `PressPathProbe`——它们每次按键打十来行，平时只是噪音），**只留下一个**：

| 探针 | 状态 | 回答什么 |
|---|---|---|
| `MainThreadHitchProbe` | **保留** | 主线程**什么时候**被占住、**多久**（只在超过 40ms 时报一次，安静时零输出） |
| `TurnTimingProbe` / `PressPathProbe` | 已删（在 git 历史里） | 一条链路上每一步的耗时；需要时照 §三③ 重新加，模式很简单 |

保留 `MainThreadHitchProbe` 的理由：它是**「出问题时唯一能告诉你'哪里开始不对劲'的东西」**，而它在一切正常时**一行都不打**。这次四轮误诊里，只要有它在，第一轮就能看到那 166ms 的停顿，不必等到第四轮。

**加探针这个动作本身，是排查里最值钱的一步——不要跳过它去直接改代码。**

---

## 八、一句话版本

> **同一问题两次没解决就停手；把感受翻译成数字；装能测的仪器；并发多角度派 agent（含批判者）看它们是否收敛；把测到的数放进用户的时间窗里做算术；然后才动第一行代码。**
