# 16 · 卡片上那颗「通话」的两条路（2026-09-26）

## 用户要的是什么

一句话：**卡片右侧那颗电话按钮，在四种模式下是两种完全不同的东西。**

- **语音 / 视频**：走语音聊天子系统（全双工 / 三段式那套引擎），是"我跟这个角色说话"。
- **文本 / 图文**：用户 2026-09-26 的原话 —— 「文本模式和图文模式的通话按钮路线是使用语音
  识别的形式，跟用户通过快捷键识别屏幕、然后提问、在鼠标右下角显示窗口回复内容是同一个
  方法……用户点击通话按钮之后，识别用户的内容，然后自动发送出去……**它的功能就是替用户
  发送文本，不用手动输入**，识别到用户的文本后自动发送过去就可以。」

第二条还有三个附加要求，每一条都决定了实现形状：

1. 「整个样式、刘海的样式跟语音视频的样式一样，就是一个通话的状态」→ 复用同一个刘海相位
   （`.externalChatting`，屏幕上是「Call」+ 右侧那枚红电话），不另造一套状态。
2. 「识别用户的语音，并且能够打断」→ 开口即打断，与语音对话同一条规矩。
3. 「**通话过程中间，允许用户在输入框里面发送问题，这是一定要允许的**」→ 通话**不能**
   接管输入框。这是"综合的、多维度的发送方式"。

## 实现：`TextCallController`（一个文件，约 190 行）

它**不碰语音聊天那套引擎**，只做一件事：把「连续监听 + 自动发送」接到这张卡片**原本的
文本管线**上。说一句话 = 在那张卡片的输入框里打一行字并按回车。

| 环节 | 走谁 |
|---|---|
| 听 | `BuddyDictationManager.startContinuousListening`（与语音聊天、对话页追问**同一个窗口**） |
| 门槛 | 3 个内容字（与语音聊天同一个数，理由见那边的注释：3 能放行「几点了」，挡住 1~2 字的回声残片） |
| 发 | `CompanionManager.sendTextCallQuestion` → 主循环卡片走 `submitTypedQuestion`；Claude Code 卡片走 `agentSessionManager.sendTurn` |
| 截不截屏 | 由卡片的模式决定（图文截、文本不截）——与用户手打时**同一条判断** |
| 答 | 原来的路：截图 → 视觉模型 → 光标旁的气泡 + 播报 |
| 刘海 | `setExternalSessionOverride(.externalChatting)`，与语音 / 视频那条路**同一个相位、同一颗挂断** |
| 挂断 | `CompanionManager.hangUpAnyActiveCall()`（刘海右侧那颗电话、卡片按钮再按一次、`NotchActivityView` 里那处，三个入口汇到这一个函数） |

## 三条结构性的边界（改这个功能前先读这几条）

### 1. 两条通话不可能同时活着 —— 因为它们抢同一个麦克风窗口

`BuddyDictationManager` 只有**一份**连续监听窗口（那个文件的注释里写着完整的历史：
"有时完全识别不了"就是调用方把别人的窗口当成自己的）。所以卡片上那颗按钮先按模式分流
（`mode.isVoiceLike ? voiceChatController : textCallController`），这就是唯一的入口分界。
谁要再加第三条通话，先解决窗口复用，别绕过分流。

### 2. 「通话活着」由**那个窗口**定义，不由一个 `Bool` 定义

`TextCallController.bindListeningWindow()` 订阅 `dictationManager.$isContinuousListening`：
**窗口一关，通话就结束**。

为什么必须有这条：窗口可以被别的东西关掉，而这些路径都不归通话管 ——
用户按快捷键去录音（录音会先结束打开的监听窗口）、麦克风权限掉了、语音聊天的会话接管。
少了这条，屏幕上会留下一个还在说「Call」、其实已经听不见的刘海 —— **那种不一致比功能少更糟**，
因为用户会继续对着它说话。

### 3. 「回答时持续监听」那条追问机制必须给通话让路

`CompanionManager.armContinuousListeningWindow()` 是对话页那条"回答播完继续听 30 秒"的入
口，它在**每一次回答开始播放**时被调用。而通话跑的正是同一条管线 —— 于是每一轮回答都会
走到这里。放行下去的后果是实测过的：它会给通话的窗口排一个到期任务，到点
`endContinuousListening()`，把通话的耳朵摘掉。

所以那里加了一句 `guard !textCallController.isActive else { return }`，与它上面那句
「语音聊天会话进行中」并列 —— 两句话说的是同一件事：**这块麦克风现在不是你的。**

## 打断

`onSpeechDetected` 里只做一件事：如果有一轮在跑或在念，`interruptActiveResponse()`。
**不在这里发送** —— 用户这句话自己的**最终转写**才是新的一轮。语音聊天那条路踩过同样的坑
（那边注释写着"否则会连开两轮"）。

## 实测（2026-09-26 晚，真机）

用户在验证期间自己对着它说了好几句，整条链路是通的：

| 观察 | 证据 |
|---|---|
| 起通话 | `📞 文本通话开始：卡片 DDB52124 · 门槛 3 字`；AX 树出现 `挂断 (955,0 88×32)` 与 `Call (739,8)` |
| 说一句 → 发出去 | `📞 文本通话：把这句发出去 ——「我现在桌面上该在做什么事情？」` |
| 图文模式真的带了截图 | 同一轮 `🧠 本轮上下文：历史 6 轮 · … · 截图 1 张`；而且回答里说出了屏幕上正在干什么（读到了代码内容） |
| 连续多轮 | 历史 6 → 7 → 8 → 9 → 10，全部落在同一张卡片的同一条会话里 |
| 通话中**用输入框**再问一句 | 回声 `🥅`：输入框文字被清空、停止按钮变红、`本轮上下文` 多一行、会话里多一条（用户要的第 3 条要求） |
| 挂断 | `📞 文本通话结束：卡片 DDB52124` + `🎙️ continuous listening ended`；刘海立刻回 idle |

### 有一条没验到，如实记在这里

**"用扬声器喂麦克风"这条路走不通**，所以我自己没法造出一句"真的被识别出来的话"。
实测（`scripts/recording-hal-amplitude-probe.swift`，输出音量 75% 与 100% 各一次，
`say -v Tingting` / `-v Meijia` 连续朗读）：

| 条件 | 麦克风峰值 |
|---|---|
| 输出 75%，短句 | **212 / 32768**（0.65%） |
| 输出 100%，长句 | **447 / 32768**（1.4%） |
| 参考：真人说话（同一天、同一支内置麦） | 1868 / 32768（5.7%） |
| 参考：App 自己认定"有人在说话"的 VAD 门槛 | 0.25（≈ 8192 / 32768） |

差了近 20 倍，**内置扬声器到内置麦克风的耦合远在门槛之下**，VAD 一次都不会响。
所以下半段（"听到 → 发出去"）我用一次性探针喂了一句已经识别好的话才验到；
而上半段的 ASR 本身是既有机器（对话页追问、语音聊天都在用它），不是这次新写的代码。
**真机上有用户自己的声音作为证据**（上表），这是最终采纳的那一份。

## 两个已知的边界（不是 bug，是没做）

- **卡片按钮的绿色高亮**：`VoiceChatController.isCalling(cardID:)` / `TextCallController.isCalling(cardID:)`。
  这里刻意**不看模式** —— 早先那版高亮的是"这张卡片选了语音模式"，于是一张只是选过语音的
  卡片会一直亮着绿电话。现在亮 = "这一通正在打"。
- **通话中手打的问题不会先打断上一轮**：`submitTypedQuestion` 本身就没有打断语义（这是
  既有行为，不是通话引入的）。实测里能看到一轮回答被后一句"接上"的现象。要改就改
  `submitTypedQuestion` 这一处，别在通话里单独补。
