# 08 · 构建与签名

这一篇解释一件看起来很小、但会决定「你每次改完代码要重开三次权限」的事：**签名方式**。

---

## 一、结论先放这里

| 签名方式 | 终端 `xcodebuild` | TCC 权限（录屏/辅助功能/麦克风） |
|---|---|---|
| **证书签名**（现在） | ✅ 安全，随便用 | ✅ 重建之后不再重新问 |
| **ad-hoc 签名** | ⚠️ **不要用** | ❌ 每次重建都被当成一个全新的 App，三样权限全部重置 |

**当前状态：证书签名。**

```
CODE_SIGN_STYLE   = Automatic
CODE_SIGN_IDENTITY = "Apple Development"
DEVELOPMENT_TEAM  = 8WS2Z3JL4F
```

（工程文件里 `6D7X9GGZAW` 出现在**项目级**配置上，App target 自己那一层是 `8WS2Z3JL4F`，以 target 为准。）

---

## 二、为什么签名方式会决定权限

macOS 的 TCC（录屏、辅助功能、麦克风这些权限）认的是 App 的 **designated requirement**。

**证书签名**的 requirement 是：

```
designated => identifier "com.yourcompany.leanring-buddy" and anchor apple generic
              and certificate leaf[subject.CN] = "Apple Development: … (WR9S5P4Y38)"
```

这是**按证书**认的。同一张证书签出来的每一版，在 TCC 眼里都是**同一个 App**，所以权限一直有效。

**ad-hoc 签名**的 requirement 是：

```
cdhash H"…"
```

这是**按二进制哈希**认的。**每一次重建，哈希都变，TCC 就认为这是一个从来没见过的 App**——三样权限全部重置。

这就是上游那个「每改一次代码就要重新授权三次」的根源。

---

## 三、上游的坑：写死的 team ID

上游把 App target 的 `DEVELOPMENT_TEAM` 钉死在 **`2UDAY4J48G`**（原作者的 team）。在任何别人的机器上，它会**在编译之前**就失败：

```
error: No signing certificate "Mac Development" found: No "Mac Development"
signing certificate matching team ID "..." with a private key was found.
```

**绝对不要**用「随便填一个 team ID」来绕过它——**keychain 里没有那张证书，自动签名对任何 team 都会失败**。要么填一个真实存在的 team，要么走下面的 ad-hoc。

---

## 四、ad-hoc 是最后的退路

一台**完全没有 Apple ID** 的机器上，ad-hoc 是唯一能让它编过的办法：

```
CODE_SIGN_STYLE   = Manual
CODE_SIGN_IDENTITY = "-"
DEVELOPMENT_TEAM  = ""
```

它能编过，是因为**这个 App 没有开沙盒**，而它声明的每一个 entitlement 都不需要 provision profile：

```xml
<key>com.apple.security.app-sandbox</key><false/>
<key>com.apple.security.network.client</key><true/>
<key>com.apple.security.device.camera</key><true/>
<key>com.apple.security.device.audio-input</key><true/>
<key>com.apple.security.temporary-exception.mach-lookup.global-name</key>
<array><string>com.apple.screencapturekit.picker</string></array>
```

**代价就是第三节说的：TCC 权限不稳定。** 而且一旦切回 ad-hoc，**终端构建就不能用了**——必须回到 Xcode GUI 里跑，因为 GUI 构建至少能让权限重授的流程顺畅一点。

## 五、日常怎么编译

### 最快的语法检查：`swiftc -typecheck`

不启动 Xcode、不碰签名、不碰 TCC，纯静态检查：

```bash
cd /Users/mjm/Desktop/clicky/leanring-buddy
xcrun swiftc -typecheck -sdk $(xcrun --show-sdk-path --sdk macosx) \
  -target arm64-apple-macos14.2 -swift-version 5 -default-isolation MainActor \
  $(ls *.swift | grep -v leanring_buddyApp.swift)
```

**那个 `grep -v` 不能省。** 裸 `swiftc` 解析不了 SwiftPM 的 **Sparkle** 模块，而 `leanring_buddyApp.swift` 是唯一 import 它的文件（自动更新用）。

**三个参数每一个都必须和工程设置一致**，否则检查的是一套不存在的规则：

| 参数 | 为什么 |
|---|---|
| `-swift-version 5` | 工程是 Swift 5（不是 6） |
| `-default-isolation MainActor` | 对应 `SWIFT_DEFAULT_ACTOR_ISOLATION = MainActor` |
| `-target arm64-apple-macos14.2` | 对应 `MACOSX_DEPLOYMENT_TARGET = 14.2` |

**源文件的默认隔离方式是这套代码库最容易被误解的地方**：未标注的类型**默认是 MainActor 隔离**的，而在 Swift 5 模式下，隔离错误**没有任何诊断**。所以配置那一层（`AppSettingsStore` / `ModelConfigurationStore` 等）必须显式标 `nonisolated`——见 [`03-设置与配置.md`](03-设置与配置.md)。

### 完整构建：`xcodebuild`

证书签名下**安全**：

```bash
xcodebuild -project leanring-buddy.xcodeproj -scheme leanring-buddy -configuration Debug build
```

比开 Xcode 快，而且在拿编译错误这件事上完全够用。

### 但它**不会**让改动生效

**macOS 不会给正在运行的进程换代码。** 构建完必须**重新启动 App** 才能看到改动。

这一点每次都要记得——尤其是改 UI 的时候，很容易以为「改了没效果」。

（设置项的改动是例外：`AppSettings.json` 变了会发通知，运行中的 App 立刻生效。但那是**数据**变了，不是代码。）

## 六、其他构建相关的事实

| 事实 | 说明 |
|---|---|
| 产品名是 `Clicky.app` | 但**目录和 scheme 叫 `leanring-buddy`** |
| Bundle ID | `com.yourcompany.leanring-buddy` |
| `LSUIElement = true` | 没有 Dock 图标、没有主窗口 |
| 有一个遗留的 `SUFeedURL` | 指向**原作者的** appcast，跟着上游遗留下来的 |
| 有两个测试 target | `leanring-buddyTests` / `leanring-buddyUITests`，是 Xcode 模板生成的，**内容基本是空的** |
| `VoiceTranscriptionProvider` 在 Info.plist | 值是 `bailian`，用来选转写后端 |

**不要重命名工程目录或 scheme。** `leanring` 那个拼写错误是上游遗留的，改它的风险远大于收益。

---

## 七、已知的非阻塞警告——**不要修**

- Swift 6 的并发警告
- `OverlayWindow.swift` 里 `onChange` 的废弃警告

这两类在 `xcodebuild` 输出里会一直出现。它们不影响功能，动它们的风险大于收益。项目里明确写着「不要尝试修这些」。

## 八、这一块的经验

| 经验 | 来自 |
|---|---|
| **签名方式决定 TCC 稳不稳**，不是无关紧要的细节 | 每重建一次重授三次权限 |
| 写死别人的 team ID 会让别人**编译都过不去** | `2UDAY4J48G` |
| 别用「随便填个 team」绕过签名错误 | keychain 里没证书，自动签名必失败 |
| `swiftc` 检查的三个参数要和工程**逐项对齐** | 默认隔离 + Swift 版本 |
| 裸 `swiftc` 解析不了 SwiftPM 依赖 | 排除 import Sparkle 的那个文件 |
| **构建 ≠ 生效**，macOS 不换运行中进程的代码 | 每次都要重启 App |
