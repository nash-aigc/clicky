# 10 · 踩过的坑

每一条都按 **现象 → 根因 → 修法** 写。**根因才是这一篇的价值**——现象只说明「坏了」，根因才告诉你下次怎么不踩。

按「坑的类型」分组，不按时间。

---

## A · 「看起来在动，其实根本没跑」

### A1 · 蓝色光标关不掉

**现象**
设置里有「光标闲置后自动隐藏」，但**它从来没有任何效果**。蓝色三角永远跟着鼠标。

**根因**（三重叠加）

1. `CompanionManager.isWannaCursorEnabled` 是唯一的开关，存在 UserDefaults，**默认 `true`**；
2. 它唯一的 UI 是菜单栏面板里的一行 "Show Wanna"，而**那一行在代码里被注释掉了**（`CompanionPanelView.swift:64-71`）；
3. `scheduleTransientHideIfNeeded()` 第一行是：

```swift
guard !isWannaCursorEnabled && isOverlayVisible else { return }
```

第 1、2 条让开关永远是 `true`，第 3 条让「按快捷键淡入、用完淡出」那段调度**一次都不会执行**。

设置页那个滑块的描述写着「关闭『显示光标』时……」，而它引用的那个控件**在界面上不存在**。

**修法**
删掉 `isWannaCursorEnabled`（连同注释掉的那段 UI 和死掉的 `showWannaCursorToggleRow`），换成三个真正的设置；把那行 guard 改成 `guard cursorPresenceMode.hidesWhenIdle && isOverlayVisible`。

**教训**
> **一个能保存但什么都不做的设置，比没有这个设置更糟。** 它会让用户以为是自己没找对地方。

### A2 · 四个「看起来合理」的 API 字段，两个是错的

**现象**
换到推理模型之后，回答要等 4.5 秒才出声。

**根因**
模型在吐第一个字之前先产生了 664–868 个推理 token（3.4 s）。

**修法** — 但这里的关键是**怎么找到对的字段**：

| 字段 | 结果 |
|---|---|
| `thinking: {"type": "disabled"}` | ✅ |
| `reasoning_effort: "none"` | ✅ |
| `enable_thinking: false` | ❌ 仍有 629 个推理 token |
| `chat_template_kwargs.thinking: false` | ❌ 仍有 378 个 |

**后两个会被接受（HTTP 200），静默地什么都不做。**

**教训**
> **要么量，要么查官方。** 凭「名字看起来对」去试，四个里错两个，而且**错的那两个不会报错**。判据要用**推理 token 数**这种客观指标，不能用「感觉快了」。

### A3 · 声音播完了，回答文字永远赖在鼠标边上

**现象**
语音念完之后，回复文字**一直显示在光标旁边，不消失、也关不掉**。把「回答文字多留一会儿」调到最短也没用。

**根因**
`BailianTTSClient.isPlaying` 由两部分组成：

```swift
var isPlaying: Bool {
    if audioPlayer?.isPlaying == true { return true }
    return isSpeakingChunkSequence          // ← 卡住的是这个
}
```

`isSpeakingChunkSequence` 在 `speakText` 里被置 `true`，而**全仓库唯一把它置回 `false` 的地方是 `stopPlayback()`**——它要等到**下一次** `speakText` 的开头才被调用。

于是**一次会话里第一段回答播完之后，`isPlaying` 就永远是 `true`**。而两个调用方都在轮询它：

- `scheduleAnswerBubbleClear` 的 `while isPlaying` 循环——**永远出不去，所以那段 linger 代码一次都没执行到**。用户把时间调多短都没用，因为**这个设置根本没被读到**；
- `scheduleTransientHideIfNeeded` 的 TTS 等待——同样出不去，**光标也不会淡出**（同一个根因的第二个症状）。

**为什么以前没暴露**：`scheduleTransientHideIfNeeded` 过去第一行就 `return`（见 A1），从来没跑到那个循环；轮询 `isPlaying` 是这次改造新加的。**一个改造前就存在的坏标志，是被新加的轮询变成致命问题的。**

**修法**
把整个分块播放序列收进一个 task，在最后一块结束、**且没有被取消**时把 `isSpeakingChunkSequence` 置回 `false`。取消时不置——否则会把新序列的播放状态误报成「说完了」。

（同时拆出 `waitUntilPlaybackFinishes()`：第一块是 `speakText` 自己启动的，对它来说「开始播」和「等它播完」是两个时刻，复用 `playAndWaitUntilFinished` 会把第一块从头重播一遍。）

**教训**
> **只由「下一次开始」复位的状态位，在「这一次结束」时永远不会复位。**
> 用轮询去等一个值之前，先确认**那个值真的会变回去**——尤其是它由别的对象维护、而这个字段只有一处写入点的时候。查一下「谁把它写回去」，比读轮询那一段更有用。

### A4 · 提示词教的是 `a+cmd`，解析器按 `cmd+a` 读

**现象**
`[PRESS:]` 这一族是这次改造新加的，功能看起来是好的：`[PRESS:return]` 能按、`[PRESS:cmd+a]` 能按。但**凡是模型自己写出来的快捷键，全部失败**——执行器回一句「不认识「a」这个修饰键，没有按」，用户看到的是「这个 AI 连全选都不会」。

**根因**
同一个协议的两半，在两个文件里各写了一遍，而且两遍不一样：

- 系统提示词那一行教模型写 `[PRESS:a+cmd]`（**键在前**）——这个写法是从方案文档里抄过来的；
- `splitKeyDescription` 按 macOS 的书写习惯实现，取**最后一个**组件当键、前面的当修饰键（即 `cmd+a` 的读法）。

于是模型照着提示词写 `a+cmd` → 解析成「键 = `cmd`，修饰键 = `a`」→ `a` 不在修饰键名单里 → 拒绝执行。

**为什么难发现**
两个用法各自单看都是对的（`return`、`cmd+a` 都能按），**错的只有「模型自己写出来的那一种」，也就是真实使用时唯一会出现的那一种**。而且它不是静默的——它报错，报的还是一句听起来很合理的「不认识这个键」，于是看起来像模型不会用工具，不像解析器写反了。

发现它的是**给解析器补的那组断言**（`[PRESS:a+cmd]` 和 `[PRESS:cmd+a]` 必须等价），不是手工试。手工试只会试出「能用」，因为人会顺手写自己习惯的那种顺序。

**修法**——两条一起改：

1. **不看位置，看名字**。哪个组件是修饰键由**它是不是修饰键名**决定（`cmd`/`command`/`⌘`/`shift`/`opt`…），剩下那个才是要按的键。这样两种顺序**都**对：`cmd+a` 和 `a+cmd` 是同一个请求——这正是「标签由语言模型写出来」所需要的容错。
2. **那张名单只留一份**，放在 `ActionTagParser.modifierFlag(named:)` 里，执行器调它。协议词汇归解析器，怎么发出按键事件归执行器。**两张表迟早会不一致**，而不一致的表现就是「这个快捷键没反应」。

提示词那一行也改成教 `[PRESS:cmd+a]`（修饰键在前），并写明「只写一个修饰键 = 按那个键本身」。

**教训**
> **协议的两半写在两个地方，就一定会漂。** 提示词说一套、解析器做一套，是本项目里第二类「静默的错」——比崩溃难查，因为它**只在模型真的用这个功能时才出现**。
>
> 判据要用**断言**，不能用**手工试**。人会顺着自己的习惯写，正好绕开那个不一致。

### A5 · 录音"录成功了"、时长也对，但每一个样本都是零

**现象**：`Wanna录音/*.wav` 有几十 KB 到 800KB、**时长完全正确**、格式正确、没有报错、没有崩溃，
而 `.jsonl` / `.txt` 是 **0 字节**。用户看到的是"录完了，但一个字都没有"。这个故障在本仓库
连续发生过十几次，**每一次都是用户在真实使用里撞出来的**（见 `15-录音采集与设备自愈.md`）。

**根因（两层，都不在我们代码里）：**

1. `AVAudioEngine.start()` 会**静默把输入重绑到系统聚合体**（官方 TN2091）—— "冷启动第一场好、
   说过话之后就不行"就是这一层。**AUHAL 修的是这一层。**
2. **别的软件把麦克风这个设备搞成了"对谁都只给数字零"**，之后连 `AudioOutputUnitStart` 都返回
   `kAudioHardwareNotRunningError`（四字符码 `'stop'`）。这一层**跨进程**（全新进程、`ffmpeg`
   都只拿到零），而且**在肇事者退出之后设备仍然卡着**。实测当时唯一 `IsRunningInput=true` 的
   是一个第三方听写软件。

**修法**：采集挂一条候选设备队列，看门狗发现"连续 90 块**精确全零**"就换下一个设备、
**同一场录音不断**；换不动时才收尾并点名是谁占着麦克风。见 `15-录音采集与设备自愈.md`。

**这个坑的教训（比修法本身重要）：**

- **"录到了"不等于"录到东西了"。** 时长、文件大小、无报错 —— 这三件事在全零的录音上**全都正常**。
  判据只能是**样本内容**（峰值），不能是"有没有数据"。
- **一个改动修好了一个真实存在的缺点，不等于它修好了眼前这个症状。** AUHAL 那次改动有探针、
  有对照、有数字，每一项都成立 —— 只是它量的是"引擎重绑设备"那一类，而当时撞上的是
  "设备被人搞死"。**两类故障的症状一模一样**，这才是当初归错因的原因。
- **一个算错的常数会一路漏到界面上。** `silentBufferAlarmThreshold` 的注释写"一块约 100ms"
  （实际 11ms），于是给用户看的文案写成"连续十秒没有任何声音"，而实际只过了 1.1 秒。
- **探针会过期，而过期的探针比没有探针更危险。** 旧探针比的是"声明的格式"，而 AUHAL 读回来的
  格式**永远是对的**（包括全零那几场），所以它一直报"全绿"。**判据失去区分度时它不会报错，
  它会报成功** —— 所以探针自己也要定期复核"它现在还能不能区分好坏"。

### A6 · 录音「根本起不来」：客户端格式跟着设备的声道数走

**现象**：按录音快捷键，什么都没有；日志里连续 `开始失败：拿不到麦克风输入（权限或设备问题）`，
紧跟一行 `AUHAL 失败④：客户端格式建不出来（48000.0Hz 3ch）`。用户的说法是「录音快捷键又无法使用了」。

**根因**：客户端格式是**跟着设备的声道数**建的，而设备在系统进入语音处理 / 聚合体状态时
**自己会从 1ch 变成 3ch / 9ch**（2026-09-26 同一天两种都量到过）。**3 声道的 `AVAudioFormat`
建不出来** —— 非交错格式要求一个合法的声道布局，1~2 声道能推断、3 声道不能 —— 于是直接抛错、
整场结束。

**修法**：客户端格式**恒为 1 声道**（我们本来只要一个声道：目标是 16kHz 单声道，多声道到了下游
那个 `AVAudioConverter` 里也一样要混成单声道），这样 1ch / 2ch / 3ch / 9ch 走同一段代码；
并且 `start()` 里也顺着候选设备队列往后试。见 `15-录音采集与设备自愈.md` 第四节「第五个失败面」。

**教训（比修法本身重要）：**

- **「起来了但给零」和「根本起不来」是两个失败面、两套代码路径。** 只给其中一个装了自愈，
  另一个照样能让用户说「又无法使用了」—— 而**用户看到的、说的都是同一句话**。
  所以下一次装自愈，要先问「这条路上还有哪些失败面」，而不是修好眼前这一个。
- **不要把设备的属性当作常量。** 同一个设备的 `MacBook Pro麦克风` 在同一天里报过 `1ch`、
  `3ch`、`9ch` —— 「设备的声道数」是**会变的状态**，代码里任何"跟着设备走"的假设都要先问
  「它变了会怎样」。

### A5 · 功能一个字都没少，只是**没有任何入口**：`connectToRole` 一个调用点都没有

**现象**（2026-09-26，在给卡片加「语音 / 视频」两个模式时撞上）
语音聊天页能打开、能选角色、能显示全部预设与音色，然而**永远连不上** —— 页头没有连接按钮，
侧栏也没有。空态那句引导语还写着「点它右边的「连接」开始」，指的是一个**已经不存在的按钮**。

**根因**
那个「连接」按钮原先住在**侧栏角色行的右端**（用户 2026-09-23 的第 5 条：「把连接按钮放在
左侧边角色卡片的右侧部分…鼠标移动距离会非常小。**不要放在右上角**」）。2026-09-26 的卡片化
改造把侧栏那一列换成了卡片区，角色列表只剩收起态那条 62pt 细栏 —— 按钮**连同它的调用点
一起被删干净了**，而 `VoiceChatController.connectToRole` 留在原地、没有任何人调用。

**判据（这次是它救的场）**
`grep -rn "connectToRole" *.swift | grep -v VoiceChatController.swift` → **空**。
一个"对外的方法"如果**一个外部调用点都没有**，它要么是死代码，要么是入口丢了。

**修法**
连接按钮搬到这一页自己的页头（那一排的最右端），一键三态（连接 / 连接中… / 挂断），
并把引导语改成指向这一页上的按钮。

**教训**
> **删掉一块界面时，必须问「它身上的入口，别处还有没有」。** 这类失败在编译期、在日志里、
> 在代码审阅里**全都是正常的**：类型存在、方法存在、界面渲染正确、没有报错。只有**真的去点**
> 才会发现。三个 agent 卡片、四个模式、全部预设都摆在那里，唯独缺那一颗按钮。
>
> 顺手的判据：**方法的调用点数，和它的可见性是一回事。** `func connectToRole` 是 internal，
> 那就应该有 internal 的调用点；`grep` 一跑就知道。

## B · 报错信息完全不指向真正的原因

### B1 · TTS 的两条路走错了会报「url 有问题」

**现象**
```
InvalidParameter: url error, please check url
```
URL 明明是对的。

**根因**
百炼的语音合成有**两条不同的路由**，模型族不同：

| 端点 | 模型族 | 请求体字段 | 音色举例 |
|---|---|---|---|
| `/api/v1/services/audio/tts/SpeechSynthesizer` | Qwen-Audio-TTS / CosyVoice | `input.{text, voice, format, sample_rate}` | `yuxiaoyun_v3.1` |
| `/api/v1/services/aigc/multimodal-generation/generation` | Qwen-TTS | `input.{text, voice, language_type}` | `Cherry` |

**音色名也是族专属的。** 把 Qwen-TTS 的 `Cherry` 丢给 Qwen-Audio-TTS 端点：

```
[cosyvoice:]Engine error [411]
```

**修法**
模型、音色、请求体字段、路径**四样必须一起动**。

**怎么判断一个模型属于哪一族**：用阿里云自己的 CLI（**官方工具，不是猜**）：

```bash
bl model code --model <模型名>
```

给 Qwen-Audio-TTS 吐 **`tts_v2` 的 websocket 示例**，给 Qwen-TTS 吐 **HTTP 示例**。

### B2 · 用户听到的永远是道歉

**现象**
不管问什么，Wanna 都念一句「抱歉，我这边出了点问题」。**视觉模型其实答得好好的。**

**根因**
`speakCreditsErrorFallback(failure:)` 在**视觉调用或 TTS 调用抛错**时念固定道歉。额度类失败（`AllocationQuota.FreeTierOnly`——免费额度用完，但控制台里「仅使用免费额度」还开着）走的正是这条路。

于是**账号问题伪装成了模型问题**。

**修法**
道歉保留（用户在等声音，什么都不说更糟），但同一个错误同时写进 `CompanionManager.lastErrorMessage`，**在面板里原样显示**。

**教训**
> **排查顺序：先查账号，再动管线。** 一句善意的兜底文案，能把一个五分钟能查清的问题变成两小时。

### B3 · `max_tokens` 超上限返回的是**空回答**，不是错误

**现象**
视觉模型返回 HTTP 200，但 `content` 是空的。看起来像「什么都没发生」。

**根因**
预算耗尽的返回就是 200 + 空内容。而**推理模型的思考也算在预算里**——预算小的时候，思考还没结束钱就花完了。

**修法**
视觉客户端把「200 但内容为空」**抛成异常**，而不是当作「没有回答」。

同时把上限钉在**最窄的服务商**上（32768，百炼的天花板），因为一个常量要同时在百炼和 DeepSeek 上合法。

### B4 · 开回声消除就起不来，报的是 `*outputNode, kAUInitialize`

**现象**

每条回复的**第一段语音都丢**，日志里两行连着出现：

```
⚠️ VoicePlaybackEngine: the engine would not start with voice processing on
   (Error Domain=com.apple.coreaudio.avfaudio Code=-10875 "(null)"
    UserInfo={failed call=err = PerformCommand(*outputNode, kAUInitialize, NULL, 0)})
   — retrying without echo cancellation
⚠️ Bailian TTS: could not play audio chunk 1/0: ... error -10875
```

报错指向**输出节点**，而问题出在**我们对一个和输出无关的节点少读了一行格式**。

**根因**

`setVoiceProcessingEnabled(true)` 会把**整个 IO**（输入**和**输出）改成 voice processing 的硬件格式——本机是 48 kHz / 输入 9 声道（改之前是 44.1 kHz / 1 声道）。

问题在于**主混音节点是什么时候被创建的**。`mainMixerNode` 是懒加载的：**读它的 `outputFormat` 才会实例化它，并把它接到输出节点上——而「接到输出节点」这一步才会创建输出的 audio unit**。

- 混音节点**在 VPIO 之前**被碰过 → 输出 audio unit 已经存在 → VPIO 配置一改，它跟着一起变成 48 kHz → `engine.start()` 成功。
- 混音节点**没被碰过** → 输出 audio unit 拖到 VPIO **之后**才懒加载 → 它按过期的 44.1 kHz 建起来，对着 48 kHz 的硬件初始化 → `kAUInitialize` 失败。

而原来的兜底逻辑（起不来就关掉 VPIO 重试）**也失败**——关掉 VPIO 会**第二次**重配 IO，混音节点又拿着一份已经不存在的格式。

**实测（2026-09-23，四个探针只差「VPIO 之前读了哪个节点的格式」这一行）**

| VPIO 之前读了什么 | VPIO 之后 mixer 格式 | `engine.start()` |
|---|---|---|
| 什么都不读 | 44100 Hz | **-10875** |
| 只读 `inputNode` | 44100 Hz | **-10875** |
| **只读 `mainMixerNode`** | **48000 Hz** | **OK** |
| 两个都读 | 48000 Hz | OK |

**注意**：读 `outputNode` **不算**（单独测过，仍然 -10875）。**必须是 `mainMixerNode`。**

**修法**

`VoicePlaybackEngine.warmUpMainMixerNode()`——就是那一行读，丢弃返回值：

```swift
private func warmUpMainMixerNode() {
    _ = engine.mainMixerNode.outputFormat(forBus: 0)
}
```

两处调用：① `setVoiceProcessingEnabled(true)` **之前**；② `connectGraphAndStart()` 里（兜底路径刚把 VPIO 关掉，IO 被重配了第二次，混音节点同样需要重新热身）。

修完日志变成一行、第一段不再丢：

```
🔊 VoicePlaybackEngine: engine started (..., echo cancellation ON (voice processing, ducking .min),
   mixer 48000 Hz / input 48000 Hz 9 ch)
```

**教训**

> **报错指向的节点，不一定是问题所在的节点。** `-10875` 说 `outputNode` 初始化失败，让人一直去查输出设备、采样率、蓝牙耳机——真正的原因是**另一个节点的初始化顺序**。查不出来的时候，做**只差一个变量的对照实验**：这次把「读哪个节点的格式」拆成四个变体跑一遍，一行就暴露了。

## C · 崩溃

### C1 · `deinit` 里调 `cancel()` → `EXC_BAD_ACCESS` in `_Block_release`

**现象**
**每次最后一段转写回来之后，进程立刻崩溃。** 崩溃点是 `_Block_release`，线程叫 `stateQueue`。看起来和转写逻辑毫无关系。

**根因**
每个转写 provider 都把自己可变状态串行化在一条私有 `stateQueue` 上，通过 `stateQueue.async { self… }` 访问。

**这个闭包隐式持有 `self`。** 所以从 `deinit` 里调 `cancel()`，等于去 **retain 一个引用计数已经归零的对象**。等这个排队的 block 稍后被释放，多出来的那一次 release 就 over-release 了 `self`。

**修法**
- `deinit` 里**只能直接给对象发消息**（比如关掉 websocket），**不能走 `stateQueue`**；
- 所有者必须在**每一条销毁路径**上显式调 `cancel()`。

**教训**
> 「从析构函数里调用一个异步方法」听起来无害，实际上是**在给一个已死的对象续命**。

### C2 · 设置窗口一关就崩，或者关了再也打不开

**现象**
两种，看少做了哪一步：关窗时崩，或者窗口关了之后再也打不开。

**根因**
`NSWindowController` 需要**同时**满足两件事：

1. 被一个**强引用**持有（这里是 `CompanionManager`）；
2. `isReleasedWhenClosed = false`。

**少任何一个都会坏**，而且坏法不同。

## D · 界面

### D1 · 设置窗口能打开，但**打不了字**

**现象**
窗口正常显示，点进输入框，**敲键盘毫无反应**。看起来像表单坏了。

**根因**
这是个 `LSUIElement` 应用，**自己永远不会是活跃应用**。不先激活，窗口**能出现但永远成不了 key window**。而**非 key 窗口的文本框会静默吞掉每一次按键**。

**修法**
`presentWindow` 里先 `NSApp.activate()`。

**教训**
> 「窗口显示了」和「窗口能用」是两件事。AppKit 里这个区别经常是沉默的。

### D2 · 分段选择器的标签撑破卡片

**现象**
离屏渲染出来一看，「只在对话时出现」这种标签换行了，把整张卡撑破。

**根因**
那是并排的分段按钮，宽度是内容决定的，长标签会换行。

**修法**
`displayName` 压到 **4 个字以内**（「一直显示 / 对话时 / 指位置时」），**含义交给那一行的描述文字去讲**。

**教训**
> 界面上的短标签和代码里的 `case` 名是**两种不同的东西**，不要指望一个名字同时干好两件事。

### D3 · 刘海静息状态漏出一团光晕：`clipped()` 的位置决定了它裁谁

**现象**
2026-09-22 给刘海胶囊换成「左右翼」布局后，**静息状态**（应该什么都不画）在刘海右侧永远漏出一团灰白光晕，杀掉 Wanna 才消失。所有活动相位的截图验证也全被它干扰。

**根因**
翼视图内部的 `ZStack` 里有一个**定尺寸**的 `RadialGradient`（88×40）。`.clipped()` 写在翼视图**内部**，裁的是 ZStack 的**自然尺寸**（被那个定尺寸子视图撑到 88 宽），不是外面动画的宽度；而外层 `.frame(width: isActive ? 112 : 0)` **不裁剪**——SwiftUI 的 frame 默认只是包一层，内容照样画出来。于是 idle 时宽度是 0，88×40 的光晕却从胶囊边缘后面探了出来。

**修法**
`.clipped()` 移到**调用点**、放在动画宽度 `.frame` 的**外面**：`.frame(width:…).clipped()`。内层那个 `.clipped()` 留着无害。

**教训**
> SwiftUI 里 `.frame(width: 0)` 是「给你一个 0 宽的框」，不是「裁成 0 宽」。要让宽度动画变成抽屉效果，裁剪必须套在 frame 外面；裁剪写在内层时，它跟随的是内容的自然尺寸，而定尺寸子视图会把它撑大。

### D4 · `Menu` label 里的图按素材原始尺寸炸开：约束压不住，只能挪走

**现象**
2026-09-22，展开面板顶栏的会话胶囊里放了一个 20pt 的 `MascotAvatarDisc`，结果图按素材原始 **256pt** 渲染，把整条顶栏撑到 255pt 高——同一组件在侧栏 38pt 渲染完全正常。

**根因**
macOS 的 `Menu` 对自定义 label 的布局约束在 AppKit 菜单渲染路径上不完整生效（机制是推测；观测事实是确凿的）。在图上加 `overlay + clipShape + frame(20)` 三重包裹**实测无效**，图照样炸。

**修法**
把图从 `Menu` label 里整个移除（`NotchSheetRootView.sessionChip` 的 label 只留 `Text` + 箭头），原位留注释禁止再放。完整证据链和修法选择顺序见 [`13-顽固问题排查法.md`](13-顽固问题排查法.md)。

**教训**
> 同一组件在别处正常、在某个宿主里炸开，问题在宿主不在组件。敌意宿主里约束不生效时，**挪走优于原地加约束**——第一次原地修失败时就该问「我在改正确的层吗」，第二次就该停手取证。

### D5 · 把参考实现的 `transform` / `clip-path` 动画移植成「逐帧改窗口 frame」

**现象**（2026-09-23）
用户按参考页 `刘海屏弹出窗口_12种动画对比.html` 的 **01 中心缩放** 提的展开效果，落地后被打回：「你刚才的效果比之前还要卡顿，窗口在展开的时候比之前更卡顿……现在是从左到右展开，展开过程中非常卡顿」。同时报了一个更细的症状：**同一行文字在展开过程中从十个字变成十一个字**——宽度一边长一边重排。

**根因**
参考页 12 种窗口动画**全部是 `transform` 或 `clip-path`，没有一种改元素尺寸**——这不是巧合，这两类都是**合成器属性**，浏览器每帧只需 GPU 重画，不触发布局（layout）也不触发重绘文字。把这个动画逐帧移植成 `NSWindow.setFrame` 是**范畴错误**：窗口每帧重建绘制表面、`NSHostingView` 每帧对整张 810×940 的面板做**变宽重排**、文字每帧重算换行。卡顿和「十个字变十一个字」是同一个错误的两个面，不是两个问题。

**修法**
用参考页自己的 **02 幕布垂落**（`winCurtain`：`clip-path: inset(… 100% …)` → `inset(… 0 …)`，`.43s ease-out`）——它本来就是「宽度不动、内容从上往下长出来」的形状，正是用户要的。窗口在**一次** `setFrame` 里到位（x / 宽度 / 顶边从第 0 帧起就是最终值），动感全部交给内容层上的一个 `CALayer` 遮罩：`bounds.height` 0 → H 与 `position.y` topEdgeY → H/2 在同一个 `CAAnimationGroup` 里插值，曲线 `CAMediaTimingFunction(controlPoints: 0,0,0.58,1)`，**主线程每帧零工作**。宽度恒定之后，换行从第一帧到最后一帧**不可能**变——这是结构性保证，不是把参数调顺了。

**教训**
> **移植参考实现前，先确认它动画的是哪个属性。** 只动 `transform` / `opacity` / `clip-path` / `filter` 的动画，搬到原生窗口上对应的是**图层或遮罩**，不是窗口 frame；把合成器动画翻译成布局动画（改 frame、改 constraint、改 `frame(width:)`），代价是每帧全量重排——在网页上是掉帧，在 AppKit 里还多一项「窗口每帧重建绘制表面」。
>
> **「同一个视觉变化既改尺寸又重排内容」的需求，答案是不改尺寸。** 用户的原始要求是「宽度一开始就固定，然后从上到下展开」——把宽度**冻住**本身就消灭了重排，遮罩只是让「从上到下」看得见。先问「哪个量可以不动」，往往比调动画曲线有效得多。
>
> **顺带一条排查纪律**：这次「AI 回复变慢」（0.1 s → 3 s）和「扬声器被调小」两条附带指控，实测都不成立——回退后空闲 CPU 仍是 7.3–8.2%（与回退前一致，且静息路径的 diff 为空），扬声器 `output volume:50 / muted:false`。**把用户报告的症状逐条量一遍再回话**，不要因为「同一次改动」就默认它们同源。

### D6 · 卡片每来一个字，就把整篇文字重排一遍——而且是**三遍**

**现象**（2026-09-23）
D5 修完展开动画之后，用户把问题重新定位到了**另一个组件**上：鼠标右侧那张 AI 回复卡片，「在从上到下渲染的过程中还是出现了很大的卡顿，**尤其是最后一行的时候**会卡顿」，用词是「极其严重」。注意「最后一行」这个限定词——同一个动作，开头顺、结尾卡。

**根因**
`CardTextFlowLayout` 是逐字排版的：一个字一个 `Text` 子视图，装进一个自定义 `Layout` 里按行拼。而**每个子视图的尺寸是现量现用的**，一次布局里量了三遍：

1. `sizeThatFits` 里的 `computeRows` 把 N 个字全量一遍；
2. `placeSubviews` 里**又调了一次 `computeRows`**，于是 N 个字再量一遍（注释写着「defensively rather than trust call ordering」）；
3. 摆放循环里**每个字还单独量第三遍**（`subviews[unitIndex].sizeThatFits(.unspecified)`）。

每次 `Text.sizeThatFits` 都是一次全新的 CoreText 解析 + 换行计算。而回复文本**每来一个流式字符就重新发布一次**，所以「一个字符的代价」是 `3 × N`——**N 是回复长度**。这就解释了用户那个看起来矛盾的描述：短回复不卡，长回复卡，**越到后面（N 越大）越卡**，所以「最后一行」最明显。`Layout.Cache` 是有的，但 `updateCache` 是空的，一次都没被用过。

**修法**
测量结果放进一个**由视图持有**的 `CardTextUnitSizeCache`（`@State`），`Layout` 只读它：

- **增量**：`CardTextUnitBuilder` 是从左往右扫、遇到不同类别的字符才收尾一个 unit，所以「追加一个字符」只可能**延长最后一个 unit** 或**新起一个**——它前面的任何一个 unit 都**不可能**变。于是复用除最后一个以外的全部缓存尺寸即可；最后一个无条件重量，覆盖「`hell` → `hello` 是前缀但不是同一个 unit」这一种前缀判据漏掉的情况。
- **量一次**：`sizeThatFits` 和 `placeSubviews` 都改成「量一次（只有新的那几个）+ 纯算术重新分行」。摆放时不再逐字测量。
- 缓存放在**视图**里而不是 `Layout.Cache` 里，因为文本一变 `Layout` 值就重建，而「SwiftUI 在 layout 值变化后怎么处置那个 cache」不该拿来当正确性的地基。缓存失效只会退化成「全量重测」——也就是旧行为，不会算错。

一个流式字符的代价从 `3 × N` 变成 **1 次测量**。

**教训**
> **「越到后面越卡」几乎总是指向「每来一个单位就把前面全部重做一遍」。** 卡顿是均匀的，通常只是量不够；卡顿**随长度增长**，那是一个 O(N)（甚至 3N）被放进了 O(1) 的位置。收到这类描述时，第一件事是去找那个「重做前面全部」的循环，而不是去调动画或减视图数量。
>
> **性能注释和性能代码一样会骗人。** 那句 `defensively rather than trust call ordering` 读起来是严谨，实际是让每次布局多量一整遍——写这种「防御性重算」之前，先问一句「重算的代价是谁在付」。

### D7 · 流式结束时，把卡片上的文本换成了「另一份」文本

**现象**（2026-09-23）
用户报了两次同一个症状：「**第一行文字在渲染时还是会出现字数变化：渲染时是八个字，渲染完之后变成九个字、七个字，你还是没有固定**」。即：一行文字，在回复流式渲染的过程中字数会**回退**——八个字变成九个，最后定格在七个。

**根因**
两个不同来源的文本被先后喂给了同一张卡片，而**它们是两个不同的字符串**：

1. 流式期间喂的是**原始回复**，里面带着 `[POINT:320,599:7]` 这类动作标签（十几到二十几个字符）；
2. 流式结束、回复被解析并念出来之后，卡片被**换成剥掉标签的文本**。

剥掉两个字符就是**换了个换行位置**。用户看到的「八个字 → 九个 → 七个」，就是「一边长一边重排」加上最后那次**缩短**。

**修法**
让「卡片显示的文本」成为**回复到目前为止的纯函数**：流式期间就喂**剥过标签的**文本（`ActionTagParser.speakableTextFromStreamedReply`，和喂给语音、喂给回声过滤的是同一个函数），流式结束时再把**同一个函数作用在完整回复上的结果**赋回去——两者**按构造相等**，于是收尾那次赋值是**逐字节的空操作**，重排不可能发生。

两处细节：收尾时**不能**换成 `finalSpokenText`。它走的是**另一个**剥离函数（`spokenTextByRemoving`，会 trim、且只删「已认领的区间」），两者可以差一两个字——这正是这次「缩短一个字符」的来源。另外，动作标签曾经是「故意给用户看的」（早期只有 `[POINT:]`、指路纯视觉，所以留着无妨），接了「操作电脑」之后标签就是执行记录，留在屏幕上既没意义又制造重排。

**教训**
> **同一个位置上先后出现的两份文本，必须由同一个函数产出，否则「换文本」就是「换布局」。** 这次的两个函数都「看起来在做同一件事」（把标签去掉），但它们 trim 与否、删哪些区间不同——**同一个意图的两份实现，就是两次重排**。收尾赋值前先问：这个字符串和屏幕上那个，是同一个字符串吗？
>
> 这条和 D5 是同一条原则在两个组件上的两次落地：**把几何钉死在第一帧，让重排结构性地不可能**，而不是「调一下让它不那么明显」。

### D8 · `fixedSize` 挂在 `ScrollView` 上：内容画到屏幕外面 1179pt

**现象**
音色面板里点一下别的分类（比如从「全双工语音」切到「流式」），**整个面板像炸开一样糊满全屏**，页头那一排按钮被盖住。用户的原话：「点击下拉菜单的其他按钮后，画面直接完全乱码，排版非常混乱」。

**根因**
面板里写的是：

```swift
ScrollView { 内容 }
    .fixedSize(horizontal: false, vertical: true)   // ①
    .frame(maxHeight: 448)                          // ②
```

① 让 `ScrollView` 的 **frame 等于内容的自然高度**（流式那一类 68 个音色、两列共 34 行，≈1621pt）；② 只把**外框**定成 448 —— 它**既不裁剪、也不改子视图的尺寸**，于是内容以外框中心为准上下各溢出八百多点。

**实测**（AX 树，点完「流式」之后）：音色格子的 y 一直排到 **−1179**，而页头按钮在 y=30 —— 整排被盖住。两列内容相加 1621pt，正好对上溢出量。

**修法**
给 `ScrollView` 一个**确定的高度**：量内容（内容 `.background` 里挂 `GeometryReader` 上报 preference）、封顶、夹进列高。它自己就会滚动，也就没有溢出这回事。再加一道 `.clipShape` 做保险 —— 让「画到轮廓之外」在结构上不可能。

**教训**
> **`fixedSize` 是「别管外面给我多少，我要我的理想尺寸」，而 `frame(maxHeight:)` 是「外框就这么大」——两个都不是「裁剪」。** 想限制一个滚动区的高度，正确做法是**给它一个确定的高度**，不是给它一个更小的外框。而这又需要先知道内容多高 —— 所以「内容多高」必须是**量出来的**，不能猜：同一个面板，全双工类量到 264，流式类量到 3075。

### D9 · 拖拽手柄只跟手一半：增益正好是 1/2

**现象**
按住面板底缘的缩放条往下拖，**窗口跟不上鼠标**，还闪跳。用户的原话：「鼠标已经移动到上面了，窗口还没有移动到上面，鼠标和窗口底部边缘，无法同时向上移动，体验极差」。

**根因**
手柄就在**它自己要改的那条边**上。它的位移来自 `DragGesture.translation`，而 `.local` 坐标空间是**相对手柄自己**的 —— 手柄跟着窗口往下走多少，translation 就少多少。设光标位移 Δ、窗口跟着长 Δ′：

```
Δ′ = Δ − Δ′   ⟹   Δ′ = Δ / 2
```

**稳态增益恰好 1/2**（一个单位负反馈）。

**实测**（脚本真拖 100pt，读回落的 UserDefaults 比例）：782.49 → 832.49，即 **+50**，和 1/2 分毫不差。修好之后再拖 −400pt：**−399**，符合「常数偏移 ~1pt、增益 1」而不是残留的增益误差。

**修法**
改读 `NSEvent.mouseLocation` 的**绝对屏幕坐标**（AppKit 全局坐标，任何窗口 frame 都动不了它），抓手偏移只在拖拽第一帧记一次。顺带把「拖动中每帧写一次 UserDefaults」拆成「拖动只改内存值、松手才落盘」。

**教训**
> **让一个视图去改「它自己所在的那个几何」时，不要用相对它自己的位移量。** 局部坐标空间会跟着被改的东西一起动，于是你量到的是「差值的一半」——不报错、不崩溃，只是慢一半。判据很简单：**如果被拖的东西因为这次拖拽而移动，就用绝对坐标**。
>
> 这条和 D5、D8 是同一类错误的三个面：**几何的来源必须只有一个，而且不能是会被自己改变的那个。**

### D10 · 未解决：`ScrollView` 收不到滚轮事件（`.overlay` 里）

**现象**
音色面板里的音色列表**滚不动**。因为面板现在被裁到 448pt，一屏只看得到 6 行 —— 「流式」那一类有 68 个音色，**其余 60 多个够不着**。

**已经量到的**（探针 + 对照实验，都不是推测）
- 探针打在 `onPreferenceChange` 里：`measured content height 3075.0, cap 448.0`（流式）、`264.0`（全双工）。也就是说**内容 3075、滚动区 448，确实该能滚**，布局不是问题。
- 对照组：**同一套合成滚轮事件**，在「对话」页的滚动区**推得动内容**（元素 y 整体下移 ~200）。所以事件投递本身是通的，工具没问题。
- 截图复核过：不是 AX 树陈旧，是真的没滚。

**已经排除的四条路**（每条都编译、重启、实测过一次）
1. `.overlay` + `.offset` → 改成 `.overlay` + `.padding`（怀疑 `.offset` 是绘制期位移、AppKit 的 `hitTest` 不认）：**还是滚不动**。
2. 去掉面板上的 `.contentShape` + `.onTapGesture`（怀疑「盖在上面的视图吃掉了滚动」——搜索结果第一条就是这个症状）：**还是滚不动**。
3. 给滚动内容加 `.fixedSize(horizontal: false, vertical: true)`（怀疑内容被压成了 frame 高度、于是「正好一屏」）：**还是滚不动**（但这一句本身是对的，留下了）。
4. `.overlay` → `ZStack` 同级孩子（怀疑 overlay 的合成层不参与 AppKit 命中）：**还是滚不动**（但顺带消掉了分类行与滚动区之间一道 ~73pt 的空白，留下了）。

**还剩下的怀疑方向**（未验证，写在这里给下一个人）
- 面板窗口（`NotchPanel`）与那块全屏透明光标浮层窗口的**窗口层级 / 滚动事件路由**关系。点击能穿过浮层落到面板上，不代表滚轮也能。
- SwiftUI 在 macOS 上把 `ScrollView` 的滚轮处理挂在 **hosting view** 上、而不是那个 `NSScrollView` 上；如果 hosting view 不是 key window 的第一个响应者，事件可能根本不下发。
- 用一圈最小复现（一个空白窗口 + 一个 `.overlay` 里的 `ScrollView`）把「是不是 overlay 的通病」和「是不是本项目的窗口配置」分开。

**教训**
> **「两次没解决就停手」这条规则，第四次、第五次也算数。** 这篇记下来的价值不是答案，是**把已经排除的路写清楚**：四条路各花了一次编译+重启，下一个人可以从第 5 条开始，而不是从第 1 条重走。
>
> 另一个可以带走的判据：**「本该能滚」要用数字证明**（内容 3075 > 视口 448），**「事件能到」要用对照实验证明**（同一套事件在另一个滚动区上生效）。这两条都有数之后，问题就不再是「布局算错了」而是「事件路由」，搜索方向完全不同。

### D12 · 「持续监听 30 秒」被播报时长吃光：窗口在用户开口那一刻关闭

**现象**（用户 2026-09-25，Ask 页面连续追问）
打断 → 提问 → 回答，前两轮都正常；**第三、四轮开始，说完话等两秒没有任何反应**。用户自己的猜测是「30 秒的计时还是按第一次按键算的」。

**日志给出的决定性证据**（`开发经验/运行日志/wanna-音效-001950.log`）

```
🎙️ continuous listening detected speech (mic level, recent mic peak 0.633, transcript: "。")   ← 用户开始问第 4 个问题
🔊 Streaming speech: playback loop exited (stopPlayback())                                    ← 打断让播报停下
📸 Companion: pre-captured 1 screen(s) — follow-up speech detected
🎙️ continuous listening window closing (listening window expired); playback idle              ← 同一瞬间窗口到期
🎙️ continuous listening ended
```

那句追问**已经被听到**（有 VAD 检测、有预截图），但**没有** `follow-up question from continuous listening: …` —— 说到一半，整条会话被拆掉了。所以不是"听不到"，是"听到的瞬间被掐断"。

**根因**：窗口的截止时间是**从起播算**的（`scheduleContinuousListeningWindowExpiry` 在播报开始时 armed），而到点之后还有一句"等播报播完再关"：

```swift
while Date() < expiryDeadline { … }          // ① 30 秒从起播开始算
while self.bailianTTSClient.isPlaying { … }  // ② 到点后等播报结束
self.endContinuousListeningWindow(...)        // ③ 播报一停就关
```

长回答（那一轮 5 段以上、播报几十秒）会把 ① 的 30 秒**在播报期间耗尽**，于是 ② 只剩"等播报停"这一个条件——而**打断正是让播报停下的那个动作**。用户一打断，窗口当场关闭。回答越长越必然踩到，这解释了"前两轮没事、后面才坏"。

**修法**：把窗口的语义改成用户要的那句话 —— **回复结束之后 30 秒**（也是「听」页面那一项的字面意思）：

```swift
while true {
    while Date() < expiryDeadline { … }                       // 等到期
    if isPlaying { deadline = now + seconds; continue }       // 还在播报 → 推到播报之后重新起算
    if utterancePending { deadline = now + seconds; continue }// 追问还在说 → 同样推后
    endContinuousListeningWindow(reason: "listening window expired"); return
}
```

两条继续条件都打了日志，所以下次再看日志能直接看到"推迟了几次"。

**教训**
> **「计时起点」写错，症状会伪装成"听不见"。** 用户报的是"它不回复我"，而代码里麦克风一直开着、识别也一直在跑 —— 死的是**提交**那一步（窗口在提交前被拆）。凡"说了没反应"，先查**这一轮的会话是不是还活着**，再查识别。
>
> 另一条：这个 bug 活下来的原因是**没有任何一行日志记录"窗口重新计时"**。一个跨多轮的状态机，它的每次状态变更都该有日志 —— 这次的修复顺带补上了。

### D11 · 一次性脚本把源文件写成了 23MB：`replace("", …)` 与「可精确重建的损坏」

**现象**
用一次性 Python 脚本改 `VoiceChatController.swift`（把 `apply` 改成委托纯函数），脚本里的切片取到了**空串**——`str.replace("", new)` 的语义是把 `new` **插进每个字符之间**。文件变成 23MB / 43 万行 / 只剩 95 个唯一行。

**为什么还能完整救回（不是运气，是损坏模式可逆）**
`replace("", new)` 的结果结构是：`new + c₀ + new + c₁ + …`——**原文件的每一个字符都还在**，只是被插入块隔开。量出插入块长 L（插入文本第二次出现的位置 − 1），按固定步长 `(i+1)*(L+1) − 1` 把每个块后面的那一个字符取出来，拼接即得原文。还原出的文件 65,702 字节、以 `import Foundation` 开头、本轮新增的 16 个符号全部在场、`git diff --stat` 与实际改动量相符（+292 −8）、类型检查与构建通过。

**修法（防再犯）**
> **不在源文件上做一次性脚本的字符串手术。** 同样的编辑用 Edit 工具做：它要求 `old_string` 精确匹配且唯一，取到空串会**直接报错**而不是静默地把每个字符缝一遍。脚本只用于**批量、无差异**的机械替换，且写完先跑 `wc -l` / `git diff --stat` 做大小 sanity check——23MB 的 diff 是一眼就该拦下的。

**教训**
> **静默失败的天花板不是"什么都不做"，是"把一切重写"。** `replace("", …)` 不报错、不崩溃，返回值看起来还是一次成功的调用。凡是"改完不看结果大小"的写法，都欠一道数值核对。

## E · 配置与数据

### E1 · 加一个 `Bool` 属性，让**所有旧配置文件读不出来**

**现象**
加了新设置之后，老配置文件直接解码失败。

**根因**
合成的 `Codable` **遇到缺键会抛错**。

**修法**
写成 `Bool?`（`nil` 读作 `false`），或者 `decodeIfPresent(...) ?? 默认值`。**默认值取「今天的行为」**，这样老用户升级后看不到任何变化。

### E2 · 原子写入的文件权限是 `0644`

**现象**
明明写了「只给本人可读」，实际权限还是 `0644`。

**根因**
`.atomic` 写入落地时跟随 umask。

**修法**
**写完之后再改一次**：

```swift
try data.write(to: fileURL, options: .atomic)
try FileManager.default.setAttributes([.posixPermissions: 0o600], ofItemAtPath: fileURL.path)
```

**只做第一步等于没做。**

### E3 · 流式识别的 `URLSession` 不能每次新建

**现象**
连续快速重连几次之后开始报 `Socket is not connected`。

**根因**
**每次识别新建一个 `URLSession` 再 invalidate，会破坏 OS 的连接池。**

**修法**
一把长命的 `URLSession`，**归 provider 所有**，所有会话共用。

### E4 · 只把字段加进 `CodingKeys`、忘了 `init(from:)`：**写得进、读不出**

**现象**（2026-09-26，给每张卡片存"用哪种模式"时）
点一下模式按钮，界面立刻生效；`AppSettings.json` 里也确实写进去了 ——
**然后重启，全变回默认**。用户会看到的就是「我改了，重启就没了」。

**根因**
`AppSettings` 的编码器是**合成的**，解码器是**手写的**（`nonisolated extension` 里的
`init(from:)`，为的是老文件缺字段时不整个 throw）。所以加一个字段是**两处**：

```swift
// ① CodingKeys 里加一个 case      ← 我只做了这一处
case cardChatModeRawValues
// ② init(from:) 里加一行 decodeIfPresent  ← 漏了
cardChatModeRawValues = try container.decodeIfPresent([String: String].self, forKey: …)
```

只做 ① 的结果是：**合成编码器会写出它**（所以磁盘上有），**手写解码器不认识它**
（所以读回来永远是 nil 或空表）。整个功能"看起来实现了"，只在重启后失效。

**判据（一行日志）**
`AppSettingsStore` 的读盘路径原先是一句 `try?` —— 解不出来就静默回落成"全默认"，
**一行日志都不留**。加了两行之后当场现形：

```
🎛 [settings] 读盘成功 模式表=[:]        ← 磁盘上明明有两个键
🎛 [mode] card=D25C2B40 → voice          ← 写是成功的
```

**修法**
补上 ②。同时把 `try?` 换成 `do/catch` **并打一行 `❌ [settings] 解不出来，整份回落默认`** ——
这条静默路径本来就是"设置看起来没保存"的另一个成因，值得永远留一行。

**教训**
> **手写解码器 + 合成编码器的组合，会让"新字段"变成一处静默的单边接线。** 同一个 struct
> 有两个 CodingKeys 消费方，只喂其中一个不会报错、不会崩、编译通过、磁盘上还有值 ——
> 唯一的症状是"重启后失效"。
>
> **判据必须落在"读"这一侧。** 这次是靠「写一行、读一行」两条日志分出来的：写成功而读为空，
> 结论只有一个。任何"保存了但没生效"的问题，都该先把这条链路的两端各打一行。


### E5 · 每张卡片各记各的模式，而**角色是共享的**：语音卡片跑着视频那一组

**现象**（2026-09-26，给卡片加「通话」按钮时撞上）
卡片处于**语音**模式（模式条上「语音」打着勾），而下面的全双工那一行显示的是
**全模态 3.8 Flash**、音色是 **Tina** —— 那是**视频**那一组的预设。也就是说这一场
按"语音聊天"起，却拿着视频那套模型和音色。

**根因（两层，缺一不可）**

1. **两个东西的"作用域"不一样**：`CardChatMode` 是**每张卡片各记各的**（用户要求两张卡片
   默认值不同），而 `VoiceChatRole.chatChannel` 是**角色上的字段、角色是共享的**。
   同一张角色在另一张卡片上被设成视频，回到这张语音卡片就带着视频的 `presetID`。
   —— 于是"模式说语音、预设来自视频"，而**两者都不是错的**，只是没人负责让它们一致。

2. **修它的判据原先取错了对象**：同步那一句写的是
   `guard controller.selectedChannel != channel` —— 比较的是**控制器内存里**那个值，
   而它的默认值本来就是 `.voice`。卡片是语音、角色里是视频时，这个 guard 恰好为假，
   于是"修不匹配"的那一步**永远不会执行**。这就是静默失败最典型的样子：代码在跑、
   判断也在做，只是判据恒真/恒假。

**修法**
`VoiceChatController.alignChannelForCardMode(_:)`：**拿角色里存的值当判据**
（`currentRole.chatChannel != channel.rawValue` 才写），并且只在确实不同时才调
`selectChannel` —— 那个函数会清掉用户选的预设、回落到该组默认预设，无条件调它等于
每次进这一页都把人家选好的预设抹掉一次。

**教训**
> **两个状态一个共享、一个不共享时，"同步"必须说清以谁为准。** 这里以**卡片为准**
>（模式是新加的那一侧，用户明确按卡片表达意图），角色是被改写的那一侧。
>
> **判据不能取"内存里看起来像对的那个值"。** 默认值恰好等于期望值时，守卫会静默失效 ——
> 这一类 bug 不会报错、不会崩、日志干净，只会让**修不匹配的代码永远不跑**。
> 判据要取**真正持有分歧的那一份数据**（这里是角色的持久化字段）。

## F · 权限与构建

### F1 · 每改一次代码就要重新授权三次

**现象**
录屏、辅助功能、麦克风，每次重建之后全部重置。

**根因**
**ad-hoc 签名的 designated requirement 是 `cdhash`**，也就是**二进制哈希**。重建 = 哈希变 = TCC 眼里的全新 App。

**修法**
用证书签名。requirement 变成按**证书**认，同一张证书签的每一版都是同一个 App。

## G · 开发工具本身的坑

### G1 · 离屏渲染探针的三个失败尝试

想不启动 App 就看到界面长什么样，试了三条路，**前两条都是死的**：

| 尝试 | 结果 |
|---|---|
| `window.setContentSize(...)` 把窗口撑高 | ❌ **无效**。SwiftUI 用约束把 hosting view 的 frame 钉死了，下一轮布局就被拉回去 |
| `firstScrollView(in:)` 找到 ScrollView 再滚到底 | ❌ **找不到**。这个 SwiftUI 版本的 `ScrollView` **不是公开的 `NSScrollView` 子类** |
| `ImageRenderer(content: 页面视图)` | ❌ **渲染出一张纯黑图**。`ImageRenderer` 画不了 NSView 支撑的内容，而 `ScrollView` 正是 |

**能走通的那条**：把 hosting view 的约束拆掉，再改它的 frame。

```swift
NSLayoutConstraint.deactivate(hostingView.constraints)
NSLayoutConstraint.deactivate(hostingView.superview?.constraints ?? [])
hostingView.translatesAutoresizingMaskIntoConstraints = true
hostingView.frame = NSRect(x: 0, y: 0, width: 780, height: 1100)
```

### G2 · 只看一张被裁切的渲染图，会去修一个不存在的问题

**根因**
**那一行是被窗口底边垂直裁切了**，不是水平溢出。把窗口撑到 1100 点再看，三行的右边缘**完全对齐**。

**教训**
> 验证布局的时候，**一定要看到完整的那张卡**。半张图会骗人。

### G4 · 展开面板透明：`withAnimation` 的事务值送达不了同帧插入的视图（间歇性）

**现象**
刘海胶囊展开后面板**透明**，透出桌面。加调试填充才发现：`HomeSpaceSheetShape` 有时画在**静息尺寸**（`expansionProgress` 在渲染侧是 0），有时画满——同一个二进制，多跑几轮结果不同。而 `didSet` 探针证明写入侧**每次都写了 0→1、且没有任何回写**。

**根因**
`expand()` 在**同一帧**里做三件事：`isExpanded = true`（切换到展开视图）、`withAnimation { expansionProgress = 1 }`、窗口 `setFrame` 动画。展开视图与写入**同帧插入**时，`withAnimation` 事务里的终止值**不保证送达新插入的 shape**——新视图按什么值渲染是竞态。写入侧 didSet 读回 1.0 与渲染侧读到 0 并存，就是因为两者根本不是同一条读路径。

**修法**
动画挂到**视图侧**：`.animation(.easeInOut(duration: NotchSupport.expansionAnimationDuration), value: panelModel.expansionProgress)` 挂在展开视图上，写入处不再包 `withAnimation`。视图读到什么值就画什么值，渲染变确定。

**教训**
> 给「同帧插入的视图」传递动画终止值，靠写入侧的 `withAnimation` 是竞态；动画挂视图侧、以值为键，才是确定的。

### G5 · 用户正在实时使用 App 时，别跑鼠标/按键探测

**现象**
用 `CGWarpMouseCursorPosition` 把光标按到刘海上做悬停展开的自动验证，连续几轮截图里面板**都没展开**——一轮里胶囊显示着说话波形，另一轮伴侣正在执行 `[TYPE:…]` 替用户往备忘录打字。

**根因**
用户**就坐在电脑前实时使用 Wanna**：他真实的鼠标移动立刻取消了我制造的悬停驻留；我 `osascript` 发的 Esc 会落到**他当时最前台的 App**（可能是浏览器）上。探测循环每次都是对用户会话的一次劫持。

**教训**

### G6 · 径向光晕被裁切 mid-fade，渲染成硬边矩形色块

**现象**（2026-09-22，刘海活动带右翼的光晕）
用户反馈「原版的颜色只在右边，你现在是左右都有」。逐项重测（合成 ctrl+option 按住）才发现三处偏差：状态词**右对齐贴着刘海**（"Listening" 止于刘海左缘前 ~5pt）、翼宽 ~78/87（我是 112/92）、右翼光晕是柔和渐隐。而我的光晕在截图里是一块**紫色矩形硬边色块**。

**根因**
`RadialGradient(colors:center:startRadius:2, endRadius:46).frame(width:88, height:40)`：endRadius 46 大于半宽 44、40pt 的 frame 又高于翼的可见高度——渐变在自己的 frame 边缘**还没有衰减到 0**，翼的 `.clipped()` 把它拦腰切断，切出的直线就是那块矩形的边。渐变没画错，是**衰减没在边界内完成**。

**修法**
换成 `EllipticalGradient`，它的半径是**单位空间的分数**（`startRadiusFraction`/`endRadiusFraction`，0.5 = frame 边缘），让衰减正好在边界处归零，裁不裁都一样。两个附带教训：① SwiftUI 这个初始化器的真实标签是 `startRadiusFraction`/`endRadiusFraction`，凭记忆写 `startRadius`/`endRadius` 会匹配到另一个重载然后报 extra arguments；② 「颜色左右都有」这类视觉描述，先拿实测数据（翼宽、对齐、渐变形状），别按字面猜。

**教训**
> 渐变装饰被容器裁切前，先确认它的衰减在**边界内**完成；`RadialGradient` 的绝对半径不会自己适应 frame，`EllipticalGradient` 的单位分数会。

### G7 · 纯黑面板在暗背景上整块隐形——圆角没丢，是对比度丢了

**现象**（2026-09-22）
用户报告「展开时右下角没有圆角」。三轮截图证明圆角**几何上一直是圆的**；问题是深色壁纸/暗色窗口前面，纯黑（#000000）的面板和纯黑的背景之间没有任何灰阶差，整个轮廓——包括下面两个圆角——一起隐形。

**根因**
静息胶囊必须纯黑才能和硬件刘海融为一体，这个约束被错误地带到了展开态：展开面板是浮在任意内容上的独立表面，它需要的是**能从背景里被衬出来**。实测：展开面板表面是 #161615（22 个灰阶差）加柔和投影，这就是它在纯黑桌面上圆角清晰可见的原因。

**修法**
面板填充改 #161615；`NSPanel.hasShadow` 在 `expand(on:)` 时开、`collapse` 的 morph `completionHandler` 里关（收起开始就关会让轮廓在动画中途跳一下；静息胶囊带阴影会在菜单栏下画出光晕，所以必须跟状态走）。

**教训**
> 「看不见形状」先做对比度排查再动几何：把怀疑的圆角数值改来改去之前，先取一点面板内外的像素颜色，差值为 0 就是轮廓问题，不是形状问题。

### G8 · 三个视图拼一条黑带，中间那个的圆角就是接缝

**现象**（2026-09-22）
按住快捷键时，刘海**左下角**（和右下角）露出一小块空白——黑带和刘海之间像没接上。用户的原话是「你的动画没有去衔接，只是在左右两边加了动画」。

**根因**
活动带是**三个并排的视图**拼出来的：左翼 / 中段（= 刘海本体）/ 右翼。中段是 `PillShape(bottomCornerRadius: isActive ? 10 : 6)` —— 它的两个底角**一直是圆的**；而两翼朝内那一侧的底角是直角（`bottomTrailingRadius: 0` / `bottomLeadingRadius: 0`，圆角只给最外侧）。

直角接圆角，接缝处就缺掉一个 ~10×10 的角。**左右各缺一个**，所以「左下角有空白」和右下角同时出现。

**为什么难发现**
三个视图各自的形状都没有问题，单看每一个都是对的；错的是**它们相接的方式**。而且它在静息时完全正常（翼宽为 0，中段的圆角就是胶囊自己的圆角），只有动画一启动才出现——所以「静态截图检查」永远看不到。

**修法**
翼伸出来的时候中段底角变直角：`bottomCornerRadius: isActive ? 0 : 6`，整个组件变成**一条底边是直线**的黑带，只有最外侧两个底角是圆的。

顺带补了 `PillShape.animatableData`：不写它，`isActive` 翻转的那一帧半径会**直接跳**（10→0），而两翼还在 0.38 s 的滑动当中——用户看到的就是「角先啪一下变方，翼再慢慢收回去」。把半径声明成 shape 的可动画数据，它就跟着同一个动画插值。

**教训**
> **拼出来的形状，接缝是几何问题，不是视觉问题。** 多个视图组成一个连续外形时，相接的那两条边必须是**同一种**角（都直角或同半径）；否则缺口就在它们的边界上，而且只在「它们真的接在一起」的那个状态下才出现。
>
> 修法不是把圆角调小，是**让中段在展开态放弃圆角**——一个连续外形只应该有两个端点的圆角，中间的接缝一律直角。

### G9 · 光晕不是「贴边的斜坡」，是含在翼内部的椭圆斑

**现象**（2026-09-22）
用户看着截图说：光晕是「在刘海屏右侧增加的那部分内容里，位于该组件的最右侧，**是在里面**，不是在外面」，同时要求「过渡非常自然」。当时的实现是「中间有颜色，过渡不自然」；按下面第一版修法改完，用户仍然回「效果非常差，你自己看」——附了一张亮青色壁纸上的实拍截图。

**第一版根因**（已作废，但值得留着）
右翼里的光晕是 `EllipticalGradient(...).frame(width: 76, height: 30)`，外面套了 `.padding(.trailing, 10)`。翼宽 88，于是光晕占 2…78，**最亮的中心离翼外缘还有 48pt**——颜色顶在中间。当时的修法是 `center: .trailing` + `endRadiusFraction: 1`（横向半径 = 整个翼宽，圆心贴最外缘），理由是「最亮处落在组件外缘、衰减刚好在内缘归零」。

**这个理由错在哪**
它把「最亮处在翼的外缘」当成了事实，但那是**推出来的**，不是量出来的。真实情况正好相反——**光晕的峰值在外缘的里面**，而且外缘处根本没有归零，是被切掉的。

**真正的量法**
不要再靠肉眼估。用户给的目标图本身就是像素，直接扫：

- 原图带宽 595px 对应 364pt，所以 **1.635 px/pt**（注意：这份截图被缩放/压缩过，不是 2×，别拿 Retina 惯例套）。
- 横着扫一行（Listening，带子右端 x≈779）：
  ```
  x=708 #020202   x=744 #113D46
  x=720 #0A1418   x=756 #12464C  ← 峰值平台（750–762）
  x=732 #0F2B32   x=768 #103E45
                  x=776 #0F3035  （外缘）
  ```
  → **峰值在离外缘 23px = 14pt 处**（翼宽 88pt，约 84% 位置）；x≈706 起全黑，**翼靠内的 44% 是纯黑的**；外缘处仍有约 60–70% 亮度。
- 竖着扫一列（x=761）：带子**从最上边就被点亮**（进去 2px 约 36%），y≈88 到峰值，到底边回到黑。→ 光晕的**竖向半径必须超出带子高度**，让翼去裁它；把渐变 frame 设成翼的 32pt 高会强行在上下边归零，留出一条暗边。

**颜色也是错的（同一个 bug 的另一半）**
旧写法是 `phase.notchAnimationTint.opacity(0.5)`——**把动画的颜色当成了光晕的颜色**。两者是**不同的颜色**：thinking 的动画点是亮品红 `#F35FD7`，而它身下的光晕峰值是 `#540067`（84,0,103，**绿通道正好是 0**，一个纯正的深紫）。实测三态峰值：listening `#12464C`(18,70,76)、thinking `#540067`、speaking `#45230F`。

`#5EEAD4` 的一半叠在黑上 = (47,117,106)，一个绿通道最大的灰青。用户的桌面恰好是青的 `#0080A6`——同色相、一半饱和度，看起来就是**一块脏兮兮的灰绿糊在带子末端**。**动画是发光体，光晕是染料**，两套颜色，各用各的表（`notchAnimationTint` / `notchGlowColor`）。

**修法**

```swift
EllipticalGradient(
    stops: phase.notchGlowStops,          // 高斯型：宽亮核 + 快速衰减
    center: UnitPoint(x: 0.84, y: 0.5),   // 峰值在翼内 84% 处，不贴边
    startRadiusFraction: 0,
    endRadiusFraction: 0.40               // 半径只有翼宽的 40% → 内缘之外早就归零
)
.frame(maxWidth: .infinity)
.frame(height: 64)                        // 仍比带子高：竖向让它超出、由翼裁掉
```

`notchGlowStops` 的五个点（1.00 / 0.85 / 0.62 / 0.36 / 0.16 / 0.00，位于 0 / .30 / .50 / .70 / .85 / 1.0）是按上面四个数拟合的：峰值 ~14pt 内、外缘 ~60%、带子上边 ~36%、内部 44% 处归零。

**复验（改完必须做，不能只看离屏渲染）**
用 `captureband` 真的去按一次用户的快捷键，抓屏再扫：

| | 目标图 | 改后实拍 |
|---|---|---|
| 峰值位置（离外缘） | 14pt | 16pt |
| 峰值颜色 | `#12464C` (18,70,76) | `#204249` (32,66,73) |
| 外缘处 | ~60% | ~55% (25,52,57) |
| 内侧归零点 | 翼的 49% 处 | 翼的 45% 处 |

改前同一位置是「一路爬升到外缘 `#245E51`(36,94,81)，然后直接跳到壁纸 `#0080A6`」——一条横贯整翼的灰绿斜坡收在一条硬边上，这就是「过渡不自然」。

**没解决的分歧（诚实记下）**
两张目标图对峰值位置的答案不一致：Listening 图峰值在离外缘 14pt 处，**Thinking 图峰值就在外缘上**（`#540067` 出现在 x=802，而带子到 x=806 才结束）。选了 Listening 的：它是用户抱怨的那一态，量的时候穿过的是一段可见的平台（更可信），而且它对亮色桌面退化得最好。Thinking 那张有可能是**翼还在展开的途中**抓的。下次碰到原图打架，先怀疑「是不是动画没走完」。

**教训**
> **「看起来在最右端」和「峰值在最右端」不是一回事。** 眼睛看到一条右端最亮的带子，很容易直接推出「圆心贴右缘」，但光晕是被翼**裁掉**的——被裁的那一侧看起来仍然很亮。要区分「渐变走完了」和「渐变被切断了」，只有一条路：扫像素，看峰值在哪、外缘还剩多少。
>
> 顺带：凡是「照着目标图调参数」的活，先把**目标图的 px/pt 标定出来**（拿一个已知 pt 数的量去除），否则所有测量都是浮的。

### G10 · 声明了圆角，屏幕上是直角：ZStack 被高个子孩子撑大后，圆角落到了裁剪线以下

**现象**（2026-09-22）
用户连问三遍「就是加一个圆角，为什么这么难」：活动带**外侧的两个底角**应该圆，实机上**只有左角是圆的，右角是硬 90°**。而 `NotchWingView` 的代码里圆角**一直写着**——`UnevenRoundedRectangle(bottomTrailingRadius: 10)`，声明得清清楚楚。改光晕改了三轮，用户盯着的那条棱一动不动，所以三次反馈全是「跟没修改一样」。

**根因**
翼的主体是一个 `ZStack { 黑色圆角矩形; 内容 }`，而 **ZStack 的尺寸取最大子视图**。右翼的内容里有那个故意做成 64pt 高的光晕（比 32pt 的带子高，见 G9——竖向半径必须超出带子才不会被上下边归零）。于是：

1. ZStack 被光晕撑到 64pt；
2. 调用点的 `.frame(height: notchHeight)`（32pt）把这个 64pt 的整体**垂直居中**；
3. 黑色矩形跟着下移 16pt，它的圆角**整体落到带子真实底边以下**；
4. 调用点的 `.clipped()` 沿带子底边一刀切平——圆角被齐着切掉，剩一条直边。

**左翼没事**，因为它的内容只有一行文字，没有高个子孩子——`ZStack` 就是 32pt，圆角在框内。**同一份代码，一圆一方。** 离屏复现把它钉死了：同一个圆角矩形，套不带光晕的 ZStack 是圆的，套带 64pt 孩子的 ZStack 再裁就是直角。

**修法**
黑色轮廓改成**基座**，内容全部装进 `overlay`（overlay 不参与父级布局，撑不大基座），内容再用 `clipShape(同一个轮廓)` 裁圆：

```swift
outline.fill(Color.black)
    .overlay { wingContent }      // overlay 不撑大布局
    .clipShape(outline)           // 内容跟轮廓一起圆
```

光晕竖向溢出的部分原来靠调用点 `.clipped()` 裁，现在由 `clipShape` 裁——裁剪权从「外面那刀」回到「轮廓自己」。半径同时从 10 调到 14：按用户给的目标图量（L29938，1.635 px/pt），外缘列底边上收 26px ≈ 16pt，两目标图在压缩模糊内给 10–16pt，取用户目标图的读数。

**为什么查了三轮才找到**
第一轮到第三轮全在调光晕的参数，每次都**用像素验证过光晕确实变了**——验证的工具没错，验证的**对象**错了。用户说「没变化」时，正确的第一反应是「**我看的是不是他在看的那个东西**」：把用户指的那条棱放大、逐列量底边，第一轮就该看到「左角圆、右角方」这个不对称——一个不对称当场就能排除「参数没调好」这类解释，因为参数对称的代码不可能产出不对称的棱。

**教训**
> **「写了」和「渲染了」之间隔着整个布局系统。** 圆角写进 Shape 不等于它上了屏幕；它会不会被父级的 frame 居中到裁剪线以下、被 `.clipped()` 切平，取决于 ZStack 里还有谁。
>
> **`ZStack` 的尺寸取最大子视图；`overlay` 不参与布局。** 要「以 A 为轮廓、BCD 叠上去」，A 用 fill 做基座、其余进 overlay——不要全塞 ZStack，除非你确认每个孩子的尺寸都不超过基座。
>
> **用户说「没变化」时，先量他指的那个像素。** 三轮「验证过生效」的修改可以全是真的，同时全都没碰到用户的抱怨——因为验证验证的是你正在改的子系统，不是他正在看的那条棱。

### G11 · 删掉一个交互时，最容易误删的是**它旁边那半截**

**背景**（2026-09-22）
用户说：「让刘海屏只有点击的时候才被触发，而不是鼠标滑动时就自动触发，鼠标滑动触发太影响体验了。」刘海胶囊长在**菜单栏那一条带子里**，鼠标沿着菜单栏横向移动（去点 Wi-Fi、去看时间）必然扫过它——悬停展开等于「路过就弹窗」，这条反馈是设计问题，不是参数问题。

**移除面**（照这个清单找，不要凭印象删）
- `NotchWindowController`：`dwellTimer` / `dwellStartedAt` / `growingPresence` / `hoverCommitTask` 四个属性，`startDwellTimer` / `stopDwellTimer` / `pollHoverDwell` / `cancelHoverGrowth` 四个方法（外加只在悬停路径里存在的 `commitHoverGrowthNow`），以及 `installIfScreensSupportIt` / `teardown` / `bindCompanionState` / `refreshFullscreenSuppression` 里的调用点；`beginExpansion(on:commitDelay:)` 退化成 `beginExpansion(on:)`（`morphTimingControlPoints` + 同帧提交），`expand(on:)` 不再有「生长中」分支。
- `NotchPanelModel.dwellProgress`（`@Published`，进度环的驱动值）。
- `NotchActivityView`：`PillShape` 上的那个 `overlay(alignment: .bottom)` 进度环 + `NotchHoverDwellRingView` 整个结构体。
- `NotchSupport`：`hoverMorphTimingControlPoints`（只为「等待期间慢慢长」存在，悬停没了它就是一条没人用的曲线）、`hoverExitMargin`（迟滞带的窄边，配合驻留计时防抖，没有计时就不需要防抖）。

**两处差点删错的**
1. **`hoverEnterMargin` 不能删，只能改名。** 它有两个含义：曾经是「光标离 pill 多近开始计时」，同时还是 `handleGlobalClick` 里**点击命中区**的外扩值。删掉它，点击展开的判定会缩回 pill 原尺寸（`restingPillFrame` 只有刘海宽度 + 每侧 2pt），点边角就不灵了。已改名为 `pillClickHitMargin`，并在注释里写明另一个余量为什么消失。
2. **`NotchPanelRootSwitchingView` 里 `expansionProgress > 0.01` 那个中间分支不能删。** 它的注释只写了「悬停生长期」，看着像悬停专属，实际上它同时承担**收起**：`collapse()` 先把 `isExpanded` 翻成 false，再沿收起曲线把 `expansionProgress` 动画到 0——那一段正是这个分支画出来的轮廓。删了它，面板收起时会瞬间闪回 pill。注释已改成描述收起路径。

**教训**
> **交互逻辑和它依赖的常量/分支，往往不是一对一。** 删悬停计时，`hoverEnterMargin` 还兼着点击命中区、`expansionProgress` 中间分支还兼着收起动画——按「注释里提到悬停」去删，就会删掉正在干活的那半截。动手前先把每个候选符号 `grep` 一遍，看它的**读点**分别在哪条路径上。
>
> **用户说的「体验不好」通常是交互模型错，不是参数错。** 悬停时长可以从 0.35s 调到 1s，但鼠标扫过菜单栏这件事不会因此变少——这类反馈先问「这个触发方式本身该不该存在」。

### G12 · 两条并行动画各管一半状态，任何一条停摆都没人兜底

**现象**（2026-09-23，偶发）
刘海收起后偶尔**缩不回去**：屏幕顶部留着一条比刘海宽一倍多的黑色圆角带（宽度 ≈ 静息窗口的 505pt、高度 ≈ 刘海+22pt 的 54pt、底部圆角 20）。用户截图对照 `HomeSpaceSheetShape` 的几何一比对就锁定了：这是 `NotchPanelRootSwitchingView` 里 `expansionProgress > 0.01` 分支画在**静息窗口**里的收起途中轮廓——窗口 frame 已经收回到静息位，但 `expansionProgress` 冻在了高位，视图就一直画它。

**根因**
`collapse()` 同时跑两条动画：窗口 frame 走 `NSAnimationContext`（AppKit），`expansionProgress` 走 `withAnimation`（SwiftUI）。两条各管一半视觉，**互相不感知，也都没有「结束后核对对方」的步骤**——SwiftUI 侧那条偶发停摆（事务被打断/渲染窗口不可见一类的竞态，复现不了确定触发条件），值冻在半路，没有任何代码再把它拉到 0。

**修法**
不追那个复现不了的竞态，改加**确定性收口**：`convergeOnRestingState(_:)` 把面板 frame 和 `expansionProgress` 都强制瞬时对齐到静息态（幂等，正常收起时是空操作），在收起动画的 `completionHandler` 里调一次，另加一个「动画截止时间 + 0.25s」的看门狗兜住 completionHandler 被跳过的情况。两条回调都用 `collapseGeneration` 代号把门——新的展开/收起把代号一顶，旧回调自动退位，不会把正在飞行的新动画瞬间吸附到终点。`teardown` 路径（`expandBackToPill: false`）原来也在 `withAnimation` 里归零进度，同样有停摆风险、且面板 model 在重建后还活着（冻值会带进新面板），改成直接赋值——反正面板随即隐藏，没人看得到形变。

**教训**
> **一个视觉变化拆给两条动画系统各管一半时，必须有一个「落地核对」步骤。** 两条动画各自正常时永远看不出问题，出问题的是「一条跑完、另一条没跑完」的组合态——而那正是最容易发生的部分失效。收口的写法比追竞态便宜：不试图让停摆不发生，而是保证停摆之后状态必然收敛。
>
> **诊断这类「偶发卡在某中间态」的问题，先拿截图量和已知形状对几何。** 黑带的宽、高、圆角半径三个数一出来，就能反推出「哪段代码、画在哪个分支、动画冻在哪个值」——比在两条动画路径里盲猜竞态快得多。

**后续（同日）：结构性修法是合并，不是收口。**
用户追问「这两个动画能不能变成一个」，这才把根因真正解决。先写探针实测（`.tmp-open-test/frame_anim_probe.swift`）：`NSWindow` 的 frame 动画是**逐帧真实 resize**（0.5 s 动画观察到 18 个真实的中间 frame，`windowDidResize` 逐帧发出），不是图层假缩放。既然窗口自己每帧都在动，`expansionProgress` 就不该有自己的 `withAnimation`——改成从面板实时 frame 推导（`syncExpansionProgressWithPanelFrame`，挂在每个面板的 `windowDidResize` 上），SwiftUI 纯粹跟着渲染。只剩一个动画源，第二条动画的停摆这类问题**从结构上不可能再发生**；G12 上半段的收口看门狗降级成只看窗口 frame（进度跟着 frame 走，snap 一次两边都到）。

> **「两条动画要同步」这个需求本身，往往是该合并成一个动画源的信号。** 同步做对了也只是不出错；把它合并掉，同步问题连同停摆、错拍、收尾不一致整类消失。判断能不能合并的关键是一次实测：动画的驱动值每帧是否真实可读（窗口 resize 是，图层假缩放不是）。

### G13 · 收起侧栏 / 全屏来回切之后，两列一起被撑出面板并整体偏左

**现象**（2026-09-26，稳定复现）
面板顶栏加了「收起侧栏」和「展开（全屏）」两颗按钮之后，只要**切换过一次**，两列就一起被撑出面板并居中：810pt 的面板里内容宽 987pt，左列左边 89pt 被裁掉（连侧栏的「Screen」按钮都看不见），右列右边 89pt 被裁掉（`复制全文` 只剩一半）。刷新一次布局（重新展开面板）能好，切一次又坏。

**根因**（两层叠加，缺一不可）

1. **回答卡片把「这一列的最小宽度」锚死在了旧列宽上。** `AnswerCardView` 把断行结果按宽度缓存在自己的 `@State`（`CardRenderPlanCache`）里，而实时区那两行是 `.fixedSize(horizontal: true)` 的（防流式期间被压缩换行，见那个视图的注释）。于是「卡片算出来的那几行有多宽」= 这一列的最小宽度，而那个数又是从**这一列自己**量出来的（`.background(GeometryReader)` + preference）——列一变窄，卡片不肯跟着变窄，量出来的宽度就不变，断行于是永远不重算。**这是一个自锁的环，不是某一处算错。**
2. **右侧那排窗口按钮挂在了 `HStack` 的 overlay 上。** 面板是「左列定宽 245、右列吃掉剩下的」，而这一排连内边距 177pt 宽；它一旦参与那一层的布局，`HStack` 的最小宽度就变成 810+177。

**修法**

- 三处内容列（`NotchHomeView` / `AgentSessionView` / `NotchArchiveView`）各自在**已有的高度测量点**上加量一个宽度，并把它当 `.id(contentColumnWidth)` 挂在 `AnswerCardView` 上：列宽一变，卡片重建一次，缓存清空 → 先按真实可用宽度重新断行 → 环断开。**不碰流式渲染那段逻辑**，也不重建页面本身（输入框草稿、滚动位置都留着）。
- 那排按钮改挂在 `ZStack` 上（ZStack 的尺寸取两个孩子的较大者，而这一排永远比两列窄，所以对布局彻底透明）。

**教训**
> **「这一列的最小宽度由这一列的内容决定，而那个内容又是按列宽算出来的」——这是自锁。** `fixedSize(horizontal: true)` + 按宽度缓存 + 把测量值喂回自己的布局，三者凑齐就再也回不到窄的一档。判断方法很简单：把容器拉宽再拉窄，如果两列**一起偏移并居中**（而不是右边留白），就是最小宽度被撑爆了，去查是谁把「内容宽度」变成了「最小宽度」。
>
> **宽度只有「增大」和「减小」两种变化，而只有减小的那一半会触发这类 bug。** 面板原来宽度写死（810，只允许拖高度），所以这个环一直存在、但永远走不到；一旦有功能让这一列变窄（收起侧栏、全屏↔小窗），它立刻现身。加「改变布局宽度」的功能时，先把「变窄」这条路走一遍。

1. **静默的失败比崩溃难查得多。** 归一化坐标、被接受的无效字段、200 + 空内容、非 key 窗口吞按键——这四个是全篇最难查的，因为它们**都表现为「看起来正常」**。

### D13 · 每块音频一个 `Task` 发送：上行乱序 + 一个我自己写出来的崩溃

**现象**（用户 2026-09-25，连续报了三个症状）
全双工会话里：① 转写出来的不是用户说的话；② 回答答非所问、还慢一拍；③ 后来我修这个时写出的泵代码**又把 App 崩了**（`Can't remove more items from a collection than it contains`）。

**根因一（乱序）**
上行每块音频这样发送：`Task { try? await self.sendJSON(...) }` —— **Swift 的 `Task` 不保证按创建顺序执行**。WebSocket 上的字节序 = 实际执行序，音频块可能乱序到达服务端。模型听到的是被打乱的语音：转写头转出错的字、理解头勉强拼出意思、回合判定被搅乱。**一个原因，三个症状。**

**修法**
单一消费者泵：按切分顺序逐块 `await` 发送，前一块发完才取下一块。`await` 挂起时让出 MainActor，不卡界面。

**根因二（崩溃，是我修根因一时写出来的）**
泵在 `await sendJSON` 挂起期间，`stop()` 路径会 `pendingUplinkAudio.removeAll()`；泵恢复后拿着**过期的余量**继续 `removeFirst(3200)` → 崩。

**修法**
"看一眼余量 + 取走"必须在**同一个同步段**里完成，且取块数量按**当下**的余量算（`min(chunk, count)`），永不多取。

**教训**
> **`Task {}` 不是"排队"，是"赛跑"。** 任何"每来一个东西就开一个 Task 去发"的写法，都必须先问：顺序重要吗？音频、输入事件、状态上报这类流式数据，答案几乎总是"重要"——顺序一乱，下游每一个消费者都在处理被打乱的流，而症状会出现在**离乱序最远的地方**（这里是"转写不对"），排查时根本想不到是发送侧。
>
> **跨挂起点共享可变集合，取用前必须按当下余量取。** `await` 的挂起点之间，任何路径都可能改掉集合——`prefix` 和 `removeFirst` 必须原子地（同一同步段）完成，或者干脆用队列类型。
