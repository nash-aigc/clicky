## 一、最初是怎么设计的，用户要的是什么

### 1.1 用户的需求（原话）

卡片样式不是我们发明的，是用户给的一份参考规范（`clip 卡片样式` / `实现说明.md`）。
它的签名效果写得很明确：

> 每个新字符进入时是**模糊的（blur 2.6）且半透明（opacity 0.2）**，
> 等它后面又来了五个 unit，它就**定格**为清晰 ——
> 在写作边缘留下约 5 个字的模糊尾巴。

用户对它的一系列补充要求（原话）：

| 日期 | 要求 | 落点 |
|---|---|---|
| 09-22 | 「如果文字特别多，它还是会在最后一话或者最后一句出现卡顿」 | 见四·① |
| 09-23 | 「第一行从 10 个字变成 11 个、再变成 12 个」 | 宽度必须由容器决定，不由内容撑开 |
| 09-23 | 「卡片左下角这几个按钮和卡片底部同时出现」 | 时间戳取**收到回复的那一秒** |
| 09-25 | 「每一句回复内容的最后几个字，总是会卡一下」（三段式同样） | 见四·① |
| 09-25 | 「最后那几个字渲染不出来」 | 见四·②、四·⑤ |
| 09-25 | 「三段式好了、全双工还是卡」 | 见四·③、四·⑤ |
| 09-25 | 「最后一次还是卡，它是突然间跳出来的」 | 见四·④、四·⑤ |
| 09-25 | 「AI 回复的内容重复了……出现两个卡片」 | 见四·⑥ |
| 09-25 | 「（全双工语音模式）最后 5 个字，不要动画，直接显示吧」 | 见五·四 |
| 09-25 | 「不要再出现这个错误了，你自己要想办法解决」 | 见五·七 |

### 1.2 最初的设计（今天之前）

```
文字 → unit 切分 → 断行 → 段落折叠 → 实时区（最后一行）
                                     └─ 尾巴那几个字各自一个 Text，模糊 → 清晰
```

四条不变量，今天之前一直是成立的：

1. **宽度由容器给，不由内容撑开。** 卡片 `.frame(maxWidth: .infinity)` —— 内容撑开
   宽度会让"断行宽度"这个量反过来被断行结果影响，第一行会多吃进一个字（实测
   314 → 315 → 316，两轮都一样）。
2. **一条断行规则，两个状态共用。** 流式与定稿都读同一份 `lines`。两套引擎会给出
   两个答案：实测一条 1482 字的回复，流式布局排成 **55 行**、整段交给一个 `Text`
   排成 **62 行** —— 回复一结束卡片当场长高 7 行（约 150pt）。
3. **增量，不重建。** 卡片每来一个字重算一次 body，`CardRenderPlanCache` 里 unit 表、
   测宽表、断行状态、段落表全是延展的。逐字 O(n) 的工作本仓库量过：**0.12ms/delta**
   （2000 字回答），一帧的 0.2% —— **所以后来所有关于"卡"的怀疑都不该往这里找**。
4. **底边连续增长。** 一行文字无论一个字还是二十七个字都是一行高，所以最后一行
   下面垫一块 `liveLineFill × 行距` 的空白，随那行填满而排出去。实测底边按
   **0.83pt/字** 连续移动，而不是每行一次 22.5pt 的台阶。

**这个设计本身没有错。错的是它的输入假设 —— 见第二节。**

## 二、设计思路

### 2.1 一条贯穿全局的原则

> **每一个判据，都必须由它真正描述的那个量来决定。**

这句话是这一天所有 bug 的共同解药。逐个看：

| 判据 | 描述的是什么 | 原先用什么判 | 结果 |
|---|---|---|---|
| 尾巴多长 | **时间**（"刚出现"） | 字数（最后 5 个 unit） | 全双工模糊 0.8 秒、三段式 0.17 秒（差 5 倍） |
| 这张卡还在长吗 | **文字还在不在来** | 这一轮还没结束 | 转录播放期间一直为真 → 尾巴糊着 |
| 哪些字单独成视图 | **模糊状态可能变的那几个** | 字数（最后 5 个） | 成串到达时视图被提前销毁 → 只有跳变 |
| 这条会话是不是全双工 | **会话本身的事实** | `activeMode`（只有快捷键路径会赋值） | 判据恒为真 → 改动等于没做 |
| 气泡边界在哪 | **文字累加器在哪重置** | 本地电平打断 | 误判 → 两张相同的卡 |

### 2.2 两个必须分开的问题

这一天最大的认知转折是：**「一个字显示得对不对」和「一段文字什么时候到」是两件事。**

- 前者是**渲染**问题：视图身份、动画生命周期、换行与折叠的一致性。
- 后者是**数据流**问题：谁在什么速率、以什么粒度把文字交过来。

我前五次修复全部只在前者里找，而真正的症状（读不出来、突然跳出来）**根在后者**：
全双工的文字是以**说话速度**到达的。这个量不是渲染能改的。

### 2.3 第三件必须分开的事：**信息**与**代理量**

`isStreaming` 这个名字骗了人。它在三个页面里指的是三件不同的事：

| 页面 | 传的是什么 | 语义 |
|---|---|---|
| Screen | `assistantBubble(streamingAnswerText, isStreaming: true)` —— 流式卡片是一个**独立的视图**，文字流一结束这个视图就不存在了，条目改由另一处以 `false` 画 | ✅ 结构上就等于"文字还在来" |
| Agent | 同 Screen 的形状 | ✅ 同上 |
| Chatting | `streamingAnswerEntryID == entry.id` —— 一个**按轮绑定的 id**，什么时候清由控制器的状态机决定 | ❌ 是"这一轮还没结束"的**代理量** |

**Screen 一直是好的，恰恰因为它的判据是结构给的，不是状态机给的。** 这就是为什么
用户反复说"三段式好了、Chatting 不对" —— 而两者用的是同一张卡片。

> **教训：一个参数叫 `isStreaming`，不代表三个调用方传的是同一件事。**
> 判据必须由**它描述的那个量**给出，不能由一个恰好相关的代理量给出。

## 三、还应关注哪些内容（同类问题的完整清单）

改这块代码之前，先确认下面每一条：

1. **判据的单位要和现象的单位一致。** 现象是"刚出现多久"（时间），判据就不能是
   "第几个字"（个数）。见二·1 的表。
2. **代理量会被误读。** 见二·3。任何 `isXxx` 参数都要问：它描述的是这件事本身，
   还是某件相关的事？
3. **任何进入布局的量都必须有硬上限。** 见四·⑦ —— 我因为违反这条，把整个面板撑宽了。
4. **视图身份一旦改变，动画就断。** `.animation(value:)` 只在视图还活着的时候跑；
   `ForEach` 的成员一变，离开的那个视图就被销毁。
5. **不可逆的状态变更不能被本地猜测触发。** 气泡边界是"解绑 id"，解绑之后下一个
   delta 会**新建一条装着全文的气泡** —— 猜错一次就是一张重复卡。而"停声"是可逆的
   （下一个 delta 就接回来），所以本地猜测只能用来做可逆的事。
6. **两条管线不能共用一套观感常量，除非先量过它们的速率。** 见七。
7. **改完必须逐帧看，不能靠读代码断言。** 见八。
8. **一次只改一处，改完验证再改下一处。** 这一天我违反了，代价是两个回归。

## 四、问题到底出在哪里

六个缺陷 + 一次判据事故。**每个都附"依据"** —— 依据是量出来的数、日志行或截图，
不是推理。

### 4.0 先给三个数（后面每一条都要用）

| 量 | 值 | 怎么来的 |
|---|---|---|
| 三段式文字到达速率 | **约 30 字/秒** | DeepSeek SSE 流式，与 Screen 页同一个客户端 |
| 全双工文字到达速率 | **约 6.1 字/秒** | 日志里一条 60 字的回复跨了上行音频块 `#2 → #100`，每块 100ms 音频 → 约 9.8 秒 |
| 播报期间麦克风电平 | **0.875 / 0.972** | `clicky-尾行不压缩-145501.log` 的 `aecprobe` 行；VAD 门槛是 0.25 |

**第二条是整件事的核心**：全双工的速率**不是缺陷，是物理限制** —— 字幕不可能比它
转写的那段话更快。所以错的是判据，不是速率。

### ① 折叠把模糊抢走了 —— **每一行一次**

**症状**：「每一句回复内容的最后几个字，总是会卡一下」

**机制**：模糊窗口是**从整篇回复末尾**数的 5 个字，而折叠是**按行**的。一行换行
闭合的那一瞬间，它末尾约 4 个字还在模糊窗口里，但那一行**已经被折进段落了** ——
而折进去的行是用一个**没有模糊修饰符的普通 `Text`** 画的。于是那 4 个字在同一帧里
被重画成清晰，**动画根本没跑**。

**依据**：`AnswerCardView` 里 `liveLineView` 只画 `lines.last`，而
`paragraphs(settlingFinalLine:)` 折叠 `lines.count - 1` 行 —— 两者在"哪一行是活的"
这件事上不一致。

**修法**：实时区从 1 行改成 **2 行**。这不是调参，是**精确的界**：模糊窗口是 5 个
unit 且一行至少 1 个 unit，所以 **5 个 unit 在结构上不可能跨超过 2 行**。

### ② 回合失败时"还在长"永远不清 —— **永久模糊**

**症状**：「最后那几个字**渲染不出来**」（字面含义，而且是永久的）

**机制**：卡片靠 `streamingAnswerEntryID` 决定糊不糊。而这个槽**只在 `finishTurn`
里清**，`finishTurn` 只有 `onTurnFinished` 一个调用者，而 `CascadeVoiceEngine` 的
**失败分支（`catch`）根本不调它**。于是文字已经流进卡片、流中途断掉的那一轮，
那张卡的"还在长"永远为真，最后 5 个字**一直**停在模糊 + 20% 透明度上，直到下一次提问。

**依据**：代码上 `finishTurn` 只有一个调用点（`onTurnFinished`），而 `catch` 分支
（`CascadeVoiceEngine` 的 `reportFailure` 那一支）没有任何清标志的动作。

**修法**：`CascadeTurnCallbacks` 增加 `onAnswerTextComplete`，引擎在**文字真正结束的
地方**报 —— 模型流返回时，以及出错时。不再等整轮结束。

### ③ 尾巴按**字数**定，而模糊表达的是**时间**

**症状**：「三段式好了、全双工还是卡」

**机制**：见二·1 的表。同样 5 个字，三段式存在 **0.17 秒**（一闪而过），全双工存在
**0.8 秒**（一直糊着）。

**依据**：四·0 的两个速率。

**修法**：`freshTailMaximumAge = settleAnimationDuration`，尾巴改由时间决定。
0.3 秒不是挑的，是**定义**：**一个字"该模糊"的时间，就是它"变清晰"所需要的时间**。

### ④ 单独成视图的集合也是按字数切的 —— **视图比动画先死**

**症状**：「最后一次还是卡，它是突然间跳出来的」

**机制**：`.animation(value: isFresh)` **只在一个视图还活着的时候才会跑**。而"哪些
字单独成视图"和"哪些字该模糊"原本**是同一个集合**（最后 5 个字）。于是文字**成串
到达**时，`unitCount` 一次跳好几个，旧的那几个 unit 当场**离开 `ForEach` 被销毁**，
`isFresh` 的翻转落在一个不复存在的视图上 —— **淡出永远不播，只有跳变**。

**依据**：逐帧截图 —— 帧 052 是一片糊带，帧 054（约 0.7 秒后，中间隔了 14 个字）
已经是全清晰，**没有过渡帧**。

**修法**：单独成视图的集合改成按**时间**切，窗口 = 模糊窗口 + 淡出时长，也就是
**一个 unit 至少活到它自己那次动画走完之后**。

> ⚠️ **这条修法我第一版做错了，代价是把整个面板撑宽 —— 见 ⑦。**

### ⑤ 真正让全双工"读不出来"的：**可读性**，不是时长

**症状**：「最后那几个字渲染不出来」+「突然间跳出来」

**机制**：这是②③④之外**独立**的一条，也是我前五次都没找到的那条。逐帧截图确认：
全双工的尾巴是 **5–6 个字连成一片、完全认不出来**——`blur 2.6 + opacity 0.2`，
深色卡片上的白字，20% 已经几乎看不见，再叠上模糊就彻底读不出来。而此时长
**约一秒的说话内容**。

用户要读的正是这一秒。**把它做成模糊 + 半透明，等于把字幕盖住一秒再突然掀开。**

**为什么三段式没事**：同一组常量，但 5 个字只存在 0.17 秒 —— 那才是参考规范设想的
"写作边缘"，一闪而过正合适。

**依据**（三条独立的）：
1. 逐帧截图：尾巴是一整片糊带，不可辨认。
2. 速率差：0.17 秒 vs 0.8 秒（四·0）。
3. `opacity 0.2` 在深色卡片上的对比度 —— 20% 白字本身就已经接近不可读。

**修法**（两部分）：
- 视觉常量：`freshBlurRadius 2.6 → 0.8`、`freshOpacity 0.2 → 0.55`（**用户拍板选的**）。
- **全双工不做进场动画**（`animatesIncomingCharacters`，用户的明确要求）：
  「（全双工语音模式）最后 5 个字，不要动画，直接显示吧」。

### ⑥ 一张回答渲染成**两张逐字相同的卡** —— 本地误判切断了气泡边界

**症状**：「AI 回复的内容重复了，它总是把回复的结果再次回复一遍。不是重新读一遍，
而是出现两个卡片」

**依据（日志，一行钉死）**：

```
33: 🧾 问候开始 resp=resp_Z5HnM「你好」
70: 🎙️ 全双工会话：本地判定用户开口 —— 就地停声     ← 用户全程一个字没说
71: 🧾 同一条回答结束，47 字
```

**一条回答、47 个字、全场没有任何 `speech_started`** —— 却有一条"用户开口"的记录。

**机制**：`DuplexVoiceEngine` 里有一个**客户端自己**的打断判定（轮询上行电平）。
它调 `onBargeIn()`，而控制器的 `onBargeIn` 会**把助手气泡的边界清掉**。于是下一个
delta 走到 `updateDuplexAssistantEntry` 的 `else` 分支，**新建了一条气泡**，而它写进去
的是 `cumulativeText` —— **已累积的全文**。两张逐字相同的卡。

**为什么本地判定会误触发**：AI 自己的声音进了麦克风（四·0 第三行，0.875 > 0.25 门槛）。

**修法**：让气泡边界**跟文字累加器对齐**。真正重置 `currentAssistantText` 的是
**服务端确认的 `speech_started`**，所以边界搬到了 `onUserSpeechStarted`；
`onBargeIn` 现在只停声，不碰气泡。

> **这条修的是"误判不能再破坏卡片"，不是"误判不再发生"。** 误判本身还在，
> 它的根是回声 —— 见第九节。

### ⑦ 我制造的那个回归：**实时区必须有界**

**症状**（用户报的三个新问题）：「卡片回复时整个窗口被撑大，左右两侧都被撑大」、
「没有逐行渲染，而是整体渲染」、「三段式完全没法正常使用了」

**机制**：④ 的修法我让**时间判据无上限地推迟折叠** —— 只要"还有字在进场动画里"，
那一行就不折。结果文字一多，**所有行**都留在了实时区；而实时区每一行是一个
`.fixedSize(horizontal: true)` 的 `HStack`（按**自然宽度**画，不受父级压缩）。
一堆不受约束的自然宽度视图叠加，**把整张卡的内在宽度撑爆，面板跟着被撑宽**。

**根因不是判据错，是判据的**结果**没有上限。**

**我违反了哪条不变量**：1.2 的第 1 条（宽度由容器给）。实时区里每一行的宽度
**不受容器约束**，所以实时区的**行数**和每行的**独立视图数**都必须有硬上限。

**修法**：**回退**（`82b2696`），并把这条写进这里 —— 任何进入布局的量都要有上限，
而且上限必须是**常量**，不能是判据推导出来的。

### ⑧ 判据事故：`activeMode` 只在快捷键路径被赋值

**症状**：改完之后用户点「连接」进全双工，尾巴**照旧是糊的**，报「没修复」。

**机制**：我把"这条会话是不是全双工"判成了 `activeMode != .duplexVoice`。而
`activeMode` **只在 `handleShortcutPress` 末尾被赋值** —— 用快捷键（⌃⌥2）起会话才有，
点「连接」时它一直是 `nil`，于是 `nil != .duplexVoice` 恒为真，**动画一直开着，改动
等于没做**。

**依据**：`activeMode` 全文只有四处赋值：初始化、两处 `= nil`、以及
`handleShortcutPress` 的末尾。

**修法**：`isDuplexSessionRunning` → 读 `isDuplexSessionLive`（`startDuplexSession`
里置真、挂断时清零）—— **这条会话本身的事实**，与谁点的、界面上高亮哪一行都无关。

> 这是二·3 那节课的第二次现身：**判据必须由它描述的那个量给出。** 用 `selectedMode`
> 也不行 —— 那是"界面上选中的那一行"，会话进行中可以被切走。

## 五、做了哪些设计（以及为什么这样就不会再犯）

### 五·一 · 判据的单位 = 现象的单位

```
freshTailMaximumAge      = settleAnimationDuration  = 0.3 秒   ← 该模糊多久
unitEntranceAnimation    = 模糊窗口 + 淡出时长      = 0.6 秒   ← 至少单独成视图多久
```

两条都是**定义**，不是调参：一个 unit 在 0.3 秒那一刻**开始**变清晰，那次动画要再走
0.3 秒才结束 —— **在这之前把它换成一个合起来的 `Text`，动画就被打断了。**

到达时间从哪来：`CardRenderPlanCache.arrivalSamples` —— 每次文字真的变长时记一个
`(那时候一共多少个 unit, 那时候的时间)`，只留最近 64 个。**O(样本数) 的一次查表，
不是每个字一个定时器。**

**两个必须记住的前提**（都是实测踩出来的）：

1. **时间判据只在真的在流时才算。** 一张只渲染过一次的历史卡片只有 1 个到达样本，
   而那一刻就是"现在" —— 时间窗口会认为**整段文字全都刚到**，把每一个字都做成
   独立视图。实测症状：Screen 页那张历史卡的 AX 树里**每个字各自成一个元素**。
2. **最后一行永远不折**，无论判据怎么说 —— 它是实时区，流式与定稿由同一个视图画。

### 五·二 · 判据由**事实**给出，不由代理量给出

- 卡片要不要做进场动画 → `isDuplexSessionRunning`（会话的事实），
  **不是** `activeMode`（快捷键路径的残留）、**不是** `selectedMode`（界面高亮）。
- Screen 页的卡片判据 → **结构**（流式卡片是一个只在那段时间存在的视图）。
  这一条一直是对的，**它就是标准答案**。
- 气泡边界 → **文字累加器重置的地方**（`onUserSpeechStarted`），不是本地猜测。

### 五·三 · 不可逆的动作不许被本地猜测触发

| 动作 | 可逆？ | 谁可以触发 |
|---|---|---|
| 停声（`playbackEngine.stopStreamingPlayback()`） | ✅ 下一个 delta 就接回来 | **本地判定可以** |
| 换气泡（解绑 `duplexAssistantEntryID`） | ❌ 下一个 delta 会新建一条装着全文的卡 | **只有服务端确认可以** |

这条现在是注释写在 `onBargeIn` 上的，不是靠记忆。

### 五·四 · 两条管线用两套观感（因为它们速率差 5 倍）

```
animatesIncomingCharacters: !controller.isDuplexSessionRunning
```

| | 三段式 | 全双工 |
|---|---|---|
| 文字到达 | ~30 字/秒 | ~6.1 字/秒（受说话速度限制） |
| 5 个字存在多久 | ~0.17 秒 | ~0.8 秒（≈ 一秒的说话内容） |
| 进场动画 | **保留**（一闪而过 = 写作边缘） | **关闭**（盖住字幕 = 不可用） |

**关掉它不是"少一个特效"，是修掉一个可用性问题。**

### 五·五 · 可读性的两个常量

| 常量 | 参考规范 | 现在 | 为什么 |
|---|---|---|---|
| `freshBlurRadius` | 2.6 | **0.8** | 13.5pt 上 2.6 是一片糊，0.8 是柔边 |
| `freshOpacity` | 0.2 | **0.55** | 深色卡片上 20% 白字接近不可读 |

规范假设的是"快速写作边缘"；在每秒 6 个字的字幕上，同样的数字变成"盖住一秒"。

### 五·六 · 实时区有界（把 ⑦ 的教训固化成规则）

```
liveLineRegionLineCount = 2      // 行数：硬上限
每行独立成视图的字数：由时间判据给，但**不允许**让折叠被无上限推迟
```

**上限必须是常量。** 判据可以决定"够不够"，不能决定"最多多少"。

### 五·七 · 验证方式：逐帧，不是读代码

见第八节。这一条是用户那句「不要再出现这个错误了，你自己要想办法解决」的直接落点。

## 六、Screen 页的卡片是怎么设计的（它用的是 DeepSeek）

Screen（左栏那个对话页，原先叫 Ask）走的是**按住说话**那条老管线：

```
按下快捷键 → 录音 → 百炼实时 ASR → 截图 → 🧠 视觉模型（默认 deepseek-flash）
          → SSE 流式返回文字 → 卡片
```

它的卡片调用长这样（`NotchHomeView`）：

```swift
// 流式中：一个**只为这段时间存在**的视图
assistantBubble(companionManager.streamingAnswerText, isStreaming: true)

// 定稿后：历史条目，由 entries 驱动
assistantBubble(entry.assistantResponse, isStreaming: false)
```

**关键差别就在这里，而且这是本文件里最重要的一条经验**：

> **Screen 的 `isStreaming` 是结构给的 —— 流式卡片是一个独立的视图，
> `streamingAnswerText` 一空，这个视图就不存在了。**
>
> 所以它天然就等于"文字还在来"这件事本身，**从来不需要谁来清一个标志**。
> 它没有②那个缺陷（没有标志可漏清），也没有⑧那个缺陷（没有代理量可误读）。

Chatting 页的差别在于：它的文字住在**一个按轮绑定的 id**（`streamingAnswerEntryID`）
上，什么时候清、清得对不对，全由控制器的状态机决定 —— 而那正是②（漏清）和⑧
（误读）的温床。

**所以 Screen 是模板，Chatting 是特例。** 以后 Chatting 这条路上的任何"这张卡还在
长吗"，都应该优先问：**能不能让它由结构回答，而不是由状态机回答？**

> 附：DeepSeek 在 Screen 页作为 🧠 的两个已知事实（与本文件相关的那部分）：
> 它只支持 `deepseek-flash`（`deepseek-v4-pro` 会拒图），它是推理模型，所以
> `thinking: {type: disabled}` 是默认开的（首字 4298ms → 817ms）。
> 它的流式速率实测约 30 字/秒 —— 第四节 ③⑤ 的对照基准。

## 七、三段式 vs 全双工：逐项对照

这是整份文档的浓缩。**同一张卡片，两条管线，差异只有速率，症状却完全不同。**

| | **Screen（按住说话）** | **Chatting · 三段式** | **Chatting · 全双工** |
|---|---|---|---|
| 文字来自 | `BailianVisionChatAPI`（DeepSeek SSE） | 识别→理解→表达三段，理解=DeepSeek 或实时模型 | `response.audio_transcript.delta`（模型说话的转写） |
| 文字速率 | ~30 字/秒 | ~30 字/秒（同为 SSE） | **~6.1 字/秒**（受说话速度限制） |
| 5 个字的尾巴存在多久 | ~0.17 秒 | ~0.17 秒 | **~0.8 秒** |
| `isStreaming` 是什么 | **结构**（独立视图） | 按轮绑定的 id | 按轮绑定的 id |
| 进场动画 | 保留 | 保留 | **关闭**（用户要求） |
| 卡片边界 | 视图本身 | `onAnswerTextComplete` | `onUserSpeechStarted`（跟文字累加器对齐） |
| 曾经的症状 | 无 | 「每一句最后几个字卡一下」（①） | 「读不出来」「突然跳出来」（③④⑤）+ 重复卡片（⑥） |
| 现在的状态 | ✅ 一直是对的 | ✅ 用户确认「基本上完整修复」 | ✅ 逐帧验证：尾巴立即清晰、无重复卡 |

**读这张表的方法**：三条管线里，只有一条的判据是结构给的 —— 而它从来没有出过问题。
**这不是巧合。**

## 八、验证方法（以后必须这样做）

这一天我三次用"读代码 + 推理"下结论，三次都被推翻：

| 我的推理 | 被什么推翻 |
|---|---|
| 尾巴在整段语音播放期间一直糊着 | `waitUntilPlaybackFinishes` 轮询 `isChunkPlaying`，而它在**每个分段间隙**都是 false（实测每段间隙 ≈0.18s、轮询 30ms）→ 窗口不是整段，最多是当前那一段的剩余 |
| 折叠抢走模糊是主因 | 修完之后症状**没有完全消失** |
| 时间窗口是主因 | 逐帧截图显示尾巴是 **5–6 个字、约一秒**，与时间窗口无关 |

**所以验证只有一种：逐帧。**

```
# 1. 连上全双工（它会自动打招呼，不需要说话）
# 2. 连拍（区域取内容列，帧率越高越好）
for i in $(seq -w 1 70); do screencapture -x -R 700,170,560,300 "f/$i.png"; done
# 3. 按文件大小找出内容变化的那几帧
ls -l f | awk 'NR>1{print $9,$5}' | awk '{if($2!=p){print $1" "$2} p=$2}'
# 4. 裁最后一行、放大，看那一条是"一片糊"还是"与正文同亮度"
sips -c 200 1120 --cropOffset 400 0 --out t.png f/58.png && sips -z 400 2240 --out tt.png t.png
```

**三个必须遵守的**：

1. **截图区域用点，不用像素。** Retina 屏 `screencapture` 出图是 2 倍，拿像素当坐标
   会差一倍，而且不报错。
2. **一次只改一处，改完立刻用同一把尺子复测。** 这一天我把三个未验证的改动叠在
   一起推上去，代价是用户拿到一个"三个新问题"的版本。
3. **量不到的一律写"推测"。** 文档与汇报里都必须区分。

## 九、仍然存在的一个上游问题（本文档之外）

**回声。** 播报期间麦克风电平实测 **0.875 / 0.972**，而本仓库记录过的关掉 AGC 之后的
实测值是 **0.241**；门槛是 0.25。引擎自报 `voiceProcessing=true AGC=false`，所以
AGC 那个修复在位 —— 这条链需要重新查（设备 / 音量 / 参考信号 / 引擎重配）。

它同时是三个症状的根：

| 症状 | 状态 |
|---|---|
| 本地电平判定误触发 → 重复卡片 | **已缓解**（⑥：误判不能再切卡片），但误判仍在发生 |
| 用户说话时反而打断不了 | 未修 |
| 语音转写被污染（实测出现过「提供一下200字的提供一个北京的200字介绍。」） | 未修 |

**这是这块剩下的唯一上游问题。** 在它修掉之前，任何依赖"用户开口"的判据都仍然是
不可靠的 —— 所以第五节那三条（判据由事实给、不可逆动作只由服务端触发、边界跟
累加器对齐）不是可选的优化，**是让系统在回声存在的前提下依然可用的必要条件**。
