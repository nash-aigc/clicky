# 03 · 语音节拍与生命周期——声音怎么跟得上画面

> 这份文档回答两个问题：**讲解的语音怎么生成和播放**（怎么才能不卡顿、不与正文抢声道），以及**这十几秒的动画归谁管**（谁能清它、谁能停它、被打断后怎么办）。
> 这两件事是评审认定的**头号风险**——比渲染器重要得多。

---

## 一、音频：按步生成，不切分（用户问题的正式回答）

### 结论

**每一步一个文本 → 一次性把 N 段并发合成好 → 按顺序播放。**

### 为什么不能「合成一整段音频，再按动画切」

| 原因 | 说明 |
|---|---|
| **没有时间戳** | Bailian 的 `SpeechSynthesizer` 端点只返回一个 WAV 地址，**不提供字级/词级对齐信息**。要按时间切就必须做强制对齐（拿带时间戳的 ASR 反标），是另一条大弯路，而且不准 |
| **切了也不对** | 即使能切，TTS 的合成是按**句子**分块的（`maximumCharactersPerChunk`，默认 500），分块边界与教学步骤**毫无关系** |
| **不需要切** | `.steps.json` 本来就是每步一句文本，天然就是 N 段 |

### 为什么要「并发合成」而不是「边播边合成」

现在的半成品 `showAnimated` 如果直接 `await speakText(每步)`，会踩两个坑：

| 坑 | 机制 |
|---|---|
| **下一步掐掉上一步** | `speakText` 在**第一段音频开始播放时就返回**（`BailianTTSClient.swift:103-105`），而它第一行就是 `stopPlayback()`（`:108`）→ 循环立刻推进，下一句把上一句掐断 |
| **每步开头静默 0.7–1.3 秒** | 按项目实测 `~19ms/字 + 450ms 固定`：25 字的一步 = 25×19+450 ≈ 0.93 秒。12 步累计十几秒的死气 |

### 现成的机制：仓库已经有这个形状

`StreamingSpeechSession`（`BailianTTSClient.swift:598`）为「逐句快答」实现的正是「**最多 N 段同时合成，按序播放**」：

- `maximumSynthesesInFlight` 控制并发上限
- `pendingSegments` 是待合成队列，`pumpSynthesis()`（`:929-942`）每轮把在飞数补到上限
- `runPlaybackLoop()` 按序播放，播完一段再取下一段
- 底层复用 `requestAudioData(for:resolvedSpeechRole:)` —— **它是 internal，注释里就写明是给这个会话用的**（`:288-290`）

**讲解只要复用这个形状**，把「分段」换成「讲解步骤」：

```
NarrationSession（新增，形状照抄 StreamingSpeechSession）
  ├─ 输入：[String]（每步一句）
  ├─ 并发上限：3（可配）
  ├─ 首段就绪 → 通知调用方「可以开始画了」
  ├─ 其余段继续在后台合成（此时动画正在画第 1 步）
  └─ 播放：第 k 步画完 → await 播第 k 段（waitUntilPlaybackFinishes）→ 第 k+1 步
```

**时序收益**：首段合成约 0.9 秒（动画还没开始，正常），之后每一步的音频**早已就绪**，步骤之间零静默。

**边界**：若某一步的音频迟迟没就绪（网络慢），播放循环要**等**它，而不是跳过——跳过会造成「讲的和画的对不上」。等待期间动画也不推进（同一时间源）。

### 音频缓存（省的是重复任务的延迟）

同一句讲解在"重画同一个图""追问后重讲"时会重复合成。加一个小的 LRU：

| 键 | 值 | 容量 |
|---|---|---|
| `(步骤文本, 音色, 语速)` | 合成的音频数据 | 最近 20 段（约几 MB） |

命中时省掉 ~19ms/字 + 450ms 的合成时间——对"再来一遍"这类追问是肉眼可感的差别。

## 二、旁白 vs 正文朗读：必须二选一

`speakText` 是**排他**的（第一行 `stopPlayback()`）。现在的顺序是「先图（含讲解）→ 后正文 `speakText(finalSpokenText)`」（`CompanionManager.swift:2649`）——**两者必然争声道**，谁后发谁赢。

| 方案 | 效果 | 建议 |
|---|---|---|
| **旁白取代正文**（推荐） | 讲解就是这次回答的内容；正文只回一句「图已经画好并讲解完了」，写进历史即可 | ✅ 讲解场景的语义就是如此 |
| 正文取代旁白 | 讲解被掐断，白板变成"静音动画" | ✗ 浪费了这条功能 |
| 合并成一段朗读 | 正文 + N 段讲解拼成一次请求 | ✗ 合成更慢，且步骤边界丢了 |

配套：`isPlaying` 会被两边争用，`scheduleAnswerBubbleClear`（`:2665`）与 `scheduleTransientHideIfNeeded` 会读到错误状态 → 讲解期间这些轮询必须**认讲解这一路**的播放状态。

## 三、时间预算：用实测速率反推上限（不能只写"10–30 秒"）

| 输入 | 值 |
|---|---|
| 每步旁白字数 | 规划器提示词要求 15–40 字（`figure_agent.py:178`） |
| TTS 速率 | ~19ms/字 + 450ms 固定（项目实测） |
| 播放速率 | 语速设置，默认 1.0 |

算一下：**10 步 × 25 字 = 250 字 → 光合成就要 250×19+450 ≈ 5.2 秒，朗读本身按正常语速约 60–75 秒**。也就是说「10 步」在任何语速下都会**超出用户预期的 30 秒**。

**建议上限（写进设置、可调）**：

| 参数 | 建议默认 | 理由 |
|---|---|---|
| `figureNarrationMaxSteps` | 8 | 10 步必然超时 |
| `figureNarrationMaxCharactersPerStep` | 25 | 40 字一步要念 3 秒以上 |
| `figureNarrationTotalTimeLimitSeconds` | 45 | 到点就停止新增步骤、剩余图元一次性揭示并收尾 |
| 淡出时长 | `步数 × 每步时长 + 8s` | 现在是固定 20s（`FigureBoardController.swift:71`），必须改成算出来的 |

顺带修一处不一致：规划器上限 10 步（`figure_agent.py:181`）、`readSteps` 上限 12 步（`FigureBoardController.swift:47`）、需求说 3–12 步——**三处数字要统一到一处配置**。

## 四、生命周期：这十几秒归谁管

### 4.1 动画 Task 必须与 `currentResponseTask` 同生共死

现在的问题：讲解的 Task 在 `placeFigureBoard` 里，**不在 `currentResponseTask` 的取消链上**。`interruptActiveResponse()`（`CompanionManager.swift:2893-2904`）只取消后者 + 调一次 `stopPlayback()`。后果：**用户说「停」，图还在画，声音还在念**（因为循环又发起了下一次 `speakText`）。

**必须**：
- 讲解 Task 注册进 `currentResponseTask` 的取消链（或持有引用并在打断时取消）
- 每个步骤边界检查 `Task.isCancelled`（现有 `showAnimated:164` 有这一行，保留它）
- 取消时：停播报 + 停动画 + 清屏 + 返回 `interrupted`（不是 `.success`）

### 4.2 清屏纪律要改（这条能省掉一半的冲突）

**旧结论已过时**（见 [01 文档第四节](01-现状与证据.md)）：截图按 `ownBundleIdentifier` 排除了本 App 的全部窗口，**模型本来就看不到自己的图**。所以：

| | 现在 | 改成 |
|---|---|---|
| 循环每步截图前清屏（`:2193`、`:2236`） | 会杀掉长动画 | **不清**（截图卫生不需要它） |
| 新问题按下 | 清 | 清（用户屏幕上不该留着上一轮的图）✅ |
| 打断 | 清 | 清 ✅ |
| 讲完自动淡出 | 20s 固定 | 按步数与时长算 |

### 4.3 消灭 20–60 秒的「死区」（**按播报模式分述，别一概而论**）

流水线顺序（实测行号）：流式播报 `:2081/2322` → 绿标注 `:2422` → 动作 `:2450` → **图板 `:2511`** → 整段合成的 `speakText` **`:2649`（在图板之后）**。

| 播报模式 | 等待期的实际体验 |
|---|---|
| **逐句快答** | 用户**先听到模型的回话**（流式播报在动作之前），然后等图 20–60 秒 |
| **整段合成** | `speakText` 排在 `placeFigureBoard` **之后** → 图生成完之前**用户全程听不到任何声音** |

两种模式下**共同的问题**是：`voiceState` 全程停在 `.processing`（`:2169`），持续监听窗要等正文 TTS 之后才开（`:2653`）→ **图生成期间用户用语音打断的能力不存在**（只能按快捷键）。整段合成模式下更糟：连"我正在画"这句话都没有。

**改成**：

```
收到 [SVG_TRACE] →
   ① 立刻回一句「正在画，稍等」（走正常播报，用户听得到）   ← 两种模式都受益
   ② figure_agent 跑在独立 Task
   ③ 画好 → 进 .responding → 开持续监听窗 → 起 NarrationSession → 开始逐笔
```

收益：死区消失、**用户能用语音打断**、刘海不再像死机。

> **需核对（不算结论）**：逐句快答模式下监听窗的确切开启时点没有逐行确认过——若它在流式播报结束时就已经打开，那这个模式下"能用语音打断"可能已经部分成立。改动前先用日志实测一次。

### 4.4 讲解要进对话历史

现在只有「图已画好」那一句进历史，**讲解内容全在 `.steps.json` 里，历史里没有**。后果：重放会话看不到讲解、历史压缩压不到它、模型追问「再讲一遍刚才那步」直接失忆。

**必须**：讲解结束时，把「任务 + 每步讲解词」合并成一条记录写入当轮 turn（与 `progressSteps` 同一类 turn-meta 字段，照 `decodeIfPresent` 规则 E1）。

### 4.5 刘海相位

现在全程 Thinking 转圈。建议新增 `NotchActivityPhase` 的一个相位（如「正在画图讲解」），由讲解 Task 驱动；`refreshActivityPhase()` 要知道讲解 Task 的存在，否则会被语音状态覆盖。

### 4.6 总闸、上限、可关闭

`AppSettings` 里**没有任何 figureBoard 相关键**（grep 为空），整个白板只被语义不对的 `pointsAtReferencedElements` 带着（`CompanionManager.swift:2417/2508`）。需要新增：

| 设置 | 作用 |
|---|---|
| 允许屏幕图板（总闸） | 关掉后模型发标签也画不出来，回一句「已关闭」 |
| 逐笔动画开关 | 关掉退回静态显示（现有 `show()` 就是降级路径） |
| 步数 / 每步字数 / 总时长上限 | 见第三节 |
| 讲解语速（可选） | 教学场景常常要慢一点 |

## 五、屏幕与系统事件（现在完全没人处理）

| 事件 | 现在的行为 | 应该 |
|---|---|---|
| 拔掉外接显示器 / 改缩放比 | `placement` 只在展示那一刻查一次屏（`FigureBoardController.swift:385-403`），全仓库没有 `didChangeScreenParametersNotification` 监听 | 监听并重算位置；屏幕消失则清掉板子 |
| 合盖 / 睡眠 / 锁屏 | 无任何 `willSleep`/`didWake` 监听 | 睡眠时暂停动画与播报，唤醒后**从头续播当前步**（不要音画错位） |
| 别人的全屏窗口盖住 | `OverlayWindow` 的 `collectionBehavior` 含 `.canJoinAllSpaces + .fullScreenAuxiliary`（`OverlayWindow.swift:29`）→ 图会画在别的 App 全屏之上 | 刘海子系统为此专门做了 `displaysCoveredByOtherProcessFullscreen` 抑制，图板要么同样抑制、要么明确接受 |

## 七、一张时序图（最终形态）

```
用户说话 ──► 模型回 [SVG_TRACE:三角形:讲解]
                  │
                  ├─ 立刻播「正在画，稍等」                     ← 死区消失
                  └─ 起 Task A（生成）
                        figure_agent：.geom → 校验 → SVG → figure.json
                            │
                            └─ 起 NarrationSession（并发合成 N 段）
                                  │  首段就绪
                                  ▼
                              起 Task B（演示，挂进 currentResponseTask）
                                   step 1: 揭示 ids[1] → trim 描边
                                   await 播第 1 段 → waitUntilPlaybackFinishes
                                   step 2: …
                                   …
                                   收尾：算淡出 → 写历史（任务+讲解词）→ 回填结果
                                            │
   用户说话/按快捷键/新问题 ──────────────► 取消 Task A+B → 停播报 → 清屏 → 返回 interrupted
```
