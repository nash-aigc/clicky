> 这份文档记的是**分流模型的修订**：出口从 5 个收到 4 个，桌面管家并入主控循环。

> 状态：**设计已定，尚未实施**。

## 一、修订后的四类

判据只有一条：**这个动作会不会改变机器状态，而且结果不确定到需要回头看一眼。**

| 类 | 判据（用户的话） | 标签 | 执行体 | 循环 |
|---|---|---|---|---|
| **① 纯视觉** | 只是问、只是标注 | `[POINT]` `[SHAPE]` | 无执行体 | 无 |
| **② 画图** | 要一张图 / 要讲解一张图 | `[SVG_TRACE]`（新）`[SVG_BOARD]` `[SVG_AGENT]` | 画图助手（python 子进程） | 无（有多步时序） |
| **③ 主控循环** | 点击、输入、打开软件/文件夹/文件、改桌面文件 | `[CLICK]` `[TYPE]` `[SCROLL]` `[SELECT]` `[PRESS]` `[OPEN]` `[WAIT]` `[AX_TREE]` + **`[FILE_LIST]` `[FILE_READ]` `[FILE_WRITE]`（新）** | 主控自己（进程内） | 有 |
| **④ 兜底** | 后台长任务、跨项目、本机两类都做不了 | `[AGENT_SPAWN]` `[AGENT_SEND]` | Claude Code agent（`claude -p`） | 有 |

两个极端是 ① 和 ④：一个什么都不做，一个什么都能兜底。中间两类按「要不要回头看」分开——② 有多步但每一步都在剧本里，③ 每一步取决于上一步的结果。

## 二、为什么合并是对的：桌面管家其实是个完整的 agent

合并前先核了它的实现（`desktop_file_agent.py`，207 行）：

| 它的内部 | 证据 |
|---|---|
| **自带模型调用** | `call_model()`（`:44`），走 `api.deepseek.com` 的 `deepseek-chat`（`:31-33`） |
| **自带三个工具** | `tool_list_files` / `tool_read_file` / `tool_write_file`（`:86/105/118`） |
| **自带循环** | `message = call_model(messages)`（`:176`） |
| **自带作用域隔离** | `resolve_inside_desktop()`（`:70`） |
| **第二套 key** | `~/Documents/SuperAgent/Agent/Wanna/instant-agent/.deepseek-key`（`:31`） |

**所以现状是「四个模型在跑」**：主控视觉模型、Claude Code CLI、画图助手内部的 DeepSeek、桌面管家的 DeepSeek。合并砍掉的是第四个。

### 收益

| # | 收益 | 说明 |
|---|---|---|
| 1 | **砍掉一层嵌套模型调用** | 少一次 DeepSeek 往返、少一个循环、少一个失败面、少延迟 |
| 2 | **文件工作变成可观察的步骤** | 现在是「发 `[PY_AGENT]` → 等结果」，多步要跨轮次发多个标签（提示词自己写着 "if the task needs another step, emit another `[PY_AGENT:]` tag"）；合并后 读→改→写→验 是循环里的正常几步，每步看结果再决定 |
| 3 | **少一个 python 依赖** | 文件操作改在进程内用 `FileManager`，顺带少一个 key 文件、一个脚本路径的失败面 |
| 4 | **少一整段系统提示词** | `[PY_AGENT]` 那节的边界说明（只能在桌面、不能开 App、不能看屏幕）不再需要 |
| 5 | **主控本来就懂上下文** | 桌面管家只看到那句任务文本，看不到对话与屏幕；主控两样都有 |

### 代价与必须补的东西

| # | 事项 | 怎么做 |
|---|---|---|
| 1 | **「只能碰桌面」的隔离要从 agent 层搬到工具层** | 现在是结构性隔离（那个脚本的世界就是 `~/Desktop`）；合并后主控本来就能开 App、点任何地方，隔离必须由**工具自己**保证：路径 `realpath` 之后必须以 `~/Desktop` 开头，挡住 `../` 与符号链接逃逸。**照搬 `resolve_inside_desktop()` 的语义并写测试** |
| 2 | **`[OPEN:]` 要能开路径** | 今天 `[OPEN:app name]` 只开 App；要能开文件/文件夹（用户明确提的"打开桌面的某一个文件夹或某一个文件"） |
| 3 | **权限模型已定：逐路径授权** | 不是「允许读写桌面」这种粗开关，而是用户逐条提供路径、每条独立开关读/写——详见 **[07 文件访问授权](07-文件访问授权.md)** |
| 4 | **步数预算共享** | 文件工作与点击共享 15 步上限；文件操作通常几步就完，暂时够用，但要在日志里能看到步数花在哪 |

## 三、文件权限：逐路径授权（已定，详见 07）

文件能力不设「允许读写桌面」这种粗开关，而是**用户逐条提供的路径 + 每条独立的读/写开关**，
在设置页里做成一个列表。完整设计（数据 schema、匹配语义、逃逸防线、设置页 UI、验收矩阵）
在 **[`07-文件访问授权.md`](07-文件访问授权.md)**。

要点三条：

1. **空列表 = 一个路径都不能碰**（不是"默认允许桌面"）
2. 校验有**单一入口** `resolveAuthorizedPath(_:mode:)`，每次都跑：绝对路径 → `realpath` → 按**路径分量边界**匹配 → 嵌套取**最长匹配** → 读/写**两条独立判据**
3. 模型在系统提示词里看到授权清单，被拒时拿到**具体理由**（否则它只会反复试同一个路径）

## 五、验收（怎么知道合并没有偷偷丢能力）

| # | 判据 |
|---|---|
| V1 | 旧 `[PY_AGENT]` 能做的三件事各有对应：列目录 / 读内容 / 写内容，逐条实测一遍 |

## 六、与 04（图形讲解）的关系

两条线互不依赖，但共用同一套分类纪律：

- 04 改的是**② 画图**这一类（内部流水线 + 一个新标签 `[SVG_TRACE]`）
- 06 改的是**③ 主控循环**这一类（并入文件能力）与**分类表本身**（5 → 4）

两边合起来，出口数从 5 变 4，真 agent 数仍是 2（主控循环、Claude Code），画图助手与文件工具都是无自主决策的执行体。
