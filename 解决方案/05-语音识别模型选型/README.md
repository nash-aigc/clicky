# 语音识别模型选型 —— 把「全双工语音模型」当纯识别器用

> **任务状态：已落地（2026-09-24）。** 三条识别路全部实测跑通，默认走第 ① 条。
> 本文是完整的需求→验证→实现记录，写给下一个动这块代码的人。

---

## 一、问题的起点

用户在语音聊天里对比了两个模式之后发现：

> 「同样是说话，全双工语音模式下词是正常的，而在三段式下，我说的话识别得非常不清楚。」

排查确认了**它们用的不是同一个识别模型**：

| 场景 | 当时用的识别模型 | 路 |
|---|---|---|
| 三段式（听） | `qwen3-asr-flash-realtime` | 实时 websocket，专用识别模型 |
| 全双工语音 | `qwen-audio-3.0-realtime-flash`（听/想/说一体） | 实时 websocket，语音对话模型 |

同一台机器、同一个麦克风的对照实验证明：**3.x 这一代语音模型的识别明显强于 qwen3-asr 那一代专用识别模型**。

## 二、用户的方案（原话）

> 「全双工语音模型好像能输出文本，也能输出文本加音频。那么有没有可能用这个模型来输出文本，
> 这样在三段式上就可以反应非常快。我只用它来做语音识别和文本输出……然后再把它生成的文本
> 发给大模型。因为它是三个流程、三个步骤，三段式可以拆开，所以我可以在一开始识别时用一个
> 模型，生成音色时用另一个模型、另一个自定义音色。但全双工语音模式下，音色不能自定义。」

**这个思路的本质**：三段式的「听 / 想 / 说」是三个独立步骤，所以「听」这一步可以单独换成
任意一个又快又准的模型——包括把全双工那个语音模型**降格当纯识别器**用。
全双工做不到这一点，因为它一个模型包办听、想、说，音色因此被锁死。

## 三、可行性验证（2026-09-24，直连真服务）

关键问题：把语音模型当识别器，**它会不会顺手把回答也生成了**（那样白花时间和 token）？

```
session.update: modalities=["text"], turn_detection=null
→ 推音频（16kHz PCM16，100ms 一块）→ input_audio_buffer.commit
→ [0.27s] conversation.item.input_audio_transcription.completed
→ 事件统计里一个 response.* 都没有 —— 模型没有生成任何回答
```

两个**必要条件**，缺一条这个用法就不成立：

1. **`turn_detection: null`** —— 不给服务端 VAD。带上它，服务端自己判回合并自己开口回答。
2. **永不发 `response.create`** —— 不发，模型永远不生成。转写照常发生，因为它是服务端
   对「用户说了什么」的记录，不依赖模型回答。

`qwen-audio-3.1-realtime-plus` 同样验证通过（0.29 秒出转写、不回话）。

## 四、三条识别路（现在代码里的全貌）

路由在 `BuddyTranscriptionProviderFactory.bailianProviderForConfiguredModel()`，
**按模型名自动分流**，不给用户「协议」开关——多一个开关就多一个能和模型名矛盾的状态：

| 模型名形状 | 路 | 文件 |
|---|---|---|
| `qwen-audio-3.x-realtime-*` | **语音模型当纯识别器**（默认） | `BailianRealtimeSpeechTranscriptionProvider.swift` |
| 其它 `*realtime*` | 实时专用识别模型 | `BailianRealtimeTranscriptionProvider.swift` |
| 其余（如 `qwen-audio-3.1-asr-flash`） | 非实时 HTTP，整句一次认 | `BailianNonRealtimeTranscriptionProvider.swift` |

非实时那条路走的**不是** OpenAI 兼容端点——是 DashScope 同步多模态生成
（`POST {base}/api/v1/services/aigc/multimodal-generation/generation`）。
用 OpenAI 兼容那条去调它只会得到 `400 url error, please check url`，完全不提模型不存在。

## 五、实测数据（同一台机器、同一段 12 秒音频 `ref16k.wav`）

| 模型 | 结果 | 耗时 |
|---|---|---|
| `qwen3-asr-flash-realtime`（实时，旧默认） | 「你好，我是你的语音助手，**很高。**」← 截断 | 流式 |
| `qwen-audio-3.0-realtime-flash`（语音模型当识别器） | **一字不差** | commit 后 **0.27s** |
| `qwen-audio-3.1-realtime-plus` | 同上（这次只喂了 3 秒音频所以半句） | commit 后 **0.29s** |
| `qwen-audio-3.1-asr-flash`（非实时 HTTP） | **一字不差** | 1.27s（12 秒音频） |

## 七、设置页文案要点（用户明确要求写清的）

「听（识别）」页最上面的「识别模型」一栏：

1. **第一句话必须是**：「实时识别比非实时更快、也更准」。
2. **作用范围必须写明**：这一项在**两个地方**生效——对话页面，和语音聊天的**三段式**。
3. **三段式与全双工的根本区别必须写明**：三段式是三步拆开的（听/想/说），每一步都能单独挑
   模型、「说」还能用克隆音色；全双工一个模型包办听想说，**音色不能自定义**。
4. 每个选项带自己的路、代价、价格。

## 八、踩过的坑（换模型的人必读）

1. **端点家族不能混**：`qwen-audio-3.1-asr-flash` 不在 OpenAI 兼容路上
   （400 `url error` 不提原因）；语音模型的实时会话**必须**带 `OpenAI-Beta: realtime=v1` 头。
2. **`turn_detection` 必须显式给 `null`**：省略它的行为和带服务端 VAD 一样
   （模型会自己接话）。
3. **流式的中间结果会改写**：屏幕上「文字总是在变」就是它，不是 bug 是流式的本质。
   用户最终为此放弃了流式展示的诉求（「只有用户把话说完了，才能理解他的意思」）。
4. **每句重开会话是自找的**：官方 commit 之后**不关连接**，同一个会话连着 commit 两次
   两次都出结果。旧的「每句 cancel+重建」造成每一轮 `Socket is not connected` →
   2.4 秒宽限兜底 → 慢、卡、交上去的是半句。修法是 `beginNextUtterance()`
   （只清「一句」的状态，会话留着）。
5. **切换宽限要跟着路走**：实时 websocket 2.4 秒、非实时 HTTP 12 秒
   （`finalTranscriptFallbackDelaySeconds` 按 provider 各自报）。

## 九、遗留与代价

- 「说到**屏幕**立即截屏」依赖流式中间结果，换到非实时后**失效**（实时路上仍正常）。
- 「说话时实时显示识别文字」在非实时路上没有中间态可显示。
- 非实时路一次只能认一句（整句交付），连续追问场景已由实时路覆盖。
