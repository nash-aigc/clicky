# 05 · 文本 agent

> 负责"把话说好"：问答、翻译、写作、讲解、总结，以及各个专业场景的写法。
> **它没有任何工具，且只有读权限、没有写权限。** 定稿 2026-09-25。

---

## 一、它为什么存在

用户的原话：

> 文本类 agent **没有任何工具调用**，它只是辅助用户不同场景的需求，去生成文本。
> 它可能包含在这个场景下应该怎么回复、在另外一个场景下应该怎么回复，
> 然后它以**技能**的形式存在于这个 agent 里面。
>
> 当用户同时处理**销售、营销、财务、金融、法律、商务、建筑**等不同场景的问题时，
> 如果全部注入系统提示词就会过载。这些场景实际上是无缝切换的，
> 因此需要把不同场景放入技能中，将**基本描述加载到上下文**，
> 再根据屏幕截图或模型理解，**自动调用对应的场景**。

## 二、权限

| 项 | 权限 | 为什么 |
|---|---|---|
| **写文件** | ❌ **不可以** | 它的产物是文字；要不要落盘由用户或执行 agent 决定 |
| 读文件 | ✅ 可以（只读） | 有时候要读一份资料才能写 |
| 工具 / MCP / 脚本 | ❌ **一个都不给** | 它是"生成质量"的 agent，给它工具只会让它跑偏 |
| 点击 / 打字 | ❌ 不可以 | — |

**这条权限差异是刻意的**：文本 agent 被误用/被注入时，最坏结果只是"写了一段不该写的字"，
不是"在机器上做了不该做的事"。

## 三、技能（场景）怎么组织

```
文本 agent 的提示词里常驻：每个场景的**一行描述**
     ├─ 销售文案 — 用户要写产品介绍、卖点、话术时
     ├─ 营销策划 — 用户要做活动方案、推广节奏时
     ├─ 财务分析 — 用户要读报表、算指标、写财务说明时
     ├─ 法律文书 — 用户要写合同条款、法律意见时
     ├─ 商务沟通 — 用户要写邮件、提案、谈判要点时
     └─ 建筑/工程 — 用户要写方案说明、技术描述时
                │
                └─ 用到哪一个 → 展开那一个的**正文**（几千字的做法）
```

**两级加载是硬保证**：场景的正文**永不全量进提示词**——否则就是用户说的"过载"。
展开方式与执行 agent 的 L1 展开同一套机制（[`细节/08-组装机制…`](细节/08-组装机制与上下文管理.md)）。

## 四、什么时候归它，什么时候不归它

| 需求 | 归谁 | 为什么 |
|---|---|---|
| 「写一篇关于 XX 的文章」 | **文本 agent** | 长内容 + 可能有场景方法论 |
| 「翻译这段话」 | 主 agent 自己答就行 | 一句话的事，不值当派活 |
| 「屏幕上这句话什么意思」 | 主 agent 自己答 | 看一眼就能说 |
| 「把这段存成文件」 | **执行 agent**（文本 agent 写不了盘） | 权限决定 |
| 「查一下我昨天做了什么」 | **执行 agent**（要读文件/知识库） | 要动工具 |

**判断口径**：**要产出"长内容/专业文本"→ 文本 agent；一句话能答完 → 主 agent 自己答；
要动工具或要落盘 → 执行 agent。**

## 五、失败怎么办

| 情况 | 处置 |
|---|---|
| 写得不合用户口味 | 用户说"再改改" → 重写（不需要循环机制） |
| 场景选错 | 主 agent 下一轮换场景（低代价，因为它不动机器） |

**没有 Claude Code 兜底**：它不动机器状态，最坏结果是文字不满意。

## 六、待实测的一点（诚实标注）

同一句话在**两个场景下该怎么说**是不同的（"这段合同怎么写" vs "这段销售文案怎么写"）。
**场景技能按需加载是否真的比全量注入更好**——需要一次对照实测（[09](09-施工顺序与验收.md) E4）。
风险在于：场景识别错了，写的方向就错了，而用户不一定看得出来。
