# 04 · 高频统计与高速通道（2026-09-25 增补）

> 用户的原话（定稿依据）：
>
> > 复盘 agent 首先要读取用户曾经所有的任务类型，然后是任务内容，再对它做概率统计或整体统计。
> > 要有一张表，统计用户的任务类型：**先分大的分类，再在每个分类下考虑有哪些具体的小类型**。
> > **如果用户的需求超过五次，就把它做一个标记**——这个任务可以单独独立出来，单独作为一个旁支路。
> > 因为遵循的是代码极简设计的哲学……旁边加上一条线。
> >
> > 目的是：如果复盘发现某一个任务或某一个需求是高频的，就应该**先把它做成一个脚本**让它快速执行，
> > 或者做成**脚本 + 参数**的形式；或者直接把某一个工具（比如某个 MCP 里的工具）**直接写入系统提示词**；
> > 或者直接把这个脚本写入系统提示词；**甚至把脚本路径直接写入系统提示词**。
> > 因为它是高频需求，让 AI 直接看到，看到之后匹配这个需求就直接执行。
> >
> > 也可以这么理解：整个 AI 架构是一条正常的路（主 agent → sub agent 的标准通道），
> > **但旁边有一个高速通道**。高速通道的实现方法**一定且只能**是通过把提示词/代码/脚本/工具/技能，
> > 或者"怎么去使用光标"这些东西**写入系统提示词**。
>
> 状态：**设计已增补，尚未实施。** 本篇是 [README](README.md) §七产出物清单的**新一类产出**
> ——前四类（技能/工具/参考条目/建议）产出的是"能力"，这一类产出的是**速度**。

---

## 一、它在复盘里是什么位置

复盘原本的产出是"把反复出现的事固化成能力"（工具、技能、参考条目）。这一篇补的是它的另一半：
**把反复出现的需求固化成"一眼就能匹配上的入口"**——同一个统计结果，两种用法：

| 统计发现 | 原本的产出（已有设计） | **新增的产出（本篇）** |
|---|---|---|
| 某个操作反复出现 | 固化成脚本 / 技能 | 同时**把它（或它的路径）写进系统提示词**，让主 agent 一眼认出、直接执行，不进循环 |
| 某类问题反复出现 | 固化成参考条目 / 技能 | 同样的手法：把"遇到这类问题该怎么办"的一行写进提示词 |

## 二、统计表长什么样

> 先分大的分类，再在每个分类下考虑有哪些具体的小类型。

| 大类 | 小类 | 出现次数 | 首次 / 最近 | 跨越天数 | 当前处置 |
|---|---|---|---|---|---|
| 系统控制 | 调音量到指定值 | 23 | 09-03 / 09-24 | 12 天 | **已进高速通道**（脚本 + 参数） |
| 系统控制 | 切换深色模式 | 7 | 09-10 / 09-23 | 9 天 | 候选 |
| 屏幕标注 | 圈出某个元素 | 6 | 09-12 / 09-22 | 6 天 | 候选（属于图形 sub agent 的活，不快通道） |
| 内容生成 | 把选中的话翻译成英文 | 11 | 09-05 / 09-24 | 11 天 | **已进高速通道**（提示词里一行） |
| 文件 | 把剪贴板内容存成桌面文件 | 4 | 09-14 / 09-24 | 3 天 | 观察中 |

**统计单位是"任务类型"，不是"句子"**——同一句原话说五次算五次，但换个说法做同一件事也要归到同一个类型里
（归类的粒度由复盘 agent 判断，它读的是任务内容与已有标签）。

## 三、阈值：五次是怎么算的

用户定的是「超过五次就标记」。为了让它真的代表"高频"而不是"某个下午的爆发"，加两条限定：

| 规则 | 为什么 |
|---|---|
| **达到 5 次**才进入候选 | 用户定的数 |
| **且跨越 ≥ 3 个不同日期** | 防止一个下午连说五遍同一件事就被判定成"长期高频"。同一天里重复五遍的，多半是当下的临时需要 |
| **且最近 30 天内出现过** | 半年前用过二十次、现在不用了的需求，不该占高速通道的位置 |

达不到的全部留在表里继续观察——**不满足就什么都不做**，这是默认结果。

## 四、晋级有四种形态（从轻到重）

| 形态 | 写进提示词的东西 | 适合什么 |
|---|---|---|
| ① **一行提示词** | "用户说『静音』→ 直接执行 `mute`" | 无参数、说法固定的 |
| ② **脚本路径** | "高频操作：调音量（脚本路径 …）" | 有脚本但参数由主 agent 现生成 |
| ③ **脚本 + 参数** | "用户说『音量调到 N』→ 执行 …，N 从话里取" | 参数明确、模式固定 |
| ④ **工具 / MCP 工具** | "遇到 X 用工具 Y（参数 …）" | 第三方能力，如某个 MCP 里的固定动作 |

**四种的共同点**：写进提示词的都是**"一眼能认出的入口"**，不是能力本身。
能力仍旧住在工具库 / 技能 / MCP 里——提示词里只有一行索引。

## 五、三条必须守住的规矩

### 5.1 进系统提示词的东西必须有预算上限

这是**和"简化提示词"直接冲突**的一件事：我们刚把 12,096 字符的动作说明搬进 sub agent，
高速通道又在往提示词里加东西。所以必须定死：

| 规矩 | 值 |
|---|---|
| 高速通道路段的总预算 | **不超过 ~800 字符（约 20 行）** |
| 超预算怎么办 | **按使用频率淘汰**：掉出前 20 名的自动降级回标准通道（不删除脚本，只是从提示词里撤出那一行） |
| 长期不用的 | 超过 60 天没命中 → 自动撤出，回到观察表 |

**没有这条，半年后提示词会重新长成今天这个胖子。**

### 5.2 必须用户批准才能进

写进提示词 = 给主 agent 一条长期指令。一条统计错了的条目不是"没用"，而是**每次遇到都会被错误地执行**。
所以沿用既有规矩（[README](README.md) §八）：进待审区，用户批准才生效；拒绝的移到 `已拒绝/`，不删除。

### 5.3 只写"入口"，不写"怎么做"

高速通道那一行只回答"这事该用哪个脚本/哪条路"。**具体怎么做仍然住在 sub agent 的技能里**——
否则我们就用另一种方式把提示词重新吹胖了。

## 六、和标准通道的关系（不冲突的原因）

| | 标准通道 | 高速通道 |
|---|---|---|
| 谁构建 | 人（设计时就写好） | **复盘 agent 从真实使用里长出来** |
| 命中后 | 主 agent 判断 → 交 sub agent → 循环 | **直接执行**，不进循环 |
| 兜底 | Claude Code | 执行失败 → **落回标准通道**（这条必须写死） |
| 上限 | 无（它是完备的） | 20 行 / 800 字符 |

**高速通道永远不是唯一的路**：它命中不了、或者执行失败，都必须能落回标准通道完成同一件事。
这条保证的是"高速通道只影响快慢，不影响对错"。

## 七、验收

| # | 判据 |
|---|---|
| H1 | 统计表按「大类 → 小类」两级呈现，每行有次数、首末时间、跨越天数（可用构造数据验证） |
| H2 | 同一句话在一天内说 5 次 → **不晋级**（未跨 3 天） |
| H3 | 跨 10 天说了 6 次 → 进入候选并出现在待审区 |
| H4 | 未批准的候选**没有**进入系统提示词（可对比提示词字节数） |
| H5 | 晋级条目在提示词里只占一行，且**不含**具体步骤（步骤仍在技能/sub agent 里） |
| H6 | 高速通道命中时**不进入**主 agent 循环（日志可验证） |
| H7 | 高速通道执行失败 → **落回标准通道**并完成任务（构造一次失败） |
| H8 | 提示词里高速通道路段超过预算 → 按频率淘汰最低的一条，并留下记录 |
| H9 | 60 天未命中 → 自动撤出提示词，回到观察表（脚本本身保留） |
| H10 | 撤出后再用起来 → 能重新晋级（不是一次性的单行道） |
