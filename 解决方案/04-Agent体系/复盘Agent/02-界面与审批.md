# 02 · 界面与审批

> 这份文档定的是复盘的**用户界面**：入口在哪、页面长什么样、审批目录怎么组织、
> 点一张卡片之后发生了什么。
> 它回答的是"用户怎么跟复盘 agent 打交道"，agent 本身的机制在 [`README.md`](README.md)。
>
> 状态：**设计已定，尚未实施**。（`归档`的搬移用户已完成，本篇不涉及。）

## 一、入口：侧边栏底部那个空位

**现状（代码事实）**：`HomeSpaceSidebarView.bottomActionRow`（`:797-823`）现在只有左边的「设置」——归档已按用户要求移到「设置 → 导入导出 → 归档」（`SettingsPage.archive`），右边空着。

**复盘按钮放进那个空位**：与「设置」同款 `NotchBarActionButton`（长方形、30pt 高、带 hover 高亮），右边对齐。两颗按钮在同一行、同一条竖直线上，符合那一行既有的排版纪律。

```
┌──────────────────────────┐
│  [ 设置 ]          [ 复盘 ] │   ← 底部一行，右侧是新按钮
└──────────────────────────┘
```

## 二、接管机制：复用现有那一套

`NotchSheetRootView` 现在用两个 `@State` 做整窗接管：`showsSettings` / `showsArchive`，**设置优先于归档**（`:73-86`）。复盘照抄这个形状：

| 改动 | 内容 |
|---|---|
| 新增 `@State showsRetrospective` | 第三个接管标志 |
| 优先级 | **设置 > 复盘 > 归档**——设置仍要最优先，因为它可能由外部请求触发（`expandShowingSettings`） |
| 外部设置请求要能退出复盘 | 照 `:178-179` 的既有做法：`consumeRequestedSettingsPageIfNeeded()` 要同时清掉复盘，否则外部的设置请求会停在复盘页上 |
| 侧栏里那些 `!showsSettings` 判断 | 还要加上 `!showsRetrospective`，否则复盘打开时侧栏仍会响应选中 |
| 从复盘页返回 | 与设置/归档同款：footer 的「返回」把 `showsRetrospective = false` |

| 元素 | 内容 |

## 四、审批目录：**按类聚合**，不是一条一个文件

### 四.1 目录

| 项 | 值 |
|---|---|
| 设置项 | 设置 → 复盘 → **审批目录**（`NSOpenPanel` 选目录） |
| **默认** | `/Users/mjm/Documents/SuperAgent/Agent/Wanna/Memory/自我升级（复盘）/` |
| 结构 | `低/`、`中/`、`高/`、`已批准/`、`已拒绝/`（不存在时自动创建） |

### 四.2 文件：**一类一个文件，一条一个小节**

用户的原话：

> 没有必要每一个脚本或每一个东西都作为一个独立文件来显示。可以把某一类的技能放在一个文件里……很多需求是相似的，这样可以减少用户查看的成本。用户是一个一个看的，如果每一个都只有一句话，就没有必要这样做。

所以：

| 粒度 | 是什么 | 例 |
|---|---|---|
| **文件** | **一个类目** | `低/技能-写作类.md`、`低/脚本-Notion.md` |
| **小节** | **一条待审项** | 该文件里的 `## 技术文章写法` |

**类目从哪来**：直接复用主控打的任务标签词表（`task_labels.json`）——复盘按 `taskLabels` 聚类，**不需要另造一套分类**。词表外的归入 `其他`。

```markdown
# 技能 · 写作类

## 技术文章写法
<!-- id: 写作-003  status: 待审  source: 2026-09-24T14:03,2026-09-24T14:11 -->
用户连改三篇文章，每次都要求：先给结论、再给原理、最后给例子。

## 竞品分析框架
<!-- id: 写作-004  status: 已批准  approvedAt: 2026-09-25T09:10 -->
对比时先列维度再打分，不要一上来就给结论。
```

- **元数据用 HTML 注释**：人读时不可见（不会把文件弄得像配置文件），程序解析时一行一个正则就能取到 `id` / `status` / `source` / `approvedAt`
- **`status` 落在小节上**，所以同一个文件里可以"批准这两条、拒绝那一条"，聚合存放与逐条决定不冲突
- **`sourceTurns` 落在小节上**（出处必须能追溯到当时那几轮对话，见 §四.4）

### 四.3 脚本：一个文件多个函数

用户的原话：

> 同一类型的脚本应该放在一个脚本文件里。

| 形态 | 约定 | 例 |
|---|---|---|
| **Python 类** | **一个文件 = 一个模块，一个函数 = 一个工具**；manifest 用 `文件#函数` 指向 | `tools/Notion/notion.py#save` / `#latest` |
| **AppleScript 类** | 一个文件一个入口（`osascript` 直接跑），或用 `on run argv` 按第一个参数分派 | `tools/备忘录/notes.applescript` |

于是**"工具"的标识不是文件路径，而是 `文件 + 函数`**——这跟"一类一个文件"是同一个思路：小工具聚在一个模块里，调用时精确到函数。

### 四.4 怎么决定"新建一个类文件"还是"追加一个小节"

复盘的每一步都按这个顺序判断：

```
一条提案（来自某几轮 turn）
   ↓
① 它属于哪个类目？→ 取 taskLabels 里匹配的那一个
   ↓
② 该类目在 低/ 里已有文件吗？
   ├─ 有 → **追加一个小节**（不新建文件）
   └─ 没有 → 建一个类文件（`低/技能-<类目>.md` / `低/脚本-<类目>.md`）
   ↓
③ 已有文件里存在**同一条**提案吗？（比对正文的语义，不是字符串）
   ├─ 存在 → 不重复写；把新的 sourceTurn 追加进那条的 `source`
   └─ 不存在 → 写入新小节
```

三条纪律：

1. **能追加就不新建**——文件数量有界，用户翻得动
2. **同类合并**——同一类的技能放一个文件；同一类的脚本放一个模块
3. **一个类文件超过约 200 行**时，复盘**提议拆分成两个类**（这属于一条"中"级提案，要用户批准，它不自己拆）

### 四.5 出处（`sourceTurns`）必须落在条目上

用户要能顺着某一条回到当时那几轮对话，判断这个结论可不可信。所以它是**小节级**的，不是文件级的——一个文件里不同条目的出处当然不一样。

## 五、点一张卡片之后发生什么

```
点「低」
   ↓
读 <审批目录>/低/ 下所有 status: 待审 的 md → 全文拼接
   ↓
作为**上下文**注入（不是系统提示词，按数据不是指令的纪律包起来）
   ↓
右列进入与**复盘 agent** 的对话：
   · 模型 = 第 4 个角色「🔍 复盘」（见 README §九，可独立配 URL/key/modelID）
   · 系统提示词 = 复盘自己的那一份（**不是**语音助手那份）
   · 用户接下来问"这些哪些要改、哪些不改"，它据此讨论
```

| 细节 | 决定 |
|---|---|
| 对话存在哪 | 新的会话类型（`ConversationSession.sessionKind = .retrospective`，`decodeIfPresent` 兜底）——**不进普通会话列表**，否则侧栏会被复盘对话挤满 |
| 切卡片 | 已选等级的内容是**每次请求现读**的，所以用户在别处改了目录，切一次卡片就同步了 |
| 复盘 agent 的工具面 | 只三样：读历史 turn、读/写审批目录、改待审项的 `status`。**不碰用户文件、不改代码、不删任何东西** |
| 是否复用主控的循环 | 不复用。复盘是"讨论 + 改文件"，不是"点击 + 看屏幕"，所以**不走**观察判据那一套 |

## 六、口头问"有哪些需要审批的"

两条路，都对：

| 在哪里问 | 谁回答 | 怎么读 |
|---|---|---|
| 在主控里问（语音/输入） | 主控循环 | 直接读审批目录并汇报——它是 **App 自己的产出目录**，不受文件授权清单约束 |
| 在复盘页问 | 复盘 agent | 它自己读 |

**建议**：主控那边把它做成一个**只读的固定动作**（不进工具库、不需要审批），因为它只是"看一眼待审列表"。

## 七、批准 / 拒绝 之后发生什么

| 等级 | 批准 | 拒绝 | App 会执行吗 |
|---|---|---|---|
| **低**（新建技能/脚本/参考条目） | 该**小节**从待审文件里移除 → 合并进正式目录对应文件（`skills/写作类.md` 或 `tools/Notion/notion.py` 的对应函数）→ **立刻生效** | 该小节移到 `已拒绝/` 的同名类文件里 | ✅ 生效 |
| **中**（改已有工具/技能） | 展示 diff，用户确认后应用 | 同上 | ✅ 应用 diff |
| **高**（删除 / 改系统提示词 / 改 App 代码） | 只能标记「已采纳」→ **用户自己动手** | 同上 | ❌ **App 不做任何改动** |

**两条硬规则**：

1. **拒绝 = 移动，不是删除**——进 `已拒绝/`，可回溯。这也是"复盘 agent 禁止删除"的体现：它连被拒绝的东西都动不了，只能看着。
2. **每次审批记一笔**（谁批的、什么时候、来源 turn），写进该 md 的 front matter，跟着文件一起走。

## 九、验收

| # | 判据 |
|---|---|
| U1 | 侧栏底部：设置左、复盘右；点复盘 → 整窗接管，左列是三张卡片 |
| U2 | **优先级**：复盘页打开时点设置 → 设置接管、复盘退出；外部的设置请求也能退出复盘 |
| U3 | 三张卡片的待审**条数** = 目录里 `status: 待审` 的小节总数（不是文件数）；改目录后跟着变 |
| U3b | **聚合**：同一类目的第二条提案**追加进已有文件**，不新建文件；跨类目才建新文件 |
| U3c | **去重**：同一条提案第二次出现时不重复写入，只往它的 `source` 里追加新的 turn |
| U3d | **脚本多函数**：`tools/Notion/notion.py#save` 与 `#latest` 都能被单独调用 |
| U4 | 点「低」→ 右列对话的上下文里**确实包含**低目录下所有待审小节（日志可验证） |
| U5 | 复盘对话**不进**普通会话列表（侧栏「对话」段不变） |
| U6 | 批准一个低风险**小节** → 它从待审文件里消失、合并进正式目录的文件、**运行时立刻可用**（接着发一句相关请求，走的是新工具/新技能）；同文件里没被批准的小节**原样留着** |
| U7 | 拒绝一个**小节** → 它出现在 `已拒绝/` 的同名类文件里，**没有被删除** |
| U8 | 高等级项**无法被 App 执行**（只有「已采纳」标记） |
| U9 | 审批目录不存在 → 自动创建；不可写 → 明确报错（不是静静地什么都不做） |
| U10 | 归档的入口仍在 `设置 → 导入导出 → 归档`（回归：这次的改动没有动它） |
