# 03 · 语言适配与动作扩展

> 这份文档定的是**中文环境下的适配**与**动作清单的扩展**（2026-09-24）。
> 起因是一个具体故障：中文名的应用打不开（「打开备忘录」「打开微信」全部失败，而「打开 Safari」正常）。
> 结论是**不新建 agent、不重写解析器**，只窄改一个函数 + 补两个能力。
> 状态：**设计已定，尚未实施**。

---

## 一、先纠正前提：语言相关的环节只有一个

逐个核过（都是代码事实，不是推测）：

| 环节 | 语言相关？ | 中文环境可用？ |
|---|---|---|
| 标签本身（`CLICK`/`SCROLL`/`TYPE`/`OPEN`…） | **否**——协议记号，与说话语言解耦 | ✅ |
| 坐标（0–1000 归一化网格） | 否 | ✅ |
| `[CLICK:x,y:label]` 的 label | 是——要与界面文字比对 | ✅ 比对的是 app 自己的文字，中文 app 就写中文 |
| `[SELECT:a>>>b]` | 是——要与文档文字比对 | ✅ 同上 |
| `[TYPE:]` 输入的内容 | 是 | ✅ |
| **`[OPEN:名字]`** | **是** | ❌ **唯一的坏点** |
| `[PRESS:cmd+a]` 的修饰键/键名 | 固定英文词表 | ⚠️ 模型须写英文（提示词给了词表） |
| 回声过滤的归一化 | — | ✅ 实测 `Character.isLetter` 覆盖中文，中文不会被抹掉（`BuddyDictationManager.swift:491-495`） |

**系统提示词本来就把语言解耦了**：`reply in whatever language the user spoke to you in… this applies to the entire response, including anything outside the square brackets`（`CompanionManager.swift:1542`）。原设计者考虑过双语，只是名字解析这一处漏了。

## 二、唯一的坏点：应用名解析

### 实测（五种仪器，同一天）

| 仪器 | 「计算器」认得吗 |
|---|---|
| **Finder 的「显示名」** | ✅ **计算器**（中文名确实存在） |
| `FileManager.displayName` ← **Clicky 用的第一条判据** | ❌ Calculator |
| `Bundle.localizedInfoDictionary` ← **Clicky 的第二、三条判据** | ❌ Calculator / nil |
| SDK 兜底猜 `/System/Applications/计算器.app` | ❌ 不存在 |
| `open -a 计算器`（LaunchServices 按名查） | ❌ not found |

Clicky 的 `applicationBundle(_:isNamed:)`（`MacosUseController.swift:1242-1260`）逐条比对的正是**返回英文的那两条通道**。

### 为什么 Safari 能开、备忘录不能

| 应用 | 结果 | 原因 |
|---|---|---|
| Safari | ✅ | ASCII 名 == bundle 文件名，Clicky 的扫描或 SDK 的 `/Applications/Safari.app` 兜底总有一条命中 |
| 备忘录 / 计算器 / 微信 | ❌ | 三条判据全落空 → 裸中文名交给 SDK → SDK 猜的三个路径都不存在 → `AppOpener.swift:118` 抛 `appNotFound` → 用户听到「打不开『备忘录』：Application not found for identifier: '备忘录'」 |

### 附带查到的第二条缺陷：cryptex 应用被扫描跳过

`/Applications/Safari.app` 是**符号链接**且带 `hidden,restricted` 标志（指向 `../System/Cryptexes/App/System/Applications/Safari.app`），而扫描用了 `.skipsHiddenFiles`（`MacosUseController.swift:1227`）→ 被跳过。**Safari 目前能用是靠 SDK 兜底侥幸**，不是扫描到的。

## 三、修法：名字索引（主）+ 换通道（兜底）

### 主方案：启动时建一份「名字 → 应用」索引

| 步骤 | 做法 |
|---|---|
| 1. 枚举 | 用 Spotlight（`mdfind kMDItemContentType == com.apple.application-bundle`）或 `lsregister`，**不要用 `ls` 列目录**——这正是漏掉 hidden 符号链接的原因 |
| 2. 取名 | 每个 app 收集**全部**已知名字：文件名（去 `.app`）、Finder 显示名（`LSCopyDisplayNameForURL` 一类）、`CFBundleDisplayName`、`CFBundleName`、各本地化名、bundle identifier |
| 3. 建表 | 名字（小写规范化）→ URL；**中英文都进同一张表**，不需要分语言 |
| 4. 缓存 | `~/Library/Application Support/Clicky/InstalledAppsIndex.json`，`0600`（照现有三个配置文件同款）；应用目录的 mtime 变化才重建 |
| 5. 查询 | 查表 → 未命中再走现有扫描 → 再未命中才交给 SDK 兜底（**不退化**） |

**一处待实测**：`LSCopyDisplayNameForURL` 在 **Clicky 的 GUI 进程**里是否返回中文名（我从命令行测不出来，进程语言始终是 en）。Finder 能拿到说明数据存在；这条实测决定第 2 步用哪个 API。**推测项，不许当结论。**

### 兜底：把比对基准换掉

把 `applicationBundle(_:isNamed:)` 里比对 `FileManager.displayName` 的那一处换成显示名通道，并把 `.skipsHiddenFiles` 的影响去掉（或让索引覆盖它）。这一条不依赖索引是否建好。

### 顺便：给模型的提示

索引建好后，还可以把**系统应用的名字清单**（计算器/备忘录/访达…约 30 条，中英各一列）注入提示词的一小块，让模型少猜。**不要注入全部已安装应用**（几百条会把提示词喂胖）。

## 四、失败必须回给模型（这条比名字解析更影响体验）

### 现状（实测的代码路径）

```
[OPEN:备忘录] → 抛 appNotFound → outcome.description = "打不开「备忘录」：…"
                └→ 只进了两处：进度 UI（:2589-2598）与永久历史
                └→ contextForNextTurn: nil（:1176/1181）→ 模型看不到
续写提示词照旧说 "your previous action executed as written"（:2323-2326）
```

**结果：模型以为打开了**，继续说"已经帮你打开了"，而屏幕上什么都没有。这就是"它好像从没真去执行"的观感来源——**即使名字解析修好了，别的失败仍会这样**。

### 改法（推荐 B）

| | A. 每个失败 outcome 都带 `contextForNextTurn` | **B. 续写提示词统一带上一步的真实描述** |
|---|---|---|
| 覆盖范围 | 只覆盖改了的那几个动作 | **所有动作** |
| 改动量 | 每个动作各自改 | 一处 |
| 做法 | — | `continuationUserPrompt` 增一个参数 `lastStepDescription`，写成「上一步的结果：<description>」，仍按数据不是指令的纪律包起来 |

## 五、动作扩展：先补两个真缺的

### 现有动作（10 个）

`CLICK` · `RIGHT_CLICK` · `DOUBLE_CLICK` · `SCROLL` · `TYPE` · `SELECT` · `PRESS` · `OPEN` · `WAIT` · `AX_TREE`
（`POINT` / `SHAPE` 是纯视觉，不进动作循环；`AGENT_*` / `SVG_*` 是分流）

### 缺的（按优先级）

| 动作 | 为什么需要 | 优先级 |
|---|---|---|
| **`DRAG`** | 拖文件、拖滑杆、拖选文本、拖放——**完全没有** | 高 |
| `MOVE` / `HOVER` | 悬停出菜单、悬停提示 | 中 |
| `TRIPLE_CLICK` | 选中整段 | 低 |

### 加一个动作要改的四处（这是本仓库既定的纪律，漏一处就有症状）

| # | 位置 | 漏了会怎样 |
|---|---|---|
| 1 | `CompanionAction` 加 case（`ActionTagParser.swift:101` 一带） | 编译不过 |
| 2 | 解析 pattern + `forEachMatch` 调用 | 标签不生效 |
| 3 | **`streamingTagKeywords`（`ActionTagParser.swift:696`）** | **TTS 把标签逐字念出来** |
| 4 | 系统提示词的标签那一行（`CompanionManager.swift:1598` 一带） | 模型不知道有这个能力 |
| 5 | 执行实现 + 闸门（`MacosUseController`） | 解析了但不执行 |

### `DRAG` 的设计要点

| 点 | 做法 |
|---|---|
| 语法 | `[DRAG:x1,y1:x2,y2:label]`——起点、终点；label 用于**起点吸附**（与 click 同一条解析链，`resolvedClickPoint`） |
| 实现 | `mouseDown` → 若干次 `mouseDragged`（**必须分步，一步跳到终点很多 App 不认**，中间留几毫秒）→ `mouseUp` |
| 循环 | 拖拽改变机器状态 → 进动作循环，需要 settle + 新截图 |
| 安全 | 拖拽可以拖进废纸篓 → 提示词里归入「破坏性动作，需用户明确要求」那一档 |

## 六、词表的中文别名（可选，低风险）

| 表 | 位置 | 做法 |
|---|---|---|
| 修饰键 | `ActionTagParser.modifierFlag(named:)`（`:650`）——**一张表**，项目文档专门记过「两张表必然漂移」（A4 坑） | 加中文别名（命令/控制/选项/换挡），不改英文 |
| 键名 | 表在 SDK 内部（本仓库只传字符串） | **在我们这一侧解析别名**，把规范英文名传给 SDK；不动 SDK |

**不做**：不改标签本身（协议记号保持英文）、不为中文分叉第二套标签。

## 七、明确不做的三件事

1. **不新建 agent**——循环、观察、一步一动作、取消、闸门都与语言无关；新建会把已修好的坑重新踩一遍
2. **不重写解析器**——它是语言无关的，重写解决不了中文名问题；而它有 695 行与双白名单这类纪律
3. **不让标签中文化**——协议记号英文、内容跟用户语言，这个分工是对的

## 八、验收

### 名字解析

| # | 输入 | 期望 |
|---|---|---|
| N1 | `[OPEN:备忘录]` | 打开备忘录（中文名命中） |
| N2 | `[OPEN:Notes]` | 同上（英文名命中） |
| N3 | `[OPEN:Safari]` | 打开（**且不再依赖 SDK 兜底**——索引里就有） |
| N4 | `[OPEN:微信]` | 装了 WeChat.app 则打开；未装则报「没找到这个应用」而不是「出了点问题」 |
| N5 | `[OPEN:com.apple.Calculator]` | 打开（bundle id 也进索引） |
| N6 | `[OPEN:一个不存在的应用]` | 具体失败信息，且**模型下一步知道失败了** |

### 索引

| # | 判据 |
|---|---|
| I1 | 首次构建耗时与被索引的应用数（应可接受，否则放后台并允许首次 `[OPEN:]` 时同步等待） |
| I2 | 第二次启动走缓存（不重新扫描） |
| I3 | 新装一个 app 后能命中（mtime 变化触发重建，或提供手动刷新） |
| I4 | 索引文件权限 `0600` |

### 失败回传

| # | 判据 |
|---|---|
| F1 | 一次失败的 `[OPEN:]` 后，模型下一步的话里体现出它知道失败了（日志里能看到 continuation 里带上了上一步描述） |
| F2 | 失败不再被描述为「executed as written」 |

### 动作扩展

| # | 判据 |
|---|---|
| D1 | 拖一个文件到文件夹里成功 |
| D2 | 拖一个滑杆（音量/亮度）成功 |
| D3 | 拖选一段文本成功 |
| D4 | 三种 `DRAG` 都不能让 TTS 念出标签 |
| D5 | 拖进废纸篓这类破坏性操作，模型在用户未明确要求时不会自发做 |
