# 01 · 总体框架 v2 —— 四步流水线与四类执行策略

> 2026-09-24 深夜重写。用户判定旧框架的**分类轴错了**：旧框架按"执行体"分（纯视觉 / 画图 / 主控循环 / Claude Code），
> 正确的轴是"**这个需求本身该怎么被执行**"。旧「画图」其实是纯显示的一种；旧「主控循环」里混着"纯代码就能完成"的
> 和"需要组装"的两种东西——它们的能力、检查方式、循环次数完全不同，不该共用一个类。
>
> 用户的原话（定稿依据）：
>
> > 第一步，由大语言模型分析设计标签。把用户的提问和当前屏幕的内容结合到一起，给到语言模型。
> > 第二步，把预先编排好的代码或关键词所对应的代码提前设定好。如果匹配，就直接执行代码，模型什么都不需要做；如果不匹配，就进行分流。
> > 不匹配时，首先让大模型介入。第一次是大模型思考是否匹配，第二次大模型介入是判断它属于哪一个类型，也就是进行分类。
>
> 状态：**框架 v2 设计定稿，尚未实施**。本文取代旧版按执行体分类的全部叙述；旧的执行体（工具库、画图助手、
> Claude Code、复盘）都还在，只是**各就各位**（映射见 §八）。

## 一、流水线：四步，两个 LLM 介入点

```
转写 + 截图
   ↓
【第 0 步 · 词面匹配】本地预设表：关键词 / 短语 → 预先编排好的代码
   ├─ 命中 → 直接执行代码，模型什么都不用做（只补一句语音收据）—— 零 AI 决策
   └─ 未命中 ↓
【第 1 步 · LLM 介入①】语义匹配：这个需求能对上预设库里的哪一条？
   ├─ 对上了 → 同上，执行对应预设（带模型生成的参数）
   └─ 对不上 ↓
【第 2 步 · LLM 介入②】分类：四类之一 + 产出该类的产物（标签 / 参数 / 计划）
   ↓
【第 3 步 · 按类执行】（见 §二）
```

| 设计点 | 决定 |
|---|---|
| 第 0 步与第 1 步的关系 | 同一张预设表，两次匹配：**词面**（本地正则，免费、2ms）与**语义**（LLM，能对上说法不同的同一条） |
| 两次 LLM 介入 | **框架上按两次介入设计**（这是用户定的结构）；实现时**允许合并为一次调用的两个阶段**——框架不管实现省不省 token（用户明说：现在重点是框架，不是 token 和时间） |
| 「分析设计标签」在哪 | 第 2 步的产出就是标签——旧的"LLM 分析设计标签"没有消失，它是分类的产物 |
| 预设表放什么 | 关键词 → 代码的**固化物**（工具库里的脚本 + 参数 schema）。固化判据不变：**要替模型记住它不可能知道的东西**（见 [`06-工具库与MCP.md`](06-工具库与MCP.md) §二） |

## 二、四类执行策略

判据轴：**这个需求的完成，靠"呈现"、靠"跑代码"、还是靠"AI 现场研究怎么组合"——组合时有没有方法论引导？**

| 类 | 是什么 | 产物 | 检查 | 循环 |
|---|---|---|---|---|
| **① 纯显示** | 画圈、移动鼠标、画图形、边画边说、逐笔画图讲解——对电脑**无任何影响**，不存文件不点击 | `[POINT]` `[SHAPE]` `[SVG_TRACE/BOARD/AGENT]` | **无** | **无** |
| **② 纯代码** | 本质是执行代码：预设脚本 + 模型生成的参数；或模型现写的一行代码。动作可能复杂，但被包装成一个代码文件 | `[RUN:工具:参数]`、`[CODE:一行]` | **不进观察循环**（无截图）；是否跑 verify 脚本由工具声明（见下） | **无** |
| **③ 组装 · 自由** | 需求既非纯显示也非纯代码，AI **自己研究**怎么实现：用哪些工具、先谁后谁、串行并行并发 | 一步一个动作：点击 → 输入 → 跑单步脚本 → 截屏保存…… | **看一步做一步**（每步截图回填） | 有，**10–30 轮** |
| **④ 组装 · 技能引导** | 同 ③，但组装按**用户预设的方法论**进行：技能热加载描述部分 → 选中 → 加载正文 → 按正文步骤组装；MCP 按官方标准协议调用 | 同 ③，外加技能引用 | 同 ③ | 有，**10–30 轮** |

### 各类的细节判定

**① 纯显示**：判据 = 完成后**机器状态零变化**。旧「画图」整类并入这里——逐笔画出 + 逐步讲解只是它的呈现方式，不改变"无影响、无检查、无循环"的性质。

**② 纯代码**：三种形态，本质相同——

| 形态 | 例 |
|---|---|
| 预设脚本 + 模型生成参数 | `[RUN:保存到Notion:内容]` |
| 模型**现写的一行代码** | 一条 `osascript`、一条 `shortcuts run` |
| 预设脚本组合进一条命令 | 打开某标签页 = 预设脚本 + URL 参数 |

**「现写代码」的安全栏（必须有的补充，用户原话允许现写，这里补边界）**：现写代码过一道**静态危险词检查**（`rm -rf`、`sudo`、重定向覆盖、删目录等即拒），**破坏性动作仍然遵守既有规则**（用户本轮回合明确要求过才执行）。通过后直接运行——它属于 ②，不进观察循环。

**「不需要检查」的准确含义**：② 不进**观察循环**（无截图、无看一步做一步）。但**脚本级 verify 不因此取消**——那是用户自己定的三件套（创建 + 独立校验 + 兜底，见 [`06`](06-工具库与MCP.md) §六）：是否跑 verify 由**工具声明**决定；高频口令类（备忘录、Notion）建议声明，复盘会为常失败的补上。

**③ vs ④ 的唯一区别**：组装时**有没有方法论**。④ 先热加载技能描述（只暴露描述部分，模型知道该用哪个），选中后加载正文，按正文的步骤/规则组装；③ 没有正文可依，全凭模型对工具的理解现场研究。**两者的执行器相同**（主控循环），可组合（④ 的某一步内部也可以是自由组装）。

### 组装类的原料（AI 研究组合的对象）

| 原料 | 说明 |
|---|---|
| 鼠标 / 键盘动作 | `CLICK` `TYPE` `SCROLL` `DRAG` `PRESS`…（单点能力） |
| **模块化单步脚本** | 工具库里的脚本按"函数 = 工具"暴露——**它们不直接完成用户指令，但可以互相拼接**，本质与 MCP 的 tools 同类 |
| MCP 工具 | 按官方标准协议调用；被提炼过的（见 §四）以纯代码形态出现 |

AI 在这里研究的是**编排**：选哪个、先谁后谁、串行还是并行、中间要不要看结果。

## 三、循环上限：最少 10 轮，最多 30 轮（2026-09-24 深夜修订）

用户的原话：

> 可能是多步骤方式，需要一个循环或几个步骤检查是否完成任务，没有完成就循环一轮又一轮，**最少 10 轮，最多 30 轮**就结束，完成不了就告诉用户。

| 项 | 值 | 说明 |
|---|---|---|
| 组装类（③④）任务循环 | **下限 10 · 上限 30** | **下限是新的**：10 轮之内**不许**向用户报「完成不了」——要么继续，要么已被打断； premature放弃比多跑几轮更伤信任 |
| 上限到顶 | **如实告知未完成** + 交代进行到哪一步、卡在哪 | 不许静默失败，也不许假装成功 |
| 单条 C 类链 | 仍算 1 步（[`04-观察判据与批量.md`](04-观察判据与批量.md)） | 批量不绕过上限 |
| B/C 判据 | **继续用于组装类内部** | 哪一步要看结果、哪条子链一次做完——判据不变，管的对象是组装里的每条链 |

## 四、提炼规则：高频 MCP 工具 → 纯代码

用户的原话：

> 如果 MCP 的某个脚本或某个工具经常被使用，但按照官方流程或使用方法需要传递很多次数据，比较麻烦，就把 MCP 里的工具和脚本直接提炼出来作为一个脚本，当作纯代码的方式来运行。
> 复盘时……直接把 MCP 里的某个工具提炼出来，单独做成一个脚本加参数的形式，用大模型生成参数、运行脚本，就可以减少很多中间 token 的消耗。

这条**已经在 06 / 复盘文档里**，此处确认它在 v2 框架里的位置：**提炼是 ④→② 的迁移通道**——经常以"组装"方式使用的东西，复盘把它固化成"纯代码"。三处落点：

| 场景 | 迁移 |
|---|---|
| MCP 某工具高频使用、传参繁琐 | 提炼成脚本 + 参数 → ② 纯代码 |
| 某需求反复靠"用户一步步引导"完成 | 梳理成**脚本组合**（→②）**或技能**（→④），看它是否有稳定的步骤序列 |
| 某类任务反复成功但没有沉淀 | 写成技能（方法论），让下次不用重新研究 |

## 五、复盘 agent 的三个新关注清单（第五个执行体的职责细化）

复盘要看的不只是"哪些能固化"，而是**三类高频模式**（用户的原话）：

| 清单 | 看什么 | 产出 |
|---|---|---|
| **A · 高频纯代码操作** | 哪些 `[RUN:]` / 现写代码反复出现 | 合并、参数化、进预设表（第 0/1 步命中率↑ → 更多请求零 AI） |
| **B · 高频组装需求** | 自由组装（③）的需求按类型聚类：哪几类任务总在拼同样的几步 | 沉淀成**技能**（→ 下次走 ④，有方法论）或**脚本组合**（→ ②） |
| **C · 反复失败 / 用户引导型** | 没有对应能力、AI 不知道调什么、或调用多次失败、最后靠用户一步步引导完成的任务 | **重点对象**：梳理成脚本（→②）或技能（→④，把"怎么被引导"写成方法论） |

清单 C 最有价值：**"用户教过 AI 一次"是最强的固化信号**——那次引导的每一步都是方法论的一部分。

## 六、Claude Code 的位置：仅两条入口，模型永不自主派发（2026-09-24 重写）

用户的原话：

> 只有这两种情况下才需要调用，否则正常情况下永远都不要使用，因为它太复杂。我们现在设计的 agent 是正常情况下满足用户高频需求的 agent。

| 入口 | 触发 |
|---|---|
| **UI** | 面板侧栏的「对话 / Agent / 语音聊天」切换器（已存在，一行不改） |
| **转写关键词分流** | 用户的话明确提到 **claude / cloud（同音模糊）/ cc（词边界精确）**，或明确说用 Claude Code 完成什么——**转写之后、模型之前**整体路由，不付视觉请求成本 |

随之移除的：系统提示词的派发节（`:1688-1690`）、`[AGENT_SPAWN]/[AGENT_SEND]` 两个 pattern 与白名单、`dispatchAgentRequests`。**模型不再知道 Claude Code 的存在**；四类流水线永远到不了它。完整设计与验收见 [`../ClaudeCodeAgent/README.md`](../ClaudeCodeAgent/README.md)。

## 八、各执行体的最终位置

| 执行体 | 在 v2 里的角色 |
|---|---|
| 主控模型（🧠） | 第 1/2 步的两次介入 + 组装类的循环决策者——**唯一贯穿始终的 AI** |
| 工具库（脚本 + manifest） | 第 0/1 步的预设库 + ② 的执行体 + ③④ 的组装原料 |

## 九、验收

| # | 判据 |
|---|---|
| F1 | 「打开计算器」命中预设表 → **零 AI 决策执行**，模型只说收据（日志可见第 0 步命中） |
| F2 | 「帮我把这句话存到 Notion」走第 1 步语义匹配命中 → 同上 |
| F3 | 「画个圈标出这个按钮」→ 分类 ①，产出 `[SHAPE]`，无截图无循环 |
| F4 | 「保存到桌面某个新路径」→ 分类 ②；若模型现写一行代码，过危险词检查后运行 |
| F5 | 「去这个网页搜 X 然后截图保存」→ 分类 ③，循环逐步执行，日志可见每步截图回填 |
| F6 | 同样的组装需求但存在技能 → 分类 ④，日志可见技能描述被热加载、正文按需加载 |
