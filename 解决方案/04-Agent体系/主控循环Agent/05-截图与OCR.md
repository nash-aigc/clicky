# 05 · 截图与 OCR

> 这份文档补的是主控循环的两个"读屏幕"能力：**按区域截屏（原图）+ 本地 OCR**。
> 用户的原话：
>
> > 我说「把屏幕左侧截下来」，它就只截取并裁剪左侧部分；说右侧、上面、下面也一样。它应该有一个截屏和一个裁剪的动作，而不是截全屏，因为我说的是左侧，截全屏对我来说没有意义。
> > 截屏时一定要原图。保存位置在设置页面里可以让用户选择……如果没有选择，默认保存到桌面一个叫克利奇（CLISCKY）的文件夹。
> > OCR 可以用 Mac 电脑内置的 OCR。比如「把左侧的内容保存到桌面上」→ 截屏左侧 → OCR → 保存。「把左侧的内容保存到备忘录里」→ 截屏 → OCR → 直接写进备忘录，不需要打开软件。
>
> 状态：**设计已定，尚未实施**。

## 一、两个必须先分清的东西：视觉用的图 ≠ 要保存的图

| | 视觉用的那份 | 要保存的那份（本次新增） |
|---|---|---|
| 用途 | 发给视觉模型看图 | 存到磁盘给用户 |
| 分辨率 | **被缩到最长边 1280** | **原图（显示器物理像素）** |
| 格式 | JPEG，质量 0.8 | PNG（无损） |
| 依据 | `CompanionScreenCaptureUtility.swift:49-50`（`maximumDimension: Int? = 1280`、`compressionQuality: 0.8`） | 新路径 |

**这是本次要动的地方**：现有截图管线为了省 token 主动降了分辨率——对模型是对的，对"我要这张图"是错的。

### 实现方式：单独抓一次原图，不动现有那条路

| 方案 | 做法 | 取舍 |
|---|---|---|
| A. 抓一次原图，派生两份（保存原图 + 自己缩放给视觉） | 省一次抓取 | **动了现有视觉管线的输入格式**（从"抓取时缩放"变成"抓取后缩放"），要重新验证画质与耗时 |
| **B. 保持现状，另开一条原图抓取（推荐）** | 视觉那条路一行不改；`[SCREENSHOT:]` 时单独按显示器物理像素抓一次 | 多一次抓取（仅在用户真的要截图时发生，频率低）；但**截图本身就是目的**，所以"画面可能变了"不是问题 |

选 B：**不碰一条已经在稳定工作的路径**，代价是用户主动截图时多几百毫秒。

## 二、两个动作

### `[SCREENSHOT:区域]` —— 抓原图并落盘

| 区域写法 | 含义 |
|---|---|
| `left` / `right` / `top` / `bottom` | 左右上下各取一半（**先做粗裁剪，这是用户明确要的第一步**） |
| `full` | 整屏 |
| `x,y,w,h`（0–1000 归一化） | 精确矩形，给"只要这一块"的场合 |

- **多显示器**：沿用全项目一致的规则——默认光标所在屏，需要别的屏就加 `:screenN`
- 落盘：PNG，文件名带时间戳（`截图-20260924-153012-左.png`），避免互相覆盖
- 回给模型：**文件路径 + 尺寸**，不是图片本身（模型不需要再看一遍自己刚截的图）

### `[CROP:原图路径:x,y,w,h]` —— 对已存在的图裁剪

用户说"它应该有一个截屏**和**一个裁剪的动作"——分开是对的：`[SCREENSHOT:left]` 是"抓左侧"，`[CROP:]` 是"把已经有的那张图再裁一刀"（比如先抓全屏存下来，再裁一份小的给别处用）。

## 三、保存位置（设置项）

| 项 | 值 |
|---|---|
| 设置 | 看与截图页新增一行「截图保存位置」 |
| 默认 | `~/Desktop/Clicky/`（首次使用时自动创建） |
| 用户可选 | 任意文件夹或临时目录（`NSOpenPanel` 选目录） |
| 权限 | **不受文件授权清单约束**——那是给模型读写用户文件的闸门，这是 App 自己的产物目录；但用户手动改到别处时以用户选择为准 |

**一处待你确认**：你写的是 `CLISCKY`，而 App 叫 **Clicky**。我按 `Clicky` 写；要 `CLISCKY` 我改（这条只是拼写，不影响设计）。

## 四、OCR

| 项 | 内容 |
|---|---|
| 用什么 | macOS 内置的 Vision 框架（`VNRecognizeTextRequest`）——**系统自带、本地、离线、无网络请求** |
| 语言 | 显式声明 `zh-Hans` + `en`（默认值不可靠，要写死） |
| 现状 | 全仓库**没有用过 Vision**（也用过 AppleScript/`osascript`：都没有）→ 都是新增依赖，但 Vision 是系统框架，无需引入第三方 |
| 速度 | 一次整屏识别通常在数百毫秒量级（本地）；比一次视觉请求（2–4 秒）快一个数量级 |
| 结果去哪 | **进上下文，不进语音**——OCR 是"读"，读到的文字不该被念出来（除非用户要求） |

### 为什么这条链路能"不需要走一步看一步"

用户的原话是「这是一个链路，不需要走一步看一步」——它正好是 [`04-观察判据与批量.md`](04-观察判据与批量.md) 里的 **C 类链**：

```
截左侧 → OCR → 写进文件/备忘录     每一步事先确定，且任何一步失败都不会让下一步有害
```

所以它应该**一次执行完**（中间不截图、不请求模型），结尾校验一次。**不碰焦点**（OCR 与写文件都不抢焦点），所以也满足 04 里"v1 只放行不碰焦点的动作"的限制。

## 五、三个高频链，建议做成复合动作

拆成原语（截屏 / 裁剪 / OCR / 写文件）最灵活，但高频需求每次都要模型拼 4 个动作，既费 token 又容易拼错。建议**原语 + 少量复合动作并存**：

| 复合动作 | 等价的原语链 | 覆盖的说法 |
|---|---|---|
| `[OCR_TO_FILE:区域:路径]` | 截屏 → 裁剪 → OCR → 写文件 | 「把左侧的内容保存到桌面」 |
| `[OCR_TO_NOTES:区域]` | 截屏 → OCR → 备忘录新建 | 「把左侧的内容存进备忘录」 |
| `[IMAGE_TO_FILE:区域:路径]` | 截屏 → 裁剪 → 保存 | 「把左侧截下来存桌面」 |

**复合动作是"常用句式"的固化物**，不是新机制：它们的每一步都还是那条链上的原语，只是预先拼好、参数化了。

## 六、备忘录那条为什么不用点界面

用户说「不需要打开软件，直接传到备忘录里新建就可以了」——对，走 AppleScript / `osascript`：

```
备忘录新建 → osascript -e 'tell application "Notes" to make new note ...'
```

三条好处：**不用等 App 启动**（省 2–5 秒）、**不用抢焦点**（用户继续干别的）、**失败有明确报错**（不是"点了没反应"）。这也是它属于 C 类链的原因。

**带附件**：`make new note with properties {body:...}` 的 HTML body 里可以嵌 `<img src="file://...">`，所以「同时把图片一并保存进去」用同一个动作就能做到，不需要额外的粘贴步骤。

## 七、验收

| # | 判据 |
|---|---|
| S1 | 「把屏幕左侧截下来」→ 产出**左半屏**的 PNG，分辨率 = 显示器物理像素（与系统截图对比像素尺寸一致） |
| S2 | 落盘位置 = 设置里的目录；没设置过 = `~/Desktop/Clicky/`；目录不存在则自动创建 |
| S3 | 文件名不覆盖：连续截两次得到两个文件 |
| S4 | 多显示器：不加 `:screenN` 时抓光标所在屏；加了则抓指定屏 |
| S5 | 「把左侧内容保存到桌面」→ **一步完成**（日志里 截屏→OCR→写文件 在同一个 step），产出文本文件内容与屏幕左侧文字一致 |
| S6 | 「把左侧内容存进备忘录」→ 新建了一条备忘录，内容正确；**期间前台应用没有被切换**（焦点没抢） |
| S7 | OCR 结果**没有被念出来**（除非用户要求） |
| S8 | OCR 的语言显式设为 zh-Hans + en：中文与英文混排都能识别 |
| S9 | 截图保存的图与发给模型的那份**是不同的两份**（原图更大），且视觉管线行为不变（回归） |
| S10 | 链路中途失败（如目录不可写）→ 失败如实回传，后续步骤不执行 |
