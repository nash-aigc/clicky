# 04 · 观察判据与批量

> 这份文档回答两个问题：
> ① **什么时候必须停下来看一眼**（判据，2026-09-24 按用户的口径修订）
> ② 由此推出**什么时候可以把多个动作合成一次做完**，以及"并发"在这台机器上到底能做到什么
>
> 触发它是一个具体例子：
>
> > 打开微信、打开备忘录，然后在浏览器里新建两个标签页，第一个标签页是什么，第二个标签页是什么，在第二个标签页里做什么。
>
> 状态：**现状已核实；批量是设计，尚未实施**。

---

## 一、物理上限：一个光标、一个键盘焦点

| 事实 | 含义 |
|---|---|
| macOS 只有**一个前台应用**、**一个键盘焦点**、**一个光标位置** | `CGEvent` 的点击和打字进的是"当前前台"，**两个 UI 动作在物理上不可能同时执行** |
| 主控的点击走 `CGEvent`（`resolvedClickPoint` → `CGEventPost`） | 所以"UI 层面的并发"不是保守，是**不存在的东西** |
| 能真并行的只有**不碰 UI 的事**：开应用（`NSWorkspace`）、读写文件、跑子进程、网络请求 | 它们没有焦点这个共享资源 |

**用户的"并发"，在 UI 上只能交替执行；能让体感变快的不是并行，是减少往返。**

## 二、判据：下一步是否取决于一个不确定的结果

**不是"要不要看屏幕"，而是"下一步做什么，是否取决于一个不确定的结果"。**

| 类 | 判据 | 动作 | 做法 |
|---|---|---|---|
| **A 呈现类** | 不改变机器状态 | `[POINT]` `[SHAPE]` | 一次性，无观察（本来就不进动作循环） |
| **B 决策类** | 改状态，**且下一步取决于观察到的结果** | 点一下之后的下一步取决于页面变成了什么样 | **一步一截图**（今天的规则，保持不变） |
| **C 执行类** | 改状态，但**整条链在开始前就完全确定** | 改名 → 移动 → 移进文件夹；连开三个应用 | **一次执行完整条链**，中间只插 settle，结尾统一核对 |

### C 的附加条件（这条不能省）

光是"结果可预测"还不够。**C 还要求：任何一步失败，都不会让下一步变得有害。**

| 例子 | 中间失败会怎样 | 能不能算 C |
|---|---|---|
| 改名 → 移动 → 移进文件夹 | 改名失败 → 后续移动失败（**无害**） | ✅ |
| 连开三个应用 | 某个没装 → 少开一个（**无害**） | ✅ |
| `cmd+T` → 输入地址 → 回车 | 标签页没开出来 → **地址打进了当前页面**（有害：可能触发搜索、污染表单） | ❌ 归 B |

**这条补充正好解释了当年那次踩坑**：那四个连发的标签页动作，本质是"往一个还没加载完的页面里打字"——**下一步的前提没有被验证**，是被误判成 C 的 B。项目记录里那次实测（四个标签页搜索框全空）不是"批处理错了"，是**分类错了**。

### 分类的单位不是动作，是链

同一个人动作在不同的链里属于不同的类：

| 动作 | 在前一种链里 | 在后一种链里 |
|---|---|---|
| `[TYPE:新文件名]` | 点进文件名框之后输入 → **B**（前提是那个框真的获得焦点，得看一眼） | 改名→移动这条链里的固定一步 → **C**（前提由模型事先声明，不需要中途看） |
| `[PRESS:return]` | 在对话框里确认 → **B**（得确认弹的是哪个对话框） | 提交一个已经填好的表单 → **C** |

**所以"哪个动作可以批量"这个问题没有答案——要说"哪条链可以批量"。** 这正是下面设计里要模型**显式声明链条**的原因。

## 三、批量怎么执行（设计）

```
模型声明一条链（显式）
   ↓
代码逐步执行：每步之间 settle（可含 WAIT）
   ↓
某步失败 → 立即停链，把「第 k 步失败 + 原因」回给模型（接 03 的失败回传）
   ↓
整条链成功 → 结尾一张截图 + 结果回填（不是每步一张）
```

**为什么这样仍然安全**：老规矩"绝不在一张没验证过的屏幕上动手"没有被破坏——链内每一步的前提都是**模型事先声明的**，而失败会立刻停链，所以没有任何一步会执行在一个已经失效的前提上。省掉的是"每步一次截图 + 视觉请求"（每次 2–4 秒），不是省掉验证。

### v1 只允许不碰焦点的动作（重要）

| 链的内容 | v1 | 为什么 |
|---|---|---|
| `[OPEN:]`（一个或多个）、文件工具、`[WAIT:]` | ✅ 允许批量 | 这些失败会**抛错**，停链即可，而且抢不了焦点 |
| 含 `[CLICK] [TYPE] [PRESS] [SCROLL] [DRAG]` 的 UI 链 | ❌ 先不做 | **CGEvent 的静默失败抓不到**：`cmd+T` 没开出标签页不会抛错，接着打字就进了错误的地方。要放进批量，得先有"廉价验证"（例如每步后读一次窗口标题/焦点元素）——**记为第二步** |

**这条限制是刻意的**：它把"当年那种坑"从设计上堵死，而不是靠提示词请求模型自觉。

### 上限

| 项 | 值 |
|---|---|
| 一条链的长度 | ≤ 6 个动作 |
| 一条链算几步 | **算 1 步**（不绕过 15 步任务上限） |
| 链内 settle | 每步之间沿用现有 1.2s；`[WAIT:n]` 显式声明更长 |
| 停链条件 | 任一步抛错、任务被取消 |

## 四、今天遇到那个例子会怎样（对比）

**今天**（一步一动作，代码强制只执行第一个，`:2510-2516`）：

| 步 | 动作 |
|---|---|
| 1–3 | `[OPEN:微信]` `[OPEN:备忘录]` `[OPEN:浏览器]`（各占一轮） |
| 4–6 | `cmd+T` → 地址 → 回车（各占一轮） |
| 7–9 | 同上（第二个标签页） |
| 10+ | 在第二个标签页里做那件事 |

**≈ 10–12 步**，每步 = 截图上传 + 视觉请求 + 1.2s settle ≈ **30–50 秒**。

**按新判据**：前 3 步是 C → 一次做完；开标签页那 6 步因为"静默失败会变有害"归 B → 仍然逐步。**所以这一步的收益是 3 步 → 1 步**，而不是把 12 步压成 2 步。诚实地标出来：**v1 的收益有限**，大头要等 UI 链的廉价验证。

## 五、真并行在哪三处（今天已经有一部分）

| 场景 | 今天 | 可以怎样 |
|---|---|---|
| 开多个应用 | 逐步串行 | 并行 `NSWorkspace` 调用（一次一步） |
| 后台任务 | `[AGENT_SPAWN]`，提示词限量每篇回复一个 | 放开到 N 个（带并发上限）——不同 agent 是独立进程，**这是真并行** |
| 画图 / 文件操作 | 已在独立 Task / 子进程 | 与主循环并行（现状基本如此） |

### 探索项（本轮不做）：用 AX 动作绕开焦点

今天的点击是 `CGEvent`，**必须前台**。Accessibility 的 `AXPress` 类动作**不需要焦点、不动光标**——理论上能让后台 app 的按钮被按下而不影响前台。这是"跨 app 真并发"的唯一技术门。

代价：AX 覆盖率不可靠（Electron、自绘控件常常不响应），而且只能按按钮，不能拖拽。**记为探索项。**

## 六、一个反直觉的结论

用户说的是"并发"，但**UI 执行上必然串行**。真正能让体感变快的是三件事：

| 手段 | 省什么 | v1 能否做 |
|---|---|---|
| 把 C 类链合成一次 | 省掉中间的截图 + 视觉请求（每次 2–4 秒） | ✅ |
| 等待期间做别的（只允许不碰焦点的动作） | 把纯等待的时间用起来 | ✅ |
| UI 链的廉价验证 | 让标签页那类链也能进批量 | ❌ 第二步 |

## 七、验收

| # | 判据 |
|---|---|
| C1 | 「打开微信、打开备忘录、打开浏览器」→ **一步完成**（日志里三个 open 在同一个 step） |
| C2 | 一条 C 类链的**中间某步失败** → 立即停链、失败如实回传，**后面的步骤不执行** |
| C3 | 含 `CLICK`/`TYPE`/`PRESS` 的链在 v1 **被拒绝批量**（走回一步一动作），并记日志 |
| C4 | 中间任何一个 B 类动作，仍然**一步一截图**，没有退化 |
| C5 | 链内不允许插入会抢焦点的动作；插入会被拒绝并记日志 |
| C6 | 15 步上限在批量生效后仍然有效（一条链算 1 步，不能绕过） |
| C7 | 一条超长链（>6 个动作）被拒绝或截断，并告诉模型为什么 |
| C8 | **回归**：连开三个 app 后，三个都真的开着（这次是"允许批量"，但必须验证不会退化成当年那个"四个标签页全空"） |
