# 06 · 工具库与 MCP

> 这份文档定的是主控循环**怎么获得新能力**：预先写好的脚本库、它和 MCP 的分工、
> 什么该固化什么不该、以及"主控只做分流、细节按需加载"这个矛盾的解法。
>
> 状态：**设计已定，尚未实施**。

---

## 一、工具的两种来源

| 来源 | 是什么 | 例 |
|---|---|---|
| **① 自己写的** | 用任何方式实现的脚本：AppleScript、Python、CLI 组合、直调 HTTP API | 备忘录新建、截图 + OCR 存文件 |
| **② 从 MCP 提炼的** | 把 MCP 的现成工具**拼成一条固定的链**，固化成一个脚本 | 「保存到 Notion 的固定页面」= 把 MCP 的 create-page 参数写死 |

**关键区别**：② 不是"调用 MCP"，而是"**把 MCP 的用法固化成脚本**"——它跑起来不依赖 MCP 进程，也不把 MCP 的工具 schema 带进每次请求。

### 用户那两个 Notion 例子，都不需要 MCP

| 需求 | 做法 | 为什么 MCP 是多余的 |
|---|---|---|
| 把内容保存到 Notion 的**固定页面** | `notion_save.py`，页面 id 写死在本地配置里 | 你的需求只有一个页面，MCP 那几十个工具里 99% 用不到 |
| 把**当前** Notion 页面保存到本地 | `⌘L` 取当前页地址（Notion 自己的快捷键）→ 脚本抓取 → 存桌面 | 取址是快捷键、抓取是 HTTP——两条路都不经过 MCP |

**MCP 的价值在"服务会变"**：上游 API 改版、鉴权流程变复杂、工具多到十几二十个且你需要灵活组合。需求固定成一两个动作时，**脚本更短、更快、更可控**。

## 二、什么该固化，什么不该（判据）

**不是按代码行数判断。** 一行也可能值得固化，一百行也可能不值得。

| 该固化 | 判据 |
|---|---|
| **要替模型记住它不可能知道的东西** | 你的页面 id、你的保存路径、你的固定模板、你的账号默认值 |
| **高频到值得省掉往返** | 一天用几次以上（每次省 2–4 秒的视觉往返） |
| **正确性可以独立校验** | 有第二条途径把事实读回来（见 §六） |

| 不该固化 | 判据 |
|---|---|
| 模型用现有原语就能现场拼出来 | 「打开计算器」= `[OPEN:计算器]`，已经是一条指令 |
| 一次性的 | 只干这一次 |
| 需要临场判断的 | 每一步取决于看到的屏幕——那是 B 类链（见 [`04-观察判据与批量.md`](04-观察判据与批量.md)），不是脚本 |

**最要紧的一条是最上面那句**：Notion「保存到固定页面」值得固化，**不是因为它代码复杂，而是因为它替你记住了那个页面 id**——模型不可能知道你 Notion 里哪个页面是笔记页。**凡是"要写死一段模型无法推断的私有上下文"的需求，就该固化。**

## 三、打开 App：是指令，不是脚本

**代码事实**（`MacosUseController.swift:1162-1184`）：

```
[OPEN:计算器]
   ↓ applicationBundleURL(matchingName:)  ← 我们这侧先把名字解析成 app 路径
   ↓ MacosUseSDK.openApplication(identifier:)   ← SDK 执行（AppOpener.swift:247）
```

**所以这一类不该进工具库。** 它已经是一条稳定指令：参数化、无状态、结果确定。把它写成脚本只会多一个失败面、多一层进程。这也是为什么"中文名解析"那个 bug 值得单独修——它是这条指令**唯一的薄弱环节**（见 [`03-语言适配与动作扩展.md`](03-语言适配与动作扩展.md)）。

**通用判据**：

| 形态 | 什么时候用 |
|---|---|
| **指令**（进程内，参数化） | 能用一条参数化、无状态、结果确定的调用表达 → 用指令。打开 App、点击、滚动、截图、OCR 都属这类 |
| **脚本** | 需要多步编排 / 解析 / 记忆私有常量 / 调外部 API → 用脚本 |
| **MCP** | 服务会变、工具多、需要灵活组合，且你不想自己跟 API 变更 → 用 MCP，但见 §五的注入策略 |

## 四、目录：按功能分类

```
~/Desktop/clicky/tools/              ← 自定义工具库（进仓库、可版本化、**不含任何密钥**）
├── manifest.json                    总清单（模型看到的只是它的投影）
├── 备忘录/
│   ├── notes_create.py
│   └── notes_latest.py              校验用
├── 提醒事项/
│   └── reminder_create.py
├── 截图与OCR/
│   ├── screenshot_region.py
│   └── ocr_to_file.py
└── Notion/
    ├── notion_save.py               自己写的（直调 API）
    ├── notion_page_to_local.py      ⌘L 取址 + 抓取
    └── notion_search.py             ⚠️ 依赖 MCP：notion（从 MCP 提炼的链）
```

| 决定 | 理由 |
|---|---|
| **按功能分类**（你的建议） | 找工具、加工具、一眼看清哪些依赖 MCP，都变简单 |
| **放仓库里**（不是 `~/.clicky/`） | 它是 **App 的能力**，该版本化、该能被 review；密钥仍然在外面（见 §七） |
| 每个工具标注 `dependsOnMCP` | 那个 MCP 没装/挂了，这类工具要能被**明确标为不可用**，而不是跑起来才报错 |

manifest 里一条长这样：

```json
{
  "name": "保存到Notion",
  "aliases": ["存到 Notion", "记到 Notion", "notion save"],
  "category": "Notion",
  "when": "用户说『把这段/这张图保存到 Notion』且没有指定页面",
  "dependsOnMCP": null,
  "params": [{ "name": "内容", "required": true },
             { "name": "附件路径", "required": false }],
  "run": "Notion/notion_save.py",
  "verify": "Notion/notion_latest.py",
  "usage": "页面 id 在 ToolSecrets.json 的 notion_note_page_id；内容支持 Markdown；附件的路径必须是本地存在的文件"
}
```

- `aliases` 解决"中文名/英文名/口语说法"的对上问题（与你说的对照表同一个作用）
- `usage` 就是**按需加载的那段细节**（见 §五）

## 五、三层加载：分流 → 工具卡片 → 技能文档

你提的矛盾是对的：**主控的提示词只该做分流，不该背所有工具细节；但它不知道细节，就会用错工具。** 解法是把"知道"和"精通"分开，分三层：

| 层 | 什么时候在场 | 内容 | 成本 |
|---|---|---|---|
| **L0 分流（常驻）** | 每次请求 | 四类分流规则 + **每个工具一行**：名字 + 「何时用」 | ≤40 个工具约 1.2 KB |
| **L1 工具卡片（命中后）** | 模型第一次调用该工具时，或参数错时 | 参数、示例、注意事项、校验方式（`usage` 字段） | 只在那一次 |
| **L2 技能文档（命中任务类型后）** | 一类任务的成套做法 | 例：「把当前 Notion 页存下来」= ⌘L → 取址 → 抓取 → 校验 | 只在那个任务里 |

**关键：加载由运行时做，不由模型做。** 模型只写 `[RUN:保存到Notion:内容]`；运行时查 manifest、执行。**参数不对或执行失败时，把该工具的 L1 卡片连同错误一起回填**——模型第二次就对了。

**这就是"失败驱动的按需展开"**：不需要它一开始就背所有细节，需要的是**第一次错的时候有人告诉它怎么对**。

再给一个主动求助的口子：`[TOOLS:Notion]` 拉某个分类的完整卡片清单（给"这个分类里有哪几个工具"的场合）。

### 要不要装 Claude Code 那种 Skills？

**不必。** 这套三层就是同一个模式的**原生实现**——清单常驻、正文按需加载。Clicky 的模型不是 Claude，把 skills 那套塞进来只是多一层翻译。

**装了 MCP 之后要不要装"技能"？** 也不要——MCP 的机制里没有 skills 这一层；它的"怎么用"就在每个工具的 `description` 里。而按 §五 的策略，我们**本来就不注入 MCP 的原始工具列表**，所以它的 description 也不会进快路径。

## 六、创建 + 校验 + 兜底（用户说的三件套）

```
[RUN:备忘录新建:今天下午三点跟王新月开会]
   ↓
备忘录/notes_create.py     创建，stdout 打印「已创建：<标题>｜<时间戳>」
   ↓
备忘录/notes_latest.py     独立读回最近一条：「<标题>｜<时间戳>」
   ↓
比对
   ├─ 对得上 → 报告成功（一条回复，全程不截图）
   └─ 对不上 → **回落到主控循环手动一步步做**，并把「脚本执行了但校验不符」写进上下文
```

| 目标 | 由谁保证 |
|---|---|
| 快 | 脚本一次跑完，**不进"一步一截图"的循环**（省掉每次 2–4 秒的视觉往返） |
| 准 | 校验脚本**独立读回事实**——不是问创建脚本"你成功了吗"（那是自我报告） |
| 兜底 | 校验不符 → 回到那条慢但通用的路径，而不是报错了事 |

**估算（标注为估算）**：

| 需求 | 今天（动作循环） | 走脚本 |
|---|---|---|
| 「添加一条备忘录」 | 打开备忘录 → 新建 → 输入 → 收尾 = 4–6 步 ≈ 15–25 秒 | 1 次请求 + 脚本 + 校验 ≈ **2–3 秒** |

## 七、密钥：绝不写进仓库里的脚本

| | 不行 | 行 |
|---|---|---|
| 位置 | `tools/Notion/notion_save.py` 内嵌 token | 脚本从 `~/Library/Application Support/Clicky/ToolSecrets.json`（**0600**）读 |
| 为什么 | 仓库是 git 仓库，一次 `git add -A` 就把令牌提交了 | 这是本项目已有的惯例：`BailianSecrets.plist`、`ModelConfiguration.json` 都住那儿 |

另外：**任何工具的输出都不要把 token 回显到 stdout**——stdout 会进模型上下文。

## 八、MCP：装，但不直灌

| 决定 | 理由 |
|---|---|
| 该装的装（Notion、搜索这类"服务会变"的） | 省去自己维护鉴权、分页、API 变更 |
| **不把整套 MCP 工具 schema 注入快路径** | 一个服务型 MCP 常有十几到几十个工具，schema 加起来几 KB；系统的系统提示词本身才 ~5 KB，**等于给每次请求的固定前缀加 50%** |
| 用几个**窄包装**把高频动作固定下来，MCP 留在那一层后面 | 既拿到"不用跟 API 变更"，又不让每次请求背着整套 schema |
| 判据 | **它给每次请求的固定前缀增加多少**。工具又少又稳的 MCP，直接暴露也没问题 |

## 九、与四类分流的关系

| 项 | 结论 |
|---|---|
| 新增分类？ | **否**。`[RUN:]` 与 MCP 调用都是 **③ 主控循环**里的动作，跟 `[OPEN:]` 同级 |
| 属于哪一档（04 的判据）？ | 多数是 **C 类**（整条链事先确定 + 失败无害）→ 可一次做完，这正是它们快的原因 |
| 抢焦点吗？ | 脚本走 AppleScript/API，**不抢焦点** → 满足 04 里 v1 批量放行的条件 |
| 闸门 | **「允许调用工具库」独立总闸**（已定，2026-09-24）：与「允许操作电脑」分开——调用你自己的脚本，与"点鼠标"风险模型不同 |

## 十、验收

| # | 判据 |
|---|---|
| T1 | 「添加一条备忘录」→ **一条回复内完成**，日志显示 run + verify 都跑了，且**没有进入动作循环**（没有截图步骤） |
| T2 | 校验不符时**回落到手动路径**，而不是报错结束（构造一次假失败） |
| T3 | 校验脚本独立读事实：把 create 脚本改成"打印成功但什么都不做"，T2 的回落必须被触发 |
| T4 | L0 常驻开销实测（字节数）；≤40 个工具时不超过约 1.2 KB |
| T5 | 工具库里**没有任何密钥**：`grep -rE "secret\|token\|sk-" tools/` 为空；密钥只在 `Application Support` 的 0600 文件里 |
| T6 | 新增一个工具只需改 `manifest.json` + 丢脚本，**不改 Swift 代码** |
| T7 | 工具调用失败（脚本不存在 / 非零退出 / 超时）→ **失败 + 该工具的 L1 卡片**一起回填，模型第二次能成功 |
| T8 | 依赖 MCP 的工具在 MCP 缺席时被**标为不可用**（而不是跑起来才报错） |
| T9 | 「允许调用工具库」关闭后，`[RUN:]` 一律被拒并说明原因 |
| T10 | **回归：`[OPEN:]` 不走工具库**——打开应用仍走原来的指令路径（`:1162`），没有多出一层脚本 |
| T11 | `aliases` 生效：中文名、英文名、口语说法都能对上同一个工具 |
