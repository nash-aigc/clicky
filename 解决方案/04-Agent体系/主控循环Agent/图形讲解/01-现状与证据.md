# 01 · 现状与证据——今天到底是什么状态

> 这份文档只陈述**已核实的事实**，每条带文件行号或实测数据。凡是没有实测支撑的一律标注「推测」，单独列在最后一节。
> 目的是回答一个问题：**「把那个半成品接上」到底够不够？** 结论是不够——有三处断点，其中两处会让功能「接上了也不对」。

---

## 一、今天有三条「在屏幕上画东西」的路径

| 路径 | 触发 | 实现 | 现状 |
|---|---|---|---|
| 蓝色光标指位置 | `[POINT:x,y:label]` | `CompanionManager` → 飞行弧线 | ✅ 可用 |
| 绿色标注 | `[SHAPE:kind:pts:label]` | `ScreenAnnotationManager`：SwiftUI `Canvas` 描线，0.7s 画上，10s 淡出 | ✅ 可用，**单次、无循环** |
| 屏幕图板 | `[SVG_BOARD:元素名:任务]` | `figure_agent.py` 出图 → `FigureBoardController` 显示 | ✅ 静态显示可用；**逐笔动画是死代码** |

绿色标注为什么是单次而不是多步：它**不进 `actions` 数组**（`ActionTagParser` 把形状请求单独放 `shapeRequests`），所以不触发「执行→截图→续写」的循环；而且每次截图前会被清掉。**这是正确的形态**——画图不改变机器状态，没有需要观察的东西，不需要循环。

## 二、半成品的三个断点

### 断点 1：逐笔动画从未接上电

- `FigureBoardController.showAnimated(...)`（`FigureBoardController.swift:115`）与 `readSteps(...)`（`:47`）在全仓库**零调用方**。
- 实际走的是 `figureBoardController.show(svgFilePath:anchoredToQuartzFrame:)`（`CompanionManager.swift:3389`）——把 SVG 当 `NSImage` **一次性**画出来。
- 含义：这不是「换掉一个动画引擎」，而是「把动画接进管线」。而下面两个断点说明，**接上之前必须先修**。

### 断点 2：SVG 切分器会吞并和丢弃图元（**实测复现**）

`splitSvgTopLevelElements`（`FigureBoardController.swift:295-351`）是「按顶层元素逐个揭示」的基础。评审者用 Python 复刻了这个算法跑真实文件：

> **证据口径**：那是**复刻的近似实现**（不是 Swift 本体）；下面的数字强度很高，但**定论以 Swift 侧单测为准**（[04 文档](04-验收与自检.md) 的 T1/T9）。复刻脚本本身没有进仓库。

| 文件 | 真实顶层元素 | 实际切出 | 后果 |
|---|---|---|---|
| `geometry-dsl/examples/triangle.svg` | 12 | **5** | 尾部 id 8/9/10 **被静默丢弃** |
| `geometry-dsl/examples/incircle.svg` | 21 | **8** | 丢弃 id 28–31（三个直角标记 + 等长标记） |
| `geometry-dsl/examples/pythagoras.svg` | 13 | **7** | 丢弃 id 20（直角标记） |
| 真实产物 `~/Desktop/Clicky图形/图形-20260924-025834.svg` | 8 | **5** | id 4–8 被并成一块 |

**根因**（`FigureBoardController.swift:331-342`）：

- 自闭合顶层元素（`<line/>`、`<circle/>`、`<path/>`）**从不增加 depth**（`:337` 的 `!tag.hasSuffix("/>")` 把它排除在外），于是深度永远回不到 0，遍历一直吞到后面第一个真正的 `</g>` 才收尾 → **多个图元被并成一段**。
- 尾部若全是自闭合元素，`elementEnd` 保持 `-1` → `:342` 的 `guard ... else { break }` **把剩下的图元全部丢掉**。

**结论**：即便 `showAnimated` 接上，三角形也只能整块蹦出来——**「画三条边」这一课无论如何编号都不成立**。

### 断点 3：步骤编号的语义三处不一致，且底层 id 有空洞

| 谁 | 认为 `n` 是什么 | 位置 |
|---|---|---|
| 规划器提示词 | 「图形对象的**定义顺序号**」 | `figure_agent.py:175-184` |
| `FigureBoardStepPlan` 文档注释 | 「最后一个 **SVG 顶层元素**的 1-based 序号」 | `FigureBoardController.swift:36-39` |
| `showAnimated` 实现 | 当**顶层元素序号**用，并裁剪成 `min(max(n,1), elements.count)` | `:136` |

三者不是一回事，而且真实数据里差得很远：

1. **`objectId` 有空洞**：`styled()` 对 `_`（不可见）对象也照样消耗 id（`evaluator.js:221`），实测 `incircle.svg` 的 id 序列是 `4 27 14 15 16 24 25 26 21 22 23 1 2 3 17 28 29 30 31` → 「第 n 个定义」与 `data-object-id == n` 只在模型完全不写 `_` 时偶然相等。
2. **顶层元素顺序 ≠ 作图顺序**：排序是 `(layer, created)`（`svg.js:180-181`），而 geom 提示词**明确教模型用 `layer`**（`figure_agent.py:106`）→ `incircle` 会渲染成「填充最先、辅助线其次、顶点最后」，**前缀式揭示的顺序与老师画图的顺序正好相反**。
3. **`<defs>` 恒占第一个顶层元素位**（`svg.ts:172-174`）→ 「第一步」永远是揭示 defs（什么都不显示）。
4. `<defs>` 里还装着 Region 的 mask —— 切分/组装时 defs 必须在场，否则 `mask="url(#g-region-N)"` 解析失败，**填充会静默消失**。

**正确语义**（见 [`02-数据面与渲染面.md`](02-数据面与渲染面.md)）：一步 = **一组 id**，揭示 = 到目前为止所有 id 的**并集**；DOM 顺序不动，只切可见性。

## 四、一条旧结论已过时，必须修正

**「截图前清屏是为了不让模型看见自己画的图」——这个理由今天不成立了。**

截图捕获按 **owningApplication 的 bundleIdentifier** 把本 App 的全部窗口从 `SCContentFilter` 里排除（`CompanionScreenCaptureUtility.swift:64-67`、`:109`）。绿圈和图板本来就不会进截图。

**这条修正很重要**：它意味着「每次截图前清屏」不再是为截图卫生服务，**只为「用户屏幕上不该留着上一轮的图」服务**。因此长动画完全可以活过中间的截图——改成「新问题 / 打断时清」即可，不需要为截图让路。

## 七、两份独立评审的收敛点

这次设计经过了两个互不相关的评审角度（一个纯读代码 + 复刻算法实测，一个按「最可能先炸」排序 + 证据审计），它们的结论一致指向：

1. **渲染引擎不是主要风险**——数据面（切分与编号）和生命周期（清屏与任务归属）才是。
2. **切分器必须换掉**，且换法不是修它，而是**别在 App 侧解析 SVG**。
3. **GSAP 在本需求上不划算**，因为它带来的六个风险面换来的能力当前用不到。

差别只在证据等级：其中一个**复刻算法跑真实文件**验证了切分器的失败（上面的数字表），所以那条按「已证实（复刻口径）」对待，定论仍以 Swift 单测为准。
