# 09 · 主 agent + 三个 sub agent（2026-09-25 架构定案）

> 用户的设计（原话摘要）：
>
> > 任何时候用户的提问都包含**屏幕截图 + 用户的问题 + 系统提示词**；系统提示词**没有必要写太多**，
> > 一两行说明怎么回答就够了。上下文有记忆，保存最近十条或全部历史——对话记录本来就在窗口里给用户看，
> > > **长期记忆已经存在，不需要调整**，也不必把它设计成多少步骤。
> >
> > 把大量"坐标怎么定位"这类东西**全部移走，但不是删掉**——放进 sub agent 自带的技能里。
> > 设计三个 sub agent：**图形 / 执行 / 文本**。执行类具备各种工具；文本类**没有任何工具调用**，
> > 只辅助生成内容，各种场景怎么回复以**技能**形式存在它里面。
> >
> > 主循环的提示词因此只剩四样：**屏幕 + 用户问题 + 历史对话 + "什么时候调用哪一个 sub agent"的那段描述**。
> >
> > 用户同时处理销售/营销/财务/法律/商务/建筑等场景时，全注入系统提示词会过载；
> > 这些场景**无缝切换**，所以放进技能：基本描述加载进上下文，**按屏幕截图或模型理解自动调用对应的 agent**。
> > 整个循环可能比脚本慢，**但逻辑简单、容易理解——牺牲性能换简单性**。
> >
> > 最终形态：**先有一个非常标准、正确的 agent 循环，然后在它旁边加一条并发/旁路路由**，
> > 专门处理更重要、更常见、更高频的问题。**不要把高频需求混进 agent 的分类里去研究**——
> > 那样逻辑就错了，因为永远分不开。
>
> 状态：**架构已定，尚未实施。** 本文不是新造一层，而是把 [01](01-分流与边界.md) 的"三类执行策略"
> 重新表述成**主 agent 视角**，并补上**权限分级**与**回传/通知**两件此前没写清的事。

---

## 一、主 agent 的提示词里有什么（四样，仅此四样）

| 槽 | 内容 | 今天的状态 |
|---|---|---|
| 屏幕 | 截图（多屏多张） | **已有**（`CompanionManager.swift:2173`） |
| 用户的话 | 原话 + 数据块 | **已有** |
| 历史 | 最近若干轮真实对话 + 压缩摘要 | **已有**（长期记忆：会话窗口 + `ConversationSessionsStore`） |
| sub agent 目录 | "什么时候叫图形 / 执行 / 文本"各一两句 | **要写**（替代今天那份 22,954 字符的大提示词） |

**移走但不删掉**：今天提示词里 `operating the computer:` 一节 **12,096 字符**（占 53%）、
`element pointing:` / `drawing on screen:` / `kinds:` 合计约 3,300 字符——
这些"怎么做"的说明搬进对应 sub agent 的技能正文，主 agent 只留"有这么个能力"一行。

## 二、三个 sub agent 的分工

| | **图形 agent** | **执行 agent** | **文本 agent** |
|---|---|---|---|
| 干什么 | 指位、画圈/画框/箭头、生成 SVG 图形与图解 | 点击、打字、按键、开 App、调音量亮度、读写文件、跑脚本、调 MCP | 生成内容：问答、翻译、写作、讲解、总结；多场景方法论 |
| 工具 | 自己的工具链（几何编译器 + 模型） | **工具最多**（`MacosUseSDK` + 工具库 + MCP） | **零工具调用** |
| 文件权限 | **只限图形相关文件的读写** | 见 §六（**建议先按已授权路径，不要直接放开全盘**） | **只有读权限，没有写权限** |
| 技能放什么 | 怎么算坐标、怎么排版、怎么动 | 各类动作怎么写、什么动作能批量 | 销售/营销/财务/法律/商务/建筑…各场景怎么写 |
| 兜底 | 画不出来 → 退化成一句文字说明 | **Claude Code**（10 轮未完成 → 升级） | 无（它自己就是生成者） |
| 结果回主循环 | ✅ | ✅ | ✅ |

**权限差异是这个设计的核心特征**（用户明确要求）：三个 sub agent 各有各的文件夹与权限，
"有的有工具，有的没有工具"。这条同时是**安全边界**（文本 agent 写不了盘）和**提示词瘦身**的手段。

## 三、结果怎么回到主循环（今天已存在，不用新造）

```
sub agent 执行完 → 结果写进数据块 → 主 agent 循环的下一轮读到它 → 主 agent 判断：
  ├─ 完成 → 总结成给用户看的话
  ├─ 未完成（可补救）→ 继续（循环上限 15 步）
  └─ 失败 → 换做法，或升级 Claude Code
```

落点就是 `pendingAccessibilityContext`（`CompanionManager.swift:2718 / 2749 / 2774`）——
它今天已经在装 `<screen_contents>` 与 `<agent_dispatch_results>`，**sub agent 的结果用同一个通道**。
配合 [06](06-工具库与MCP.md) §5.5 的三态协议：`failed` 必须回传，`done_verified` 直接播报，
`done_unverified` 由主 agent 逐案决定要不要多看一眼。

## 四、结果怎么告诉用户（"用户并不知道"这件事的解法）

用户的要求：全部完成后**在鼠标右下角显示一个对号 + "任务完成"之类，停 2–3 秒**；
可以只显示文字不播报，也可以播报。通知文字**由主 agent 根据任务内容总结生成**
（任务内容 400 字 → 总结成适合播报的一句）。

| 元素 | 今天已有的落点 |
|---|---|
| 画对号 / 完整图形 | `ScreenAnnotationManager`（已能画圈、箭头、线、曲线、多边形 + 标签胶囊） |
| 文字（"任务完成"） | 光标旁气泡（`OverlayWindow` 的 conversation bubble） |
| 2–3 秒后消失 | 已有的自动消失机制（绿圈 10 秒淡出；气泡有 linger 机制，改成 2–3 秒即可） |
| 摘要文字 | 主 agent 同一轮回复里生成，不需要额外调用 |
| 语音播报（可选） | 现有 TTS；不播报时只是不调它 |

**不需要新窗口、不需要新面板**——三个元素在今天的代码里都有现成的。

## 五、旁路：高频需求单独一条路，不混进 agent 分类

用户的原话是本篇最重要的一条设计原则：

> **不要把高频需求与 agent 混在一起研究分类，那样逻辑就错了，因为永远分不开。**

所以最终形态是两条并列的路：

| | **标准路**（主 agent + sub agent 循环） | **旁路**（高频直通） |
|---|---|---|
| 覆盖 | 所有需要理解、需要多步、需要判断的需求 | 少数几个高频、模式固定、结果确定的场景 |
| 代价 | 慢一点，但逻辑统一、易理解 | 快、省 |
| 优先级 | **标准**——它是系统的正确形态 | **补充**——它只解决"最常见的那几件" |

**判断顺序**：先问旁路（能不能直通），直通不了再进标准循环。
**旁路是谁建的**：不是拍脑袋定的，是**复盘 agent 从真实使用里统计出来的**——某类需求超过五次且跨 ≥3 天，标记为候选，用户批准后写成提示词里的一行入口（脚本 / 脚本+参数 / 工具 / 技能路径，四种形态）。预算 20 行 / ~800 字符，超了按频率淘汰，60 天不用自动撤出——详见 [`../复盘Agent/04-高频统计与高速通道.md`](../复盘Agent/04-高频统计与高速通道.md)。
旁路具体是几个什么场景、用什么判据（代码匹配还是模型），见 [07](07-工具路由与instant-agent.md)——
那份文档已经实测过"JEV 暂时不移植、目录破 150 条再升级闭集路由"，本篇不改它的结论。

## 六、风险与前置依赖（诚实标注）

| # | 事项 | 现状 |
|---|---|---|
| R1 | **三个 sub agent 的权限分级依赖 [02 文件访问授权](02-文件访问授权.md)**——那张"逐路径 + 读/写分开"的白名单**设计已定、尚未实施**。没有它，就做不到"图形 agent 只能碰图形文件""文本 agent 只读不写" | **前置依赖** |
| R2 | **执行 agent 的"全盘读写"是本系统风险最集中的一处**。建议第一期**不给全盘**，仍走 02 的白名单 + 现有两道闸门（「允许 Clicky 操作电脑」「允许打字和按快捷键」）；要放开全盘，必须是用户明确、单独的一次选择 | **建议收紧** |
| R3 | 图形 agent 的"显示"**不该由它做**：agent 只产出图形数据，画到屏幕上仍是 App 的活（`ScreenAnnotationManager` / `FigureBoardController`）。把显示塞进 agent 会让同一个绘制逻辑出现两份 | **边界澄清** |
| R4 | 主 agent 的"sub agent 目录"要写多细，决定它选得准不准——**目录太粗会选错 agent，太细又回到今天的胖提示词**。这是本篇唯一需要实测调参的地方 | **待实测** |
| R5 | 文本 agent 的"场景技能"会不会互相干扰（同一句话在销售/法律两种场景下该怎么说）——**技能按需加载是否真的比全量注入更好，需要一次对照实测** | **待实测** |

## 七、验收

| # | 判据 |
|---|---|
| A1 | 主 agent 的提示词只剩四样（屏幕/用户的话/历史/sub agent 目录），**不含**坐标与动作说明；字符数较今天（22,954）显著下降 |
| A2 | 说"圈一下这个按钮" → 图形 agent 接手，主 agent 提示词里没有出现几何/坐标说明 |
| A3 | 说"把这个存成文件" → 文本 agent **拒绝写**（无写权限），或转交执行 agent |
| A4 | 说"帮我把桌面那个文件夹整理一下" → 执行 agent 接手；失败 10 轮 → Claude Code；再失败 → 用户收到通知 |
| A5 | 任一 sub agent 完成 → 结果回到主循环，主 agent 给出总结；用户看到鼠标右下角对号 + 文字，2–3 秒后消失 |
| A6 | 通知文字是主 agent 按任务内容生成的摘要，不是固定文案（构造一次 400 字任务验证） |
| A7 | 旁路命中时**不进入**主 agent 循环（日志可验证）；旁路未命中时一律进标准循环 |
| A8 | 高频场景（对屏幕提问）在旁路未命中时，走标准循环仍能正确回答——**标准路是完备的，旁路只是加速** |
