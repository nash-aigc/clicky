# 05 · 对话气泡与语音回合的写盘复盘（2026-09-25）

> 这一篇复盘的是**语音对话里「谁说了什么、显示在哪里」**这一层的全部问题：
> Ask 页面的独立全双工管线、Chatting 三段式/全双工的气泡顺序、回声尾巴「嗯。」、
> 用户提示词重复两份、顺序穿插、连接卡死。整理成文，让后来者（包括未来的 AI）
> 不用再把这些坑重踩一遍。

## 一、协议时序：一切问题的总根源

Bailian 全双工实时协议（`qwen-audio-3.0-realtime-flash` 等）的**真实事件顺序**，
与直觉相反（全部来自事件流仪器实测，见 `DuplexVoiceEngine` 里的 `🎧 [event]` 日志）：

```
用户开口说话
  ↓ （音频 100ms 一块上行，server_vad 判定）
🎧 input_audio_buffer.speech_started      ← 服务端听到你开口
🎧 response.created                       ← AI 立刻开始生成本轮回答
🧾 response.audio_transcript.delta ×N     ← AI 说的内容（增量）
🔊 response.audio.delta ×N                ← AI 说的音频（先排进队列，慢慢播）
🎧 response.done                          ← 本轮回答生成完毕（注意：早于音频播完！）
🎧 input_audio_buffer.committed
🎧 conversation.item.input_audio_transcription.completed  ← 你的转写，最后才到！
```

**三个致命的推论：**

1. **用户的转写比本轮回答的 `done` 晚到。** 任何"谁先到谁先写"的落盘逻辑都会把
   回答写在问题前面，或者把问题配给上一轮的回答。
2. **`response.done` 早于音频播完。** 音频 delta 是先排进 `playerNode` 队列再慢慢播的，
   所以「AI 的话说完了」和「AI 的话播完了」是两个时刻，打断必须分别处理。
3. **打断发 `response.cancel` 可能收到 `Conversation has no active response.`
   （`param=response.cancel`）**—— 这是**请求级错误，不是致命错误**：服务端那一轮
   刚好自己结束了，你的 cancel 是冗余的。把它当致命错误收掉整场会话，就是
   「用户一开口电话就断」的直接原因。

**结论：处理这类会话，唯一的依据是事件流日志。** 每个事件都带 `response_id` /
`item_id`，`DuplexVoiceEngine` 已装全事件流仪器（`🎧 [event]` / `🎧 [user-transcript]` /
`🧾 [ai-text]` / `📝 [写盘]`），顺序问题先读日志再动手，不要读码推测。

## 二、Ask 页面：独立管线的诞生与它的写盘状态机

### 2.1 为什么必须是独立管线

第一版把 Ask 的语音呼叫**塞进了 `VoiceChatController`**——后果立刻显现：
`NotchSheetRootView` 有一条 2026-09-23 定的规则「会话在跑就切到 Chatting 页」，
Ask 的呼叫被它当成了 Chatting 会话，用户一收起面板再展开就被强行切页。

用户的原话（需求书）：**「我不是让你照抄 Chatting 那套东西……你应该理解它搭建管线
的逻辑，然后设计一条全新的管线。」**

最终形态（`AskVoiceCallController.swift`）：与 Chatting 的差别是**编排层**的，
不是传输层的——引擎（`DuplexVoiceEngine`）复用，编排各自独立：

| | Chatting（VoiceChatController） | Ask 语音电话（AskVoiceCallController） |
|---|---|---|
| 单位 | 角色 + 预设 | **Ask 的某一个会话** |
| 上下文 | 角色系统提示词 | 该会话聊天历史（`<chat_history>` 标签，进 `instructions` 只发一次） |
| 落点 | Chatting 页转录流（内存数组） | **Ask 会话本身**（`ConversationSessionsStore`，与打字同一条路径） |
| 截图 | 三段式会截 | 从不截屏 |
| 侧栏 | 展开时会切页 | **只管刘海状态带，绝不切侧栏** |

教训：**「会话在跑就切页」这类全局规则，判据必须精确到"哪个控制器"**。
`voiceChatController.connectionPhase` 只描述 Chatting 的会话；新的独立管线加进来时，
所有引用这个判据的地方都要重新过一遍。

### 2.2 连接卡死：「连接中」永远不变成「通话中」

**两个独立的根因，先后撞上：**

1. **接通判据选错。** 第一版让「已连接」等 `onFirstAudioScheduled`（AI 第一次出声），
   但这条管线**不打招呼**——用户说话之前 AI 不出声，判据永远等不到。用户实测：
   「一直是连接中」。
2. **问候语与配置应用赛跑。** 第二版加了开场白（用户要求「先让 AI 说两个字，
   声音播放开始的那一秒切已连接」），结果问候语的 `response.create` 与服务端应用
   `session.update` **赛跑**——配置还没应用完，问候被**静默丢弃**（无报错、无事件），
   还是永远「连接中」，15 秒兜底报「可能没真的在服务」。

**修法：**
- 接通判据改回「第一段音频出声的那一秒」（与 Chatting 一致，用户明确要求），
  开场白保证了这个音频必然到来；
- `start()` 发完 `session.update` 后**等 `session.updated` 确认**（协议握手本义）
  才装 tap、才返回发问候——赛跑在结构上不可能；
- 15 秒兜底保留：等不到就如实说明，不把界面永远吊在「连接中」。

### 2.3 写盘状态机：配对、开场白、空白卡

Ask 的转录落进**持久的会话存储**（与打字共用），比 Chatting 的内存数组多一层约束。
最后的形态是**双槽状态机**（任何时刻至多一个非空）：

- `pendingUserTranscript`：用户说了、回答还没写（转写先于回答 `done` 到达时）。
  回合结束写盘时一条写全：问在上、答在下。
- `pendingPairIndex`：回答写了、用户转写还没补（**常态**，见协议时序）。
  转写到达时按下标补配进同一条。

**四个曾经踩过的坑：**

1. **「谁先到谁先追加」** → 回复排在提问上面。
2. **用「最后一条」找配对** → 转写晚于下一轮开始时，配到别人的条目上
   （问赵金麦、答杨幂；话被插到别处、那个位置气泡不显示）。修法：记住
   **自己刚写的下标**，绝不用"最后一条"。
3. **开场白回合落盘** → 写出一条「问空答有」，把用户第一问吸过去
   （问北京、答你好）。修法：开场白**不写盘、不参与配对**——它是接通信号，
   不是对话内容。
4. **一个回合写两条** → 用户那条的回复是空的 → 渲染出**空白卡**（用户截图中
   大片的空白区域）。修法：一个回合一条；通话进行中"还没写完回答"的最后一条
   由流式气泡顶替渲染。

### 2.4 本地打断：全双工的「瞬间打断」是加出来的

三段式打断「瞬间」，是因为它用**本地能量 VAD**（50ms 轮询、阈值 0.25、累计 0.20s、
同一进程内判定）。全双工原先只靠服务端 `server_vad`——打断要等「100ms 攒块 +
上行 + 服务端判定 + 下行事件」，结构上不可能瞬间。

修法：把三段式同一套判据搬进 `DuplexVoiceEngine`（`startLocalBargeInWatch`），
用户开口**就地停声**，不等服务端。三个配套：

- **打断的 `response.cancel` 若收到 "no active response" 错误，只记日志，绝不收尾**
  （冗余报文 ≠ 致命错误——这条曾经把整场会话收掉）；
- **打断后到达的助手音频要丢掉**（`isDiscardingAssistantAudio` 闸，下一次
  `response.created` 解开），否则 `stopStreamingPlayback()` 清空一次队列后，
  随后到达的 delta 会把声音重新排回去；
- **开场白播放期间不武装本地 VAD**：AEC 尚未收敛，麦克风会听到 AI 自己的
  问候声而误触发（日志实测：问候播放中 `本地判定用户开口` 误触发一次）。
  用户第一次开口（`speech_started`）才武装。

### 2.5 上行乱序：一个原因解释三个症状

上行每块音频原来这样发：`Task { try? await sendJSON(...) }` —— **Swift 的 Task
不保证按创建顺序执行**，音频块乱序到达服务端，模型听到的是被打乱的语音。
一个原因，三个症状：**转写不是用户说的话、回答答非所问且慢一拍**。

修法：单一消费者泵（`pumpUplinkChunksInOrder`），逐块 `await`，前一块发完才取
下一块。**首版泵还写出了一个崩溃**：`await sendJSON` 挂起期间 `stop()` 清空了
`pendingUplinkAudio`，泵恢复后按过期余量 `removeFirst` → 崩溃
（`Can't remove more items from a collection than it contains`）。
修法：「看余量 + 取走」放同一同步段，取块数量按**当下**余量算。

**教训（两条都要记）：**
> `Task {}` 不是"排队"，是"赛跑"。流式数据的发送顺序重要时，必须显式串行化。
> 跨 `await` 挂起点共享可变集合，取用前必须按当下余量取。

## 三、Chatting 页面：三段式的三个问题

### 3.1 用户提示词显示两份

两个写入点叠加：interim 转写创建一个**实时气泡**（一边说一边变），final 定稿后又
`startTurn` **追加**一份同文气泡。截图里两句一模一样的问句就是这两份。

**用户同时提出了交互改版**：「希望用户的提示词是一次性展示出来的，不要一个字
一个字地显示，而是在用户说完整句话后一次性显示。」

修法（一举两得）：**interim 完全不显示**（`onTranscriptUpdate: { _ in }`，说话期间
的反馈由 Listening 相位动画承担），说完后 `startTurn` 追加**唯一的**用户气泡。

**注意这里与 Ask 的设计差异（都是用户定的）**：Ask 的会话历史带标签进上下文、
要持久化，所以走"配对写盘"；Chatting 三段式的转录是内存气泡，用户要一次性显示。
**不要把一边的方案抄给另一边。**

### 3.2 回声尾巴「嗯。」

**现象**：AI 回复一出现，紧接着自动多一条用户气泡「嗯。」

**机制**：AI 回复播放的尾音通过麦克风被识别出来（AEC 残留 + AGC 已关但峰值
临界）。它有三条上屏路径，全部堵住才算修：

1. **interim 实时气泡**：回声尾巴的 interim 也会创建实时条目。→ 已随"一次性显示"
   消失（interim 不再显示）。
2. **晚到的 final**：`isContinuousListeningAwaitingFinal == false` 时 final 走
   "忽略 late final" 分支，**连 `onUtteranceDropped` 都不调**——先前由 interim
   创建的气泡没人撤，就留在屏上。→ interim 不显示后此路无气泡可留。
3. **门槛**：`continuousListeningMinimumTranscriptCharactersForThisWindow`（语音
   聊天传 3）按**内容字**计（字母/数字，不含标点），「嗯。」只有 1 个内容字 → 丢弃。

**相关的既有防线（不要拆）**：系统 AEC + AGC 关闭（`VoicePlaybackEngine` 头部）、
说话快捷键在会话中=挂断（否则两条管线抢同一根麦克风 tap）、以及
`BailianRealtimeSpeechTranscriptionProvider` 那边的 0.6s 自产瞬态静默窗。

### 3.3 摄像头/屏幕在语音聊天下自动折叠

语音聊天下两个设备开关被能力层**直接压掉**（`selectedModeSupportsCamera == false`），
而"关掉就自动折叠"挂在 `setCameraEnabled` 上——不走开关就永远不折叠，空占位框
一直展开。修法：预览框渲染时兜一层——**当前设置不支持画面就强制折叠成一条**
（`VoiceChatPreviewStrip.pane` 里按能力层判）。判据走能力层意味着
「视频聊天 + 全双工语音模型」（同样不支持画面）也会正确折叠。

## 三·五、卡片渲染卡顿：多角度收敛的一次完整排查（2026-09-25）

用户报「AI 卡片在回复时，渲染文字到一半就会很卡」，并且给了一个关键对照：
**全双工非常顺畅，卡顿只出现在三段式**。第一反应是往卡片组件（AnswerCardView）
里找，但用户明确要求「调用多个 sub agent，从多角度去看真正的问题根因，
直到所有根因收敛，再去解决问题」。三个互不重叠的角度各自独立排查，结论收敛
到**两条与卡片本身无关的主线程占用**——卡片只是受害者。

### 根因一：TTS 分句解码全在主线程（af72b91）

- **现象翻译成的问题**：「卡」发生在文字渲染到一半——那一刻正是第一个分句的
  音频合成返回、开始解码的时刻。
- **仪器量到的**：日志里 `[hitch]` 打点显示主线程被占住 **300~400ms**，
  时间窗与「文字冻结半秒再跳后半段」完全吻合。
- **代码路径**：`BailianTTSClient` 的解码三步（WAV 字节写临时文件 → `AVAudioFile`
  全量读回 → `AVAudioConverter` 整段转引擎格式）原先同步跑在调用它的
  `@MainActor` 上，**每个分句一遍**。
- **为什么全双工顺滑**：全双工直接收 `response.audio.delta`（24kHz PCM），
  根本不走这条解码路。这个对照本身就是最强证据。
- **修法**：解码搬 `Task.detached`，`AVAudioPCMBuffer` 用 `@unchecked Sendable`
  盒子搬运（后台创建 → 主线程只做节点调度，无并发访问）。文字渲染与音频
  合成从此解耦。

### 根因二：每个流式 delta 的固定主线程开销（bd843a9）

四个小东西叠加，每个 delta 都要付一遍，长回答尾部最卡（用户原话
「尤其是最后一行的时候会卡顿」）：

1. **`NSRegularExpression` 每个 delta 现场编译 2~4 次** ——
   `speakableTextFromStreamedReply` 里的两个正则改 `static let`，编译一次。
2. **历史条目每帧重跑 tag 剥离** —— 显示路径上的 `stripActionTagsForDisplay`
   对**每一条**历史回答每帧重新剥标签；加了按原文为 key 的 512 上限缓存
   （`actionTagStripCache` + 锁）。
3. **`DateFormatter` 每个条目每帧新建** —— 改静态复用实例。
4. **每个 delta 一次 0.2s 动画滚动** —— 动画滚动意味着每帧都在重新定位一个
   正在变大的内容，永不停止；流式路径全部换成 `scrollToBottomInstantly`
   （无动画 `scrollTo`）。

### 教训（写给下一次）

- **「渲染卡顿」的第一嫌疑人不一定是渲染组件。** 这次两个根因都不在
  AnswerCardView 里，而在「同一时刻主线程上还跑着别的什么」。对照实验
  （全双工顺滑 vs 三段式卡顿）指出的是**管线差异**，不是视图差异。
- **多个互不重叠的角度并行排查、看结论是否收敛**，比一个角度反复深挖快得多，
  而且能排除「顺着上一次的错猜继续挖」的沉没成本。这次三选二的收敛才动手。
- 把用户感受翻译成**仪器能回答的问题**（「卡」→「主线程在哪个时间窗被谁占了
  多久」）之后，`[hitch]` 打点一次就定了性；没有这一步，两条根因都会退化成
  「看起来像」。

### 三·六、第二轮：长文「最后一句卡顿」——卡片被排除，代价在 TTS 派发（2026-09-25）

上一轮修完后用户反馈「比之前流畅很多了，但**文字特别多**时最后一句还是卡」。
第二轮没有再顺着「卡片哪里慢」猜，而是先装三件仪器，把三个候选**分别**量掉：

| 仪器 | 量什么 | 结果 |
|---|---|---|
| 独立 Swift 探针 | 卡片缓存路径里每个 delta 的 O(N) 操作（`String.count`、`index(offsetBy:)`、共享缓冲 `popLast`、两次正则扫全文） | 2000 字回答下**每个 delta 合计约 40µs**（一帧的 0.2%）。**量级上不成立**，当场排除 |
| `🔎 [delta]` 打点（回答管线内） | 每 20 个 delta 处理耗时 + 当时正文长度 | **0.12ms/delta**，正文 84→681 字只从 1.6ms 长到 2.8ms/20 个。**不是它** |
| `⏱️ [hitch]`（已有）+ `sample` | 主线程忙多久、忙在哪 | 主线程样本 913/3110 在 `CA::Transaction::commit → layoutIfNeeded → SwiftUI/AttributeGraph`；**不是卡片的 plan（9 个样本）** |

把 `[hitch]` 打上时间戳、与已有的 `[aecprobe]`（本来带 `t=`）对齐之后，结论反转了：

- `vpToggleAfter` 落在 **200ms** 忙段的正起点；`bringUp isRunning=true` 落在
  紧邻的 **159ms** 忙段内 —— **引擎带 voice processing 的冷启动本身**
  就吃掉 200+159+174 ≈ **530ms**。
- 46 次 hitch 里 **35 次挤在回答开始后的头 16 秒**（约 4.3 秒的主线程占用），
  之后是 15 秒的**空窗**；正文继续流到 1500 字期间只剩零星 40~70ms。
- **所以卡顿不随正文变长而增加** —— 与「卡片越画越慢」的假设直接矛盾，
  也与 `sample` 里卡片 plan 只占 9 个样本一致。

**结论（有数字支撑，不是推测）**：卡片的流式渲染不是瓶颈；剩下的主线程代价在
**逐句快答的 TTS 派发 + 播放引擎冷启动**这条路上，并且集中在回答开头，不集中在
结尾。用户感受到的「文字特别多时最后一句卡」，一部分是**段数随正文变多**（每段
一次派发），一部分是终止时刻的 settle + 尾巴段合成。

**这件事给下一次的三条**：

1. **「哪里卡」和「什么时候卡」是两个问题。** 用户说的是「最后一句」，仪器说的是
   「开头 16 秒」。两个都对 —— 之前一直按前者找卡片，才找不到。
2. **O(N) 不等于慢。** 这条缓存路径确实每个 delta 都在做 O(N) 的活，但常数小到
   40µs；**先量常数再谈复杂度**，否则会在正确的方向上做无用的优化。
3. **已有探针要打时间戳。** `[aecprobe]` 一直带 `t=`，`[hitch]` 不带 —— 只差这一个
   字段，对齐就晚了一轮。

**尚未做**（留给下一次，需要单独一轮验证）：把 TTS 派发与引擎冷启动移出
主线程、或在回合开始时预热点火，让那 530ms 与视觉请求重叠而不是压在文字上。

## 四、通用教训（写给下一次）

1. **顺序类问题，先装事件流仪器再动手。** 每个事件带 `response_id`/`item_id`/
   文本前缀打一行。五次不成功的补丁，第六次靠日志一次定位。
2. **「谁先到谁先写」在流式协议里几乎总是错的。** 先画出协议的真实时序图
   （哪个事件先到、哪个后到），再设计写盘状态机。
3. **一回合一条记录。** 用户文本与回答文本必须落在同一条（哪怕先后到达），
   否则空卡、错位、重复全都会出现。
4. **区分「致命错误」与「冗余报文」。** 服务端的请求级错误（invalid_request_error）
   如果被当成致命错误收掉会话，症状会伪装成"连接断了"。
5. **本地 VAD 会听到 AI 自己的声音。** 武装时机（AEC 收敛之后）与阈值
   （0.25，实测校准）都不要随意动。
6. **两条管线（Ask / Chatting）的写盘方案是用户分别定的**，差异是有意的。
   改任何一边之前先读本文，别把一边的方案抄给另一边。
