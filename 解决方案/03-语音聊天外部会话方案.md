## 一、这条线的架构：Wanna 是"指挥"，Chrome 是"战场"

语音聊天**不移植** pipecat——外部 VoiceWeb 项目（`~/Documents/SuperAgent/APP/Test/voice-web`，pipecat + FastAPI，端口 8890）自己跑完整条语音链路（识别/LLM/播报/打断），它自己的 Chrome 页面承载 WebRTC 音频（浏览器 AEC 是打断不误触的前提，见 坑 1：`实现方案/08-踩坑总表.md:11`）。

Wanna 的角色是**驱动**：

```
Wanna (VoiceWebSessionController)
  → 探测 :8890/status，服务器不在就拉起（子进程，日志落 ~/Library/Logs/voice-web-server.log）
  → 确保一个 VoiceWeb 页面在 Chrome 里活着（本文档的主角）
  → POST /external/command {action:"connect", engine, mic, ...}
  → 轮询 /external/state 直到页面自己回报 ready
  → 会话期间镜像转写/回复 → 刘海相位（Connecting → Chatting）+ 右翼挂断按钮
  → 挂断：POST disconnect + endSession（音效 + 刘海瞬间收起）
```

关键约束：**浏览器无法被绕开**。WebRTC 采集+播放必须在同一条浏览器音频链路里（参考项目自己的铁律），所以"Chrome 和那个标签页活着"是这条线**存在的前提**——这正是后文大半问题的来源。

## 二、用户需求 → 解法对照表（每条：需求 / 根因 / 修法 / 代码位置）

### 需求 1：Chrome 绝不能浮到前台，必须后台运行

**用户原话**：「如果是必须打开chrome，让它在后台实现，不要再前端看到」「它拉起来之后是前端拉起来的……直接覆盖了我窗口的界面」。

**根因（实测+SDK 证据，两个 agent 独立收敛）**：
- `-g` / `--background` / `NSWorkspaceOpenConfiguration.activates = false` 是**同一个请求**（`kLSLaunchDontSwitch` == `NSWorkspaceLaunchWithoutActivation` == `activates`，SDK 接口逐位核对），约束的是 **LaunchServices 的"启动"动作**。
- Chrome **已经在运行**时没有"启动"这回事：URL 作为 **Apple Event** 交给活着的 Chrome，**激活是 Chrome 自己的响应**，`-g` 管不到。
- 结构性死角：URL 投递给**没有窗口**的 Chrome 时，会**逼它创建窗口**——而"创建窗口"正是应用把自己提到前台的地方。
- **实测证实**：`verifyChromeStayedInTheBackground` 每次都报 `frontmost=Chrome`，无一例外。

**修法（分三层，按场景）**：
1. **冷启动（Chrome 没跑）**：`-g -j`（`-j` = 启动后立即隐藏，LaunchServices 会执行）→ 冷 Chrome **完全不可见**。只敢用在冷路径——对运行中的 Chrome 用 `-j` 会把用户自己的窗口全部藏掉。
   `VoiceWebSessionController.launchChromeWithoutOpeningAnything()`
2. **冷启动拆两步**：先裸启动 Chrome（不带 URL）→ 等它起来恢复会话（≤8s）→ **再**开页面。URL 落进**已存在的窗口**，"创建窗口→提权"那条路根本不走。
3. **热路径（Chrome 已在跑）**：**拦不住就撤销**——记住用户当前的前台 App，Chrome 一浮起来**立刻把用户弹回去**（只做一次，避免和"用户主动切 Chrome"打架）。用户最多看到一闪，位置不丢。
   `openVoiceWebPageInBackground()` + `verifyChromeStayedInTheBackground(restoring:)`
   **故意不用** `NSRunningApplication.hide()`——那会把用户自己开的所有标签页藏掉，比要避免的干扰更大。

**储备方案（未启用，写在注释里）**：给 Wanna 独立 Chrome 身份（`--user-data-dir` + 子进程启动，不走 LaunchServices），用户自己的 Chrome 根本收不到事件；代价是多一个进程树 + 新 profile 要重新授权麦克风。

### 需求 2：只要 Wanna 在跑，Chrome 和标签页就必须活着

**用户原话**：「只要当前项目在运行，Chrome 就必须在运行……如果没有启动就增加定时检测」「它应该同时检测 Chrome 跟这个标签页两个是不是存活的状态，这个才是真正这个工具的使用的前提」。

**根因**：这是**两个独立的存活问题**，早期只用了一个信号（桥接上报）回答两个问题：
- Chrome 退出 → 死页面的上报在服务器 35s 有效期内**继续冒充活页面** → Wanna 以为页面在 → 不开页面 → 连接空等 60s。
- **删掉标签页** → 同样：死上报冒充 → 「把 Chrome 里面的那个标签页删掉，它就又出现一个无法连接的操作了」。

**修法（三个检测点 + 两个判据，用户亲自设计的分布）**：

| 检测点 | 时机 | 做什么 |
|---|---|---|
| ① 定时 | 每 **3 分钟**（`chromeKeepAlivePollSeconds`） | Chrome 不在 → `-g -j` 裸启动；然后检查页面 → 不在就补开（顺带**预热**） |
| ② 点「连接」 | 按键那一瞬 | `runSession` 先查服务器 → 再查 Chrome + 页面，缺哪个补哪个 |
| ③ 点「语音聊天」分区 | 切过去那一瞬 | `prepareForConnect()` 单飞预热（服务器+Chrome+页面）——**把用户选角色、移鼠标的两三秒变成预热预算**，点连接时无可再等 |

两个判据（`ensureVoiceWebPageIsAvailable` / `bridgeReportsALivePage`）：
- **Chrome 存活**：`NSWorkspace.runningApplications`（和 LaunchServices 同一张表，判定与投递永不打架）。
- **页面存活**：`phase != nil` **且** `report_age_seconds < 20`（页面心跳 10s 一次，两个周期没声就是没了）。

**配套改动（服务器侧）**：`server.py` 的 `/external/state` 把每条上报的年龄带出来（`_ts` 一直有，以前在返回前被 `pop` 掉）——没有这个字段，Wanna 无法分辨"活页面"和"还没过期的死页面"。**Wanna 对缺字段做了兼容**（退回旧行为），所以服务器新旧版本都能用；字段生效后 35s 的幽灵窗口缩到 20s。

### 需求 3：等待必须能自救（不许"失败 + 孤儿会话"）

**实测数据（`VoiceWebConnectTiming` 探针首次运行即破案）**：

```
+0ms      页面检查：已有活页面，什么都不做   ← 死标签页的旧上报
+26411ms  phase=nil                        ← 旧上报这时才过期
+33592ms  重新检查 → 没有活页面 → 打开页面
+35829ms  phase=ready —— 连接成功
```

连接相信了死标签页 → 什么都不开 → 空等 60s → 超时报错收刘海；**然后**页面才被开出来、连上了——于是出现「页面在正常聊天，刘海却什么都没有」的孤儿会话。

**修法（`waitForConnection`）**：
1. **每 8 秒重新问一次"页面在不在"**（不是"有没有上报"），没有就当场开——旧上报 35s 过期后自救必然触发，**把失败变成一次（慢的）成功**。
2. **预算按"这次连接已经付出了什么"**：启动过 Chrome 或开过页面 → **150s**；否则 60s。冷 Chrome 单独就实测超 30s。
3. 关键原则：**不把正确性押在"服务器是最新版"上**——自救逻辑在 Wanna 侧，服务器旧版本也能工作。

### 需求 4：挂断的反馈（音效 + 刘海瞬间收起）

**用户原话**：「用户点击挂断的按钮……必须有一个挂断的音效」「点击挂断按钮之后，通话确实立即挂断了，但刘海的动画还会继续显示（通话中）持续三五秒钟」。

**修法**：
- **音效**：生成的**下行双音**（E5→A4，`session-hangup.wav`，0.35s），在 `disconnectCurrentSession()` 这个**唯一漏斗**里响——刘海右翼红图标、语音聊天页挂断按钮、再按连接快捷键，全走这里。**页面自己掉线不响**（那不是"你挂断了"）。
- **刘海瞬间收起**：挂断清掉 `externalSessionOverride` 后会落进"thinking→speaking 空隙"的 2.5s 相位保持（防翅膀闪烁用的）——挂断是**结束**不是**空隙**，和用户手动停止同一个待遇：`setExternalSessionOverride` 检测到"从会话相位清空"时**跳过保持、当帧置 idle**。

### 需求 5：连接成功的反馈（音效 + 动画）

**用户原话**：「连接成功应该也有一个声音」「连接成功应该也有一个动画」。

**修法**：
- **音效**：`session-connect.wav`——挂断音的**反向**（上行 A4→E5），一对听感对称的确认音。只在 `waitForConnection()` 真正通过的那一行响。
- **动画**：连接前后的相位切换（Connecting→Chatting）原来**没有任何动画**（文件里唯一的 `.animation` 驱动翅膀**宽度**，而那时宽度早已到位）。右翼内容现在**弹一下**：scale 0.5 → spring 回 1（~0.32s），挂在 `.onChange(of: phase)` 到达 `.externalChatting` 上——按构造只在真连接时触发；尊重"减弱动态效果"。

### 需求 6：`Chatting` 的字母间距

**用户原话**：「chatting 这个单词，每个字母间距太大了（connecting 这个单词是正常的）」。

**根因（考古出来的）**：`notchStateWordTracking` 是个只有一格的 switch——只有 `.externalChatting` 返回 `1.4`。起因是更早的一次**误读**：用户当时写「Chatting（C H A T I N G），显示效果会更好」是在**描述**那个词的样子，代码把它当成了"拉大字距"的指令。

**修法**：属性和调用点整个删除，六个状态词共用同一套字距（不设 `.tracking`）。

### 需求 7：不要干扰用户正在做的事（浮现的最后一公里）

**用户原话**：「如果 Chrome 必须要调到前台，能不能让它在显示到前台的那一秒瞬间隐藏掉」。

**修法与取舍**（见需求 1 第 3 层）：**撤销而不是隐藏**。`NSRunningApplication.hide()` 会把用户自己的 Chrome 窗口全部藏掉——比要避免的干扰更大；还原用户原来的 App 则什么都没有碰。**冷启动路径**（真正是"启动"）用 `-j`，LaunchServices 的隐藏请求会被执行，屏幕上什么都不出现。

**已知残留（用户表示可接受）**：热路径上 Chrome 仍会**闪一下**（浮起→被弹回）。彻底消除需要走储备方案（独立 user-data-dir + CDP `background: true`，那是唯一带显式"不要前置"参数的机制），代价是多进程树 + 重新授权麦克风 + 本机开调试端口。

## 四、策略沉淀（这次反复验证有效的几条）

1. **两个存活问题要分开问**。Chrome 存活 ≠ 标签页存活 ≠ 上报存在。三个信号各管各的，缺一个就会出现"幽灵页面"。
2. **正确性不押在另一个项目的新旧上**。服务器兼容旧版（缺字段→退回旧行为），但 Wanna 侧的自救逻辑（8s 重问、预算自适应）保证旧服务器下也只是"慢"而不是"死"。
3. **拦不住的就撤销**。`-g` 对运行中的 Chrome 无效是结构性的（Apple Event 的应答方是 Chrome 自己）；与其对抗，不如记住用户现场、把现场还原。
4. **把等待变成预算**。用户进入语音聊天分区到按下连接之间的两三秒是天然预热窗口；冷启动的代价让"已经启动过东西"的连接多付预算（150s），而不是让所有连接同一个超时。
5. **测量先于修改**（00 号文件主规则）。本次 `VoiceWebConnectTiming` 第一跑就定位了 26s 幽灵等待；`verifyChromeStayedInTheBackground` 第一跑就证伪了 `-g`。没有这两个仪器，这两个问题还会各花几轮。

## 五、二次事故（2026-09-24）：标签页堆积 + 抢焦点，把刘海屏彻底打死

**用户原话**：「我打开这个菜单，也就是刘海屏这个窗口，它会自动打开 Chrome，并新建一个全新的标签页，导致我完全打不开这个窗口。每次点击时，它都会自动退出这个窗口……相当于我永远无法点击这个刘海屏」「无论我断开多少次，它永远都是一个标签页，而不是像现在这样增加几百个标签页」。

这是「自有 Chrome 实例」（§三·需求 1 的储备方案落地）引入的回归。**三个根因叠在一起**，而且第一个是本次最值钱的发现——它是**量出来的**，不是推出来的。

### 根因 1：`pgrep` 的模式以 `-` 开头 → 存活判定**一直**是假的

```bash
$ pgrep -f "--user-data-dir=$HOME/Library/Application Support/Wanna/VoiceWebChrome"
pgrep: illegal option -- -
usage: pgrep [-Lfilnoqvx] ... pattern ...
（退出码 2）
```

`pgrep` 把以 `-` 开头的模式**当成了选项**，直接报错退出。于是
`isOwnedChromeRunning()` **从写下的第一天起就一直返回 false**，日志里那句
「自有 Chrome 实例存活=否」从头到尾都是假的。修法：模式前面挂一个 `.*`
（`.*--user-data-dir=…`）就正常了。

> 教训：一个「永远返回同一个值」的判定函数，比没有这个函数更危险——它会让上面所有的
> 决策看起来都被核对过。所以本次把它的结果**打进日志**（`存活=是/否`），
> 假值当场现形。

### 根因 2：把「是不是我们的页面」当成了「有没有页面」

`bridgeReportsALivePage` 要求上报里带 `owned: true` 才算活页面。这个字段回答的是
**另一个问题**（「这个页面能不能自己点亮屏幕共享」）。后果是灾难性的级联：

| 触发点 | 频率 | 行为 |
|---|---|---|
| 进入语音聊天分区（`prepareForConnect`） | 每次点进去 | 开一个标签页 |
| 定时 keep-alive | 每 3 分钟 | 开一个标签页 |
| 连接中的自救循环 | 每 8 秒，一次连接预算内可触发 7 次 | 开一个标签页 |

只要那个字段因为任何原因缺失（页面加载的是缓存的旧补丁、用户自己 Chrome 里的旧标签页），
「没有活页面」就**永远成立**，上面三个触发点每次都得开一个新标签页——
这正是「几百个、几千个」的来源。

**修法**：把两个问题分开问（这正是本文档 §四·策略 1 早就写过的话）。

- 「有没有页面」→ **任何一条新鲜上报**都算（`phase != nil` 且 `report_age_seconds < 20`），
  它决定**开不开新页面**；
- 「是不是自有实例的」→ `owned`，它只用来**打一行日志**。

顺带解决第二个隐患：活页面存在时再开一个，会让服务器同时收到两个 reporter，
就是 CLAUDE.md 里记过的「十个页面互相踩」。

### 根因 3：`hide()` 在调用者不是活跃 App 时**什么都不做**，所以「藏起来」从来不是防线

```swift
NSRunningApplication(processIdentifier: pid).hide()   // 实测返回 false，窗口纹丝不动
```

文档（[cooperative activation](https://developer.apple.com/documentation/appkit/passing-control-from-one-app-to-another-with-cooperative-activation)）
把这写得很清楚：「**Only the active app can influence the activation context**」。
从真实 App 里跑，日志一行行都是「隐藏自有实例：未生效」。

那么「冷启动」「热启动」必须分开看——**这两个是实测出来的，不是推的**：

| 路径 | 命令 | 实测结果 |
|---|---|---|
| **冷启动**（实例没跑） | `open -n -j -g … URL` | 16 秒采样，前台应用**一次都没变**（`-j` 隐藏 + `-g` 不前置在**真正的启动**上有效） |
| **热投递**（实例已在跑） | 把 URL 交给活着的实例 | Chrome **自己浮起来**，`-g` 管不到，`hide()` 也撤销不了 |

所以「抢焦点」只有热投递这一条路，而它在旧代码里是**最常走的一条**。

### 修法：把热投递这条路**删掉**，而不是去补救它

页面没了、实例还在时，不再「补一个标签页」，而是**先把这个实例退掉，再走冷路径**：

```
存活=是 → 没有活页面 → 自有实例已退出：是（实测 367ms）→ 冷启动（前台全程不动）
```

配套两条结构性保证（本次一起加的）：

- **防抖**：30 秒内不重复开页（覆盖「刚开完、页面还没挂载上报」那个窗口）。
- **硬上限**：连续两次开页都没换来任何一次上报，就**停止开页**并说明原因，直到有页面真的活过来。
  正常路径永远走不到——页面挂载后几秒就心跳。

于是「标签页永远只有一个」从「希望如此」变成了**结构上不可能不是**：
有活页面 → 一个都不开；没有活页面 → 先把实例退掉再开，同一时刻只会存在一个标签页。

### 本次的实测证据（三段）

| 场景 | 命令/状态 | 结果 |
|---|---|---|
| 有活页面时启动 App | `存活=是` → `已有活页面，什么都不做` | **`打开页面` 出现 0 次**；自有实例 pid 不变；前台 16 秒采样一直是 `Orca` |
| 实例在跑、页面死了 | `存活=是` → 没有活页面 → `自有实例已退出：是`(367ms) → 冷启动 | 前台 20 秒采样**一直是 `Orca`**；新 pid 起来，页面重新上报 |
| 实例没跑 | 冷启动 | 前台 16 秒采样**一次都没变** |

### 附带修好的一个探针可用性问题

macOS 上 `print` 到管道/文件是**块缓冲**的，所以本项目的探针（`⏱️ [voiceweb]` /
`⏱️ [hitch]` / `[listen]`）在 `> 日志文件` 启动时全都会攒在 4KB 缓冲里——
实测应用跑了两分钟，日志文件仍是 **0 字节**，而窗口里其实已经有输出。
`CompanionManager.start()` 里加一行 `setvbuf(stdout, nil, _IOLBF, 0)` 改行缓冲后，
上面那三段证据才拿得到。
